# 故障排查与复盘方法论手册

> 适用范围：通用故障排查步骤、线上止损、假死无响应排查、P99 延迟优化、故障确认恢复、复盘/RCA 写法。
> 两句话：**先止血再治病**——恢复优先于定因；**每个数字回到账上**——凭印象复盘
> 的故障会再来一次。

---

## 1. 通用故障排查步骤（五段循环）

```
现象 => 界定 => 定位 => 处置 => 验证
  ^__________(未定论则换假设重来)
```

1. **现象**：用户语言→工程语言（「打不开」→ 5xx 率？哪个入口？哪个时间起？);
   三问钉死：影响面（多少用户/多少流量）、起止时间（对齐变更单）、可比基线（昨日同时段）。
2. **界定**：划掉一半嫌疑域。入口（网关/客户端/SDK)→ 链路（LB/服务/DB)→ 数据（特定租户/特定查询）
   三层各掷一颗探针，任何一颗出界即排除整层。
3. **定位**：变更先行（80% 事故有新发版/配置变更/容量拐点三配一），日志/监控/链路三角互证。
4. **处置**：见 §2 止损分级；处置动作只记为「假设」，写完预期再动手。
5. **验证**：恢复判据要提前写完（指标回到基线位持续 N 分钟）——
   「看起来好了」不是判据（本仓 S3-3 执行后验证同一条戒律）。

纪律：超过 30 分钟没换过假设 = 假设错了——换域重投，不要在同一个域里撞到天亮。

## 2. 线上故障快速止损（分级菜单，按代价从小到大先选）

| 级 | 动作 | 适用 | 代价 |
| --- | --- | --- | --- |
| L0 | **回滚**（镜像 tag / 配置开关） | 故障随新版本起，变更单能对上 | 新功能暂不可用 |
| L1 | **降级**（关重功能开关/切只读/降精度） | 非核心拖垮核心（推荐页拖垮交易） | 部分功能缺席但主链活 |
| L2 | **切流**（摘 LB 节点/切备集群/机房调度） | 单节点/单机房病灶 | 剩余容量承接，需容量预案 |
| L3 | **限流/熔断**（入口限流=床单保命） | 外部洪峰/下游慢拖 | 部分用户直接拒绝 |
| L4 | **重启/扩容** | 内存泄漏慢病/容量不足 | 状态性服务慎用；先保现场 |

两铁律：
- **先保现场再重启**(L4 前一秒抓 thread dump + `top -H` + 错误日志截屏）——
  重启是最快的恢复也是最快的失忆;
- 止损动作只一个责任人（临阵多手>2 人并行操作是事故的放大镜）。

## 3. 假死无响应排查（进程活着，请求全挂）

特征：监听端通、进程在、所有请求超时无 5xx——假死比死难查。

```bash
# 1. 线程画像:jstack 连拍三次(间隔 5s),比较红区线程有没有变化
jstack <pid> > t1.txt; sleep 5; jstack <pid> > t2.txt
grep -c BLOCKED t1.txt; grep -A5 BLOCKED t1.txt | head -30
# 死锁识别:jstack 自带 "Found one Java-level deadlock" 段

# 2. 池耗尽三查(应用池往往是假死替身,见下 §5)
#   数据源 Hikari: /actuator/metrics/hikaricp.connections. 三兄弟
#   连接池 active/max 打平=假死真相高频项

# 3. GC 闷死:Full GC 来回跑,JVM 吞吐<95%
jstat -gcutil <pid> 1000 5    # O 区逼近 100% 且 FGC 频升=内存病不是并发病

# 4. 外部调用哑等:HTTP 客户端没设读超时,下游哑了全线程挂 socketRead
grep -c socketRead t1.txt     # 数十个一色 socketRead=缺超时配置
```
处置对号：死锁→代码修；池耗尽→扩容或放血（见 §5);GC→堆与泄漏查（dump+MAT);
哑等→补超时+熔断，重启只接线不保真。

## 4. P99 延迟优化（如「接口 P99 3.5 秒」）

P99 是**尾部生物**，平均值优化的公式不通用：

1. **分段量**：总时延拆段（网关接入/应用执行/外部调用/DB/序列化），
   分段耗时直方图里找尾巴站的那一段——别全链路平均着查。
2. **尾巴画像**：尾的请求有什么共同点？大载荷？特定租户？冷缓存？
   `P99 ≠ P50 × K`——如果有共性，那是类请求问题不是整体问题。
3. **GC/停顿段检查**：偶发尖刺对齐 safepoint(GC 日志/`-XX:+PrintSafepointStatistics`)；
   停顿型尾巴给 G1 暂停预算或堆规整，不给参数盲调。
4. **排队模型**：线程池/worker 打满时，超时将不是计算慢而是排队久
   （`tomcat.threads.busy` 贴 max 即证据）；扩容体系只在到达率<服务率时救场。
5. **结案双账**:P99 回到目标 + P50 不准变差——把尾压下去把均值推高的优化，
   只是把疼痛分给了所有人。

## 5. 连接池耗尽排查与解决

症状：`getConnection timeout` / 请求堆积 / Tomcat 线程满——三者连环即池案。

| 病因 | 证据 | 处置 |
| --- | --- | --- |
| 借而不还（代码漏 close) | active 缓慢爬坡永不降；栈帧里挂 connection 借出点 | 代码修；Hikari `leakDetectionThreshold=30000` 开发期开启警告 |
| 慢查询霸池 | active 贴 max 且 connection.wait 高；DB 端 PROCESSLIST 一片慢 | 治 SQL（手册 MySQL 卷 §1)；池小一点比大一点好（小池=天然背压） |
| 下游服务拖死 | 每个入站带 N 长事务跨外部调用 | 拆解调用出事务;事务边界最小化 |
| 池配置错配 | max 10 vs 并发 500 | `max≈(core_count×2)+spindle_count` 起算，按到达率校 |

底线：连接池是**执行资格证**不是排队券——加大 max 而不治病，是把 DB 拖死时间预约到下周。

## 6. 复盘与 RCA 文档写法（合格线）

不合格复盘的三种病：写成检讨书（专注人）、写成流水账（没有时间轴）、写成愿望清单（改进项无 owner)。
合格的 RCA 五段定式：

1. **影响账**（用数字）：起止分秒、影响用户/流量/金额、SLA 账本冲销多少;
2. **时间轴**（到分钟）：首次异常 → 发现 → 止血 → 恢复 → 验证，
   发现到止血间隔是 MTTR 的真实素材，不许合并成一行「迅速处置」;
3. **根因链**（到第 5 个为什么）：从直接原因挖到「为什么会允许发生」——
   「证书过期」不是根因，「没有提前 30 天的告警」才是;
4. **止血账与止血副作用**（诚实栏）：回滚/降级/切流各带来什么损失，不许只写功劳;
5. **改进项每件三要素**:owner + deadline + 验证标准——「优化监控」不是改进项，
   「加 30/14/7 天三级告警并被演练触发一次」才是。

落库纪律：复盘沉淀进知识库（本仓设计：工单办结可生成复盘文档回灌知识库——
37 号批起运维手册在案）,**未沉淀的复盘等于没复盘**——下一次换一个人还会踩同一坑。
