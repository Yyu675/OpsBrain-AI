# 告警治理与通知手册

> 适用范围：告警风暴抑制、同 Pod 重复告警去重、钉钉通知接入。
> 元原则：**告警是给人读的队列，不是给机器留的流水**——每一条都应该可能触发动作；
> 永远不动作的告警是噪声，是第二天真告警的迷彩服。

---

## 1. 告警风暴怎么抑制

### 风暴的三个来源（先分类再下药）
| 源 | 特征 | 对应抑制层 |
| --- | --- | --- |
| 真洪峰（基础设施域崩） | 数百台同刻报同根因 | 分组收敛：Alertmanager `group_by` 根因维度 + `group_wait` |
| 规则过毛（阈值抖穿） | 单对象分界上下翻飞触发恢复交替 | 滞后带：`for:` 拉长 + 阈值加迟滞（触发 80/恢复 70） |
| 重复指纹（同对象同因） | 同一告警同 key 反复到 | 去重指纹 + 静默窗（dedup 与本仓 §2 同宗） |

### 抑制层从上往下叠（别跳层）
1. **源层**：规则只报「需要动作」的条件；能自愈的先自愈并报观察级而不是告警级；
2. **路由层（Alertmanager)**:
   - `group_by: ['alertname','cluster','module']` ——同根归一股;
   - `group_wait: 30s` / `group_interval: 5m` / `repeat_interval: 4h` ——首报别抢着刷，
     重复按小时收口；
   - `inhibit_rules`：高级别抑制低级别（P0 在场时，同主机的 P2/P3 消息沉默）——
     示例的语义是「故障的大哥说话，小弟闭嘴」;
3. **消费层（本仓）**：工单不是告警的复印机——dedup 指纹内已有聚合抑制（S4-1 预检零调用
   双分支钉测在案）；风暴下工单的理应是聚合后的一条，不是 500 条。

### 风暴进行时（值班姿势）
1. 先认机制在不在岗（dedup/聚合是否在压——未压先查指纹 label 漂移）;
2. Alertmanager 临时 silence 该规则（**必须设终止时间**——无时限 silence 是下一场事故的种子）;
3. 事后必答：这场风暴的哪一层本来该拦住它？改那一层，不许三层一起改（那样的修复不可归因）。

## 2. 同一 Pod 短时间大量相同告警会不会重复建单？

**不会——前提是 label 指纹稳定。** 设计（本仓告警域同宗）:

- 一条告警的「身份」= 指纹（alertname + 关键 labels 序列化）;
- dedup 窗内同指纹告警**聚合进已有工单**（追加出现次数/最新时间线），不开新单；
- 窗口过后同指纹再来才按新事件开单——「同 Pod 反复崩」理成一张工单的告警时间线，
  不是一排订单的阅兵。

要守住的边界两条：
1. 指纹 label 集变更（alertname/instance 改写规则）会**生成新指纹**=dedup 自然失效——
   不是 bug，是 topology 变了；改规则时评估指纹值域的稳定性；
2. 聚合抑制 ≠ 丢告警：次数与时间线全落时间线，审计面一样能回溯每次出现
   （同键风暴/跨键同源校验在 6 场景警报回放集钉着）。

## 3. 钉钉机器人通知接入

```yaml
# Alertmanager receiver 示例(经相关适配 webhook 或直接 webhook_url)
receivers:
  - name: dingtalk-p0
    webhook_configs:
      - url: 'http://<relay>:8060/dingtalk/opsbrain/send'
        send_resolved: true
```

接入五要点：
1. **机器人加签用密**:webhook 加签 secret 与 token 都走 secrets 管理（手册 §密钥），
   不落 git 不落日志；
2. **分级路由**:P0/P1 → @所有人 + 电话级通道;P2 → 群消息不 @;P4 → 仅存档——
   分级从 label(`severity`→P0-P4 映射已在契约）来，别在模板里 if-else 二写分级口径；
3. **内容卡三行**：标题（alertname+摘要）/ 影响（对象+持续分钟）/ 动作链接
   （工单 ID，一键到位）——告警卡片论斤卖字多是最差的形态；
4. **Resolved 一定要发**：恢复通知是 MTTR 的收尾证据，且能让人安心走出夜；
5. **通道自检**：通知链定期发测试心跳（心跳失败=通道故障先修通道）——
   真告警发不出去的监控告警系统，比没监控更差。
