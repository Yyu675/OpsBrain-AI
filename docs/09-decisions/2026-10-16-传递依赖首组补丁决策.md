## 3. 利弊比较

- **采纳：Tika双入口定向管理/Boot属性覆盖同线补丁**。改动小、保持LangChain4j1.2.0 / Spring6.2 / Boot3.5 API主线；代价是需独立维护临时覆盖，验证全模块一致性和运行时兼容。Netty tcnative有自己的2.x版本流，随Netty BOM托管，不强塞4.1版本；其漏洞仍属于本批目标检查，绝非豁免。
- 不采纳：仅升Tika core。优点是单行更少，缺点是PDF/parser混版且存在已知漏洞，不能验收。
- 不采纳：一起跳Boot4/Spring7/Tomcat11/Netty4.2。可能覆盖更多风险，但破坏性兼容范围明显变大，不适合作为本批最小修补。
- 不采纳：加忽略/抬阈值/直接替换生产扫描输入。只能改报表，不能修实际运行库；原生输入仍有Boot工具库覆盖余量，不能偷换为完整生产门禁。

## 4. 实施与验收流程

1. `pom.xml` 管理Tika3.2.2 core + standard-package两处入口；新标准包自身同版父POM带齐同版parser，原生闸验证全部`org.apache.tika`模块，防止混版；Boot `netty.version`覆盖4.1.137.Final；不保留无法构建的`tomcat.version`覆盖。
2. 真实LangChain4j Bean解析文本/HTML/生成PDF；Tika直接PDF/XFA健康对照必须抽出标记文本，恶意XFA只能安全拒绝/不泄漏，且本地假数据HTTP端点必须0请求。不读取宿主秘密、不访问公网。
3. 注入旧Tika3.0.0真实负对照，单测必须恰好1失败/0错误，classpath必须含旧core、不含修补后core；不能把下载/编译失败当成负对照。随后修补版完整`clean verify`必须通过。
4. 保留前端`npm run verify`、真实浏览器、PostgreSQL SQL+HTTP+CLI回归；无连接显式失败，不做静默跳过。
5. 原生SBOM生成→一次Trivy SBOM扫描→同源convert保留原生门禁码→实际Boot JAR SHA256绑定。新增两组专项验收：必需模块存在、每个目标variant与实际Boot字节绑定、目标全模块精确版本一致、无扫描覆盖缺项、两组HIGH/CRITICAL=0；输入SHA绑定，陈旧输出先清除，低于HIGH+CRITICAL口径不能通过。
6. 全量剩余漏洞/不完整项照报。本批专项验收通过不是整体安全通过，也不是部署或灰度批准。
