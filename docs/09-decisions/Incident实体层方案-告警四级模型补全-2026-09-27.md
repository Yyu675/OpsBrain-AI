# Incident 实体层方案：告警 → 事件 → 工单 四级模型补全

> 日期：2026-09-27 ｜ 状态：**待拍板** ｜ 类型：架构决策（本文件只出方案，不含实现）

---

## 一、背景与缺口

PRD（`log/BUG.md`）的核心概念模型是四级：

```
Alert（告警）→ Incident（事件，一组关联告警）→ Ticket（工单）→ Knowledge（知识）
```

**当前实现是三级**：`sys_alert` 经去重/聚合抑制后直挂工单，`Incident` 这一层不存在（2026-09-27 全库 grep 无任何 Incident 实体）。

9-27 批次落地的三个机制让三级模型比原来能打了，但也让缺口更清晰：

| 机制 | 现状 | 没有 Incident 层的缺口 |
|---|---|---|
| 观察窗（FR-3.1） | warning 级窗口内自愈不留单 | 「自愈率」靠 `RESOLVED + ticket_id IS NULL` 反推，是**口径推导**而非实体事实 |
| 风暴模式（FR-2.5） | 摘要事件聚低级别告警 | 摘要是「全局速率」的账，**同根因事件**（如一个节点宕机引发的 17 条告警）没有聚合体 |
| 聚合抑制（方向 E） | 同 service+module 告警挂到组工单 | 挂单是**工单层**关联，「这些告警是同一件事」这个事实本身没有实体承载 |
| 压缩比 | 告警总数 ÷ 建单数 | 分母是「工单」，但 PRD 语义的分母应是「事件」——一次事件多次告警的数字被高估 |

## 二、方案对照

### 方案 A：维持三级，补口径推导（零改造）

保持 `Alert → Ticket` 直挂，所有 Incident 语义用 SQL 派生（观察窗统计已这么干）。

- **优点**：零改动、零风险；9-27 批次已把最痛的点（抖动工单、风暴）消解大半
- **缺点**：派生口径散落在各查询里，改一处忘一处；「同一事件的复发史」无法表达；压缩比永远口径不纯
- **成本**：0 ｜ **能力上限**：中

### 方案 B：新增 `sys_incident` 实体表（PRD 正解）

告警接入后先入 Incident（同 system+service+时间窗归并），Incident 按策略建单；自愈/风暴/压缩比都以 Incident 为实体。

```sql
incidents(id, system, service, title, severity, status,
          first_alert_at, last_alert_at, alert_count,
          self_healed bool, ticket_id, created_at, resolved_at)
```

- **优点**：四级模型完整；压缩比 = 告警数 : 事件数 : 工单数（三层各自成口径）；自愈率实体化；Incident 时间线天然是复盘素材；与 PRD 契约完全一致
- **缺点**：写入主链路插一层（AlertService 改造）；现有聚合抑制/观察窗/风暴三套机制的语义要迁到 Incident 层（它们目前都作用在 Alert 层）；回归面大（告警链是系统咽喉）
- **成本**：约 1 周（表 + 链路改造 + 三套机制迁移 + 回归）｜ **能力上限**：高

### 方案 C：派生 Incident（只读视图，不落表）

用 SQL 视图按 `(system, service, 10 分钟窗)` 把告警聚成「虚拟事件」，只供效能大盘/报表读，写入路径不动。

- **优点**：零写入路径改动；压缩比、事件数分布等**报表口径立即正确**；事故面为零
- **缺点**：读模型不能承载状态机（Incident 无生命周期）；观察窗/风暴仍工作在 Alert 层；写侧能力不变
- **成本**：约 1 天（视图 + 效能大盘读数接入）｜ **能力上限**：报表层全对，操作层不变

## 三、建议

**先 C 后 B，不选 A。**

1. **立即做 C**（本迭代）：把「告警压缩比」修正为「告警数 : 事件数 : 工单数」三档口径，事件数用派生视图。报表层的误导今天就消除，且为 B 探明聚合口径。
2. **B 作为 L5 前置项入 backlog**：L5（预测性运维）需要事件级的历史关联（「这个事件的复发周期」），那时 Incident 实体是刚需。届时以 C 的视图口径为验收基准迁移。
3. **不选 A**：口径推导会随告警量增长而越来越失真，且每条新统计都要重新发明一次「什么是一个事件」。

## 四、若拍板 B 的迁移要点（备案）

1. `sys_incident` 建表 + `sys_alert.incident_id` 回填列（PRD 8.1 已有设计）
2. 写入路径：`insertOrIncrement` 后先归并 Incident，再挂工单——单写者仍是 AlertService
3. 观察窗/风暴/聚合抑制改判 Incident 层状态，Alert 层只保留指纹去重
4. 回归锚点：`AlertWebhookChainIntegrationTest` + 观察窗/风暴 50 例单测全绿
5. 灰度：新旧双写一周，对比派生视图与实体表的事件数一致后切读
