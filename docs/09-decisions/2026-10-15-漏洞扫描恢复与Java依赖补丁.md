# 批110–112：恢复漏洞扫描，并修复首扫抓到的 Java 依赖

## 决策与范围

**推进修复；全部门禁与真实扫描通过前不合并，不扩大灰度。** 沿用 PR #15 / 当前固定分支，工程问题各自独立提交，不另建分支、不修改豁免去掩盖新增红灯。批109 的灰度口径修复仍随该 PR 验证。

## 事实链与原因

1. 用户手动扫描 `38733568519` / `38733401478` 在 Set up job 失败。最外层 `aquasecurity/trivy-action@v0.28.0` 存在，内部 `setup-trivy@v0.2.1` 不可解析。旧闸只查顶层 tag/branch，故漏报。
2. 新递归检查器在旧工作流上本地 exit 1，准确指出 parent→setup 链。先核验签名 tag `v0.36.0` 的 commit `ed142fd0673e97e23eac54620cfb913e5ce36c25`，其内部安装器为 `setup-trivy@3fb12ec12f41e471780db15c232d5dd185dcb514`（v0.2.6）。当时完整链 11 个节点通过。
3. 首次真正扫描 run **38763086455**，25s，两个目标：前端 package-lock.json、pom.xml；检出 HIGH **CVE-2025-59952**，MinIO 8.5.12→8.6.0。不是下载失败或误报。公告：[GHSA-h7rh-xfpj-hpcm](https://github.com/advisories/GHSA-h7rh-xfpj-hpcm)，上游补丁 `f7a98d06b25e5464bdd4811b044e25ff9101d37f`。
4. `MinioXmlSecurityTest` 直接调用 SDK 的 String/Reader XML 解码器；使用固定假属性值、finally 恢复，不读真实秘密。**旧版红证据**：PR run **38763460638**，后端 2049 例，新增 4 例中 String/Reader 两例失败、无错误：期望 `${opsbrain.minio.xml.security.probe}`，实为探针假值。其余两例验证普通 region round-trip 与畸形 XML 拒绝。
5. 升级 MinIO 后 run `38764135087` 的 e2e 编译报 `okhttp3.HttpUrl` 缺失：8.6.0 使用 OkHttp 5，多平台入口不能代替 Maven 编译需要的 JVM 字节码。补 `okhttp-jvm:5.1.0`，并把旧 MockWebServer 4.12.0 对齐到 5.1.0。加真实 SDK + 本地 HTTP 协议夹具，验证 bucketExists、上传、签名链接、删除；不是完整 MinIO 服务端测试。
6. `38764135144` 的第一遍扫描红，但第二遍 JSON 为 0；不能据后者宣布安全。改为固定 setup commit 安装工具 **v0.70.0**、显式 CLI 执行，留下第一遍 gate 的 JSON、日志与原始退出码。run **38764494554** 的第一遍实际检出另 **5 条 HIGH**，而第二遍仍为 0。双扫不一致根因**未核实**，不能归咎网络或缓存；第一遍才是门禁证据。
7. 针对第一遍五条结果逐项查 GitHub 公告，采用下表最小补丁线。复扫 **38764845589** 已 success；随后 PR run **38764845956** 后端 **2050 例、0 失败、0 错误、2 跳过**，空库 42 表，证明补丁构件实际可解析且完整后端回归通过，不是仅改版本字符串骗扫描。

## 安全结论的边界

扫描识别到的目标只有 npm lock 与 Maven POM，不能把这一结论扩大为所有生产镜像、所有传递/运行时依赖均无漏洞。MinIO XML 测试不等于完整 S3 合规验证；本地 HTTP 夹具不是真 MinIO 服务。扫描库会更新，本次 0 不是永久保证。旧版“生产 npm audit 0，所以整个仓首扫应绿”的推断已被真扫证据否定。
