# 企业告警通知与恢复模板优化方案

- 日期：2026-10-13
- 状态：提案，待确认后实施；本次仅交付设计，不修改运行逻辑。
- 范围：告警触发、恢复、AI 诊断补充、提醒策略、字段与渠道契约。

## 1. 背景与现状核验

用户提供的通知存在标题重复、定位字段不足、时间口径不透明、恢复与关单指令矛盾、诊断无关联对象却再次紧急提醒等问题。首轮设计时未收到可查看的企业模板截图；后续用户补充 Zabbix 告警/恢复截图，截图分析及采纳调整见第 10 节。

代码核验：

| 位置 | 当前行为 | 设计影响 |
| --- | --- | --- |
| `domain/alert/entity/Alert.java` | 已有 source/system/service/module、告警状态、首末发生时间、恢复时间、工单号、原始 labels/annotations | 第一阶段可复用现有数据，不必先建设全新事件平台 |
| `domain/alert/service/AlertService.java#notifyAlert` | 在自动建单链中拼接 Markdown，按高危级别强提醒 | 需要拆出统一渲染器；不能把告警通知是否发送绑定到建单成功与否 |
| `AlertService.java#handleResolvedAlert` | 更新恢复状态、广播 WS、执行工单恢复策略 | 此方法未见恢复钉钉模板调用，需要补齐外部恢复事件发送路径 |
| `application/diagnosis/DiagnosisOrchestrator.java#publishCompletion` | 证据不足直接使用 urgent；群正文直接复用含取证明细的诊断摘要 | 需要将审计明细和通知摘要分离，并检查发送时的告警状态 |
| `domain/notify/NotifyMessage.java` | 仅 title/markdown/urgent 三字段 | 无法表示指定值班人、事件类型、幂等键和业务关联 |
| `domain/notify/DingTalkNotifier.java#buildPayload` | urgent 对应正文追加 @所有人及渠道 at 配置 | 紧急程度和接收对象被耦合，需要拆开 |

全仓文本检索未找到用户贴出的“认领/恢复请至”“无需处理，留痕归档”等原文。应对照实际部署 commit、配置、外部 Alertmanager/机器人模板和消息来源定位，不能宣称当前 Java 模板就是这些文字的唯一来源。

“49 天 2 小时”不能直接判定为计算错误：可能是历史 startsAt、测试固定时间、延迟/重放、时间转换或真正长时间未恢复。必须核查原始 startsAt/endsAt、记录首次发生时间、接收时间、部署时区，不可简单截成几分钟。

## 2. 决策：通知回答五个问题

1. **哪个对象**：环境 + 系统/服务 + 实例/节点，不能只用 infra。
2. **出了什么问题**：中文故障名称 + 原始规则，数值仅展示真实来源。
3. **什么时候**：开始、恢复、时区和持续口径。
4. **当前什么状态**：告警、认领、业务验证、工单分别描述。
5. **谁做什么**：责任人、明确的下一步和可点击详情入口。

群消息负责快速决策，详情页/工单负责完整取证。一个事件只使用一个正文主标题；渠道通知列表 title 可相同，不在正文再复制两次标题。不能保证客户端绝不同时显示列表标题与正文标题，但可以避免服务端重复拼接。

确定性字段和模板不依赖 LLM；AI 只能提供有证据的诊断补充，不能编造环境、影响范围、当前值、恢复原因或责任人。

## 3. 模板设计

### 3.1 生产告警示例（示意数据，不代表本次测试告警真实事实）

```text
【告警｜P0】生产 · node-01 · 节点监控不可达

告警对象：生产 / 基础设施 / node-01（10.0.1.20:9100）
触发条件：up = 0 持续 2 分钟（来源：监控规则）
发生时间：2026-10-13 14:30:00 UTC+08:00
已持续：5 分钟（截至 14:35:00）
业务影响：待确认；目前仅确认该监控目标不可达
处理状态：待认领｜负责人：基础设施值班组
关联工单：TKT-20261013-0015

请值班人员认领，并核查节点连通性与监控采集进程。
[查看告警并认领]  [查看工单]  [处置手册]
```

规则名保留在告警详情；没有中文映射时可以显示 `NodeDown`，但不能仅凭规则名断言“主机宕机”。`up=0` 也可能是 exporter、网络或采集问题。没有规则表达式/实测数值时展示“触发说明”，不展示虚构的阈值。

### 3.2 本次 IT44c08600 的可诚实渲染版本

以下仅使用用户消息中可确认的数据；正式渲染应以持久化原始字段为准。

```text
【告警｜P0】infra · NodeDown-IT44c08600

告警说明：集成测试告警 IT44c08600
告警对象：infra；具体实例未提供
发生时间：未提供，需核查原始 startsAt
持续时间：原通知显示 49 天 2 小时，时间口径待核查
关联工单：TKT-20261013-0015

请值班人员认领，核对告警目标与发生时间。
[查看告警并认领]  [查看工单]
```

“集成测试告警”来自原文，不能据此自动认定整个部署处于测试环境。只有可信的环境标签或接入配置才能决定测试通道隔离。时间戳经验证正确且确实长达 49 天时，应照实展示开始时间与持续时间，不做异常归零。

### 3.3 恢复通知：监控恢复不等于业务恢复或工单完成

```text
【恢复｜原P0】生产 · node-01 · 节点监控告警解除

告警对象：生产 / 基础设施 / node-01
发生时间：2026-10-13 14:30:00 UTC+08:00
恢复时间：2026-10-13 14:42:00 UTC+08:00
本次持续：12 分钟
恢复依据：收到监控源 resolved 事件
业务验证：待值班人员确认
关联工单：TKT-20261013-0015（待确认处置结果）

无需继续处理该监控告警；请验证业务可用性并补充工单记录。
[查看告警]  [查看工单]
```

注意：

- 只有恢复事件时，不写“指标恢复正常”，更不写“业务已恢复”；有复查指标才展示数值、采样时间和条件。
- 人工标记恢复应写“人工标记恢复”，不能冒充监控恢复。
- 缺失/非法 endsAt 回退接收时间时应标“恢复接收时间（源未提供有效恢复时刻）”；此时持续时间只能标估算，不能当作精确 MTTR。
- 故障原因未经确认时写“未确认”或不显示；不默认写“系统自动修复”。
- 若同工单还有其他活跃告警，写“该告警已解除，工单仍有 N 条活跃告警”，不提示关单。
- 默认遵循现有 hint/off/auto 配置和工单状态机；不能为了模板好看自动关单。已关闭则显示已关闭，不再要求关单。
- 本次 IT44c08600 的恢复通知同样不得补造开始/恢复时刻、恢复数值或验证结果。

### 3.4 AI 补充：不再以独立紧急故障形式广播

```text
【诊断补充】infra · NodeDown-IT44c08600

关联告警：NodeDown-IT44c08600｜工单：TKT-20261013-0015
诊断结果：暂无法判断根因，未形成可靠诊断结论
主要限制：指标与日志查询无匹配数据；未检索到相关变更及知识记录
建议下一步：核对目标实例和采集标签；检查节点连通性与采集进程
安全说明：本次未触发自动处置（仅在执行台账能确认时显示）

[查看取证记录]  [查看工单]
```

默认写入告警详情、工单活动流及现有 WS 诊断事件，不新增群消息。只有需要新增人工动作且原告警仍活跃时，才发简短补充给负责人；没有负责人则进入值班路由，不因为 INSUFFICIENT 直接 @所有人。

发送时原告警已恢复：保存诊断明细，默认抑制群补充；确有待办时明确写“告警已解除，诊断未完成，仅供复盘”，且不紧急提醒。

完整 metrics/changes/logs/knowledge 明细、查询范围、查询时间窗、错误分类与脱敏日志样本仍保留，不删除审计证据。

## 4. 字段契约与降级

| 展示字段 | 优先来源 | 缺失处理 |
| --- | --- | --- |
| 中文故障名 | 已审核规则映射 | 原始 alertName；不让模型随意改写事实 |
| 环境 | 接入配置 / 已约定且可信的 env/environment 标签 | 未标注；不得默认为生产 |
| 系统/服务 | Alert.system/service | 未标注；infra 仅按原值展示 |
| 对象 | 按规则类型选择 labels.instance/node/pod/namespace 等 | 对象未提供；不能用测试后缀当主机名 |
| 当前值/阈值/单位 | 已约定 annotations 字段或结构化监控查询结果 | 省略，改展示现有触发说明 |
| 影响范围 | 业务监控、资源拓扑或人工确认 | 业务影响待确认 |
| 开始/恢复 | firstOccurredAt/resolvedAt，加来源与时间质量 | 显示未知或明确标为接收时间/估算 |
| 负责人 | 实际工单指派 + 服务负责人路由 | 待分配，通知值班组 |
| 状态/待办 | 告警与工单真实状态、关联活跃告警数 | 未查询成功时写“请到工单确认”，不猜状态 |
| 告警/工单链接 | 受信任的平台公网基础地址 + 真实 ID | 缺 ID 不生成链接；不显示假按钮 |
| 手册 | 校验过的 runbook_url 或受控规则映射 | 缺失则隐藏 |

公网基础地址为部署配置，示例 `[查看告警]` 不代表已实现按钮。实际 Markdown 使用完整 HTTPS 链接直达 `/alerts/{id}`、`/tickets/{id}`；群里单独写 `/alerts` 不可点击且需要人工搜索。不得向外泄露签名令牌；链接需要登录和权限验证。外部 annotations 的 URL 只允许受信任 HTTPS 域名，拒绝不安全协议和钓鱼地址。

新增配置遵循 `devops.*`，提供中文注释；若新增持久化字段，走新的 Flyway 迁移，不改存量迁移。

## 5. 正确解释取证状态

通知用人话表达，但详情必须保留机器状态，不以文案替代诊断算法修正。

- `NO_DATA`：本次查询无匹配数据；可能是时间窗、标签、采集覆盖、权限或确实没有记录。不能一律视为排除了故障因素。
- 查询到变化并有匹配证据：可展示已知事实，不等于证明因果。
- 源未接入：写“未接入”，不是“没有日志”。
- 查询失败/超时/权限不足：显式区分失败原因，不能回退空列表冒充 NO_DATA。
- 未找到知识文档：写“未检索到相关处置文档”，不是“关键监控异常”。
- “没有变更”只有在数据源可用、对象匹配、覆盖完整且窗口合理时，才支持限定范围的排除；否则标为“未查到，不能排除”。
- “人工接手”是建议的处置方式，不是必须全群惊醒的新故障等级。

## 6. 生命周期与提醒策略

| 事件 | 默认群行为 | 强提醒条件 |
| --- | --- | --- |
| 首次触发 | 发一条核心通知 | P0/P1 通知实际值班人；全员仅按审批后的升级策略 |
| 同事件重复上报 | 更新发生次数与时间，默认不再发群消息 | 级别升级、影响扩大、到期未认领等新增事实 |
| 已认领 | 更新详情/工单；必要时普通状态通知 | 不 @所有人 |
| AI 证据不足/无新结论 | 默认仅留痕 | 活跃事件有新增人工待办时定向提醒 |
| 恢复 | 普通恢复通知 | 默认不 @所有人 |
| 恢复后迟到的诊断 | 留痕，默认不发群 | 不紧急提醒 |
| 测试/演练 | 独立机器人/测试群，标题显式标识 | 不触发生产全员提醒；依据可信环境配置而非名称猜测 |
| 无匹配活跃事件的恢复 | 留痕与乱序处理 | 不凭空生成业务恢复成功消息 |

告警去重键不等于事件唯一 ID：恢复后同一对象再次触发必须开启新事件。每次状态变化使用 `eventId + lifecycleSequence + eventType + channel` 作为稳定幂等键。并发首次触发、重复恢复、通知重试都不能产生重复业务消息；多个实例不能只靠本地内存去重。

同工单关联多个告警时，单条告警恢复和整组恢复需区分。可先逐条普通恢复，再逐步聚合；不要把任意一条 resolved 当作整组解除。

告警持续提醒与未认领升级的阈值由现有 SLA/正式值班策略决定，不在本设计中随意指定 5 分钟或 10 分钟。群消息限流也要依据渠道额度和值班反馈配置。

## 7. 可落地架构与实施顺序

### 阶段一：最小可用闭环（不依赖 LLM，不先建设模板编辑平台）

1. 对照部署版本和实际消息源，查清告警/恢复模板来源以及 49 天的时间来源。
2. 在 domain 中提供渠道无关的结构化通知上下文与确定性渲染器；告警业务服务不再散落拼接字符串。领域代码不引入 MVC 类型。
3. 将告警通知从“建单成功后才发”的逻辑拆开；建单失败仍能发告警，工单字段写“创建失败/待补建”，并保留失败告警与重试机制。
4. 补齐 resolved 的群通知，发送前取真实工单状态；恢复文字按恢复来源/时间质量分支渲染。
5. 诊断审计摘要与通知摘要分开；通知包含 alertId/ticketId 关联和下一步，发送前检查事件是否仍活跃。
6. 钉钉先使用兼容 Markdown 链接；无指定人员能力前，不宣称已经定向提醒。过渡期间至少取消“诊断不足默认全员”和“恢复全员”行为，生产告警路由须先核对值班保障方案。

### 阶段二：可控提醒与可靠投递

- 将 urgent 拆成 severity、eventType、mentionPolicy、recipients 等语义；兼容现有发送接口，其他渠道不得漏实现。
- 平台用户到钉钉用户标识的映射需配置和授权验证；机器人具体类型的 @能力通过真实渠道验收，不假设所有机器人都支持同一 API。
- 引入通知 outbox/投递台账：业务状态变更与待发送事件在同一数据库事务提交，独立发送器有限重试、限流、失败可见；网络调用不放事务内。
- 重试以幂等键抑制平台内部重复；第三方无幂等能力时，“渠道已接收但本端超时”可能重复，不能承诺严格端到端 exactly-once。
- 发送前按事件版本抑制已过期的待发送触发/诊断，避免队列乱序造成“先恢复后紧急告警”；保留抑制原因和原始事件审计。投递顺序与源事件时间分开记录。
- 生效配置带模板版本，可灰度到测试群和有限服务，回滚旧渲染器不丢事件。

### 阶段三：企业化可配置

规则中文映射、多服务差异化字段、聚合摘要、多渠道适配、受控模板预览。模板只允许受控占位符，不执行用户脚本；字段缺失预览、版本审计、权限控制一并实现。先验证固定模板易读性，再建设可视化编辑器。

本阶段不需要修改统一 ApiResponse 或引入新的免鉴权入口；认领/恢复动作仍走已鉴权的平台页面与既有状态机，不能用群内 GET 链接直接改变状态。

## 8. 验收标准

### 内容与事实

- 正文只有一个主标题；摘要与详情相同时不重复；不存在裸路径和空按钮。
- 有对象标签则显示精确对象；标签缺失明确未知，不补造生产环境、主机、指标和影响。
- 告警、恢复共用同一事件/工单关联；恢复显示来源和后续待办，不同时出现“无需处理”与“必须关单”的矛盾指令。
- 49 天数据分别覆盖“真实长故障”“历史固定测试时间”“源时间非法”“时区差异”，不以删持续字段掩盖问题。
- 源 resolved、人工恢复、缺失 endsAt、仍有其他活跃告警、工单已关闭均有独立模板断言。

### 生命周期与可靠性

- 首次触发、重复上报、认领、升级、恢复、复发、迟到诊断及恢复重试的消息数量与提醒对象均可断言。
- 建单失败仍有告警通知；诊断不足默认不 @所有人；恢复后迟到诊断不发紧急群通知。
- 对象无日志、源未接入、权限不足、超时和无变更分别测试，不混成 NO_DATA。
- 真实告警→建单→诊断→恢复链路集成测试覆盖上述行为；outbox 阶段增加并发、重启重放、失败重试和顺序测试。
- 渠道成功回执仅表示机器人接口接受，不声称值班人已读或已认领。
- 真实手机端测试群验收排版、可点击链接、登录回跳、指定 @对象和生产/测试隔离。未通过实测不声称渠道兼容性完成。

### 安全与维护

- 通知正文不包含 token、敏感日志、附件签名直链；Markdown 外部内容转义、长度有界并链接完整记录。
- 规则手册 URL 校验、收件人映射授权与跨权限链接均有测试。
- 实施时按仓库约定运行后端 verify；涉及前端则运行前端 verify；新增测试执行注入-还原验证。本次仅设计文档，不声称这些测试已运行。

## 9. 后果与边界

收益：值班人员可快速定位与行动；证据不足不再成为无上下文的第二次全员告警；恢复、验证和关单语义一致；现有 labels/annotations 和工单链路可以复用。

代价：需要校准上游字段、维护值班人与渠道账号映射，并补齐恢复通知与可靠投递。指标/影响/恢复依据的质量依赖真实采集，不能仅通过模板解决。

优先确认：真实部署模板来源、环境标签约定、时区约定、机器人类型和值班升级策略。即使这些还未确认，也可先实施标题去重、真实字段降级、诊断摘要分离和恢复语义修正。

## 10. 补充：基于企业 Zabbix 截图的采纳调整

### 10.1 可辨识内容与事实边界

截图含同一事件的两条消息：

| 字段 | 告警 | 恢复 |
| --- | --- | --- |
| 当前状态 | PROBLEM | OK |
| 主机 | primera01 | primera01 |
| 地址 | 10.210.44.11 | 10.210.44.11 |
| 监控项目 | HPE Primera: Get errors | 相同 |
| 监控取值 | Failed to receive data: volumes : Error: cannot get URL: Timeout was reached. | 未显示取值 |
| 告警等级 | Average | Average |
| 告警信息 | HPE Primera: There are errors in requests to WSAPI | 相同 |
| 告警时间 | 2026.10.13 17:37:55 | 相同 |
| 恢复时间 | 不适用 | 2026.10.13 17:38:47 |
| 持续时间 | 未显示 | 54s |
| 事件 ID | 12002061 | 12002061 |
| 告警平台 | http://10.196.80.240/zabbix | 相同 |

截图未展示时区、环境、业务影响、处置动作和恢复指标；不能据此补充这些事实。显示时间相减为 52 秒，与源持续时间 54s 有差异，不能从图片判断原因。也不能据 OK 断言有人修复了存储故障。

原始告警指向 HPE Primera 的 WSAPI 请求异常，并包含超时信息。通知可以解释为“监控侧获取 volumes 数据失败，请求超时”，但不能断言存储设备宕机、卷不可用或业务中断。

### 10.2 采纳与不照搬的取舍

1. **采纳固定字段顺序**：状态→主机/对象→地址→监控项→取值→等级→信息→时间→事件 ID→入口。降低值班人员扫描和两条消息比对成本。移动端每行尽量一个字段，避免表格和大量装饰。
2. **采纳独立、对称的恢复消息**：恢复仍显示对象、监控项、原事件和开始时间，新增恢复时间与持续时间，使脱离上一条消息也能理解。代价是少量重复，但这是有效定位信息，不等于重复标题/摘要。
3. **采纳原始监控取值**：它提供实际排障线索，既支持数字也支持字符串，不应只设计 currentValue/threshold 两个数值字段。过长内容脱敏截断，完整原文在详情保存。
4. **改进状态表达**：使用“告警中（PROBLEM）”“监控恢复（OK）”；平台 FIRING/RESOLVED 与源状态分别保存，不把 ACKNOWLEDGED 映射为 OK。
5. **改进级别表达**：保留 Average，来源到平台级别通过按源配置映射，展示如“源级别 Average；平台级别按路由策略确定”。未确认映射前不能硬写 P0 或 P2，更不能由英文等级直接决定全员提醒。
6. **改进恢复空取值**：无数据写“未提供恢复取值”，不写“0”“正常”；只有真实复查值才显示数值和采样时间。
7. **改进入口**：平台主页保留为次要入口，主入口直达事件详情和工单。图中的内网 HTTP 地址是实际环境事实，不自动改为 HTTPS；生产外链建议由部署配置提供受信任 HTTPS 地址或明确 VPN/内网访问条件。
8. **改进时间契约**：源时间、接收时间、源持续时间、计算持续时间、时间质量分开处理。截图验收样本必须检测 52/54 秒差异；默认正文展示单一口径，原始值保留于详情。无法验证时标注“源报告 54 秒，展示时间计算 52 秒，待核查”，不能静默覆盖事实。
9. **保留业务行动层，但不让其淹没监控事实**：核心字段之后再附负责人、工单和一句下一步；认领状态独立于源状态，无工单时不延迟告警发送。

### 10.3 建议的统一字段契约增量

在现有 Alert 派生上下文上增加可选的 hostName、targetAddress、monitorItem、observedValueText、sourceSeverity、sourceStatus、sourceEventId、recoveryEventId、problemEventId、timeQuality 等语义。数据可来自明确约定的 labels/annotations；不能假设当前接入自动提供所有字段。

- Zabbix monitorItem 与 Prometheus alertName 不完全等价；保留监控项和规则两种概念，没有监控项时只显示规则，不能伪造。
- 地址可能为 IP、host:port、Pod、云资源标识；原始 instance 不能无条件当作主机 IP。解析须按源/资源类型配置。
- 支持 observedValueText，而不只支持浮点值，以覆盖本图中的 API 报错文本。
- 外部事件身份至少包含 source + 接入实例/租户 + sourceEventId；不同监控源同号不能冲突。若源把恢复事件和问题事件分别编号，必须通过 problemEventId 关联。
- 当前截图不能证明仓库已有 Zabbix 接入。阶段一只复用现有 Prometheus/Alertmanager 字段，不承诺仅修改模板就能接入 Zabbix；有需求时另外实现适配器并遵守现有 webhook 鉴权、限流及接入实例注入约束。

### 10.4 调整后的验收补充

- 以截图为字符串取值样本：超时错误不能被渲染成数值阈值告警或存储宕机结论。
- 告警与恢复关联同一问题事件，跨源/跨实例同号、复发新事件及独立恢复事件编号分别测试。
- 空恢复取值不显示正常；原始级别保留且不自动全员提醒；未标环境与时区明确未知。
- 移动端纯文本/Markdown 降级仍保持字段顺序；不依赖卡片、颜色或按钮才能理解。
- 原始错误文本中的 token、密码、URL 查询参数和内网资产信息按通知受众与组织策略脱敏，完整记录受权限控制；不能默认所有群都可披露内部 IP。
