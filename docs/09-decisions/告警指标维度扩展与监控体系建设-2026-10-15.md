## 0. 结论（先给答案）

**要建，但不是"加维度"，而是「先接线 → 再按动作价值扩维 → 其余明确不做」。**（D-a 已于当天实施，见 §4.5）

现状不是"维度太少"，而是**已有的线没接上**：修复前 15 条告警规则里真正能响的只有 5 条，
10 条要么被鉴权拦成哑巴（6 条恒不亮）、要么让宕机规则**恒亮误报**（1 条）、要么根本没有数据供给（3 条）。
在这种状态下继续加维度，只是往一块没通电的看板上多贴几张纸。

| 档 | 内容 | 何时 | 成本 | 判断 |
| --- | --- | --- | --- | --- |
| **D-a 接线** | ①给 Prometheus 一个可用的抓取身份 ②看板 2 个死面板改名/删 ③把本审计脚本接进 CI | **已完成（2026-10-15）** | 半天 | ✅ 见 §4.5 |
| **D-b 扩维** | 5 组维度：`severity`/`system`/`source` + 告警质量四反指标 + 送达比与静默秒数 | 灰度期内（1~2 天） | 1~2 天 | 建议：这是"告警有没有吵到人"的度量，比再加时延分位值钱 |
| **D-c 不做** | SLO/误差预算、长期存储、Grafana provisioning IaC、全标签笛卡尔积、APM | 本轮明确不做 | — | 见 §6，现在做就是分心 |

**一条判据（贯穿全档）**：一个维度只有在「**值不同 → 值班动作不同**」时才配进标签；
一条规则只有在「**有人能在 15 分钟内做点什么**」时才配报警。

## 2. 五处「有电不亮」（现象 / 证据 / 后果 / 复跑）

### 2.1 抓取面被鉴权拦死 —— 影响面最大的一条

- **现象**：`/actuator/prometheus` 与其余 `/actuator/**` 一起被 Sa-Token 拦；`monitoring/prometheus.yml` 的
  `opsbrain` job **没有任何凭据字段**（`authorization`/`bearer_token`/`basic_auth` 全无）。
- **证据**：`WebConfig` 显式注册了 `/actuator/**`（除 health）登录校验；`application-prod.yml` 把
  `auth-enabled` 写死 `true`（不给环境变量关的口子）；实测裸抓 401。
- **后果**（按规则逐条数）：
  - `OpsBrainDown`（`up{job="opsbrain"}==0`）→ 抓取恒失败 ⇒ `up` 恒 0 ⇒ **常亮误报**（P0 级）；
    历史 `sys_alert` 里反复出现的 OpsBrainDown 曾被归因到"targets 写成了 `app:8088`"，那次只修了地址，**鉴权这一半没修**。
  - `OpsBrainFrequentRestart`/`OpsBrainUrgentPendingHigh`/`OpsBrainApprovalBacklog`/`OpsBrainJvmHeapHigh`/
    `OpsBrainHttp5xxRate`/`OpsBrainNotifyDeliveryFail` → 恒无数据 ⇒ **永不触发**（6 条哑规则）；
  - 看板上引用 `opsbrain_*` 的 5 个面板 → 恒空。
- **复跑**：`python3 tools/verify/monitoring_audit.py --probe http://localhost:8088/ai/actuator/prometheus` → B 段 + E 段。

### 2.2 看板有 2 个「查无此指标」的死亡面板

- **现象**：面板「诊断/工具时延」查 `devops_diagnosis_seconds_bucket` / `devops_tool_seconds_bucket`。
- **证据**：全仓检索这两个名字**只出现在看板 JSON 里**；代码里的真实指标是 `opsbrain_diagnosis_seconds`
  （且**从没有过** `tool_seconds`——工具耗时指标未实现）。
- **后果**：面板永远空白。"有看板"≠"有数据"，而空面板比没面板更坏：它让人以为监控已经覆盖了诊断时延。
- **复跑**：审计脚本 A 段（本次 2 条硬缺口）。

### 2.3 依赖类三条规则没有供给（不误报，也永远不响）

- `OpsBrainPostgresDown`(`pg_up`) / `OpsBrainRedisDown`(`redis_up`) / `OpsBrainMinioDown`(`minio_*`)：
  compose 里**没有** postgres_exporter / redis_exporter，MinIO 服务在但 prometheus.yml 里**没有抓它**。
- 规则注释写着"规则先就位（无数据时 for 持续不满足不误报）"——这个判断是对的，但代价是：
  **PG 真宕机时这三条不会响**。中间件故障只能靠应用报错倒查，也就是"用户先痛"。
- **复跑**：审计脚本 C 段。

### 2.4 看板没有承载（Grafana 不在 compose 里）

看板 JSON 自称"4-4 备用盘，Grafana 接入即用"——即目前**没有 Grafana 服务**跑它。
这不是缺陷（手工导入是常见做法），但意味着"L2 监控栈一键部署"这句话里，**看板不在其中**。

### 2.5 CI 不校验监控配置

改指标名、改规则表达式、把 `${service}` 占位留错——CI 全绿。
本仓已经为 OpenAPI 快照、CSS 令牌、生成物新鲜度都建了门禁，**监控面是唯一没有门禁的配置面**，
恰恰是"改一边忘一边"最容易发生的地方（看板死面板就是这么来的）。

## 3. 维度扩展：现状 vs 建议

### 3.1 现状：告警链几乎没有维度

| 指标 | 现有标签 | 能回答的问题 |
| --- | --- | --- |
| `opsbrain_alert_received_total` | 无 | 收了多少 |
| `opsbrain_alert_dedup_total` | 无 | 去重命中多少 |
| `opsbrain_ticket_autocreate_seconds` | `result` | 建单快不快 |
| `opsbrain_diagnosis_seconds` | `result` | 诊断快不快 |
| `opsbrain_notify_total` / `notify_delivery_total` | `result` | 通知受理/送达各多少 |

**答不了**：哪个系统在吵、哪个 P 级在涨、哪个来源（Zabbix/Alertmanager）质量差、观察窗到底拦了多少、
是哪一类"未建单原因"占多数、各渠道送达率谁高谁低——而这些才是值班人真正用来分流的轴。

### 3.2 建议新增（D-b，5 组）

| 组 | 维度/指标 | 回答的问题 | 为什么值 |
| --- | --- | --- | --- |
| ① 告警入口 | 给 `alert_received_total`、`alert_dedup_total` 加 `severity`(P0~P4) / `system` / `source` | 哪个系统在吵、哪个 P 级在涨、两个来源谁更脏 | 三轴都是**值班动作的分叉点**（找谁、要不要叫醒、接得对不对） |
| ② 告警质量反指标 | `observation_suppressed_total{level}`（观察窗拦下）、`storm_aggregated_total`、`escalated_total`、`unticketed_total{reason}` | "告警有没有吵到人"——降噪到底降了多少 | **当前完全看不到**：降噪是产品卖点，却没有度量；比再加时延分位更值 |
| ③ 送达质量 | `notify_delivered_ratio`（或规则化）、`notify_silent_seconds`（距上次送达秒数） | 送达率、以及"多久没送出去" | 现有规则只拦 `result=error` 的**绝对值**；`silent_seconds` 一条指标同时覆盖"没配渠道"和"渠道坏了" |
| ④ 诊断成效 | `diagnosis_evidence_status{kind,status}`（四路证据各态计数） | 四路证据里哪一路长期 FAILED/NO_DATA | 直接指认"缺哪个数据源"，比看诊断耗时有用 |
| ⑤ 工单流速 | `ticket_resolved_seconds`（Timer）+ `ticket_open` by `priority` | MTTR/在水位按优先级拆 | 效能页现在靠 SQL 现算，指标化后可做趋势与预警 |

**基数预算**（Prometheus 的成本模型：series = 标签取值组合数）：
`severity(5) × system(~10) × source(2)` ≈ 100 series/指标 → 乘 2 个 counter = 200 series，
加其余各组合计几百 series，**远低于任何部署的基数预算**。也就是说 D-b 的成本几乎为零，
成本真正在**人**：每加一个维度，就多一处"改代码时要同步的地方"（所以 D-a 第③件门禁是它的前置）。

### 3.3 三条红线（扩维时不可越）

1. **事件级/高基数维度不进标签**：`alert_id`、`trace_id`、`event_id`、`trigger_id` 一律不进——
   它们每来一条告警就产生一个新 series，时序库会被打爆，聚合也失去意义。
   这是 F1 缺陷的同一条教训的另一个面：**F1 就是"事件级字段（`event_severity`）混进了身份键"**，
   导致恢复事件配不上原告警、告警永久 FIRING。**身份键与事件属性必须分家**——指标标签同理。
2. **"未知"必须能从指标上区分**：「未配置渠道」与「渠道故障」都会表现为 `delivered=0`（F3 口径）。
   扩维时必须能表达"未知"（如 `configured` gauge 或 label），否则会把没配渠道读成故障，
   把一个假故障喂给告警链自己（自我误报的闭环）。
3. **指标名/规则/看板三者必须可机械对账**：没有对账脚本，任何一处的改动都是静默失效（§2.2 就是活例）。

## 4. 理由与利弊（逐档）

### D-a 接线（半天）

- **理由**：这是"其他一切监控投入的乘数"——不接，加多少维度都是 0；而且它同时消掉一个**P0 级误报源**
  （OpsBrainDown 常亮）——误报是监控体系最快的信任杀手。
- **利**：①10 条规则从"哑/误报"变成"能响"；②看板可读；③CI 门禁防漂移；④工作量小（三处小改，不碰业务代码）。
- **弊**：①抓取凭据是**新的一份凭据**（要进密钥轮换 SOP——本仓已有该 SOP 文件，顺势纳入）；
  ②门禁会把历史遗留的监控配置问题一次性暴露出来（这是好事，但要接受"上闸当天可能红"），
  故顺序必须是**先修 A/B 两处，再上闸**。
- **不做的代价**：继续保持"看似有监控"的状态，直到真出事时发现 OpsBrainDown 之外什么都不响。

### D-b 扩维（1~2 天）

- **理由**：现在能看到"处理慢"，看不到"告警吵"；能看到"送达失败次数"，看不到"送不出去的时长"。
  运维体验的核心指标（噪声、降噪效果、送达可靠性）恰好在盲区。
- **利**：①降噪能力第一次可量化（观察窗拦下多少、风暴聚合多少）——这是产品叙事里最硬的证据；
  ②四路证据状态指标能直接指认"缺哪个数据源"，把诊断 WEAK 的归因从"猜"变成"看"；
  ③几乎零基数成本。
- **弊**：①每个维度都是"改代码要同步的一处"，必须配 D-a③ 的门禁；②阈值仍是拍脑袋，
  需要真窗数据回填（本仓规则里已写明"起步阈值，真窗首周校准"的纪律，沿用即可）；
  ③`unticketed_total{reason}` 的 reason 文本要**枚举化**（不能用自由文本做标签，否则基数失控）。
- **不做的代价**：灰度期结束后拿不出"降噪到底有没有用"的数据，只能讲机制、讲不了效果。

### D-c 不做（明确清单）

| 不做项 | 理由 | 反悔条件 |
| --- | --- | --- |
| SLO / 误差预算 | 没有真实用户 SLO 基线，现在定义等于拍脑袋；且服务对象是内部值班，不是外部用户 | 出现明确的对外可用性承诺 |
| 长期存储 / Thanos / remote write | 30 天保留对灰度与复盘足够；长期存储是"先有量再看"的决定 | 保留期不够用、或需要跨年趋势 |
| Grafana provisioning 全量 IaC | 当前只有 1 个看板，手工导入的成本 < 维护 provisioning 目录的成本 | 看板数 ≥5 或需要多环境一致 |
| 全标签笛卡尔积 / 方法级指标 | 基数与维护成本双高，且绝大多数维度无人消费（审计脚本 F 段已经能报"无人消费的指标"） | 出现具体的排查需求 |
| 引入 APM / 商业监控 | 单机部署 + 2g 预算；现有 Prometheus 栈够用 | 微服务化之后 |
