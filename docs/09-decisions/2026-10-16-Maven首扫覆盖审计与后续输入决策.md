# 批114：Maven 首扫覆盖审计与后续扫描输入决策

## 结论：推进审计，不能宣称扫描覆盖闭环

**本批推进独立、可复跑的覆盖审计；不批准“当前首扫已覆盖全部运行时依赖”的结论。** 不抬漏洞阈值、不加忽略规则，不把新的覆盖差异当成原扫描已经发现并处理的漏洞。

上一批解决 raw/gate 的事实漂移，本批发现**原始扫描本身还有大面积覆盖缺口**。下一优先项应是 Maven 原生生成的 runtime SBOM 作为 Java 扫描输入的独立实验，而不是调缓存/加重试、用“0漏洞”关闭安全事项。

## 实际结果，而非设计预期

首轮 [run38781339101](https://github.com/Yyu675/OpsBrain-AI/actions/runs/38781339101)，PR HEAD `1119e9c`，audit job `116582194618`：

|---|---:|
| Maven compile/runtime 唯一 GAV | 293 |
| 包含 type/classifier 的运行时变体 | 298 |
| Trivy `pom.xml` 包集（剔除根项目） | 32 |
| 逐 GAV 匹配 | 32 |
| 缺失 | **261** |
| 额外扫描 GAV | 0 |
| 对已识别 GA 的版本偏差 | 0（不等于所有运行时版本均识别） |

这不是拿所有生态的总包数对比：前端不进入 Java 分子；根项目不算外部依赖；双方按同名**同版本**匹配。首扫196个跨生态包的旧数字不能用于证明Java运行时覆盖。

缺失示例包括 `logback-classic/core:1.5.32`、`sa-token-core:1.44.0`、`azure-core:1.55.3`、`jackson-databind:2.19.4`、`langchain4j-core:1.2.0` 等传递依赖。这里只证明它们没出现在对应扫描包集，**不是声称这些版本必有漏洞**，也不是断言漏项全部由HTTP429造成。

证据来自Check annotations的计数/指纹与前10个缺失条目：[证据文件](../09-operations/evidence/maven-scan-coverage-2026-10-16.json)。首版将完整差异发成单条注解，被截断至4086字符且不能解析；不把该条作为全量JSON证据。现已改为压缩分片+SHA256回放，完整审计结果以最终HEAD对应CI及artifact为准，不以旧HEAD绿灯替代。

## 落地流程

1. 生产job维持批113的一次fs→同源派生→convert，阈值及豁免不变。
2. 新job `needs: trivy-repo-scan`、`if: always()`，在**独立runner**下载同run的raw artifact。即使漏洞门禁红，仍可取证；若缺原始报告则报错，不把缺失当空包集。它不会提前预热首扫的Maven缓存。
3. JDK21执行固定 `maven-dependency-plugin:3.8.1:tree`，明确runtime、JSON、输出到/tmp。真实Maven错误保留退出码和诊断，不跳过，不用手写pom直接依赖代替解析结果。
4. helper独立校验runtime范围与数据形状：compile/runtime纳入，test/provided/system/import整棵子树排除；optional直依赖仍属本项目运行时。去重按GAV，记录type/classifier变体但不宣称classifier或字节已覆盖。
5. 每个GAV对账，分开missing、version_mismatches、extra；extra不当漏扫。空runtime、缺目标/包清单、未解析版本、未知scope、损坏JSON均报红，不能得到0/0“100%”。
6. audit JSON包含checkout SHA、源tree/raw/pom的SHA256、双方清单、全量差异与变体。tree/audit/log always上传；输入错误清除旧审计文件，拒绝旧绿证据。
7. 默认**审计模式**：合法差异返回0，但warning和`status=incomplete`明确覆盖未达标；工具/输入错误返回1。`--strict`存在且有测试，但本批不暗中把未核清差异变成新生产门禁。原漏洞门禁红不会被本job成功覆盖。

## 为什么这样推进：利弊与取舍

| 方案 | 利 | 弊/边界 | 决定 |
|---|---|---|---|
| 仅检查扫描目标存在/总包数 | 成本低 | 实证已有32/293；目标存在仍可漏大量传递依赖 | 不足以判覆盖 |
| Maven预热后继续pom扫描 | 可能提高解析成功率 | 改变首扫条件、仍不等于Maven有效模型/冲突仲裁结果 | 本批不做，先独立取证 |
| runtime tree对账 | 复用真实解析，范围明确，可逐项找漏项/版本差异 | 增加一次Maven解析成本；GAV不能证明classifier/字节 | **本批采用** |
| 立即把覆盖差异设成生产硬闸 | 能阻止以漏扫结果放行 | 尚未定义非jar/多平台变体与scanner表达差异，会把调查与新门禁混成一批 | 不暗中启用；明确保留不完整状态 |
| Maven原生CycloneDX runtime SBOM→Trivy | 有望避免scanner二次解释Maven模型 | 要核对SBOM与runtime tree、测试scope/classifier；也要保留前端与Secret扫描，不能只换命令丢扫描面 | **下一批优先做独立实扫实验** |

后续SBOM方案应先证明：runtime GAV覆盖可核对、已知传递CVE可检出、Maven/SBOM生成失败不可跳过、前端/Secrets仍受同等门禁、不会再让另一遍报告覆盖原始退出码。在真实结果出来前，不承诺“换SBOM就全绿/安全”。新增发现若需依赖补丁，另按实际漏洞最小修复，不混进这次审计。

## 验证与边界

- 本地新增对账17例、实际YAML shell协议5例，加既有49例，共71例通过；fake工具仅验证控制流，不冒充Maven/Trivy实跑。真实Maven与Trivy由上述run执行。
- 三个隔离变异均被测试咬住：只比包数→2例红；忽略版本→1例红；误豁免optional直依赖→1例红。还测了长审计分片恢复与实际JSON文件SHA256一致，避免首轮注解截断重演。
- pom和审计工具变更加入限定PR触发；普通业务push不新增漏洞库扫描成本。
- 本批是新审计能力，**不是“仅修红自动合并”类别**，保留PR待验收。
- 工程绿不代表覆盖完整或运行时安全，更不代表灰度验收；0/17、真渠道/真人ACK、观察覆盖继续保留。
