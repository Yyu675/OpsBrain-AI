## 一、问题背景与旧模板缺陷分析

用户明确否定旧模板的可理解性，指出不能只微调措辞，也不能只处理触发模板，**告警触发、告警恢复、诊断不足** 三种通知均须结合项目实际情况进行优化重构。

通过对代码仓库 `AlertNotifyTemplate.java`、`AlertService.java` 及用户提供的真实生产通知截图进行深度分析，提炼出旧实现的关键缺陷：
1. **触发卡（Firing）缺陷**：
   - 缺乏硬核定位维度：在基础设施或硬件监控场景，缺少明确的主机（Host）、管理 IP（Target Address）及监控项（Monitor Item）字段，信息散乱在 description 或 labels 中；
   - 监控取值机械化：此前仅支持简单数字或阈值拼接，当遇到真实系统抛出的错误长文本（如 `Failed to receive data: volumes : Error: cannot get URL: Timeout was reached.`）时，易被误处理或截断混乱；
2. **恢复卡（Resolved）缺陷**：
   - 与告警触发卡缺乏**高度对称性**，字段顺序漂移增加值班比对成本；
   - 虚假恢复或取值空白：原先若源未给恢复取值容易造成误解；同时在多告警聚合工单下，容易误导运维直接关闭整张工单；
3. **诊断不足卡（Diagnosis / Insufficient）缺陷**：
   - Agent 取证不足时仅输出抽象结论，缺乏具体的**采集缺口明细与人工介入排查建议**；
   - 容易让值班人员产生“系统未发现错误即等于业务正常”的致命误判。

## 二、优化重构核心设计

### 1. 吸收企业真实通知精髓，保持像素级阅读对称性
- **字段顺序标准化**：
  - 触发：`[级别] 服务 告警名 | 实例` → 摘要 → 影响 → **告警主机** → **告警地址** → **监控项目** → **监控取值（支持错误文本）** → 持续时长 → 详情 → 首步动作 → Runbook → 关联工单与状态 → 平台直达链接；
  - 恢复：`[已恢复] 级别 服务 告警名` → 摘要 → **恢复主机** → **恢复地址** → **监控项目** → 原告警说明 → **恢复取值（明确标注来源与复测状态）** → **持续时间（精确/估算区分）** → 关联工单状态与多告警防误关护栏 → 平台直达链接。

### 2. 多信号源（Zabbix等）硬核字段归一化契约
- 在 `AlertAnnotationKeys` 中增补多源定位契约：
  - `MONITOR_ITEM`（`monitor_item`，对应监控项目）；
  - `TARGET_ADDRESS`（`target_address`，对应发生/恢复 IP 地址）；
  - `HOST_NAME`（`host_name`，对应发生/恢复主机名）。
- `ZabbixSourceAdapter` 同步注入对应注解，确保 Zabbix 原始事件无缝对齐。

### 3. 诊断不足可操作性增强
- 在证据不足（`INSUFFICIENT`）或薄弱（`WEAK`）时，结构化输出取证状态清单；
- 明确输出排查建议（检查探针连通性、日志上报链路与权限，优先转人工研判）；
- 强化安全防线：明确标注“不要据此认定业务正常”。
