## A 阶段结果（子代理两度 524 失败，改为主线程定向核查）

覆盖四类模式（针对 B 暴露的「生成代码与真实库脱节」模式）：

1. **配置注释 vs 实现**：prod 占位符防护良好（`__MUST_SET_*__` 拦截 + CORS 启动检查）；发现 P2-1：REAL 模式下 chat 渠道 API key 为占位符无启动拦截（embedding 有 RealModeStartupGuard 实调自检，chat 无）——延迟到用户对话才 401。
2. **前后端契约**：`service`→`module` 有 mapServiceToModule 映射层（api/services/ticket.service.ts:368）；告警响应字段防御性读取（alerts.ts:34）；审批列表 status/page/size 参数对齐。**未发现 P0/P1 契约漂移**。
3. **死代码**：tickets.query.ts 的 invalidateList/invalidateAll 无业务调用方（工单页走 Pinia）——P3 清理候选。
4. **CacheConfig 注释失实**：承诺 knowledge-meta 10min TTL，实际全局 5min 且无 @Cacheable 消费者——P2，注释误导后续维护者。

## 核心教训（写入决策的原因）

1. **空库迁移路径必须实证**：1543 测试全绿 ≠ 空库可部署——Testcontainers 集成测试连的是「已经历过修复的迁移序列」的库，而生产空库走的是「当前 V1 一次性全量」路径。两个幻觉索引都只在这条路径上炸。
2. **联调驱动 > 静态审计**：登录 500（SpEL）、缓存一致性、CSP 分域风险均由真机行为暴露。
3. **子代理不稳定时（本机内存 3.5GB + 网关 524）主线程定向核查是可靠回退**。
