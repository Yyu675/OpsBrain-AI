## 二、三条存量策略的评估

### P4 磁盘告警自动回收日志（host.log.rotate）— 建议：继续演练

- **阻断事实**：`host.log.rotate` 没有注册执行器（已注册的只有 K8s restart/scale 与 mock）。现在关掉 dry_run，命中后会被治理门以 NO_EXECUTOR 拒绝——不产生任何效果，只产生噪音台账。
- **要做它，先补执行器**：host 级动作（清日志）需要 SSH/agent 通道，这是一个新的执行面，爆炸半径与 K8s 不同级。
- **结论**：维持 dry_run=true，作为「策略匹配+留痕」的持续验证器跑着。

### P3 Pod 崩溃自动重启（k8s.pod.restart）— 建议：等有真实 K8s 再评

- 执行器存在（fabric8），白名单条目存在（CONTROLLED_WRITE，当前 disabled）。
- 本机没有 K8s 集群，执行器的真实行为（含 undo）无法验证。在没有可验证的集群前谈「放开自动重启」是空话。
- **结论**：阻塞在环境，不阻塞在设计。接入一个测试集群后，先手动触发几次看台账与 undo，再谈策略自动执行。

### P0/P1 数据库连接池打满（db.connection.kill）— 建议：短期内不碰

- HIGH_RISK_EXECUTION 级动作，执行器不存在，且「杀数据库连接」是生产事故级的动作。
- **结论**：维持现状（disabled + dry_run），它存在的意义是治理框架的演示，不是真的要自动杀连接。

## 三、信任阶梯的下一级（推荐动作）

真正值得放开的是 mock 级之外的第一步**真实但可逆**的动作。候选：

1. **k8s.deploy.scale（缩容再恢复）**：可逆性最强（undo = 恢复原副本数），但需要 K8s 集群。
2. **接入一个测试 K8s 集群（如 kind/minikube）**，用 `k8s.pod.restart` 演练一周，攒够「执行成功率 / undo 成功率 / 误触发率」三个数后再评审 P3。

在那之前，生产环境**一条都不放开**是正确的——今天的演练留痕机制就是为此设计的。

## 四、评审通过时的操作清单（供届时照做）

1. 确认目标策略的 action_key 有已注册执行器（`/api/v1/healing/executors` 可查）。
2. 确认白名单条目 enabled 且环境匹配。
3. 先 `POST /api/v1/healing/executions` 手工触发一次同动作，看台账 SUCCEEDED。
4. 策略 `dry_run` 关闭走独立端点（`/policies/{id}/dry-run`），审计会单独留痕。
5. 放开后的前 7 天盯 `/api/v1/healing/stats` 的 verifyFailRate 与 undoSuccessRate。
