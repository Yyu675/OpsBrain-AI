# 批113：Trivy 单次扫描与同源门禁

## 决策：推进，但不把“同源”当作依赖覆盖完整

**采用一次 `trivy fs` 留原始报告 → 离线按 `Status=fixed` 派生 → `trivy convert --exit-code 1` 原生判门禁。** 不改 Trivy 0.70.0、不改默认 HIGH/CRITICAL、不加漏洞豁免、不改生产依赖。

理由：双扫会重新解析 Maven，第二遍退出 0 并不说明依赖图或发现完整。现在从同一份事实派生政策结果，彻底去掉第二次生产解析导致的报告漂移，而不是靠重试或“取最后一次绿”。这修复的是报告链路，不是证明所有远端依赖都已解析成功。

## 证据：先承认探针自己的假绿

- run [38772526074](https://github.com/Yyu675/OpsBrain-AI/actions/runs/38772526074)，outside-default：gate **11 个 CVE**、full **1 个**；指定 MinIO CVE 两遍均存在，但另 10 个已丢失。首版 `consistent=true` 只检查指定 CVE，**该一致性结论作废**。
- 其余内置输出、memory 缓存、反转顺序的对照后来都仅剩这个直接依赖 CVE。这不能证明历史是缓存问题，也不能证明某次实际收到 429；没有历史 HTTP 证据。
- 源码机制：Trivy v0.70.0 的 `pkg/dependency/parser/java/pom/parse.go` 对远端 POM 非 200 可仅 Debug 并继续，因此可能没有完整传递依赖却仍成功退出。
- run [38773493944](https://github.com/Yyu675/OpsBrain-AI/actions/runs/38773493944)，HEAD `90cadae`，真实工具+真实 DB+本地 Maven 仓库实证：

| 条件 | 漏洞发现 | CLI 退出码 |
|---|---|---|
| 仓库健康，根 POM → 唯一 bridge → MinIO 8.5.12 | CVE-2025-59952 | full 扫描 0（留档模式） |
| 同一仓库注入 HTTP 429、memory 缓存重新扫描 | 发现消失 | 仍为 0 |
| 从第一份健康报告离线派生并 convert | CVE-2025-59952 保留 | **1，正确拦截** |

convert 期间对该 Maven 仓库请求数 **0**。该 run 的生产 raw/gate 两目标均为 0 HIGH/CRITICAL，manifest 记录 196 个包及源/派生 SHA256，artifact `trivy-report` 上传成功。**这里引用的是 Check annotations 和 artifact 元信息，不冒充已下载检查原始 artifact。** 摘录见 [证据 JSON](../09-operations/evidence/trivy-single-source-2026-10-16.json)。后续按包/路径指纹与包清单比对的加强，以 PR #16 最新 HEAD 检查为准，不用旧 run 替代新版本验收。

## 生产流程及失败处理

1. 只有一次 `fs`，保留选定严重级别内的全部漏洞（含无补丁项）及默认 Secret 扫描结果，显式保留包清单。输出 `/tmp`，不让报告成为扫描输入。
2. raw 扫描非零、缺/坏 JSON 或摘要失败均不放行；派生工具校验 SchemaVersion、非空目标、漏洞 ID、发现字段形状与两个必需目标：`pom.xml`、前端 `package-lock.json`。
3. `trivy_policy.py` 深拷贝报告，只筛 `Vulnerabilities`。v0.70.0 `ignore-unfixed` 的确切规则是 **Status=fixed**，不是 `FixedVersion` 非空。八种官方状态及缺省 unknown 均有测试；未知新状态拒绝，不静默豁免。Secrets、Misconfigurations、Licenses、Packages、元数据原样保留。
4. `convert` 不支持 `--ignore-unfixed`，故不能直接传这个参数；使用已派生 JSON，由 Trivy 自己判断失败。保留 CLI 原始非零码，摘要不能吞掉红灯。
5. raw、派生输入、gate、哈希 manifest、两份 CLI 日志均 always 上传。真实受控探针放在生产扫描**之后**，不先消耗 Maven 请求或干扰生产取证。
6. 可选 `--matrix` 才重跑旧的在线调查矩阵。新判据要求所有 gate 的 **目标/CVE/包/版本/路径指纹**均出现在 full，且包清单相等；full 可以多出未修复漏洞。不能再只检查一个 CVE，也不能把相同 CVE 在不同包上的发现合并成一个。

## 方案利弊与未选项

| 方案 | 好处 | 风险/成本 | 决定 |
|---|---|---|---|
| 继续双扫、加重试/缓存参数 | 改动小 | 无法保证第二次解析与第一次同一事实，仍可能“最后一遍绿” | 不选 |
| Python 自己判失败码 | 易实现 | 容易漏掉 Secrets/配置等 Trivy 原生语义 | 不选；只派生状态，不自己判门禁 |
| 单扫+准确派生+convert | 同源可追溯，保留原生失败判断；不再为 gate 访问 Maven | 维护一个绑定 0.70.0 的小契约；升级必须复核 Status/convert | **本批采用** |
| canonical Maven/SBOM 与扫描包覆盖核对 | 能进一步发现首扫本身的依赖缺口 | 需另做真实依赖解析/覆盖基线、定义运行与开发依赖边界 | 后续独立评估，不冒称本批已做 |
