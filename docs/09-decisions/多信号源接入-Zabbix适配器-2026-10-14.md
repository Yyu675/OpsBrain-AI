## 一、为什么现在做

78 号文档给的判据是「**出现第二个真实接入源时**再抽中性模型——届时两套字段摆在面前，
才知道中性模型该长什么样」。本轮的输入正好是那一刻的现场素材：用户提供的 Zabbix
告警/恢复微信通知（PROBLEM `2026-10-13 17:37:55` / OK `17:38:47`，
`primera01` / `10.210.44.11`，事件 ID `12002061`，Average，取值含
`Failed to receive data: volumes : Error: cannot get URL: Timeout was reached.`）。

把它落成代码之后，接缝上「两套字段并存」不再是想像：Alertmanager 是自由标签模型
（`labels`/`annotations` 任意键值、RFC3339 带偏移量时间），Zabbix 是固定字段模型
（`event_*`/`trigger_*`/`host_*` 宏、无时区墙钟、恢复是**另一条事件**）。
两类差异全部收敛在适配器里，核心链（去重 / 建单 / 诊断 / 通知）**一行未改**。

## 二、接缝形态（本轮新增的三个件 + 一处改动）

| 件 | 职责 | 关键取舍 |
|---|---|---|
| `AlertSourceAdapter#sourceName()`（改） | 来源标识，供错误提示与接入文档共用一份事实 | 默认取实现类名；两实现覆盖为 `prometheus` / `zabbix`（运维认的词，不是 Java 类名） |
| `ZabbixSourceAdapter`（新） | 「读懂 Zabbix」的全部规则：字段映射、级别翻译、标签解析、时间解释、指纹与恢复判定 | 级别**认不出就原样透传**、时间**解析不出就给 null**、标签撞保留字**让位不报错**——三处都是「不猜」 |
| `DTO/ZabbixWebhook`（新） | 形状不收窄的负载容器（`@JsonAnySetter` 收下全部键，容错访问器取值） | 不写字段对齐的 POJO：Zabbix 的 body 由管理员在「媒介类型」里拼装，写死字段会在别人改一个宏名时 400 |
| `AlertSourceNormalizer`（新） | 按 `supports` 选源并归一化 | 选不中**抛异常**（控制器翻成 400）而不是静默忽略；错误消息列出已注册来源 |
| `ZabbixWebhookController`（新） | `POST /api/v1/alerts/webhook/zabbix` | body 收 `Map<String, Object>` 再包成 DTO —— 见 §六 契约门禁 |

`AlertService` 的改动只有两处：注入点从「单个 Alertmanager 适配器」换成注册表
（两个实现并存时该注入点会直接变 `NoUniqueBeanDefinitionException`，必须显式选），
以及新增跨源入口 `processSourceWebhook(Object)`。

## 三、字段映射

| Zabbix | 平台 | 说明 |
|---|---|---|
| `trigger_name` ＞ `event_name` | 告警名 | 跨 PROBLEM/OK 稳定；两者都缺 → 拒绝该负载（不留无名告警） |
| 标签 `service` ＞ `host_name` ＞ `host_ip` | service | Zabbix 没有「业务服务」概念，host 是最近似的影响面 |
| `event_severity` | P0~P4 | 6 级压缩为 5 级，见 §四 |
| `host_name` / `host_ip` | labels: `host` / `instance` | 去重键的标签维度；`instance` 缺 IP 回落主机名 |
| 事件标签 / 主机标签 | labels（保留字与字典键除外）+ 注解（字典键） | 主机级铺底、事件级覆盖 |
| `event_name` / `trigger_description` / `item_value` / `opdata` | annotations: summary / description / current_value | 按 `AlertAnnotationKeys` 字典落位 |
| `event_date` + `event_time` | `startsAt`（PROBLEM）/ `endsAt`（OK） | 无时区墙钟，按部署时区解释，见 §五 |
| `event_status=OK` | resolved | 恢复在 Zabbix 里是另一条事件，见 §五 |

## 四、级别翻译：为什么必须翻译，且为什么不做兜底猜测

核心链的 `normalizeLevel` 只认 `CRITICAL/WARNING/INFO/P0~P4`，其余**一律落到默认 P3**——
Zabbix 的 `Average`/`High`/`Disaster` 原样透传的后果是「服务器宕机与磁盘快满得到同一个级别」，
且不报错。故适配器按 6→5 压缩：

| Zabbix | 平台 | 依据 |
|---|---|---|
| Disaster / 灾难 / `5` | P0 | 业务中断级 |
| High / 严重 / `4` | P1 | 高危 |
| Average / 一般严重 / `3`、Warning / 警告 / `2` | P2 | 需人工处理但非即刻 |
| Information / 信息 / `1`、Not classified / 未分类 / `0` | P4 | 信息量级（压缩掉 P3：Zabbix 没有「次要」这一档） |

规则细节：英文/数字/中文三种形态都认（`{EVENT.SEVERITY}` 在本地化界面里就是中文），
大小写与下划线归一（`DISASTER`/`not_classified`）；**认不出的级别原样透传**并留一行 WARN——
猜成 P0 会制造误报（半夜叫人），猜成 P4 会漏掉真故障，都比「落到核心链默认值 + 原始词留在
`event_severity` 标签里可追溯」更差。

## 五、两处「不许猜」

**时间**：`event_date`/`event_time` 是 Zabbix 服务器本地时间的墙钟，负载里没有偏移量。
平台所有 TIMESTAMP 列都是无时区本地时间，生产部署时区固定 `Asia/Shanghai`
（`DeploymentTimeZoneContractTest` 在管），故**默认用部署时区**（`ZoneId.systemDefault()`）
解释，需要时用 `devops.alert.zabbix.timezone` 显式指定——不写死时区名，否则平台迁到别的
时区部署时会静默平移所有事件时刻。时区配错时**持续时长仍然正确**（PROBLEM 与 OK 用同一把尺子），
只有绝对起始时刻整体平移；解析失败交 `null`，由核心链标 `START_TIME_ESTIMATED` 并在卡片上
写明「估算」——**绝不回退成 `now()`**：把「不知道」写成「就是现在」会让持续时长凭空归零。

**去重指纹**：`zabbix:<trigger_id>@<host_name>`，**不含 `event_id`**。Zabbix 的恢复事件有
独立 id（真样本里 PROBLEM `12002061` / OK `12002062`），把 event_id 混进指纹会让恢复配不上
原告警——表现为「恢复了但告警一直挂着」，且没有任何报错。同理，适配器**不注入**
`system` 标签：来源（`sys_alert.source`）与业务系统（`sys_alert.system`）是两件事，
核心链按既有规则把它回落成 `default`；若硬塞 `zabbix`，按 system 统计来源分布就会得到错误结论
（注意别把回落值 `default` 读成「适配器写了 system」，那是核心链的既有语义）。

## 六、与 Alertmanager 端点的三处有意差异

| 维度 | Alertmanager 端点 | Zabbix 端点 | 理由 |
|---|---|---|---|
| 负载形状 | 强类型 DTO | `Map` 收下 → 包成 DTO | Zabbix 的 body 由管理员拼装，形状不固定 |
| 不认识负载 | 一律 200 | **400** | 客户端不同：Alertmanager 会给非 200 重投（静默丢告警更危险）；Zabbix 的 Webhook 媒介类型会在脚本里读状态，400 让「动作调用失败」直接出现在 Zabbix 事件日志里——接入自测阶段就能看到 |
| 空负载 `{}` | 200 不处理 | 200 不处理 | 接入方的「测试」按钮会发最小负载，返回非 200 会卡住自测 |
| 鉴权 | `WebhookGuard`（token/HMAC/限流） | 同一套 | 不为此源再造一套防护；两端点都在鉴权白名单内，调用方是机器 |

契约快照的更新方式也是有意选择：**body 收 `Map`**（springdoc 渲染为内联对象，
不新增命名 schema），而不是直接收 DTO —— 后者会注册一个空属性 schema，
为了一个纯转发用的类型去动契约快照不值当。快照只加了
`POST /api/v1/alerts/webhook/zabbix` 一条。

## 七、测试与验证边界（诚实清单）

**本地能做的**（沙箱无 Java 编译器：JRE-only、JDK release 资产域被墙、PyPI/npm 无 ECJ）：

1. **语法闸**：tree-sitter(java) 对全部新增/改动 `.java` 逐个解析，只认 `ERROR/MISSING` 节点 → 0 错；
2. **规则镜像自检**（`/tmp` 侧脚本，不入库）：把适配器规则逐条镜像成 Python，跑在
   **从 Java 测试文件里解码出来的同一批样本**上（`javasrc.py` 负责解码文本块与字符串字面量）
   → **64 项断言**全一致，含级别表 15 项、指纹、`+08:00` 时间、52 秒持续时长、字典键分流，
   外加「形态表与 Java 源码对账」（防镜像与实现各写一套、双方都自检通过）；
3. **快照门禁双向自检**：`node tools/ci/check-openapi-freshness.js` 在「live = 新快照」下绿；
   把新端点从 live 里摘掉后**必须红**（实测红并点名 `POST /api/v1/alerts/webhook/zabbix`）——
   证明这次手改的快照真被门禁覆盖，而不是「改了但没人管」；
4. **静默失效扫描**：测试里所有 `PROBLEM_JSON.replace("A", "B")` 的 A 逐个校验是否为样本子串——
   本轮真抓到两处（含字面 `\n` 的多行目标 + 一处整行删除），replace 不生效时测试会「看着还在跑」，
   这是最隐蔽的一类假测试。

**本地做不了、由 CI 承担的**：`./mvnw verify` 全量编译 + 1967 例测试 + 新增用例执行
（`ZabbixSourceAdapterTest` 27 例、`AlertSourceNormalizerTest` 6 例、
`ZabbixWebhookControllerWebTest` 8 例、`AlertServiceTest` 跨源入口 3 例）。
沙箱无 Maven 网络，故本轮**不声明「已通过编译」**，只声明上列四道本地闸全绿。

## 八、有意不做

- **不做 sender/API 拉取模式**：Zabbix 的 Webhook 媒介类型是官方推荐的单向推送路径，
  用 API 轮询要自己管游标、去重与限流，且把「告警时效」压在轮询间隔上；
- **不建 Zabbix 专用表**：告警本体统一进 `sys_alert`，Zabbix 的原始事实
  （`event_id`/`trigger_id`/`host_ip`/原始级别/事件时间/恢复状态）落在 annotations 的
  `zabbix_*` 键上——按来源分表的下一站就是「查询要跨表 UNION」，得不偿失；
- **不引新依赖**：标签解析（`{EVENT.TAGSJSON}` / `{EVENT.TAGS}` / 对象数组三种形态）
  用一条正则 + 逗号分支完成，不为一个小结构把 JSON 解析器带进主链路；
- **不做 proxy 聚合**：Zabbix proxy 的聚合由 Zabbix 自己负责，平台侧再做一层等于两处口径。

## 九、与通知模板方案的关系

适配器把 annotations 填成 `AlertAnnotationKeys` 字典的口径，通知卡片因此对 Zabbix 源
**同样有内容**（影响 / 当前值 / 首步动作 / 看板链接），缺料时走既有的「整行省略」纪律——
卡片渲染逻辑零改动，这正是「卡片只认字典、不认来源」的设计红利。

反向约束同样成立：**字典键不进 labels**。labels 参与 SHA-256 去重键，把会随事件变化的
文案（比如「当前取值」）放进去，同一条问题每次推送都会算出新键，表里会堆出多条
「同源不同键」的告警——这类错误不报错，只表现为「告警数变多了」。

## 十、本轮改掉的静默缺陷（五处，全都不报错）

| # | 缺陷 | 不修会怎样 | 怎么发现的 |
|---|---|---|---|
| 1 | `ZabbixWebhook.stringify` 的 List 分支少外层 `[...]` | 数组形态标签（`{EVENT.TAGSJSON}` 被媒介类型声明成数组）会落进「逗号分支」解析出垃圾键，标签全废 | 规则镜像逐条对账 |
| 2 | 标签合并顺序反了（先 event 后 host.putAll） | 主机级陈旧标签**盖掉**事件级现场值（如 env=staging 盖掉 prod），且不报错 | 写用例时对照「事件级应覆盖主机级」的常识 |
| 3 | 只认 `event_opdata` | 官方文档与常见实施用 `opdata` 的脚本会整段丢失操作数据 | 镜像用真样本断言 description 含 opdata 时炸出 |
| 4 | 日期只认 ISO 短横线 | **Zabbix 的 `{EVENT.DATE}` 默认是 `2026.10.13`（点分隔）**——所有真实事件的时间都解析不出来，表现为持续时长归零、卡片写「估算」 | 把镜像的日期口径与 Java 源码**对账**时炸出（原先两边各写一套、都「自检通过」） |
| 5 | 两处 `catch (DateTimeParseException ignore)` 只吞不打 | `SilentCatchContractTest` 会因「白名单外文件新增静默 catch」判红；且真故障时现场没有证据 | 读契约测试的扫描口径 |

第 4 条的教训写进镜像顶部：**镜像必须与实现逐条对齐，不对账的镜像等于在核对另一份规则**——
现已加一条「从 Java 源码提取形态表，与本侧比对」的断言。
