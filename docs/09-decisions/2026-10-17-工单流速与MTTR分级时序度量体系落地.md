**状态**：已批准并落地  
**分支**：`arena/e9b6efb2-opsbrain-ai`  
**关联 PR**：PR #35

### 一、背景与问题

在《告警指标维度扩展与监控体系建设》（`docs/09-decisions/告警指标维度扩展与监控体系建设-2026-10-15.md`）D-b 规划中，第 ⑤ 组度量聚焦于**工单流速面（Work Order Velocity & MTTR）**。
现状存在以下痛点：
1. **在办工单水位缺乏优先级细分**：
   - 此前存量 Gauge 仅有 `opsbrain.tickets.urgent_pending`（P0+P1 合并统计）；
   - 值班管理与效能大盘无法从时序上直接看清 P0、P1、P2、P3 各档位的未结工单水位走势，缺少分级拥堵预警依据。
2. **MTTR（解决耗时）完全依赖 PostgreSQL 即时 SQL 计算**：
   - 效能卡此前每次拉取均通过 SQL 实时对 `sys_devops_ticket` 聚合计算；
   - 缺少时序级的解决耗时直方图（Timer），导致 Prometheus 无法建立历史分位值（P95）趋势，也无法通过 Alertmanager 配置 MTTR 劣化规则。

---

### 二、决策方案与技术实现

1. **底层仓库统计支持**（`DevOpsTicketRepository.java`）：
   - 增加方法 `countOpenByPriority(String priority)`；
   - 口径：`status NOT IN (RESOLVED, CLOSED, VOID) AND priority = ?`。

2. **业务指标中枢扩展**（`BusinessMetrics.java`）：
   - **在办工单按优先级拆分 Gauge**：
     - 登记 `opsbrain.tickets.open{priority=P0~P3}`；
   - **解决耗时 Timer**：
     - 登记 `opsbrain.ticket_resolved_seconds{priority}`；
     - 暴露安全 API `recordTicketResolved(String priority, long millis)`。

3. **工单服务状态机打点接入**（`TicketService.java`）：
   - 在工单流转方法 `updateStatus` 中，当目标状态为 `RESOLVED` 时：
     - 计算 `Duration.between(createTime, now).toMillis()`；
     - 异步上报 `recordTicketResolved(priority, elapsed)`；
     - 采用安全防御性调用（`try-catch`），不影响工单主状态机与事务提交。

4. **Grafana 看板自监控与静态机械对账闭环**：
   - 在面板 1（工单水位）增加 Target：`opsbrain_tickets_open`（按 priority 分组）；
   - 在面板 7（RED 自监控）增加 Target：`histogram_quantile(0.95, sum by (le, priority) (rate(opsbrain_ticket_resolved_seconds_bucket[5m])))`；
   - `tools/verify/monitoring_audit.py` 静态对账 18 个代码声明指标全部通过，0 缺口、0 孤立；
   - `MonitoringConfigContractTest` 保持全绿。

5. **单测防护**：
   - `BusinessMetricsTest` 新增 `ticketOpenAndResolvedMetrics` 测试各优先级 Gauge 与 Timer 计数；
   - `TicketServiceTest` 新增 `updateStatusToResolvedRecordsMttrMetrics` 验证工单转 RESOLVED 时打点正确性。

### 三、利弊与影响分析

- **利**：
  1. 实现了工单生命周期核心流速度量，从“只有计数”升级为“时序分位与分级水位”；

  3. 指标基数极小（P0~P3 共 4 个 series），对时序库开销几乎为零。
- **弊**：
  - 无负面影响。
