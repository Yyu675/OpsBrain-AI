## 一、背景与决策

既有 RAG 链路是「单层知识库」：所有文档共用一个 `sys_knowledge_doc` 表、
一套硬编码切片参数（父 2400 / 子 600 / 重叠 100 字符），入库只有手工录入
与批量导入（JSON）两条纯文本通道。对标外部 RAG 产品后确认两点可借鉴：

| # | 借鉴点 | 解决的问题 | 决策 |
| - | - | - | - |
| 1 | **多知识库顶层实体 + 按库切片参数** | SOP 长文手册与故障 FAQ 的最优切片粒度不同，全局一套参数必然对其中一类欠优 | ✅ 采纳 |
| 2 | **二进制文档上传解析入库** | 运维存量材料大量是 PDF/Word/Excel，手工复制粘贴入库成本高、且原文格式丢失无法审计 | ✅ 采纳（Tika 解析） |

## 二、决策 1：多知识库 + 按库切片参数

### 2.1 三层结构

```
sys_knowledge_base（新增，切片参数挂载点）
  └─ sys_knowledge_doc.kb_id（新增外键，V2 迁移回填默认库）
       └─ sys_knowledge_chunk.kb_id（新增冗余下沉列）
```

- **默认库 `code=default`**：V2 迁移承接全部存量文档；禁止改 code、禁止停用
  （它是「未指定库的新建文档」的回落键，改了/停了会让这类文档无处落）。
- **不提供物理删库**：删库会让其下文档失去归属。关闭用 `DISABLED`——
  拒收新文档，存量文档仍可检索。

### 2.2 切片参数逐字段回落

`ChunkProfile(parentChunkSize, childChunkSize, overlap)` 为不可变 record，
构造期校验不变量 `parent > child > overlap >= 0`（违反会让切片窗口无法前进）。

库的三个字段**逐字段独立为 null 回落全局默认**——允许只覆盖其中一项
（如只把 FAQ 库的子段落调小），默认值改动时未覆盖字段自动跟随。

### 2.3 kb_id 冗余下沉到 chunk（免 JOIN 保 HNSW）

与 `visibility` 同一理由（V1 已实测过的坑）：检索走 chunk 的 HNSW 向量索引，
过滤字段若只在 doc 表就必须 JOIN，带 JOIN 的 `ORDER BY embedding <=> ?`
会让 PG 放弃 HNSW 退化为全表扫描。**代价**：文档换库后必须重建索引，
否则切片仍挂旧库——`KnowledgeDocService.update` 已把换库纳入重建触发条件。

### 2.4 参数变更不自动重建存量

全库重嵌是付费 API 成本。参数变更只对之后的索引生效；存量生效须显式调
`POST /api/v1/knowledge/bases/{id}/reindex-all`（`requireDestructive` 仅 ADMIN，
逐篇「删旧切片→按库参数重切→向量化→写入」，单篇失败落 FAILED 不阻断，
可经既有 `/docs/reindex/pending` 补偿）。

### 2.5 明确不做（本阶段）

- **检索层暂不按库过滤**：`kb_id` 下沉是为将来「按库限定检索范围」铺路，
  当前检索仍全库。检索过滤上线时需同步考虑 Agent 工具白名单的语义。

## 三、决策 2：二进制文档上传解析

### 3.1 链路

```
安全校验（AttachmentSecurityGuard，白名单/大小/路径穿越，与工单附件同一份实现）
  → Tika 解析出纯文本（ApacheTikaDocumentParser，按内容嗅探不信任扩展名）
  → 原件留存 MinIO 独立桶 devops-knowledge-source
  → KnowledgeDocService.create（清洗/精确去重/SimHash 近似告警/向量化全链复用）
```

### 3.2 关键取舍

- **选 Tika 而非 PDFBox+POI 定向组合**：格式全覆盖
  （PDF/Word/Excel/PPT/TXT/HTML），且是 LangChain4j 原生 `DocumentParser`
  接口，与切片链无缝衔接；独立成 Bean（`DocumentParserConfig`）便于测试 stub。
- **同步处理，不开异步通道**：与手工新建同一链路——发布即触发索引，
  60s 超时与 FAILED 重试状态机天然兜底。
- **解析产物是纯文本**：PDF/Word 的标题层级在解析后丢失，父子切片退化为
  按大小切分——解析管线的固有损耗，检索质量由 L4 相似度熔断兜底。
- **原件留存失败不阻断入库**（Fail-Safe，与 MinioConfig 同哲学）：
  留存是审计增强，对象存储挂掉不应让知识库完全不可写入；
  结果以 `originalStored=false` 如实标记。
- **扫描件（纯图片 PDF）拒绝入库**：解析文本 < 10 字符视为无有效内容，
  如实报错而非存一篇永远检索不到的空文档。

### 3.3 安全面

上传走 `AttachmentSecurityGuard.validate(file, allowedExtensions)` 重载——
工单附件与知识文档的合法类型集合不同（日志/配置 vs PDF/Word），
但路径穿越、双扩展名、大小、畸形名这些攻击面一致，集中一份实现，
白名单作为参数传入。权限：`requireEdit`（ADMIN+OPS，可逆操作）。

### 联调揪出并已修的真问题

1. **MinIO 凭证漂移**：`.env` 的 `MINIO_ACCESS_KEY=devops` 与容器实际
   `devops_minio` 不符——附件桶从某时起就不可用（启动 WARN 无人感知），
   上传原件留存触发了设计好的 Fail-Safe 降级（`originalStored=false` 如实透出）。
   已修正 .env。
2. **增量编译残留导致列表 500**：`spring-boot:run` 在 target/classes 半旧状态下
   启动，列表端点 NoClassDefFoundError。干净重启恢复。
   （教训：验证前必须确认运行实例加载的是当次代码。）
