## 一、用户原话（2026-10-06，大白话记录）

> 洞A 和洞B 其实类似：执行完一条命令，应该**先验证环境是否得到修复和改善，以后才执行下一条命令**。只有这样一步一步执行，才能确保修复方向是正确的。如果一次性全部执行，很难保证方向正确；方向不正确又一次性全量执行，会导致系统出现**无法估量的事故**。

## 二、纲领提炼：两个"洞"是同一件事

此前评估把缺口拆成两个（洞A=执行成功但业务变差、洞B=无金丝雀分批）——**按机制看是同一个缺陷的两面**，统一为一条模式：

**步步执行 · 步步验证 · 验证不过不迈下一步。**

| 维度 | 现状（已上线的 6 层保险） | 纲领要求（V1.3 要补的） |
| :--- | :--- | :--- |
| 验证对象 | **动作完成**（pod Ready=命令成功） | **效果改善**（错误率/连接数/延迟等业务指标真的变好） |
| 执行粒度 | **一次全量**（重启就是全量重启） | **分步推进**（先小比例试水，验过再扩大到全量） |
| 方向错了会怎样 | 动作成功即收场，业务变差无人察觉 | 下一步**不会被触发**；已执行的按策略回撤——事故被锁死在"第一小步"的爆炸半径内 |

**类比**：给病人换药——现在是"药打进去了=成功"；纲领要求"打完第一针先看体征，好转才打第二针，恶化立刻停"。

## 三、实现时的四条硬约束（出方案必须满足）

1. **每步执行后必须验证"业务效果改善"**，验证数据来源=既有监控指标（Prometheus 在栈内，不引新观测面）；
2. **验证通过才自动推进下一步**；验证不过 = **停步 + 回撤已执行步**（回撤复用既有 undo 机制，不新造回滚）；
3. **爆炸半径有上限**：首步比例/数量从保守值起（如 10% 或 1 个实例），扩大级数与等待窗口可配；
4. **全程入既有执行台账**（steps_json 时间线 + 台账九态），每步的验证读数、停步/回撤理由可回放——**可回放是审计与信任升级的凭据**。
