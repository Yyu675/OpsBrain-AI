# 决策：告警工单结构化上下文 + 取证明细回填（工单详情「像 bug 排查报告」）

**日期**：2026-09-30
**状态**：✅ 已落地（方案 A+B 全量 + 第二轮补全，含 V14/V15 迁移）
**来源**：用户反馈——「工单内容只有一两行，不知道具体哪里出了问题；应该像排查
bug 一样先看报错日志、定位到类/方法/行号」。列 A/B/C 三方案，用户拍板 **B 主 + A 从**，
并两轮追加「完善补全没考虑到的方面」。

---

## 一、关键认知（为什么工单以前「薄」）

1. **告警本体有信息上限**：Prometheus 告警 = 指标越限，信息只有 labels + annotations
   （instance/pod/阈值/PromQL），天生没有「哪个类哪个方法哪行代码」——那是应用日志里的东西。
2. **日志证据链原本是断的**：取证链（Loki → LogPatternMiner Top 模式）早已建成，但
   `LOKI_ENABLED` 默认 false、日志证据不进工单侧任何可见位置——值班人在工单里只能
   看到一句结论，证据不足时连 `buildFinalSummary` 承诺的「附已获得的取证记录」都是空话。
3. **9-30 上午 24fc4b2 已把告警上下文写进新单描述**，但缺 JSON 机读块；存量旧单是
   创建时快照、永远停在一行文本（实测最短 4 字符）。

## 二、方案取舍

## 三、落地内容

### A：工单描述结构化

- **新单**（`AlertService.buildTicketDescription`）：核心描述 → 告警元信息 →
  原始标签 → 注解 → `### 结构化上下文（JSON）` 围栏块（全字段 + labels +
  annotations）。时间字段先 `toString()` 再入块——裸 `LocalDateTime` 序列化依赖
  JSR310 模块，非 Spring 装配会把整个 JSON 块打掉。序列化失败只丢块不丢描述。
- **旧单**（`V14__ticket_description_backfill_from_alert.sql`）：从 `sys_alert`
  存量 labels_json/annotations_json 按同模板重建，**36 张薄描述工单已回填**
  （幂等谓词 = 尚无 JSON 块；聚合组多告警挂一单 → `ORDER BY a.id LIMIT 1`；
  jsonb 列比较守卫用 `IS DISTINCT FROM '{}'::jsonb`——**不能拿 `''` 字面量比
  jsonb 列**，PG 会把字面量转 jsonb 直接报错，V14 首次启动就栽在这）。
- **配套**：钉钉通知只带核心描述（结构化全文会淹掉通知卡关键信息）；
  聚合关联留痕带级别 + `@instance`。

### B：取证明细进工单

- **`buildEvidenceDigest`**：逐方向状态（`[type] STATUS：title`）+ 日志 Top-5
  模式（模板/次数/首个样本，类名就在模板里；截断 140/160 字符保界）。
  拼进 summary → **一处拼四处可见**：AI 分析区回填 / 诊断会话落库 /
  钉钉+WS 通知 / 工单活动流。
- **每次诊断完成必写工单活动流**（`recordDiagnosisActivity`，字段注入
  `required=false`）：SUFFICIENT/WEAK → 「AI 诊断完成…」，INSUFFICIENT →
  「AI 诊断结果（证据不足，待人工）」。**遵守批 79 边界**：INSUFFICIENT 仍不进
  AI 分析表（不占版本号），活动流是另一张表；且分析区可能被「近期已有版本」
  跳过，活动流才是取证内容在工单侧的常驻入口。
- **诊断异常路径留痕**（`recordDiagnosisFailureActivity`，第二轮补全）：
  取证链中途崩掉时 `completeSession` 走不到，此前工单时间线上「AI 没查」和
  「AI 查挂了」外观完全一样——现在 catch 里写「AI 诊断执行失败」+ 错误摘要 +
  traceId，诊断链最后一条静默路径被封。
- **`V15__ticket_activity_detail_to_text`**（第二轮实证发现）：
  `sys_ticket_activity.detail` 原 `VARCHAR(512)`，SUFFICIENT/WEAK 的
  明细（方向状态+日志模式+假设+traceId）普遍超长 → INSERT 报
  `value too long` 被 repo 护身 catch 吞成 WARN → **工单时间线静默缺行**。
  扩 `TEXT`（PG 展宽是元数据级、瞬时）。历史丢失的几行不重放——诊断会话/
  证据/分析区都有完整副本，活动流只是第四展示面。
- **Loki 默认启用**（`LOKI_ENABLED` 默认 `false→true`；`.env` 原本已 true；
  compose `logs` profile 注释同步更新）：Loki 缺席时查询如实 FAILED 并在
  取证明细点名（连不上≠查过没有）；不接 Loki 的部署显式 `LOKI_ENABLED=false`
  回到 UNAVAILABLE。看门狗对探测失败本就按未知处理，不误报。
- **日志 pattern 加 `%xEx`**：异常时打印全堆栈（类/方法/行号）——没有它，
  日志模式里只有异常消息行，取证明细定位不到代码行。

### 前端

- `TicketDetail.vue`：工单描述从 `{{ }}` 纯文本改 `v-html="renderMarkdown(...)"`（全局
  `safeMarkdown` 白名单净化入口），补 `:deep` Markdown 子元素样式（标题降级 /
  JSON 块深底代码区）。
- `TicketActivityLog.vue`：活动流 `.activity-text` 加 `white-space: pre-wrap` +
  `overflow-wrap: anywhere`——多行取证明细不加 pre-wrap 会挤成一行墙字，
  长哈希/LogQL 需要强制断行。
- `KnowledgeSinkDrawer.vue`（第三轮下游卫生）：沉淀给 LLM 的源文本里
  ① 描述剥掉结构化 JSON 块（正文段已含同信息，带块=描述烧两遍 token）；
  ② 活动明细压平换行 + 200 字截断——源文本结构约定是「一条活动一行」，
  V15 后的多行明细会打散它。测试钉住两个行为。
