## 一、总体判断：这个项目的真实水位

先说结论，避免下面的问题清单造成误判：

**这不是一个烂项目。恰恰相反，它的代码质量明显高于典型的应届生作品。**

审查中反复看到这类注释：

> `// P2-25：SSE 断开时通知 Agent 服务取消流式执行，防止后端继续跑完模型流并写库建单。`
> `// 正常完成不取消：取消标记已由 streamAgent 轮询循环 finally 清理，此处再调 cancelStream 会重建标记导致残留（P2-23 教训）。`
> `// 配额 key 必须在此解析——当前仍是 Controller 请求线程，Sa-Token 登录上下文（ThreadLocal）可用。下方 runAsync 一旦切到 sessionExecutor 虚拟线程，StpUtil.isLogin() 就取不到登录态了。`

这些是**真正踩过坑之后才写得出来的东西**。SSE 取消传播、虚拟线程下的 ThreadLocal 失效、`KEYS` 换 `SCAN`、SHA-256 做 Redis key、DOMPurify 全局唯一入口 + tabnabbing 防护 —— 这些细节很多三五年经验的工程师都不会主动处理。

**那么问题在哪？**

问题在于：**这个项目的"深度"远超它的"地基"。**

| 维度 | 水位 |
| :-- | :-- |
| 单点技术深度（RAG/Agent/SSE/缓存） | **高**（超出应届水平） |
| 异常路径考虑 | **高**（审计铁律、降级、补偿都有） |
| **工程地基（CI/测试/可观测/部署）** | **接近于零** |
| **生产就绪度** | **低**（3 个 P0 缺陷，单机内存态假设） |

打个比方：**你造了一台调校精密的发动机，但车没有仪表盘（无 traceId 日志）、没有刹车测试（无 CI/无后端测试）、油箱有个洞（内存泄漏）。**

所以下面的路线规划，核心逻辑就一句话：**先补地基，再谈优化。**

## 二、审查发现的问题清单（14 项，附文件行号）

### 🔴 P0 —— 会导致生产事故，必须优先修

#### P0-1：`InMemoryChatMemoryStore` 永不清理 → **必然 OOM**

**位置**：`infrastructure/AgentEngineConfig.java:96`

```java
@Bean
public ChatMemoryStore chatMemoryStore() {
    return new InMemoryChatMemoryStore();   // ← 进程内 Map，按 memoryId 无限增长
}
```

**问题**：LangChain4j 的 `InMemoryChatMemoryStore` 内部是一个 `ConcurrentHashMap<Object, List<ChatMessage>>`。每个新 `sessionId` 都会插入一个条目，**而项目中没有任何地方调用 `deleteMessages(memoryId)`**。我验证过：

- `AgentStateManager` 有 30 分钟空闲驱逐 ✅（`AgentStateManager.java:94`）
- `HotMemoryStore`（Redis）有 TTL 滑动续期 ✅
- `AgentMemoryManager.evict()` 只清 Redis 热记忆（`AgentMemoryManager.java:204`）
- **`chatMemoryStore` 无任何驱逐路径** ❌

更糟的是 `DevOpsChatController.doStream()`：`sessionId` 为空时**退化为 `sessionId = traceId`**，而 `traceId` 是 `UUID.randomUUID()` —— 意味着**每一次匿名单轮对话都会在 map 里永久插入一个新条目**，每个条目最多 20 条消息（`maxMessages`）。

**量化影响**：假设单条消息平均 500 字符（运维场景常粘贴日志，实际会更大），一个会话满窗 20 条 ≈ 20KB。日活 1000 次对话 → 每天泄漏约 20MB，**且永不释放**。一周 OOM，一个月必挂。

**修复**：给 `ChatMemoryStore` 包一层带 TTL/LRU 的实现（Caffeine `expireAfterAccess(2h)` + `maximumSize`），或在 `AgentStateManager.evictIdleSessions()` 里同步调 `chatMemoryStore.deleteMessages(sessionId)`。**后者改动最小（约 10 行），推荐先做。**

> 注意：`AgentEngineConfig` 的注释自己写了「适用于单实例部署，分布式部署时可替换为 Redis backed store」—— 但**单实例同样会 OOM**，注释低估了问题。这不是分布式问题，是生命周期管理缺失。

#### P0-2：SSE 60s 超时 < 推理模型 120s 超时 → **复杂问题必然超时失败**

**位置**：`DevOpsChatController.java:109` vs `AiModelConfig.java:100,141`

```java
// Controller
SseEmitter emitter = new SseEmitter(60000L);          // 60 秒

// AiModelConfig（reasoner 与 reasonerStreaming 都是）
.timeout(Duration.ofMillis(timeout * 2))              // 60000 * 2 = 120 秒
```

**问题**：SSE 连接 60 秒就超时，而推理模型（`qwen-max`，专门用于复杂堆栈分析）允许跑 120 秒。**任何耗时超过 60 秒的推理请求，用户端 100% 收到「连接超时」**，而后端模型还在继续跑（虽然 `onTimeout` 会调 `cancelStream`，但已产生的 token 成本已经发生）。

这直接命中你的核心卖点场景：README 说「复杂堆栈问题走 reasoner 模型」—— 而这恰恰是最容易超过 60 秒的场景。

**加重因素**：Spring MVC 还有一个 `spring.mvc.async.request-timeout`，我 grep 过**未配置**（默认取决于容器，Tomcat 通常 30s 或不限）。三个超时值（SSE 60s / 模型 120s / MVC async 未设）互不协调。

**修复**：确立超时层级 `SSE > MVC async > 模型总超时 > 单次模型调用`。建议：
```yaml
spring.mvc.async.request-timeout: 180000    # 180s
devops.ai.sse.timeout-ms: 150000            # 150s，SseEmitter 读它而非硬编码
devops.ai.alibaba.timeout: 60000            # turbo 60s / reasoner 120s（现状）
```
并且**加心跳**：SSE 长时间无数据时，代理层（Nginx）也可能断连。每 15 秒发一个 `:heartbeat` 注释帧。

#### P0-3：`CostQuotaManager` 配额是**单机内存态** → 多实例失效 + 重启清零

**位置**：`application/runtime/CostQuotaManager.java:84,~150`

```java
private final Map<String, UserQuotaUsage> userQuotas = new ConcurrentHashMap<>();
private volatile LocalDateTime lastResetTime = ...;
```

**问题（三重）**：
1. **进程重启配额清零** —— 用户跑满日额度，重启服务即可重新开始烧钱；
2. **多实例部署完全失效** —— 两个 Pod 各记各的，实际额度 = 配置值 × 实例数；
3. **`resetDailyIfNeeded()` 是惰性触发**（只在 `preCheck`/`recordUsage` 里调），若某天完全无请求，`lastResetTime` 不推进，跨多天后的重置逻辑需要仔细验证边界。

这是「**成本熔断机制本身不可靠**」—— 而成本控制是你 README 的核心卖点之一（"单用户花费降低超 70%"）。

**修复**：配额状态迁到 Redis（`INCRBYFLOAT` + `EXPIREAT` 到当日 24 点，天然日重置、天然跨实例）。改动约 60 行，且 `HotMemoryStore` 已经有 Redis 操作范式可直接参照。

> 顺带：`CostQuotaManager` 的类注释里有个 `TODO(P2-鉴权)` 说「当前 userId 由调用方传 sessionId 过渡」。但我在 `DevOpsAgentServiceImpl.java` 看到 `resolveQuotaKey(sessionId)` 已经"优先 userId 回退 sessionId"，说明鉴权已落地。**这个 TODO 已过期，注释与代码不一致，容易误导后续开发（包括 AI）。**

### 🟠 P1 —— 安全与架构缺陷，两周内修

#### P1-1：知识库**完全没有权限模型** → 越权读取

**证据**：
```bash
grep -n "visibility|permission|ownerId|tenant|scope|role" domain/rag/KnowledgeDoc.java
# → 零命中
grep -n "userId|permission|filter" domain/rag/HybridRetrieverService.java
# → 零命中
```

`KnowledgeDoc` 的字段只有 title/category/author/content/status/tags 等，**没有任何可见性或归属字段**。检索服务也不做任何用户维度过滤。

**影响**：任意登录用户可以检索到**全部**知识库内容。对"企业级私有化知识库"这个定位，这是硬伤 —— 真实企业里，财务系统的运维手册不该被实习生检索到。

**更隐蔽的路径**：即使前端隐藏了某些文档，**用户仍可通过 AI 对话间接套出内容**（"帮我查一下核心交易库的主从切换步骤"）。RAG 场景下，权限必须在**检索层**做，不能只在 API 层做。

**修复**：`knowledge_doc` 加 `visibility`（PUBLIC/INTERNAL/RESTRICTED）+ `owner_dept`，检索 SQL 带上当前用户的可见范围过滤。这也是 L3+ 商业化的前置条件。

#### P1-2：语义缓存**无用户/权限隔离** → 跨用户信息泄漏

**位置**：`SemanticCacheService.java:165,391`

```java
public String tryHitCache(String userQuery) { ... }
private String answerKey(String userQuery) {
    return ANSWER_KEY_PREFIX + sha256(userQuery);   // ← key 只含问题内容
}
```

**问题**：缓存 key 只由问题文本决定，**与用户身份无关**。结合 P1-1（知识库无权限），一旦将来加了权限：用户 A（高权限）问「核心库主从切换步骤」→ 答案含机密内容进缓存；用户 B（低权限）问同样问题 → **直接命中缓存拿到机密答案，绕过所有权限检查**。

即使不加权限，也有另一个问题：**相似度 0.85 阈值的语义匹配 + 跨用户共享**，意味着 A 的问题里如果带了具体主机名/IP/工单号，B 可能拿到含 A 上下文的答案。

**修复**：key 加权限维度（不是加 userId —— 那会让命中率归零）。正确做法是 `sha256(query) + ":" + permissionScopeHash`，同权限域内共享缓存。

#### P1-3：`@Transactional` 写在 Controller 层（分层违规 + 事务边界错误）

**位置**：`controller/KnowledgeTagController.java:45,58,68`（3 处）

```java
@Transactional          // ← 在 Controller 上
public ApiResponse<...> xxx(...) { ... }
```

**问题（两个）**：
1. **违反你自己的分层规范**。`docs/02-architecture-design/后端干净架构与分层职责规范书.md` 明确规定 Controller 只做 HTTP 适配。全项目 19 处 `@Transactional`，只有这 3 处在 Controller，**是明显的破窗**。
2. **事务边界过大**。Controller 方法里通常包含参数校验、DTO 转换、响应组装 —— 这些都被圈进事务，**数据库连接被无谓持有**，高并发下连接池会更早耗尽。

**修复**：下沉到 `KnowledgeTagService`。改动很小（约 20 行），但象征意义大 —— 破窗必须补，否则规范就是废纸。

#### P1-4：Maven Wrapper 脚本缺失 → **仓库无法开箱构建**

**证据**：
```bash
ls -a | grep mvn
# → 只有 .mvn/     （mvnw 和 mvnw.cmd 都不存在）
cat .mvn/wrapper/maven-wrapper.properties
# → distributionType=only-script    ← 明确声明依赖 mvnw 脚本
```

`.mvn/wrapper/maven-wrapper.properties` 存在且 `distributionType=only-script`，但**根目录的 `mvnw` / `mvnw.cmd` 两个脚本文件都不在仓库里**（很可能被 `.gitignore` 误伤，或从未提交）。

**影响**：任何人 clone 你的仓库（**包括面试官**）都无法用 `./mvnw` 构建，必须自己装对应版本 Maven。这对求职作品是直接减分 —— "clone 下来跑不起来"是最糟的第一印象。

**修复**：`mvn wrapper:wrapper -Dmaven=3.9.16` 重新生成并提交，检查 `.gitignore` 是否排除了 `mvnw`。**成本 5 分钟，但影响很大。**

#### P1-5：无 API 限流 + `/alerts/webhook` 免鉴权（上轮已提，此处补充新证据）

补充发现：`/api/v1/chat/stream` 的 **POST 版本走 `@RequestBody`，无长度上限校验**（只在 `SecurityInputGuard` 里校验 1~1500 字，但那是进入 Agent 之后）。配合 `spring.servlet.multipart.max-request-size: 20MB`，攻击者可发 20MB 的 JSON body 打满内存。

## 三、技术栈评估：**一个都不要换**

我逐项评估了是否有更换必要，结论是**全部保留**：

| 技术点 | 是否更换 | 理由 |
| :-- | :-- | :-- |
| Spring Boot 3.5 + Java 21 | ❌ 不换 | 已用上虚拟线程（`Thread.ofVirtual()`），选型现代且正确 |
| LangChain4j 1.1 | ❌ 不换 | Java 生态的 Agent 框架事实标准，且你已用 BOM 统一版本 |
| PostgreSQL + pgvector | ❌ 不换 | 对这个数据量（企业内部知识库）**完全够用**。上专用向量库（Milvus/Qdrant）是过度设计，还会引入运维复杂度和一致性问题 |
| JPA + JdbcTemplate 混用 | ❌ 不换 | 实体 CRUD 用 JPA、聚合统计用 JdbcTemplate 是**正确的工程判断**，不是混乱 |
| Sa-Token | ❌ 不换 | 比 Spring Security 轻量，对单体项目更合适。SSE 场景已处理好（fetch-event-source 带自定义头） |
| Vue 3 + Element Plus | ❌ 不换 | 换 React/Tailwind 是重写，收益为零 |
| TanStack Query | ❌ 不换 | 已是最优解，且你用得很规范 |
| Vite 8 + npm | ❌ 不换 | 换 Bun/Rsbuild 是纯成本 |

**唯一的"技术点实现方式"需要改的 4 处**（注意：是改实现，不是换技术）：

1. `InMemoryChatMemoryStore` → **Caffeine TTL 包装** 或接入驱逐（P0-1）
2. `CostQuotaManager` 内存 Map → **Redis 计数器**（P0-3）
3. SSE 硬编码 60s → **配置化 + 三层超时对齐 + 心跳**（P0-2）
4. Controller 层 `@Transactional` → **下沉 Service**（P1-3）

> **给你一个判断标准**：换技术栈的唯一正当理由是"现有技术无法满足需求"。你目前所有问题都是**实现细节问题，不是选型问题**。应届生作品最忌讳的就是"为了简历好看而堆技术"，面试官一眼就能看穿。**把现有栈用到极致，比堆五个新框架有说服力得多。**

### 4.2 断裂的链路：3 条 ❌

| 断裂点 | 说明 |
| :-- | :-- |
| **权限链路** | 用户有 role/permission（Sa-Token 已落地）→ **但知识库检索不消费它**。权限信息在 API 层就停住了，没有贯穿到数据层 |
| **成本链路** | 有配额管理器、有单价配置、有 `recordUsage` → **但状态在内存，重启即失效**，且没有成本数据的可视化出口（Dashboard 无成本面板） |
| **可观测链路** | 有 traceId 字段、有 AgentCallLog 落库 → **但日志里没有 traceId**（未接 MDC），且**两套 traceId 生成逻辑长度不一致**（8 位 vs 32 位）。链路"有数据但连不起来" |

### 4.3 L2+ 演进的前置缺口

你规划了 L2（实时监测）→ L5（全自动自愈）。以当前地基评估：

| 演进阶段 | 前置缺口 |
| :-- | :-- |
| L2 实时监测 | webhook 无鉴权无限流（P1-5）→ **告警风暴会直接打挂系统**，必须先修 |
| L3 智能分级 | 无统一审计中间件（只有工单域有 TicketActivity）→ **AI 自动决策无法追溯** |
| L4 半自动自愈 | 无权限模型（P1-1）→ **无法界定"AI 能操作哪些资源"** |
| L5 全自动 | 配额单机内存（P0-3）→ **成本熔断不可靠时，绝不能给 AI 自动执行权** |

**换句话说：P0/P1 这些问题不修，L2 都上不去。** 它们不是"优化项"，是"演进的前置条件"。

### ⚠️ C1 的已知局限（必须知晓）

AI 对话链路的知识检索**目前恒为「仅 PUBLIC」**。
原因：工具运行在模型 HTTP 回调线程，取不到 ThreadLocal 中的 scope
（项目已有同类记录：`ToolRuntimeManager` 在该线程同样取不到 traceId）。

这是**刻意选择的失败方向**——两种失败代价不对称：
- 取不到就放行 → 权限在最关键的 AI 链路上静默失效，越权无声无息；
- 取不到就收紧 → 最坏是 AI 答不出受限内容，用户会反馈，问题会暴露。

代价是 ADMIN 在对话中同样查不到受限文档。彻底解决需改为
「每请求构建 AiService 实例」或使用 LangChain4j 的工具上下文透传，
不能靠 ThreadLocal。已登记 AGENTS.md，列入阶段 D。
