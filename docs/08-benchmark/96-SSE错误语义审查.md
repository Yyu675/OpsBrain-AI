## 二、缺陷 1：SSE 错误事件丢弃 `code`

### 成因

后端 `sendErrorEvent` 下发 `{traceId, code, message}`，code 来自 `BizError`。
但前端两处消费方的 `onError` 都是：

```ts
chat.finishStreaming(`❌ ${data.message || '请求失败'}`)
```

**`data.code` 整个不用。**

于是同一个错误在两条路上呈现完全不同：REST 侧走 `getBizError()` 查表，
用户能看到「下一步做什么」；SSE 侧只有后端那句 message。

### 用户可见后果（已量化）

SSE 侧会下发 8 个码，其中 **3 个是可重试的**：

| 码 | 名称 | Retry |
|---|---|---|
| `50002` | SSE_CONNECTION_ERROR | **SAFE** |
| `50001` | INTERNAL_ERROR | **SAFE** |
| `42901` | RATE_LIMITED | **BACKOFF** |
| 40001 / 40003 / 40005 / 40006 / 40301 | 其余 | NEVER |

丢弃 code 等于**把 `BizError` 里精心标注的 Retry 语义在主链路上全部作废**。

最典型的一处：`DevOpsChatController` 下发 `SSE_CONNECTION_ERROR` 时
message 只有**「连接超时」四个字**。它重试就能好，
用户却完全看不出这一点，多半以为服务坏了就走了。

而 SSE 是本产品的**主链路**——AI 问答全走它。

### 修复

`bizCode.ts` 新增 `toStreamError(code, message, fallback)`，
与 REST 侧查同一张 `BIZ_ERRORS` 表。三个设计取舍：

1. **hint 拼进对话气泡正文，而非只放 toast**——气泡会留在页面上，
   toast 几秒就消失，用户回头看不到该怎么办；
2. **文案优先级：后端 message 优先**（常带上下文，如具体的配额原因），
   码表 title 兜底。message 用 `trim()` 判空——后端偶尔下发 `"  "`，
   直接 `||` 不会回落，用户看到一片空白；
3. **title 取码表短标题供 toast 用**，与含 hint 的 text 分工。

## 三、缺陷 2：流中途出错时已生成内容被抹掉

### 成因

`chat.finishStreaming(errorText)` 的实现是 `msg.content = errorText`——**整体覆盖**。

而同一个文件里另外两条收尾路径都是**保留**的：

| 路径 | 做法 |
|---|---|
| `onClose`（服务端断流） | `${partial}\n\n_（连接已中断，以上为已生成内容）_` |
| `stopGeneration`（用户点停止） | `${partial}\n\n_（已停止生成）_` |
| **`onError`** | **`❌ ${errorText}` 直接覆盖** |

三条路径两种做法，唯独 `onError` 抹掉——**这是不一致，不是有意设计**。

### 用户可见后果

模型答了半页诊断思路或半段命令，中途报错（50001、50002 都会走这里），
那半页被一句错误提示整个替换。而它往往已经有用，用户还没来得及复制。
**运维排障场景下这半页可能就是当时最需要的线索。**

### 修复

保留 partial，错误提示以分隔线追加在后面；
无 partial 时只显示错误，不留 `\n\n---\n\n` 开头的残迹。

`KnowledgeSinkDrawer.vue` 侧本来就是 `+=` 追加（正确），无需改动——
修复后两处终于一致。

## 五、一个夹具坑

`SSETokenEvent` 的字段名是 `text` 而非 `content`。
我第一版夹具写成 `content`，`appendToken` 收到 `undefined`，
断言「内容被保留」反而红了——**看起来像产品代码有问题，实则是夹具错**。

这与 92 号记的「CI 红了也不等于产品代码有问题」同型，
但这次是在本地发现的，代价只有一次重跑。已在测试里注释说明。

> 补一条操作层面的判据：断言失败信息里出现 `undefined` 时，
> 先怀疑夹具的字段名，而不是产品代码的逻辑。

## 六、下一步建议修复思路

### 立即可做（下轮首选）：`http.ts` 与 `BIZ_ERRORS` 的两套文案合并

95 号已列为中期候选，本轮的经历让它的优先级上来了——
**本轮就撞见过这两套文案互相矛盾**（40004 在 `bizCode.ts` 里是
「当前状态不允许该操作」，在 `http.ts` 里是「数据不存在」）。

现状：`utils/http.ts` 的 `toFriendlyError` 对
40001 / 40004 / 40009 / 40021 有**硬编码分支**，
而 `bizCode.ts` 已有覆盖 23 个码的完整文案表。

**做法**：让 `http.ts` 统一走 `getBizError()` 查表。
但**不是纯机械替换**——有些分支的措辞是刻意区分的
（如 40009 在 `http.ts` 里说「你的编辑基于旧版本」，比码表的
「请刷新页面查看最新内容」更具体）。需要逐条核对：
措辞更好的应该**回填到码表**，而不是丢掉。

预期产出：`http.ts` 只保留查表 + 兜底，四个硬编码分支消失；
码表文案得到增强；加一条契约测试禁止再在 `http.ts` 里写码分支。

### 中期候选

1. **日志脱敏契约固化**。94 号已扫完给出结论（574 条日志、3 处含敏感字段名、
   全部安全），只差把扫描规则写成测试。成本低，防的是 83 号那类重演。
   连续两轮列为候选未做，建议下下轮清掉。
2. **SSE `complete` 事件的字段契约**。本轮只审了 error 路径。
   `complete` 带 `costRmb`/`toolResults`/`citations`，
   前端 `ChatMode` 对它们做了不少解析（如识别 `createDevOpsTicket` 工具结果），
   这些字段名前后端是否有契约保护？值得一查——
   字段改名不会有编译错误，只会静默失效。

### 明确不做

- **给 SSE 加自动重试**。`toStreamError` 已返回 `retryable`，
  看起来「顺手就能自动重投一次」。不做的理由：AI 问答有成本
  （每次调用都计费、都占配额），自动重试等于用户不知情地花两份钱；
  且流式请求可能已经产生了部分输出，重试会让对话里出现两段半截回答。
  正确的做法是**把重试的决定权交给用户**——这也是本轮只做「提示可重试」
  而不做自动重试的原因。
