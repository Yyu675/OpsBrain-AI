### 2.3 建议索引（2 个）

#### P1: 看板最近告警热查索引
```sql
-- 覆盖 findRecentFiring: WHERE status='FIRING' ORDER BY created_at DESC LIMIT 100
CREATE INDEX idx_alert_firing_recent 
  ON sys_alert (status, created_at DESC) 
  WHERE status = 'FIRING';
```
**收益**: 看板「最近触发」查询从 SeqScan → Index-Only Scan（status 过滤 + 排序一步到位）

#### P2: 告警分组关联工单索引
```sql
-- 覆盖 findActiveGroupTicket: WHERE service=? AND module=? AND status IN(...) AND ticket_id IS NOT NULL
CREATE INDEX idx_alert_group_linked 
  ON sys_alert (service, module, status, ticket_id) 
  WHERE ticket_id IS NOT NULL;
```
**收益**: 现有 idx_alert_service_module_status (service, module, status) 只覆盖前三列，ticket_id 过滤需回表 → 四列联合索引避免回表

```sql

  ON sys_diagnosis_session (status, created_at ASC) 
  WHERE status = 'QUEUED';
```
**收益**: DiagnosisQueueScheduler 60s 扫描从 SeqScan → Index-Only Scan（批76 P2-3 引入的排队机制核心查询）

#### P2: 告警诊断历史全态索引
```sql

```
**收益**: 现有 idx_dsession_alert_running 部分谓词索引只覆盖进行中/排队中，查询历史会话（COMPLETED/FAILED/REJECTED）需全表扫 → 无谓词全列索引覆盖所有状态

### 4.3 建议索引（2 个）

#### P1: 审批僵尸单扫描器索引

```sql
CREATE INDEX idx_approval_zombie_scan 
  ON sys_approval_request (status, update_time) 
  WHERE status = 'APPROVED';
```
**收益**: ApprovalExpireScheduler.scanAndRecoverZombies() 从 SeqScan → Index Scan（批76 P2-2 引入）

#### P2: 待审批列表倒序索引
```sql
-- 覆盖 findPendingApprovals / findByStatus: WHERE status=? ORDER BY create_time DESC
-- 替换现有 idx_approval_status_time (status, create_time ASC)
DROP INDEX IF EXISTS idx_approval_status_time;
CREATE INDEX idx_approval_status_time_desc 
  ON sys_approval_request (status, create_time DESC);
```
**收益**: 审批列表分页查询（前端「待处理」Tab）ORDER BY DESC 从 backward scan → forward scan

**问题汇总**:
- **P1 慢查**: `findByAssignee` (assigned_to + ORDER BY created_at DESC) —— 前端「我的工单」Tab 核心查询，ORDER BY 回表排序
- **P2 优化**: `findByStatus` (status + ORDER BY id DESC) —— 前端「按状态筛选」分页，ORDER BY 主键回表（但主键排序成本相对低）
- **P3 全文检索**: `searchTickets` —— 多列 LIKE OR 条件，现有 B-tree 索引无法覆盖，需引入全文检索（PostgreSQL `tsvector` + GIN 索引，或外部 Elasticsearch）

### 5.3 建议索引（2 个）

#### P1: 我的工单列表索引
```sql

CREATE INDEX idx_ticket_assignee_time 
  ON devops_ticket (assigned_to, created_at DESC);
```
**收益**: 前端「我的工单」Tab 从回表排序 → Index-Only Scan（高频查询）

#### P2: 状态分页优化索引（可选）
```sql
-- 覆盖 findByStatus: WHERE status=? ORDER BY id DESC
CREATE INDEX idx_ticket_status_id 
  ON devops_ticket (status, id DESC);
```
**收益**: 前端「按状态筛选」分页从回表排序 → Index Scan（主键排序成本已低，此索引为锦上添花）

## 七、遗留问题与后续方向

### 7.1 遗留问题
1. **全文检索缺失**: `searchTickets` 多列 LIKE OR 无法用 B-tree 索引覆盖，需引入 PostgreSQL `tsvector` + GIN 索引或 Elasticsearch
2. **全表计数优化**: `countAll` / `countActive` 类查询在大表场景（10 万+）依然需全表扫，可考虑维护计数器缓存（Redis）或物化视图
3. **慢查询监控缺失**: 当前仅静态审计，缺生产环境慢查询日志采集与分析（pg_stat_statements 扩展）

### 7.2 后续方向
- **方向2**: 前端列表虚拟化与懒加载（批 81）
- **方向3**: 缓存分层策略（热数据 Redis、冷数据 DB，批 82）
- **方向4**: 慢查询监控接入（pg_stat_statements + Prometheus exporter，批 83）
