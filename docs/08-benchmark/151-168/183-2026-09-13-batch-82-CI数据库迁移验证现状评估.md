## 一、现状评估：已有防护

### 1.1 CI 流程中的 Flyway 验证（已存在 ✅）

**位置**：`.github/workflows/ci.yml` 第 74-98 行

**步骤名称**：「迁移校验与空库全量建账」

**执行逻辑**：
```yaml
- name: 迁移校验与空库全量建账（Flyway migrate+validate，路线图步骤 0-1.6/0-1 验收）
  run: |
    # 1. 创建独立验证库
    PGPASSWORD=devops_password psql ... -c "CREATE DATABASE flyway_ci_scratch;"
    
    # 2. 执行 Flyway 迁移
    ./mvnw -B -ntp flyway:migrate \
      -Dflyway.url=jdbc:postgresql://localhost:25432/flyway_ci_scratch
    
    # 3. 执行 Flyway 校验（checksum 验证）
    ./mvnw -B -ntp flyway:validate \
      -Dflyway.url=jdbc:postgresql://localhost:25432/flyway_ci_scratch
    
    # 4. 验证表数量 >= 33（V1 基线全量建表）
    TABLES=$(psql ... -c "SELECT count(*) FROM information_schema.tables ...")
    [ "$TABLES" -ge 33 ] || { echo "::error::..."; exit 1; }
```

**覆盖范围**：
- ✅ **迁移完整性**：空库全量执行 V1__baseline.sql，验证 33 张表全部创建
- ✅ **checksum 一致性**：flyway:validate 检测迁移脚本是否被意外修改
- ✅ **隔离性**：使用独立的 `flyway_ci_scratch` 库，与后续测试库物理隔离
- ✅ **失败回帖**：失败时通过 `gh api` 回帖到 commit，取证 Flyway 日志（第 99-112 行）

## 二、用户新策略的影响分析

### 2.1 策略变更：所有变更追加至 V1__baseline.sql

**影响**：
- ⚠️ **checksum 变更频繁**：每次追加索引/表/列，V1 文件 checksum 都会变化
- ⚠️ **Flyway validate 会失败**：已应用 V1 的数据库会检测到 checksum 不匹配

### 2.2 现有 CI 流程的适配性

**好消息**：✅ **CI 流程完全适配新策略**

**原因**：
1. **每次 CI 都从零开始**：
   - `CREATE DATABASE flyway_ci_scratch` 创建空库
   - 空库首次执行 V1__baseline.sql，不存在 checksum 冲突
   - 验证的是「最新 V1 能否在空库上正确执行」，而非「增量迁移」

2. **测试库同样从零开始**：
   - 第 114-123 行「初始化数据库 Schema」直接执行 V1__baseline.sql
   - `@SpringBootTest` 测试的是「最新 Schema + 应用代码」的兼容性
   - 不涉及已存在数据库的迁移升级

3. **隔离性保障**：
   - Flyway 验证库 `flyway_ci_scratch` 与测试库 `devops_knowledge_db` 隔离
   - 每次 CI 跑完即销毁（GitHub Actions runner 生命周期结束）

**结论**：
- ✅ **CI 流程无需修改**
- ✅ **每次 CI 都是「V1 基线完整性验证」，与追加策略天然匹配**
- ✅ **失败回帖机制已就绪**（批 64 引入）

## 三、风险点与防护建议

### 3.1 风险：生产环境 checksum 冲突

**场景**：
```
1. 生产库已应用 V1__baseline.sql（版本 A）
2. 开发者追加批 80 索引至 V1__baseline.sql（版本 B）
3. 生产环境重启应用 → Flyway 检测到 V1 checksum 变化 → 启动失败
```

**现有防护**：
- ⚠️ **应用启动配置**：`validate-on-migrate: true`（批 69 设置）
  - 启动时会执行 checksum 校验
  - 检测到不匹配会**阻止应用启动**

**推荐方案**：
1. **开发/测试环境**：直接重建库（报告 182 方案 A）
2. **生产环境**：手动执行增量 SQL + 修复 Flyway 元数据

### 3.2 防护：生产部署 Checklist

**建议创建**：`tools/deploy/prod_migration_checklist.md`

**内容**：
```markdown
# 生产环境数据库变更 Checklist

## 前置条件
- [ ] CI 绿灯（Flyway migrate+validate 通过）
- [ ] 本地测试环境验证变更
- [ ] 备份生产数据库

## 方案 A：重建库（首次部署 / 可接受停机）
1. 备份：`pg_dump > backup_$(date).sql`
2. 停止应用：`docker-compose down -v`
3. 重启：`docker-compose up -d`（Flyway 自动执行 V1）

## 方案 B：增量变更（已有数据 / 最小化停机）
1. 手动执行新增 SQL（V1 diff 出的增量语句）
2. 修复 Flyway 元数据：
   UPDATE flyway_schema_history 
   SET checksum = <新checksum> 
   WHERE version = '1';
3. 验证：重启应用，观察启动日志
```

### 3.3 监控：Flyway 健康度

**建议接入 Prometheus 指标**（方向 2 监控增强）：

## 四、CI 流程优化建议（可选）

### 4.1 增强：索引创建性能验证

**目标**：验证新增索引的创建耗时，防止生产环境阻塞

**实现**：
```yaml
- name: 索引创建性能基线验证
  run: |
    # 1. 在 flyway_ci_scratch 库测量索引创建时间
    START=$(date +%s)
    PGPASSWORD=devops_password psql -h localhost -p 25432 -U devops \
      -d flyway_ci_scratch \
      -c "EXPLAIN ANALYZE CREATE INDEX idx_test ON devops_ticket(id);"
    END=$(date +%s)
    DURATION=$((END - START))
    
    # 2. 超过阈值（如 30s）则警告
    if [ $DURATION -gt 30 ]; then
      echo "::warning::索引创建耗时 ${DURATION}s，生产环境请评估停机窗口"
    fi
```

**成本**：约 10 行配置，可选增强

### 4.2 增强：迁移脚本静态扫描

**目标**：检测 SQL 脚本常见问题（如缺少 `IF NOT EXISTS`）

**工具**：`sqlfluff` 或自定义脚本

**示例**：
```yaml
- name: SQL 迁移脚本静态扫描
  run: |
    # 检查所有 CREATE INDEX 是否包含 IF NOT EXISTS
    if grep -E "CREATE INDEX [^;]+" src/main/resources/db/migration/*.sql | grep -v "IF NOT EXISTS"; then
      echo "::error::检测到未使用 IF NOT EXISTS 的索引创建，可能导致重复执行失败"
      exit 1
    fi
```

**成本**：约 5 行配置，可选增强
