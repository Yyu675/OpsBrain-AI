## 一、T6 告警风暴压测(`scripts/loadtest-alert-storm.sh`)

**实测数字(100 条/秒 × 10 秒 = 1000 条)**:
- **P95 = 22ms**(判据 < 500ms,余量 23 倍)——webhook 接收链路风暴下不阻塞
- HTTP 200=484 / 429=516 / **5xx=0 / 连接失败=0**
- 入库 574 条(DB 直查口径)零丢失;幂等重发 20 条不增行
- **风暴聚合抑制实证**:574 条风暴 → 0 新增工单(同 service+module 5min 窗口全关联既有组单——6.58 降噪设计风暴场景实证)

**途中辨明的一个设计语义(判据反转)**:首轮判「429=误伤」是错的——429 来自 `WebhookGuard` **有意防风暴闸**(`devops.alert.webhook.rate-limit:300/60s`,A6 修复设计在案):429+Retry-After 让 Alertmanager 退避重投,与「Prometheus 非 200 即重试」契约自洽。**悄悄丢弃告警比慢一点收到危险得多**(WebhookGuard javadoc 原文)。判据修正为「触闸=设计生效实证」。

**脚本两处自纠**:①API total 差值口径被 65s 窗口等待期的历史入库污染(BEFORE 取样晚于部分入库)→ 改 DB 直查(LoadTestStorm 专属前缀+压测开始时刻);②P95 采样改 200 样本集。

1. **`pg_dump` 缺 `--clean --if-exists`**——恢复时 `CREATE flyway_schema_history` 撞已存在对象,`ON_ERROR_STOP` 在第一条 CREATE 即中止,**业务表全部没恢复**。教训:全量备份的恢复语义必须演练实测——pg_dump 默认产物假设目标库是空的,而真实故障恢复的目标库几乎必然残留半套对象。
2. psql `-cA -c` 参数错位(每表一条 ERROR 噪声)。
3. 演练破坏 `sys_user` 后登录全 401——重启后端 `AuthDataInitializer` 自动补种(顺带验证其幂等性)。
