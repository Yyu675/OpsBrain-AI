## 三、429 假红根因与修复(件 2)

**因果链**:共享上下文的 5 个 `@SpringBootTest` 集成类,每个用例都真实登录 → 同 IP(127.0.0.1)同桶 60 秒窗口内累计远超 10 次 → 后续登录全部 429 → 断言 `expected 200 but was 429` 失败写进 surefire XML → GitHub 从上传的测试报告 artifact 自动提取成 annotations。**本地复现**:三类连跑 10 失败(ChatStreamSse 2 + Governance 8),与 CI annotations 完全吻合。

**修复**:`AuthLoginChain`/`ChatStreamSse`/`ChatStreamSseTimeout`/`GovernanceRoleGuard`/`AlertWebhookChain` 五个集成类加 `@TestPropertySource(properties = "devops.security.rate-limit.enabled=false")`。判据:限流滤件防的是**外部恶意流量**,测试上下文的 127.0.0.1 登录不是它的保护对象;`RateLimitFilterTest` 用自建 properties 直测 Filter 不经 Spring 上下文,限流行为本身的测试保护**零损伤**。**修复后五类连跑 42/42 全绿**(修复前同场景 10 失败)。

## 四、SilentCatch 漂移修复(件 3)

- `BusinessMetrics.safe()`(批 48/49)吞供体异常返回 NaN——**NaN 语义本身正确**(Prometheus「抓不到」),但按契约「吞可以,留线索是底线」补一条 `log.warn` 指认哪个量因何退化(与 Down 指标塌陷警报互补不重复)。
- **注入-还原闭环**(AGENTS §3.9):移除 warn → 测试红(2 失败)→ 还原 → 绿。测试真实有效。
- 注意:修复走的是「补线索」而非「登记 ALLOWED」——把有意旁路登记进白名单会削弱契约;补日志让该处自然退出静默集合,总数回落不升。

## 五、途中环境账(不阻交付)

- **Testcontainers 本机不可跑**:Docker Desktop 29.6 的 `docker_cli` npipe 管道对 docker-java 的 /info 返回 400 空壳(docker-java 1.21.3 兼容缺陷),`NpipeSocketClientProviderStrategy` 必败。CI Linux runner 无此问题。本机跑法:Docker Desktop 开「Expose daemon on tcp://localhost:2375」+ `DOCKER_HOST=tcp://localhost:2375`。
- **python 是 Windows Store 存根**(历史坑重演):静默 catch 复刻扫描器改用 Node 实现;期间发现复刻正则必须与 Java 原版**逐字对齐**(CATCH 只匹配 `Exception|Throwable`、HAS_LOG 要求 `log.` 后跟方法级别)——第一版复刻因匹配任意 catch 虚报 36 处,对齐后 23,与 Java 测试同判。
- **mvnw 退出码链**:GitHub runner bash 下 `PIPESTATUS[0]` 可用,`set +e` 窗口内 maven 非零码能透传,grep 兜底双保险——CI 绿的真因是 maven 实际 exit 0(测试失败 XML 由 artifact 提取通道显形,非本次 run 失败)。
