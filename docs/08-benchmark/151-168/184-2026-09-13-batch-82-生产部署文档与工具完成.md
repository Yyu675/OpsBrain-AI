   - 场景 C：数据损坏（恢复全量备份）

   - Q1: checksum 不匹配 → 修复步骤

### 1.2 Flyway Checksum 计算助手（✅ 已完成）

**文件**：`tools/deploy/flyway_checksum_helper.sh`

**功能**：
1. **自动计算本地 checksum**：
   ```bash
   # 使用 cksum 命令模拟 Flyway CRC32 算法
   cksum V1__baseline.sql | awk '{print $1}'
   ```

2. **查询数据库 checksum**：
   ```bash
   # 从 flyway_schema_history 表读取版本 1 的 checksum
   psql -c "SELECT checksum FROM flyway_schema_history WHERE version = '1';"
   ```

3. **对比与诊断**：
   - ✅ 一致 → 提示无需修复
   - ⚠️ 不一致 → 生成修复 SQL + 交互式更新

4. **生成修复 SQL**：
   ```sql
   -- 自动生成带时间戳的备份表
   CREATE TABLE flyway_schema_history_backup_20260913_143022 AS ...;
   
   -- 更新 checksum
   UPDATE flyway_schema_history SET checksum = <新值> WHERE version = '1';
   
   -- 验证更新
   SELECT version, checksum, ... FROM flyway_schema_history WHERE version = '1';
   ```

5. **交互式执行**（可选）：
   ```bash
   # 显示对比结果，询问是否立即更新
   当前数据库 checksum: 123456789
   新计算 checksum:     987654321
   继续执行更新？(yes/no):
   ```

**使用方式**：
```bash
# 基本用法（自动检测 V1__baseline.sql）
./tools/deploy/flyway_checksum_helper.sh

# 指定迁移文件
./tools/deploy/flyway_checksum_helper.sh src/main/resources/db/migration/V1__baseline.sql

# 非交互模式（仅计算，不更新）
INTERACTIVE=false ./tools/deploy/flyway_checksum_helper.sh

# 自定义数据库容器名
DB_CONTAINER=my-postgres-1 ./tools/deploy/flyway_checksum_helper.sh
```

**安全保障**：
- ✅ 自动备份 flyway_schema_history 表（带时间戳）
- ✅ 交互式确认（防止误操作）
- ✅ 彩色日志输出（INFO/WARN/ERROR 区分）
- ✅ 错误处理（文件不存在/容器未运行）

**篇幅**：约 200 行，完整可运行

## 二、解决的核心问题

### 2.1 问题 1：checksum 冲突处理模糊

**旧状态**：
- 用户策略调整后（所有变更追加至 V1），生产环境会遇到 checksum 不匹配
- 手动修复步骤散落在报告 182，无标准化流程
- checksum 计算依赖手动公式，易出错

**新状态**：
- ✅ Checklist 提供完整的「方案 B - B.3 修复 Flyway checksum」步骤
- ✅ `flyway_checksum_helper.sh` 一键计算 + 对比 + 生成修复 SQL
- ✅ 交互式确认 + 自动备份，降低误操作风险

---

### 2.2 问题 2：生产部署无标准化流程

**旧状态**：
- 开发环境重建库（`docker-compose down -v`）简单直接
- 生产环境如何应用变更？文档缺失
- 回滚预案不清晰，遇到问题无章可循

**新状态**：
- ✅ Checklist 提供「方案 A（重建库）」+「方案 B（增量变更）」双轨选择
- ✅ 详细步骤拆解：前置条件 → 执行 → 验证 → 回滚
- ✅ 3 大回滚场景覆盖（SQL 失败/checksum 错误/数据损坏）
- ✅ 常见问题 Q&A（checksum 不匹配/索引耗时长/备份不一致）

---

### 2.3 问题 3：风险评估与停机窗口模糊

**旧状态**：
- 索引创建耗时多久？无预估
- 何时需要维护窗口？无判断标准
- 变更风险如何分级？无量化依据

**新状态**：
- ✅ 停机窗口评估表：
  - 10 万行以下：<5s，可在线执行
  - 10-100 万行：5-30s，建议低峰期
  - 100 万行以上：>30s，需维护窗口
- ✅ 变更风险分级：
  - 低风险：新增表/字段（无数据迁移）
  - 中风险：新增索引（评估创建耗时）
  - 高风险：修改字段类型/删除表（需确认无依赖）

## 四、使用场景示例

### 4.1 场景：批 80 索引部署到生产环境

**背景**：
- 本地开发环境已合并批 80 P1 四索引至 V1__baseline.sql
- CI 绿灯（空库验证通过）
- 生产环境已有业务数据，无法接受长时间停机

**执行步骤**：

#### 步骤 1：备份数据库
```bash
cd tools/deploy
BACKUP_FILE="backup_$(date +%Y%m%d_%H%M%S).sql"
docker exec devops-platform-backend-postgres-1 \
  pg_dump -U devops devops_platform > "$BACKUP_FILE"
ls -lh "$BACKUP_FILE"  # 确认备份文件大小
```

#### 步骤 2：提取增量 SQL
```bash
# 对比 V1__baseline.sql 变更（批 80 新增了第 1420-1469 行）
cat > incremental_batch_80.sql <<'EOF'
CREATE INDEX IF NOT EXISTS idx_alert_firing_recent ...;
CREATE INDEX IF NOT EXISTS idx_dsession_queue_fifo ...;
CREATE INDEX IF NOT EXISTS idx_approval_zombie_scan ...;
CREATE INDEX IF NOT EXISTS idx_ticket_assignee_time ...;
EOF
```

#### 步骤 3：手动执行增量 SQL
```bash
docker exec -it devops-platform-backend-postgres-1 \
  psql -U devops -d devops_platform < incremental_batch_80.sql
```

#### 步骤 4：计算新 checksum
```bash
./flyway_checksum_helper.sh
# 输出：
#   [INFO] 本地文件 checksum: 987654321
#   [INFO] 数据库记录 checksum: 123456789
#   [WARN] ✗ checksum 不一致，需要修复
#   继续执行更新？(yes/no): yes
#   [SUCCESS] checksum 更新完成
```

#### 步骤 5：重启应用并验证
```bash
docker-compose restart backend
docker-compose logs -f --tail=100 backend | grep Flyway

# 验证健康
curl http://localhost:8080/actuator/health

# 功能冒烟测试
# - 登录前端
# - 访问「我的工单」列表（验证 idx_ticket_assignee_time 生效）
# - 查看告警看板（验证 idx_alert_firing_recent 生效）
```

**耗时估算**：
- 备份：10-30s（取决于数据量）
- 执行 SQL：<5s（4 个索引，假设各表 <10 万行）
- checksum 修复：<5s
- 应用重启：10-20s
- **总计**：~1 分钟

**停机窗口**：仅应用重启阶段（10-20s）

**背景**：
- 生产环境应用启动失败
- 日志显示「Migration checksum mismatch for migration version 1」
- 需要快速恢复服务

**执行步骤**：

```bash
git log --oneline -1 src/main/resources/db/migration/V1__baseline.sql

```

#### 步骤 2：运行 checksum 助手（非交互模式）
```bash
INTERACTIVE=false ./tools/deploy/flyway_checksum_helper.sh
# 输出：
#   [INFO] 本地文件 checksum: 987654321
#   [INFO] 数据库记录 checksum: 123456789
#   [WARN] ✗ checksum 不一致，需要修复
#   -- 生成修复 SQL（省略具体语句）
```

#### 步骤 3：手动执行修复 SQL（从助手输出复制）
```bash
docker exec -it devops-platform-backend-postgres-1 \
  psql -U devops -d devops_platform <<'EOF'
CREATE TABLE flyway_schema_history_backup_20260913_150522 AS
  SELECT * FROM flyway_schema_history WHERE version = '1';

UPDATE flyway_schema_history
SET checksum = 987654321
WHERE version = '1';
EOF
```

#### 步骤 4：重启应用
```bash
docker-compose restart backend
docker-compose logs -f --tail=50 backend
# 观察：Flyway 验证通过 → 应用正常启动
```

**恢复时间**：~2 分钟
