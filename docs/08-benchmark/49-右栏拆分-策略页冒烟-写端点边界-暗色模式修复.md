## 二、两个真实缺陷

### 缺陷 A：卸载后仍改路由，污染下一个页面的地址栏

**线索来源**：`KnowledgeBase.vue` 里两个防抖，一个有卸载清理一个没有。

```
const applySearch = debounce(..., 300)
onBeforeUnmount(() => applySearch.flush())      // ← 有

const syncUrl = debounce(() => router.replace({ query }), 200)
watch([...七个筛选项], syncUrl)                  // ← 没有
```

`TicketList.vue` 的同名 `applySearch` 也有 `flush()`。
**同一模式在相邻两处不一致，通常不是设计，是漏了。**

**用户可见后果**：用户点了分类筛选，200ms 防抖还没到就跳去工单列表，
定时器随后触发，`router.replace` 以**当前路由**为基准执行——
地址栏变成 `/tickets?cat=K8S`，工单列表按一个它不认识的参数刷新。

**关键取舍**：修复必须用 `cancel()` 而非照抄上面那行的 `flush()`。
两者回调性质不同——`applySearch` 的回调只动本组件数据，卸载后执行最多白跑；
`syncUrl` 的回调改全局路由，卸载后执行就是污染别人。
注入验证里专门放了「误用 flush」这一项，确认测试能区分两者。

**流程**：测试先于修复。修复前该用例报的是
`router.replace` 从 `persist.ts:217`（debounce 定时器回调）在卸载后被调用，
且当时路由已是 `/tickets`。拿到这个确切读数之后才动产品代码。

### 缺陷 B：暗色模式下白底白字

**规模**：28 处 `background: white` / `#fff`，横跨 Dashboard、Home、
TicketDetail、Login、ActionItemBoard 等核心页面。

**为什么严重**：`useTheme` 的默认模式是 `'system'`——
**任何系统设为深色的用户，一打开就是暗色界面**，
不存在「我没开暗色所以没事」。而 `--text-1` 在暗色下是接近白的
`oklch(0.95 …)`，压在硬编码白底上就是**白底白字，直接读不了**。

**为什么确定是疏漏**：`CollapsibleCard.vue` 第 74 行写死 `background: white`，
第 90 行的 hover 态却用 `var(--color-surface-hover, var(--surface-2))`。
同一个文件、相隔 16 行，一个跟随主题一个不跟随。

**刻意保留 1 处**：`SettingsDialog` 的开关滑块。它压在有色轨道上需要固定对比，
跟随主题会让暗色下的滑块变成深灰压在深灰轨道上，**开关看起来像消失了**。
已在代码里写明理由，避免下次清理时被「顺手改掉」。

## 三、拆分方法论：逻辑不搬，只搬 DOM

`TicketDetail.vue` 右侧栏拆成 4 个组件时，
`addTag`/`removeTag`/`useTicketAttachments` 的回调**全部留在父组件**，
子组件只把交互原样 emit 回去。

结果：`TicketDetail.actions.test.ts` 等 **80 例一行未改直接通过**。

这是刻意的验收标准。改了测试再看它绿，等于把标尺和被测物一起挪动，
测不出搬运有没有出错。

### 拆分中发现的真实陷阱：scoped 样式不穿透

上传按钮用的 `.btn-outline` 定义在 `TicketDetail.vue` 的 **scoped** 样式里。
按钮搬进子组件后，父组件那份定义就管不到它，
用户看到的是一个没边框、没内边距的裸文字链接。

**这类回归类型检查过、测试过、只有肉眼看得出来**，是模板拆分最易漏的一类。

### 顺带清掉 39 个死 CSS 类

`.ai-insights` / `.insight-*` 十条是 `TicketInsights` 抽出去时的遗留，
`.empty-card` / `.loading-spinner` 等九条在改用 `AppEmpty` / `PageLoading` 后失效。

死样式不报错也不影响渲染，但会让下一个人以为「页面上还有这块 UI」，
照着改半天发现毫无效果——这正是本次拆分前排查右侧栏花掉的时间。

## 四、注入-还原验证结果

| 批次 | 注入 | 抓到 | 漏网及处理 |
|------|------|------|-----------|
| 右栏组件 | 6 | 5 | activity key 去掉序号——**实测无可观测差异，据实改写注释** |
| 策略页冒烟 | 7 | 7 | — |
| URL 同步 | 4 | 4 | 防抖 wait 改 0 第一版漏网，已修正断言 |
| 主题令牌 | 2 | 2 | — |

### 两次「假绿」的教训

**其一**：我原先在组件注释里写「activity 的 key 去掉序号会导致 Vue
复用错节点、两行内容互换」。实测（探针对比 patch 结果与 console warn/error）
发现**那是错的**——纯静态列表下重复 key 与正确实现毫无可观测差异。

处理方式是**改注释而不是补测试**：把臆测的后果换成实测结论，
并说明那条用例守的其实是「内容不被去重」。

**其二**：URL 同步的防抖断言原本在 0ms 处检查「还没导航」，
而 `setTimeout(…, 0)` 仍是异步，同步检查看不到差异——
把 wait 改成 0 照样通过。改为跨过防抖窗口中段（150ms / 200ms）后才真正有效。

**共同点**：边界用例必须让正确实现与错误实现给出**不同答案**。

## 五、误报核实：三处 addEventListener 不解绑

扫描发现 `useTheme` / `main.ts` / `persist.ts` 有 add 无 remove。
逐个核对后确认都是**单例/应用级监听**，进程内只注册一次，不该解绑。

**未做改动**——避免为了「配平计数」引入真实缺陷。
这延续了上一轮的方法教训：初筛必须逐个核对，不能直接报数。
