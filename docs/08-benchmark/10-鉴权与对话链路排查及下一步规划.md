## 第一部分：本轮修复的缺陷（3 项）

### 🔴 1. SSE 断流致对话框永久卡死（可用性）

`fetchEventSource` 在服务端关闭流时**正常 resolve**——不抛错、不进 catch、
不触发 onError。而 ChatMode 只在 `complete` / `error` 回调里调 `finishStreaming()`，
这条路径下 `isStreaming` 永远停在 `true`：

- 输入框 `:disabled="chat.isStreaming"` → 一直禁用，打不了字
- 发送按钮被「停止生成」替换，而 `abortController` 已置空，
  `stopGeneration` 第一行就 return → **点了没有任何反应**

用户唯一出路是刷新页面，且完全不知道为什么。触发场景都很常见：
后端超时切断、网关 502、Nginx `proxy_read_timeout` 到期。

**修复**：`chatStream` 补 `onClose` 回调接线到 `onclose`；ChatMode 在其中兜底收尾，
按「是否已有内容」区分文案——有内容则**保留已生成部分**并注明中断。
`onBeforeUnmount` 同样补收尾（原来只 abort，但 `isStreaming` 在 store 里跨组件共享，
切走再回来输入框仍禁用）。

### 🟠 2. 开放重定向校验可被反斜杠绕过（安全）

原校验 `startsWith('/') && !startsWith('//')` 实测放行了这些：

| 输入 | 原校验 | 浏览器解析为 |
|---|---|---|
| `/\evil.com` | 放行 | `https://evil.com/` |
| `/\t/evil.com` | 放行 | `https://evil.com/` |
| `/\\evil.com` | 放行 | `https://evil.com/` |

反斜杠在 WHATWG URL 规范里按正斜杠处理，`\t\n\r` 被剥离后重新解析。

**可利用性（据实说明，不夸大）**：vue-router 走 `history.pushState`，
浏览器强制同源，单靠它跳不出去。真正的出口是 `router.onError` 里的
`window.location.assign(to.fullPath)`——真实浏览器导航。触发链是
「构造 redirect → 用户登录 → 恰好该路由 chunk 加载失败 → onError 兜底 assign」。
链条不短，但校验本身确实是错的，兜底逻辑不该反过来成为逃逸出口。

**修复**：新增 `safeInternalPath`。**不做黑名单**（列举 `\` `\t` 永远列不全），
改为用 URL 解析器判同源——以占位 origin 解析，origin 变了即跨站。
这与浏览器实际行为一致，不依赖我们对规范的记忆。
返回归一化路径而非原串（否则控制字符交给 `assign` 时会被再解析一次）。

### 🟠 3. maxlength 静默截断，粘贴的堆栈被砍掉（数据完整性）

前端 `maxlength="120"` / `"1000"`，后端 `@Size(max=255)` / `@Size(max=20000)`，
数据库 `VARCHAR(255)` / `TEXT`。**前端严了一个数量级。**

`maxlength` 是静默截断：运维粘贴 3000 字堆栈，浏览器只留前 1000 字且无提示，
用户以为贴全了。**编辑态更糟**——打开描述超长的老工单再保存，
超出部分被永久截掉。1000 字连一段完整 Java 堆栈都放不下，
而"粘贴堆栈"正是这个输入框的主要用途。

**修复**：标题对齐 255；描述**去掉 maxlength**改软上限，超出时红字提示
并在提交前拦下。选"软上限+拦截"而非"放大 maxlength"，因为
**可见的拒绝永远好过不可见的截断**。

## 第二部分：下一步推进建议

### 🔴 第一优先级：启用 CI（阻塞项，30 秒）

**这是目前唯一的硬阻塞**。后端 50+ 个改动文件从未编译过——沙箱内无 JDK
且 Maven 全部镜像不可达，我只能做静态校验。

```bash
git pull && mkdir -p .github/workflows
git mv ci/github-actions-ci.yml .github/workflows/ci.yml
git commit -m "ci: 启用工作流" && git push
```

**为什么必须先做这个**：后端改动包括权限过滤、事务边界、全局 Filter、
`@Valid` 注解、`ManagedExecutors` 泛型——这些都是编译期能发现的问题，
但现在一个都没验证过。继续叠加新功能只会让首次编译的错误更难定位。

启用后我可以接着修首次编译错误。

---

### 🟠 第二优先级：补齐"能防住回归"的测试（3-5 天）

当前 717 个测试集中在 utils / composables / store，而**两个最复杂的文件零测试**：

| 文件 | 行数 | 测试 |
|---|---|---|
| `TicketDetail.vue` | 2655 | 0 |
| `TicketList.vue` | 2597 | 0 |

这两个文件承载了工单的全部交互，而本轮在它们里面就发现了状态机漂移、
时间戳错误、事件订阅失效三类缺陷——**都是靠人工排查发现的，没有任何测试能防住复发**。

**建议顺序**（这个顺序不能反）：

1. **先补组件测试**（2-3 天）：状态流转按钮的可用性、批量操作的可达性计算、
   筛选与 URL 同步、乐观更新回滚。用 `@vue/test-utils` 挂载真实组件，
   只 mock api 层。
2. **再拆分 SFC**（2 天）：有了测试才敢动。按「工具栏 / 表格 / 详情面板 /
   对话框」拆，每拆一个跑一次测试。

**反过来做（先拆后测）风险极高**——在没有安全网的情况下重构 5000 行
最复杂的业务代码，引入回归的概率远大于收益。这也是我前几轮一直没动它们的原因。

---

### 🟠 第三优先级：前后端契约自动化（1-2 天）

本轮和上轮各发现一起"两侧各写一份、悄悄漂移"的问题：

- 工单状态机：前端 `ALLOWED_TRANSITIONS` vs 后端 `TicketEnums`（手工同步）
- 字段长度：前端 `maxlength` vs 后端 `@Size`（本轮修复）
- 业务码：前端 `bizCode.ts` vs 后端 `BizError`（已有契约测试）

现在靠"镜像一份 + 断言"防漂移，但**镜像本身还是手工维护的**。

**可行方案**（按投入排序）：

| 方案 | 投入 | 效果 |
|---|---|---|
| 后端加契约测试导出 JSON，前端测试读它断言 | 1d | 单一真相源，改后端即失败 |
| 引入 OpenAPI（springdoc）+ 前端类型生成 | 3-5d | 彻底解决，但改动面大 |
| 维持现状（手工镜像 + 断言） | 0 | 能防住"改了一侧忘另一侧"，防不住"两侧都改错" |

**建议先做第一个**——投入小，且能覆盖当前三处已知契约。

- **ECharts 进一步瘦身**：已实测 570KB 中 293KB 是 `echarts/core` 固定开销，

  其余 15 个已有防护且能正常工作，为统一而统一风险大于收益。

## 附：本轮方法补充

前几轮总结过"穷举比对"和"跑起来 curl"。这轮又补一条：

**读第三方库的源码，而不是猜它的行为。**

SSE 断流卡死这个缺陷，是我去看 `fetch-event-source` 的 `fetch.js` 才发现的——
它在流关闭时走的是 `resolve()` 而非抛错。只看自己的代码，
永远会以为"流结束了总会触发点什么"。

同理，开放重定向那条也是用 `new URL()` 实际跑出来的，
而不是凭"反斜杠应该会被拦住"的直觉。

**涉及第三方库边界行为时，20 行探针脚本比 200 行推理可靠。**
