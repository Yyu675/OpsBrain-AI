## 二、patch 内容（单 hunk，+23 行）

```diff
 verify 之后、上传测试报告之前，插入两个 step:
 1) 评测指标基线对比 —— node tools/audit/eval_compare.js
      --current target/eval-metrics.json
      --baseline tools/audit/eval_baseline.json
 2) 上传评测指标 —— actions/upload-artifact@v4, always(), 30d
```

设计取舍（每条写进了 patch 内 YAML 注释，随 patch 走）：

1. **无基线不误红。** 建账窗口（4-3.2）到来之前，门禁处于「带鞘」状态：
   打印引导、rc=0 放行。闸门的意义是治劣化，不是恐吓空窗。
2. **不引 `setup-node`。** 评测工具链本来就是 node 单文件脚本，ubuntu-latest
   托管 runner 预装 node；为一个脚本增加一条 action 供应链是负资产。
3. **单 hunk 最抗漂移。** 后期 ci.yml 其他处改动不影响本 patch 的 apply 面；
   若 verify 周边文案改动导致失配，`git apply --3way` 或手工对齐一处即可。
4. **RAG/LLM 层不在 patch 内开闸。** 种子摄取未入 CI 流程前开 `EVAL_RAG`
   只会收获持续红（前置断言已写明失败原因），这是「接线」与「伪接线」的分界。

## 四、权限落地 checklist（workflows 权限到手后，按序执行）

1. `git apply tools/ci/s4-3-eval-regression-ci.patch` → 提交推送（此步消耗权限）
2. 首跑观察：backend job 应出现「评测指标基线对比」step，输出 `⚠ 未找到基线…首跑` + rc=0
3. EVAL_RAG 真实窗口跑出首份指标 → 下载 artifact → 本地
   `node tools/audit/eval_compare.js --current … --baseline tools/audit/eval_baseline.json --update` → 提交基线（门禁出鞘）
4. 后续劣化（比率类 ±2pt / 计数方向语义）即红，现场从 `backend-eval-metrics` artifact 对账
5. （另批）种子目录摄取入 CI 流程后，backend job env 增 `EVAL_RAG: 'true'`，RAG 层六指标自动并入对比；`EVAL_LLM` 恒手动 job，不进默认 CI
