# 106 · S2-1 告警驱动的自动诊断编排器（阶段 2 骨架）

## 一、本次交付

| 产物 | 内容 |
|---|---|
| `V4__sys_diagnosis_session.sql` | 诊断会话表（alert_id 唯一索引 + trace_id 索引） |

## 二、核心设计决策

### 2.1 异步 + 不阻塞告警链路

- 诊断池核心 4 线程、最大 8、队列 100（路线图建议值）
- 弃用 `CallerRunsPolicy`，拒绝使 webhook 背负诊断开销
- 降级：池满时记 WARN 日志，回退为仅建票（告警入库优先）

### 2.2 traceId 唯一真相

- `TraceContext.capture()` 在提交侧接管，`TraceContext.restore()` 在诊断线程恢复
- 告警、工单、诊断、证据在同一条 trace 下流转
- MDC 自己没有 cross-thread 传播能力，必须显式搬运

### 2.3 取证确定性编排（不做模型工具规划）

- 三方向指标确定性采集（`metrics / changes / logs` Collector）
- 告警场景要求取证路径稳定可回放——随机性只会稀释证据质量
- 推理步骤留给 S2-2（LLM 合成），不在编排器里做 if-else 混合判定

### 2.4 证据不足硬终止

- 聚合判定 `INSUFFICIENT` → 摘要改为「终止推理，转人工」
- 推理步骤不会进入，防止断章取义

### 2.5 诊断失败不反噬

- 诊断池内的一切异常都只记录在 `sys_diagnosis_session.status = ERROR`/`FAILED`
- 建单/告警入库早在提交时就已完成，诊断延迟或失败不影响上游

## 三、判定映射（路线图 §5.6 逐条翻译）

| SUCCESS | NO_DATA | FAILED | 判定 |
|---|---|---|---|
| ≥2 且 0 个 FAILED | 0 | 0 | SUFFICIENT：证据充分 |
| ≥1 | 0/1 | 1 | WEAK：证据薄弱，置信度 ≤ 0.6 |
| ≥2 个 FAILED | ≥1 | 任意 | INSUFFICIENT：证据不足，终止 |
| 全部 NO_DATA | 任意 | 0 | INSUFFICIENT：无有效证据 |

路由开关在 `EvidenceAggregator.aggregate(...)`，编排器的 `buildFinalSummary()`
只做汉化翻译，不做重评。

## 四、诊断会话表（V4）

```sql
sys_diagnosis_session (
    id            BIGINT AUTO_INCREMENT,
    trace_id      VARCHAR(64) PRIMARY KEY,     -- 诊断主体的唯一标识；同时贯穿告警→工单→证据
    alert_id      BIGINT NOT NULL REFERENCES sys_alert(id),
    ticket_id     VARCHAR(64),                -- 允许在建单后回填；RUNNING 阶段可空
    service       VARCHAR(128) NOT NULL,
    status        VARCHAR(16) NOT NULL,        -- RUNNING / COMPLELETED / REJECTED / FAILED
    sufficiency   VARCHAR(16),                 -- SUFFICIENT / WEAK / INSUFFICIENT
    summary       TEXT,                        -- 判定后的校验摘要
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 「进行中」唯一索引：同告警不重复触发诊断
CREATE UNIQUE INDEX idx_dssession_alert_running
    ON sys_diagnosis_session (alert_id) WHERE status = 'RUNNING';
```

`ON CONFLICT (alert_id) WHERE status = 'RUNNING' DO NOTHING` 让重复触发在 INSERT 时静默拒绝。

## 六、本次发现并沉淀的边界问题

`DiagnosisEvidenceRepository.save(...)` 的 payload 字段映射结论必须与 S1-5 阶段 1 保持
一致：`collectedAt` 反映证据采集时刻的 `LocalDateTime`，诊断会话表中的 `created_at`
反映诊断处理完成时刻——两者语义上差一个「处理延迟」，审计告警延迟指标时
这是约束不可忽略的边界理由。
