## 一、本批清零的三个验收缺口

| 路线图条目 | 原文要求 | 本批落法 |
|---|---|---|
| 3-3.4 | 执行前二次校验：幂等（同一告警同一动作短时间内不重复执行） | 编排器幂等闸：`devops.healing.idempotency-window-seconds`（默认 300 秒）内同 alertId+actionKey 已有 PENDING_APPROVAL/SUCCEEDED 台账 → REJECTED 留痕，演算与审批均不发生 |
| 3-1.4 | 未实现 rollback 的执行器无法注册（启动即失败） | 折中版强契约：执行器新增 `undoCapable()`（默认 true）+ `maxPermissionLevel()`（默认 SAFE）；注册表启动校验「非只读必须可撤销」，违规抛 IllegalStateException |
| 3-3.6 | 执行审计全量落 `sys_operation_audit` | 分工明确：HTTP 面（管理员触发/撤销）已由 OperationAuditInterceptor 全量覆盖；本批补上 **agent 面**——`requestedBy="auto"` 的执行由编排器旁写审计（action 键如 `healing.execute` / `healing.submit_approval` / `healing.execute_approved` / `healing.undo`），旁写失败只告警不阻断 |

## 二、3-1.4 折中的理由（不回避与路线图的差异）

路线图要求「每个执行器必须实现 rollback，缺失则注册失败」；PRD D1 却明确
第一个真实执行器是 **K8s fabric8 只读**（V1.2）。只读执行器天然没有撤销语义，
强制实现 rollback 会让它要么无法注册、要么实现一个撒谎的空方法——
后者比不实现更坏（报告 109 的「审计诚实性」同一立场）。

折中：**按声明的最高权限分级**——

- 声明 `READ_ONLY_DIAGNOSTIC` 最高权限 → 豁免撤销要求（为只读轨铺路）；
- 声明 `SAFE_AUTO_HEALING` / `DESTRUCTIVE_HIGH_RISK` → `undoCapable()` 必须 true，否则启动失败。

**宁可服务起不来，不让一只「不可撤销的手」摸到生产系统。**

## 三、幂等闸的语义边界（两个刻意的「不拦」）

1. **REJECTED / FAILED / UNDONE 不拦**：失败重试与撤销后重来是值班员的正当诉求；
   只拦「还在等审批」和「已成功未被撤销」——重复执行的真实风险只来自这两类。
2. **手工触发（alertId 为空）不拦**：管理员在界面上点第二次是明示意图，
   弹层确认即可；幂等闸针对的是告警风暴下自动管线的无脑重放（S3-2 的后顾之忧）。
