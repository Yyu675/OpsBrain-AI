## 一、结论先行

变更取证闭环已通：**写入端**（`/api/changes` 幂等回调端点，CI/CD 友好）→ **存储**（后 Flyway 时代首个增量迁移 V2 `sys_change_event`）→ **取证工具**（`queryRecentChanges`：NO_DATA 与 FAILED 语义严格区分，时间相关性分档评分）。日志取证（S1-3）按阶段顺序排下一轮，本报告预留 §六挂账位。

## 二、设计决策

| 决策点 | 选择 | 依据 |
|---|---|---|
| 数据源 | **自建事件注册表 + 写入 API**，非事后翻 CI 系统 | 路线图原断：「变更关联是根因定位性价比最高的单一方向」；CI 系统认证/限流/格式都是额外故障面，写入端点最稳 |
| 幂等 | `UNIQUE(source, external_id)` + `ON CONFLICT DO NOTHING`；重发返 200 + `deduplicated=true` | CI 流水线重发/重试是日常，不该红；`external_id=NULL` 的手工录入按 PG 语义不参与唯一（可在表注释追索） |
| 时间字段 | `change_time`（实际发生）与 `reported_at`（入库）分离 | 上报延迟本身是可观测信号 |
| 相关性评分 | **分档**，不要连续衰减函数 | 运维心智就是档位（「刚发布 5 分钟」）；可读、可测、可向人解释。5m→1.0 / 30m→0.8 / 1h→0.6 / 2h→0.4 / 6h→0.2，单调不增；>6h→0.1 留给聚合器 |
| 三态 | 空=NO_DATA（有效排除证据，非错误）；只有查询抛异常=FAILED | §5.3 📌：推理层权重完全不同 |
| 鉴权 | 复用 `KnowledgeWriteGuard.requireEdit()`（ADMIN/OPS） | 不新开签名机制——避免再造一个 webhook 验签对照组 |
| 返回规模 | `MAX_ROWS=20` + `truncated` 标记；summary 入库 VARCHAR(2000) 截断 | 与日志工具的 2000 字符纪律同构，防上下文刷屏 |
| sourceRef | 可读谓词转述（表名+服务+窗口），非 SQL 全文 | 库内数据无谓 PromQL；回放归 S1-5 落库 traceId |
