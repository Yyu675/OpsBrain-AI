## 一、结论先行

`queryServiceMetrics` 已上线 Agent 工具白名单：Prometheus 未启用→`UNAVAILABLE`、数据源故障/熔断→`FAILED`（证据缺口）、连通但无序列→`NO_DATA`、有数据→`SUCCESS`（IQR 检出异常清单，可能为空但语义明确）。**四态不落默、不伪装**，工具失败就是失败——这是路线图为整个阶段 1 立的灵魂。

## 二、设计决策（为何如此做）

| 决策点 | 选择 | 依据 |
|---|---|---|
| 异常检测算法 | **IQR（Tukey 1.5 栅栏）**，非 3-sigma | 运维指标普遍右偏/尖峰肥尾，均值方差被自身尖峰拉走（掩蔽效应）；IQR 用分位数天然抗离群，30m 窗 ~30 点小样本也稳 |
| 基线定义 | 中位数；偏离倍数 = 当前值/基线，<1.2x 判噪音 | 无量纲，可跨指标比较；20% 阈值抑制正常抖动 |
| PromQL 来源 | **进 yml 查询目录**（`devops.metrics.query-catalog.*`），非硬编码 | label 约定因现场而异（k8s 用 `pod=`、Spring 用 `application=`）；写死=假验收。默认四项 CPU/内存/错误率/P99，新增=加一行 yml |
| 服务名进入 PromQL 前 | 白名单 `[a-zA-Z0-9._-]{1,128}` | `@Tool` 是模型可达面，注入边界在工具层（§5.4 📌 同款纪律） |
| 返回结构 | `Evidence` 四态轻模型 + `sourceRef`=实渲染 PromQL（非模板） | 1-1.4 验收「PromQL 可粘贴 Grafana 复现」只能用渲染后的实串 |
| 治理 vs 业务 | @ToolMeta 治理（timeoutMs=15000, maxRetries=1）+ collector 无治理注解 | T14/S0-3 分工惯例延续 |
| 步长策略 | 目标 ~60 点/序列（30m→30s、2h→2m、1d→24m） | IQR 样本足够 + 响应体可控 |
| 时间窗上限 | 7d | 防模型传 365d 打爆 Prometheus |

## 四、验收标准对照（路线图 §5.2）

| # | 标准 | 状态 | 证据 |
|---|---|---|---|
| 1 | Agent 收到"order-service 响应慢"时能自主调用工具并拿到数据 | 🟡 工具与 @Tool 描述已就位，被 LLM 选中归 EVAL_LLM 手动 job 首跑验收（S0-4 口径） | DevOpsTools.@Tool 描述；deliver/TOOLS_EVAL.md 机制 |
| 2 | Prometheus 不可用时明确"数据源不可用"，不谎称指标正常 | ✅ | `prometheusDownYieldsFailed` + `disabledYieldsUnavailableWithoutAnyRequest`（零网络调用断言） |
| 3 | 单次调用 P95 ≤ 15s | ✅（机制保障） | timeoutMs=15000 + Prometheus 客户端默认 5000ms |
| 4 | PromQL 可在 Grafana 直接粘贴复现 | ✅ | `emptyResultIsNoDataNotFailed` 断言 sourceRef 含渲染后服务名、无 `{service}` 残留 |
