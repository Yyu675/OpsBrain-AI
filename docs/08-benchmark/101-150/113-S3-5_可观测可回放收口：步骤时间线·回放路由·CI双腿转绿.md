## 二、设计取舍：为什么步骤不拆表

备选方案是 `sys_healing_step` 子表（一行一节点）。未采纳：

1. **写入基数极小**：每次执行节点 ≤12 个，一次序列化全量写入比逐行 INSERT 简单，
   且没有针对单节点的独立查询需求（回放永远按执行维度取全序列）；
2. **既有范式一致**：`params_json / pre_snapshot_json / verify_result_json` 都是 TEXT+JSON，
   `steps_json` 与其同基调，详情 API 服务端代解析（烂掉降空数组，不炸接口）；
3. **一致性收益**：步骤与主行同事务面更新，不会出现「主行 SUCCEEDED、步骤缺 EXECUTE」
   的跨表漂移（节点写入只在紧接 insert/markFinished 的原子局部时点上做）。

代价也诚实记录：步骤不可独立索引检索——若将来要按节点名做聚合统计（如「AUTO_UNDO
月发生率」），需迁子表。当前无此需求，不为想象中的报表拆表。

## 三、读-改-写的诚实边界

`handle()` 主线的节点在已知执行 id 后一次性写；事后节点（验证/撤销/升级、批准续走）
走 `readStepsJson → 解析 → 追加 → 覆写`。三个明确取舍：

- **损坏的既有序列不抢救**：解析失败即 warn + 从空序列重写——损坏本身会被日志看见，
  比静默丢弃或硬编码兜底诚实；
- **步骤写失败不拖垮主流程**：台账行是主事实，时间线是回放材料；
  回放缺材料的退化形式是详情页「无步骤数据」档，不是主流程异常；
- **undo 双入口共用 MANUAL_UNDO 节点**：自动撤销路径在 undo() 返回后再补一行 AUTO_UNDO，
  两行并存能看出「自动触发的撤销」与「人工按下的撤销」，语义不靠猜。

## 四、CI 修红战役终局（十层洋葱全记录）

分支曾长期处于「0 绿」状态（docs-only 提交也红，问题远早于 S3 代码）。
GitHub Actions 日志通道（results-receiver）在本环境持续 EOF，全程通过
**check-runs annotations API** 逐层剥出失败根因，共十层、无一靠猜：

| # | 层 | 修法 |
|---|---|---|
| 1 | `K8sRestartPodExecutor` 漏 `KubernetesClient` import | 补一行 import |
| 2 | `FlywayMigrationIntegrationTest` 常量冻结在 V2/V3 时代 | 断言推进到当前迁移集（本批同步 `{1..10}`） |
| 3 | WS notifer 模板引用 `getType()` 幽灵方法 | 移除幽灵引用 |
| 4 | langchain4j 1.2.0 API 漂移（chatModel 签名） | 对齐新版调用 |
| 5 | `DiagnosisOrchestratorTest` 测试与生产漂移×5 | 逐点对齐 |
| 6 | Mockito strict-stubbing 误杀共享桩 | lenient 化特定桩（非全局宽松） |
| 7 | fabric8 `RETURNS_DEEP_STUBS` 在 6/7 版接口层级下链式返 null | 分层显式桩（每级明确返回值） |
| 8 | `PrometheusClient` 两级 HTTP/业务失败塞进同一 catch | 两级分诊 + 逐级透出 |
| 9 | 测试 fixture JSON 尖峰少一层 `]`（python 复算锁到列号） | 补 `]` |
| 10 | `ApiResponse.code` 语义：`0=成功`，非 HTTP 200 | 断言对齐真实语义 |

另有状态流转守卫（`DiagnosisSessionRepository.complete/fail` WHERE 补
`status='RUNNING'` + 影响行数核对）作为并发契约一并落地。

**转绿标志**：`d9cbe2f` 起「后端 · 编译与测试」与「前端 · 类型/规范/测试/构建」
双腿连续两轮全绿；本批（V10 + 时间线 + 前端回放）随推即验。
