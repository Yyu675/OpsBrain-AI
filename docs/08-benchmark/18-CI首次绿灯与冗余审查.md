### 其中三个值得单独说

**① `maven-toolchains-plugin`（#4）——「装了 JDK 21 却仍构建失败」**

它在 `validate` 阶段就要求 `~/.m2/toolchains.xml` 存在并匹配 JDK 21，
否则直接失败。但仓库里没有这个文件，CI 的 `setup-java` 不生成它，
新克隆仓库的开发机同样没有。报错还指向 toolchain 而非真实原因。

删而不是补文件：补文件要在 CI、每台开发机、Docker 里各补一份；
而 `<java.version>21</java.version>` 已通过 parent 传给
`maven.compiler.release`，toolchains 只是把同一件事再声明一遍。

**② 语义缓存漏传权限域（#6）——被编译器拦下的越权**

```java
// streamAgent 内，但 knowledgeScope 是 handleStreamChat 的局部变量
cacheService.putCache(query, finalAnswer, knowledgeScope.cacheScopeKey());
```

读缓存带了 scope，写缓存却拿不到。**如果当时图省事改成调用不带 scope 的
重载，代码就能编译通过** —— 但答案会被写进「无权限域」的桶，
下一个任意权限的用户用语义相近的问题就能命中，C2 的权限隔离形同虚设，
且失效得悄无声息。正确修法是把 scope 显式传进去。

**③ `TtlChatMemoryStore` TTL=0 永不回收（#8）——真实生产缺陷**

```java
if (now - e.getValue() > expireAfterAccessMs)   // TTL=0 时是 0 > 0 == false
```

TTL 配成 0（压测、故障演练会这么配）时语义完全颠倒：
「立即过期」变成「永不过期」，内存会被吃满。改为 `>=`。

### 一次过度修复与回退

修 #8 时我把 `TraceIdFilter` 也加进了 `@WebMvcTest` 排除清单——
但它没有任何依赖，不是上下文启动失败的原因（真正原因只是
`OperationAuditInterceptor` 依赖 `@Repository`）。
结果 `jsonPath($.traceId).exists()` 失败。

**没有删掉这条断言来让测试变绿**：traceId 是排障入口，
「响应里没有 traceId」在生产上意味着一条链路无法追踪。
改为 `@Import` 装回该 Filter + `MockMvcBuilders.addFilters` 只织回它一个，
鉴权仍保持关闭。

## 二、一个环境问题与它的解法

CI 原始日志存放在 Azure blob（`productionresultssa7.blob.core.windows.net`），
本沙箱访问不到——与 Maven 全部镜像被挡是同一层网络限制。
`annotations` API 可达，但默认只有一句 `Process completed with exit code 1`。

前 4 轮因此只能靠静态分析试探，每轮几分钟。第 5 轮起改为：

**让 `mvnw` 在 CI 下把 Maven 的 `[ERROR]` 重放为 `::error::`**，
由 GitHub 转成 annotation（该 API 可达）。此后每轮都能直接看到真实报错，
定位速度从「猜」变成「读」。

这个改动本身也有长期价值：错误会直接标注在 PR 的对应代码行上，
评审时不必点进日志翻。非 CI 环境行为完全不变。

同时为本地静态核对拼了一套可用的编译链（均来自可达的 npm / PyPI）：
- JVM：PyPI `jdk4py` 21.0.8.2
- 编译器：npm `@vscjava/java-language-server` 内含的 ECJ

它能可靠地查出语法错误与 record accessor 冲突这类**不依赖外部 JAR** 的问题。
