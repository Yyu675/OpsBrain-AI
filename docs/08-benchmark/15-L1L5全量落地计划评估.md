# 15 · "后端 L1-L2 落地 + 前端 L1-L5 全量页面"计划评估

> 评估日期：2026-08-24
> 结论：**不建议按原计划直接执行**，建议调整为三阶段递进方案

---

## 一、先说一个必须澄清的事实

### 「前端预留接口 + 友好提示」这件事**已经做完了**

计划的第三项要求"未实现的后端接口，前端预留好接口并做好友好提示"。
实测确认：**这套机制早已存在并覆盖全部 14 条未落地路由**。

| 组成 | 现状 |
|---|---|
| 占位组件 | `ComingSoonPanel.vue` ——含阶段徽章、能力清单、状态说明 |
| 承载页 | `FutureCapability.vue` ——含面包屑返回入口 |
| 路由 meta | 每条路由声明 `stage` / `description` / `capabilities`（共 68 个能力点） |
| 覆盖路由 | 14 条（L2×3、L3×3、L4×8） |

而且它的设计取舍是对的——`FutureCapability.vue` 里有一段注释写明：
分组面包屑刻意不可点击，因为"给它挂链接会跳到 404，宁可不可点，
也不给出跳到不存在页面的链接"。

**所以这一项无需实施。** 如果对占位页的视觉或文案不满意，那是另一个
（很小的）任务，不该和"实现 L1-L5 全部页面"绑在一起。

## 二、原计划的工作量实测

### 前端 L1-L5 全量页面 = 14 个页面 / 68 个能力点

| 阶段 | 路由 | 页面 |
|---|---|---|
| L2 | 实时监控、趋势分析、接入管理 | 3 |
| L3 | 自动化策略、动作白名单、风险等级配置 | 3 |
| L4 | 自愈任务（列表/详情/步骤/验证/回滚）、Saga 补偿、人工介入 | 7 |
| L4 | 审计日志 | ✅ 本会话已完成 |

按本会话实际数据估算：使用日志页（1 个页面 + 2 个后端端点 + 22 例测试）
耗时约 1 个完整轮次。**14 个页面 ≈ 14 个轮次**，且其中多数比使用日志复杂
（自愈任务详情涉及执行编排、实时日志流、回滚状态机）。

### 后端 L1-L2 落地 = 真实基础设施集成

这是**比前端更重的部分**，且当前几乎是空白：

| L2 能力 | 后端现状 |
|---|---|
| 告警接入（Alertmanager Webhook） | ✅ 已有 |
| 告警列表/详情/确认/恢复 | ✅ 已有 |
| **Prometheus 指标拉取** | ❌ 无（grep 全项目仅在注释中出现） |
| **实时指标总览 / 服务健康拓扑** | ❌ 无数据源 |
| **趋势分析（历史指标、容量预测）** | ❌ 无时序数据存储 |
| **接入管理（Prometheus/K8s/云平台连接）** | ❌ 无 |

**实时监控页需要的不是"写个页面"，而是先有一套指标采集与存储。**
这意味着：接入 Prometheus HTTP API（或 VictoriaMetrics）、
设计指标缓存策略、处理时序数据聚合——这是独立的基础设施工作。

## 三、为什么不建议直接执行

### 🔴 阻塞项 1：后端 189 个 Java 文件从未编译过

```
沙箱: java: command not found
Maven: 全部镜像不可达（已试 8 个源）
CI: .github/workflows 不存在（GitHub App 无 workflows 权限）
```

**在这个前提下新增后端代码，是在未验证的地基上继续盖楼。**

本会话已经修的后端内容（权限过滤、事务边界、全局 Filter、`@Valid`、
`ClientIpResolver` 依赖注入、契约导出反射）全部处于"有理由相信正确、
但未验证"的状态。再叠加 L2 的 Prometheus 集成，首次编译的错误量
会指数上升，且难以定位是新代码还是存量代码的问题。

### 🔴 阻塞项 2：本次会话刚发生过一次工作区重置

就在本轮评估开始时，我发现**工作区被重置回了基线 `89e4f74`**——
59 个提交在本地全部消失，31 个后端 Java 文件变成未跟踪状态。

我已核实远程完好（`647ee58`）并完成恢复，逐文件比对确认**零丢失**，
790 个前端测试全部通过。但这说明环境本身存在不稳定因素。

**在这种环境下启动一个需要连续十几轮的大工程，风险很高。**
每一轮都可能需要重新恢复环境。

### 🟠 结构性问题：会放大已有的测试缺口

当前测试覆盖：

| | 覆盖率 |
|---|---|
| 后端 Controller | **1 / 17** |
| 后端 Service | **3 / 21** |
| 前端（不含 .vue） | 66.7% |

按原计划执行后，Controller 会增加到 25+ 个，Service 增加到 30+ 个，
而测试覆盖率会被进一步稀释。**先补测试再扩功能，和先扩功能再补测试，
后者的返工成本是前者的数倍**——本会话修的 22 个 bug 里，
有相当一部分正是早期"先写功能"留下的。

### 🟠 产品判断：L4/L5 页面的价值依赖真实执行能力

自愈任务、Saga 补偿、人工介入这些页面，展示的是**自动化执行引擎的运行状态**。
而这个引擎目前不存在。

做出来的页面只能展示空列表——它比现在的 `ComingSoonPanel` 更糟：
占位页诚实地说"能力建设中"，而空列表页会让用户以为"功能有了但没数据"，
反复去查为什么没数据。

**这违反了项目已有的一条契约（AGENTS.md）：半成品不提供交互。**

## 四、建议的替代方案：三阶段递进

### 阶段 A：解除阻塞 + 夯实地基（1-2 周）

**前置（你，30 秒）**
```bash
git pull && mkdir -p .github/workflows
git mv ci/github-actions-ci.yml .github/workflows/ci.yml
git commit -m "ci: 启用工作流" && git push
```

**我来做**
1. 修首次编译错误，核对契约 JSON diff（0.5-1 天）
2. 后端 Controller 契约测试 16 个（3-5 天）
3. 后端 Service 事务/回滚测试（3-5 天）
4. 端到端联调，含使用日志页两个新端点（1-2 天）

**产出**：后端从"未验证"变成"已验证"，具备继续扩展的地基。

### 阶段 B：后端 L2 真实落地（2-3 周）

按依赖顺序，**每一步都能独立交付价值**：

| 步骤 | 内容 | 前端可交付页面 |
|---|---|---|
| B1 | Prometheus HTTP API 客户端 + 指标缓存 | — |
| B2 | 指标查询端点（instant / range query） | **实时监控** |
| B3 | 时序聚合与容量趋势计算 | **趋势分析** |
| B4 | 数据源连接管理（CRUD + 健康检查） | **接入管理** |

**关键取舍**：不自建时序存储，直接代理 Prometheus 查询。
自建 TSDB 是数月工程量，而运维场景下 Prometheus 已是事实标准，
用户本来就有。

完成后 **L2 三个页面自然落地**，且每个页面都有真实数据。

### 阶段 C：L3 按需推进，L4/L5 维持占位（视需要）

**L3（自动化策略/白名单/风险分级）**：这三个是**配置类页面**，
不依赖执行引擎，可以先做——配置存下来，等引擎就绪再消费。
建议在 B 阶段完成后评估。

**L4/L5（自愈任务/Saga/人工介入）**：**建议维持 ComingSoonPanel**，
直到自动化执行引擎真正落地。理由见第三节最后一条。

## 五、如果你希望立刻看到页面产出

我理解"想看到更多页面"的诉求。有两个**不违反上述原则**的选项：

### 选项 1：L3 配置类页面先行（约 3-4 轮）

自动化策略、动作白名单、风险等级配置——这三个是纯配置 CRUD，
不依赖执行引擎，后端只需三张表 + 标准 CRUD 端点。
做完就是**完整可用的功能**，不是空壳。

且它们有真实价值：即便引擎未就绪，运维团队也可以先把
"哪些动作允许自动执行、什么风险等级需要几人审批"这些策略定下来。

### 选项 2：把占位页做得更有信息量（约 1 轮）

现在的 `ComingSoonPanel` 只有静态文案。可以升级为：
- 展示该能力的**依赖项进度**（如"实时监控 · 等待 Prometheus 接入"）
- 提供"订阅上线通知"入口
- 给出当前可用的替代方案链接（如实时监控 → 先看告警列表）

投入小，且让占位页从"什么都没有"变成"告诉你现在能做什么"。

---

## 六、我的建议

**推荐路径：先做阶段 A，同时并行选项 1。**

阶段 A 解除阻塞（依赖你启用 CI），选项 1 在等待期间产出可见页面。
两者不冲突——L3 配置页是纯 CRUD，即便后端未编译验证，
它的复杂度也远低于 Prometheus 集成，风险可控。

**明确不建议的**：一次性铺开 14 个页面。
在后端未编译、Controller 测试 1/17、环境刚发生过重置的前提下，
这个规模的工程失败风险很高，且大概率产出一批"看起来有、实际没数据"的页面。
