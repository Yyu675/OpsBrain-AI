## 二、本轮修复的两个缺陷（同一形态：机制存在 ≠ 机制生效）

### 缺陷 1：上下文预算裁剪结果被丢弃

`ContextBudgetManager.allocate()` 会按优先级
（证据 > 工具结果 > 历史）精算出 `includedHistory`，
但主链路**只取了 `isWithinBudget()`** 做通过/拒绝判断，裁剪结果整个扔掉。
全仓 grep 确认 `getIncludedHistory/Evidence/ToolResults` **零调用点**。

真正生效的只有 LangChain4j `MessageWindowChatMemory` 的**按条数**截断（20 条）。

**二者不等价，已量化**：

```
CHARS_PER_TOKEN=1.5，窗口 32000，预留 1500 + system 800 → 可用 ≈ 29700 token

单条  500 字符 →   333 tok → 20 条 =   6667 tok  ✅
单条 2000 字符 →  1333 tok → 20 条 =  26667 tok  ✅
单条 5000 字符 →  3333 tok → 20 条 =  66667 tok  ❌ 溢出 2.2 倍
单条 8000 字符 →  5333 tok → 20 条 = 106667 tok  ❌ 溢出 3.6 倍
```

运维场景贴一段 5000 字符的日志/堆栈**很常见**。溢出后由模型侧静默截断，
被切掉的往往是最早的关键前提，表现为「AI 忘了前面说过的约束」。
另已确认 `HotMemoryStore` 与 `TtlChatMemoryStore` 都**没有长度兜底**。

### 缺陷 2：温记忆从未进入模型

`loadContext` 从 PostgreSQL 查出跨会话关键事实后，只拼进一个
用于预算计算的局部变量，而 `engine.chat(sessionId, query)`
**只带会话 ID 与当前问题**。

三层记忆的「温层」在读取侧空转：用户上一轮确认过的环境信息
（集群名、版本、已排除的原因）在窗口滚动出去后彻底丢失，
AI 会重复追问已经回答过的事。

### 为什么这两件事长期没被发现

**都没有任何报错**。窗口溢出看起来像「AI 忘事」，温记忆丢失看起来像
「AI 重复提问」——两者都像「模型不太聪明」而非系统缺陷，
排查方向会跑到提示词工程上去。

### 修法要点

- 采纳裁剪结果，并在裁剪发生时记 INFO（此前连日志都没有）；
- 新增 `buildPromptWithMemoryAnchor`，把关键事实以「记忆锚点」前缀
  拼进 userMessage。**不改接口签名**：LangChain4j 的 `@SystemMessage`
  是编译期常量，无法按会话动态注入；
- 锚点自身限长 **1200 字符**（约 800 token，占 32k 的 2.5%）——
  不设上限等于把「防溢出」的口子重新开在这里，而温记忆会随轮次累积增长；
- 锚点显式标注**「非本轮提问内容」**：不加说明模型会把它当成用户刚说的话，
  复述「你刚才说集群是 prod-a」——而用户这轮根本没提。
  这类幻觉很隐蔽，**内容是对的，只是归因错了**。

## 三、一个测试盲区，以及它暴露的普遍问题

注入验证时把 `engine.chat(sessionId, promptWithMemory)` 改回
`engine.chat(sessionId, query)`——**即本次修复的缺陷本身**——
锚点拼装的那批用例**全部照常通过**。

它们只测了拼装函数，**没人验证拼装结果有没有被真正用出去**。

而「函数写好了却没接上主链路」恰恰是本轮两个缺陷的共同形态。
只测纯函数，会让同样的错误再犯一次而测试全绿。

已补两条源码级接线断言（`engine.chat` 必须传拼装后的值、
主链路必须消费 `getIncludedHistory()`），重新注入后确认能抓到。

> **沉淀判据**：给「计算 + 应用」两段式的机制写测试时，
> 除了测计算是否正确，还必须测**计算结果有没有被应用**。
> 前者是纯函数测试，后者是接线测试，缺一不可。

（另修一处会导致假阳性的写法：注释里为说明「此前是怎么错的」正好
写了反例字面量，`doesNotContain` 会恒假。本地预跑时实测撞到并修正。）

## 四、仍存在的两个缺口（未修，附方案与判断）

### 缺口 A：熔断统计与 Agent 会话状态是**单实例内存态**

```java
// ToolRuntimeManager
private final Map<String, CircuitBreakerStats> circuitBreakers = new ConcurrentHashMap<>();

// AgentStateManager（类注释自承）
// 生产环境应持久化到 Redis/PostgreSQL，此处用内存演示
private final Map<String, SessionState> sessionStates = new ConcurrentHashMap<>();
```

对照：**工具幂等已经走 Redis**（`SET NX EX`，跨实例生效）。
也就是说同一套治理体系里，幂等是分布式的，熔断和状态却是单机的。

**多实例部署下的实际后果**：

| 场景 | 现象 |
|------|------|
| 实例 A 熔断了某工具 | 实例 B 毫不知情，继续打爆下游 —— 熔断保护被稀释为 1/N |
| 会话被 LB 路由到另一实例 | 状态机从 NEW 重新开始，`WAITING_APPROVAL` 等中间态丢失 |
| 实例重启 | 所有在途会话状态归零 |

**为什么本轮不改**：这是**部署形态决定的**问题。当前是单实例部署，
改造要引入 Redis 状态机 + 分布式熔断器，涉及状态迁移的原子性
（CAS 或 Lua 脚本）与 Redis 不可用时的降级策略，
是一次独立的架构改动，不适合夹在缺陷修复里做。

**建议方案（按投入排序）**：
1. **最小改动**：会话状态与熔断统计迁到 Redis，
   状态迁移用 Lua 脚本保证「读-判-写」原子性；
   Redis 不可用时降级为内存态并记 WARN（**失败方向朝可用**，
   因为状态机本身不是安全边界）；
2. **配套**：给 `AgentStateManager` 加 `stateStore` 接缝
   （沿用本项目 `Notifier` / `Retriever` 的可插拔范式），
   内存实现与 Redis 实现并存，按配置切换——单实例部署无需付出 Redis 往返代价；
3. **验收**：契约测试遍历两种实现，断言「状态迁移在并发下不丢更新」。

### 缺口 B：冷记忆归档只存摘要，不含对话原文

`ColdMemoryArchiveScheduler` 的类注释已如实写明这个边界，
并在归档 JSON 里用 `contentScope: SUMMARY_ONLY` 显式标注——
**这是好的做法**（防止日后有人拿归档当完整对话记录用）。

根因是热记忆 Redis TTL 仅 120 分钟，而归档窗口按天计，
执行时原文早已过期。

**建议**：若将来需要全量对话回放（合规审计、模型评测取数），
需让对话主链路把原文**旁路转写**到持久层。
这会触及 SSE 主流程，属于独立需求，当前不做是合理的取舍。

## 五、已确认完好、无需改动的机制（避免重复排查）

- **工具调一半失败怎么回滚**：`SagaCompensationManager` 逆序回滚
  （`step_seq DESC`）+ 单步失败不中断整批 + 补偿失败升级
  `MANUAL_INTERVENTION_REQUIRED` + 人工介入看板。本项目已为它补过
  21 例测试并修过「单步异常中断整批」的真缺陷（75 号报告）。
- **工具失败怎么处理**：按 `ToolFailureType.isRetryable()` 分类重试
  + 指数退避 + 超时控制 + 熔断（单机，见缺口 A）+ Redis 幂等。
- **并发写冲突**：8 个仓储用乐观锁，`moveCategory` 甚至有
  「读时比对 + UPDATE 影响行数」双重检查（76 号报告已补测试）。
- **定时任务多实例重复执行**：5 个 `@Scheduled` 全部有幂等保护，
  `ColdMemoryArchiveScheduler` 的 `markArchived` 带 CAS 条件（80 号报告已核）。
