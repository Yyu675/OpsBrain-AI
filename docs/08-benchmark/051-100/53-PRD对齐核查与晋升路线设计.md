### 这件事本身就是最该修的「缺陷」

PRD 是团队对齐用的唯一文档。现在它把**已经做完的七项**写成待做，
后果不是文档不好看，而是：

- 有人会照着 PRD 去「实现」告警接入，写出第二套 `AlertService`；
- 排优先级时会把资源投到已完成的事情上；
- 对外汇报「我们还在 L1.5」，而实际能力已明显超出。

**我的第一条建议：先修 PRD，再谈新功能。** 这是本轮成本最低、收益最高的一步。

## 二、真实的成熟度定位：不是 L1.5，是 L2.5

PRD 自评 `L1.5`。按它自己引用的四层模型逐条对照实际代码：

| 层级 | 判据 | 实际 |
|---|---|---|
| L1 智能监控 | 自动发现 + 阈值告警 | ✅ Alertmanager Webhook 接入 |
| L2 关联分析 | 告警压缩 + 噪音抑制 | ✅ dedupKey 去重 + occurrenceCount 聚合 |
| L3 根因定位 | RCA + 传播路径 | ⚠️ **半个**——有 RCA 记录闭环（confirmRootCause / 复盘文档），无因果推断与传播路径 |
| L4 自动化闭环 | 工作流自动化 + 自动修复 | ⚠️ **治理骨架齐全，执行器为零** |

**准确定位：L2.5。** 说 L1.5 低估了两个档位。

而 L4 的状态最值得说清楚——这是上一轮我实测的结论，本轮复核仍然成立：

> 策略引擎、动作白名单、风险分级、审批链、Saga 补偿**全部实现且有测试**，
> 但 `DevOpsTools` 里**只有 2 个 `@Tool`**：检索知识库、创建工单。
> 全仓无 kubectl / K8s client / ssh 调用。
>
> **方向盘、刹车、安全带都装好了，还没装发动机。**

## 四、可行性设计建议（按投入产出排序）

### P0 · 文档对齐（0.5 天，纯收益）

1. 重写 `docs/PRD.md` 的 §三覆盖度表与 §5.2 路线图，按本文第一节的实测结果
2. 成熟度自评 L1.5 → L2.5
3. 把「已完成」与「未完成」用**代码位置**佐证，而不是状态标记——
   状态标记会再次过时，代码引用不会

> **可行性**：无技术风险。**唯一注意**：不要顺手把 PRD 的历史叙述删掉，
> 那些「为什么这么定」的判断（如「不盲目追监控接入」）仍然成立且有价值。

### P1 · Saga 补偿中心前端落地（2-3 天）

后端已就绪，只缺页面。设计要点：

- **列表页**：`/saga/attention` 的三类记录（PARTIAL_SUCCESS /
  COMPENSATION_FAILED / MANUAL_INTERVENTION_REQUIRED）分组展示，
  高亮 `businessKey`（用户真正关心的是"哪条数据坏了"）
- **详情页**：`/saga/{id}/steps` 渲染成执行链路时间线，
  失败步骤标红并展示 `errorMessage` + `failureHint`
- **补偿按钮**：调 `POST /saga/{id}/compensate`。**必须二次确认**，
  且沿用 ApprovalCenter 那套**串行化**（一次只允许一个补偿在跑）——
  逆向补偿会回滚已落库的写操作，并发下发同样不可预测

> **可行性高**：接口、鉴权、测试后端全有。前端可直接复用
> `ApprovalCenter` 的交互骨架（我上轮刚为它补了 22 例测试，模式已验证）。

### P2 · 可观测性（3-5 天，路线 B 的前置）

这一条**不是可选项**。当前系统能监控别人，却监控不了自己：
pom.xml 无 actuator、无 micrometer。

在补齐之前，「自动化执行是否安全」这个问题**无法回答**——
你连它做了什么、耗时多少、失败率多高都看不见。

最小集：
- `spring-boot-starter-actuator` + `micrometer-registry-prometheus`
- 暴露 `/actuator/health`（K8s 探针）与 `/actuator/prometheus`
- **自定义指标优先埋这三处**：工具调用耗时与失败率、
  Saga 补偿成功率、LLM 调用成本与 token 数
- 健康检查要含 **DeepSeek 可达性**与**向量库可达性**——
  这两个挂了系统表面正常、AI 全废

> **注意一个坑**：`/actuator/**` 默认不在 `/api/**` 之下，
> 不会被 SaInterceptor 拦截。必须显式配置，否则等于把内部指标裸奔在公网。
> 这正是本项目 `WebConfig` 已有拦截器配置需要同步修改的地方。

### P3 · Flyway 接管 27 个手工 SQL（2-3 天）

现状：`sql/` 下 27 个 `migration_v*.sql`，**无版本表、无自动执行**。
换台机器部署要人肉按顺序跑，漏一个就是运行期字段不存在。

设计要点：
- 用 `flyway.baselineOnMigrate=true` + `baselineVersion` 接管**已有库**，
  不要试图让老库从 v1 重放
- 现有文件名 `migration_v11_xxx.sql` 需重命名为 `V11__xxx.sql`
- **prod 环境务必 `flyway.cleanDisabled=true`**（默认就是，但要显式写）

> **风险提示**：这是唯一一条**动了会影响现有部署**的建议。
> 建议先在 dev 环境验证 baseline 接管，确认 `flyway_schema_history`
> 生成正确后再推 prod。

### P4 · 路线 B 最小切口：一个只读工具（1-2 周）

**不建议一上来接 K8s 写操作。** 先用只读动作把治理链路跑通：

```
新增 @Tool: queryPodStatus(namespace, podName)
  ↓ 策略引擎匹配（AutomationPolicy）
  ↓ 白名单校验（ActionAllowlistEntry）
  ↓ 风险分级 → READ_ONLY，免审批
  ↓ 执行 → ToolExecutionRecord 记录
  ↓ 无副作用，无需补偿
```

**为什么从只读开始**：现有的 `ToolExecutionRecord`、
`SagaCompensationManager` 至今**只被「创建工单」一个场景验证过**。
先让只读动作把链路走通，再上有副作用的。

**待你拍板的关键决策**（上一轮我问过，这里再明确一次）：
第一个执行器接哪类目标系统？

| 选项 | 凭证管理 | 适合场景 |
|---|---|---|
| K8s（fabric8 client） | ServiceAccount + RBAC，最规范 | 容器化环境为主 |
| 云厂商 API | AK/SK 轮转，需 KMS | 多云/混合云 |
| 内部脚本平台 | 复用现有鉴权，最省事 | 已有成熟运维平台 |

这个选择决定执行器抽象与凭证层设计，我不替你默认。

## 五、明确不建议做的事

| 事项 | 理由 |
|---|---|
| 相似工单改向量检索 | PRD 自己写了「过度工程化」陷阱。同服务筛选够用，且 `HybridRetrieverService` 已有向量能力，真要改是接线不是造轮子——但收益低于 P1~P3 |
| 自愈任务 5 个页面 | 后端零实现，做出来还是壳 |
| 智能派单 | 需要历史处理数据训练，当前数据量不足以支撑；且 PRD 的「按需渐进」原则适用 |
| 继续大规模补前端测试 | 300 行以上含业务逻辑的页面**已全部覆盖**（1613 例），边际收益明显下降 |
