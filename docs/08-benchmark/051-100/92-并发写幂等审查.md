## 二、缺陷：守卫有了，但返回行数被丢弃

### 成因

`require(id)` 只读取当前状态，它与后续 UPDATE 之间存在**先查后写窗口**。
PostgreSQL 默认 READ COMMITTED，并发的 `delete`/`merge`
可以在这个窗口里把标签置成 `DELETED`/`MERGED`。

`rename` 的问题最隐蔽——**它的守卫是对的，错在没看返回值**：

```java
jdbcTemplate.update("... WHERE id = ? AND status = 'ACTIVE'", ...);  // 返回值被丢弃
jdbcTemplate.update("UPDATE sys_knowledge_doc_tag SET tag = ? ...");  // 无任何守卫
```

竞态发生时：

1. 第一条更新 **0 行** —— 标签本体没改名，符合预期；
2. 第二条**照样执行**，而它没有任何状态守卫 ——
   把全库文档上的旧标签名批量改成了新名字。

### 用户可见后果

标签管理页里这个标签还是旧名（或已消失），而所有文档上挂的却是新名。
两者对不上之后，**按标签检索文档会一条都搜不到**——
文档上的 `tag` 值在标签表里根本不存在。静默数据损坏，没有任何报错。

`delete` 那处是另一种形态：走 merge 分支后 `merge` 已把状态置为 `MERGED`，
随后被**无条件**覆盖成 `DELETED`。两种状态语义不同
（合并可追溯到目标标签，删除不可），覆盖后审计上再也看不出
这个标签是被合并走的。

### 真实 PostgreSQL 验证

沙箱无 Docker，但 `pgserver` 能起真库。实测：

```
带 ACTIVE 守卫的 UPDATE 影响行数 = 0        -> 修复后在此抛错终止
旧行为下第二条 UPDATE 影响行数 = 2          <- 文档标签被改写
标签表: ('K8s', 'DELETED')
文档上的标签: ['Kubernetes']
>>> 指向不存在标签的文档关联数 = 2          (按标签检索会一条都搜不到)

delete 覆盖场景：
旧行为(无守卫): MERGED 被覆盖 -> DELETED
修复后(带守卫): 影响行数=0, 状态保持 -> MERGED
```

不是推演，是真跑出来的。

### 修复（三处）

| 方法 | 改动 |
|---|---|
| `rename` | 第一条 UPDATE 检查行数，0 行抛错终止，**第二条根本没机会执行** |
| `merge` | 状态闸门加 ACTIVE 守卫，并**上移到改写文档之前** |
| `delete` | 走 merge 分支后直接 return；纯删除分支加守卫并检查行数 |

**`merge` 的闸门上移是关键**：放在最后的话，两个并发 merge 都会先把
文档改写一遍才发现冲突，那时数据已经被动过了。闸门在前，后到者 0 行即抛错回滚。

## 三、注入-还原验证

| 编号 | 注入 | 结果 |
|---|---|---|
| R1 | `rename` 丢弃行数检查（还原旧行为） | 🔴 `Expecting code to raise a throwable` |
| R2 | 仍抛错，但把文档改写**挪到抛错之前** | 🔴 `Never wanted here: update(contains("UPDATE sys_knowledge_doc_tag")) But invoked here` |

**R2 是这轮最关键的验证**。它证明核心断言 `verify(never)` 不是摆设：
只验「抛了异常」的测试会让 R2 溜过去，而 R2 恰恰是要防的数据损坏形态。

> 有人会说事务会回滚，所以 R2 无害。不对：
> **依赖回滚兜底与从不发生错误写入是两个安全等级**，
> 且 `merge` 里的闸门顺序问题无法靠回滚解决——
> 两个并发事务各自回滚不了对方已提交的改写。

## 四、把规则固化为契约

`StateTransitionGuardContractTest`（2 例）守住
「状态流转 UPDATE 必须带前置状态守卫」。

### 扫描器第一版有 bug —— 记录以免后人重犯

守卫正则最初只认 `AND status`，把 `markExpired` 的
`WHERE status = 'PENDING'` 误判成无守卫，报出「1 处缺陷」。
**看起来完全合理**，实际是误报。修正为匹配 WHERE 子句里
`status` 的任意条件（`=` / `IN` / `<>` / `!=`）后误报消失。

> 这印证了那条老判据的另一面：「全中或全不中时先怀疑扫描器」——
> 但**结果看着合理时也该怀疑**。分辨方法只有一个：逐条点开核对。

### 双向自验

- **正向**：8 处状态流转全部有守卫，`unguarded` 为空；
- **反向**：故意去掉 `KnowledgeTagRepository` 的守卫，立刻报出 2 处。

两个方向都做，才能同时排除「恒真」与「恒假」。

### 另两条防误判措施

1. **剥注释后再扫** —— javadoc 里引用 SQL 片段说明设计，不剥会扫进说明文字；
2. **WHERE 子句提取以文本块结束符为界、最多向后 500 字符** ——
   放宽窗口会跨到下一条语句的 WHERE 上（85 号「匹配范围过宽」的教训）。

### 契约测试自身的注入验证

| 编号 | 注入 | 结果 |
|---|---|---|
| S1 | `merge` 去掉 ACTIVE 守卫 | 🔴 主扫描精确报出 `sys_knowledge_tag.status='MERGED' WHERE: WHERE id = ?`，防回退断言同时红 |

## 五、本轮踩的一个坑：CI 红了也不等于产品代码有问题

契约测试第一版的防回退断言按**单行连续文本** `contains` 匹配 SQL，
但产品代码里长 SQL 写成 `"UPDATE ... SET ... " + "WHERE ..."`，
源码中间夹着 `" + "` 与换行缩进，匹配必然落空。CI 因此红了一次。

修法是加 `flattenJavaStrings` 把 `" + "` 折叠掉再匹配。

> 89 号报告写过「CI 红了不等于验证通过」。这次是它的**镜像**：
> **CI 红了也不等于产品代码有问题**——断言写错与产品代码有问题
> 在 CI 上表现完全一样，只能靠读失败详情区分。
>
> 修正后**在本地做了双向验证才提交**（正向匹配、反向去掉守卫后不匹配），
> 不再靠 CI 试错。

## 六、下一步建议修复思路

### 立即可做（下轮首选）：N+1 查询普查

`TicketController` 用 `fillTags` 批量装填避免 N+1，说明团队意识到了这个问题，
但这是**逐个发现**的模式，没做过系统扫描。

**可机械判定的切入点**：列表类方法体内，`for` / `stream().map()` 循环里
出现 `jdbcTemplate.query` / `findById` / `repository.` 调用。
扫描器写法可以复用本轮的方法体截取逻辑（从形参右括号后第一个 `{` 配平）。

预期产出：真有 N+1 的修成批量装填；没有的固化契约，
防止后人在列表接口里写循环查库。这条规则**适合机械判定**，
契约测试的收益比逐个单测高。

### 中期候选

1. **错误码一致性**。`40001/40004/50001` 在各 controller 里是硬编码字面量，
   语义是否处处一致未经校验。做法：抽出常量类 + 契约测试锁住「不得裸写数字」。
   风险点是改动面广（130 个端点），建议先扫描统计再决定是否动手。
2. **事务边界复查**。本轮发现 `KnowledgeTagService` 的 `@Transactional`
   标注正确（C3 修过），但全仓还有多少 `@Transactional` 标在了
   `private` 方法或自调用路径上（Spring AOP 不生效）——这类缺陷同样静默。
   可机械判定，适合扫描。

### 明确不做

- **给所有先查后写路径加悲观锁（`SELECT ... FOR UPDATE`）**。
  本轮的守卫式修法（状态条件下沉到 WHERE + 检查行数）已经解决问题，
  且是无锁的。改悲观锁会引入锁等待与死锁风险，
  在这个并发量下**代价远高于收益**。理由存档，避免后人反复纠结。
