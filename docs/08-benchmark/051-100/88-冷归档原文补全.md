## 二、解决的问题

三层记忆里热层（Redis）TTL 仅 **120 分钟**，而冷归档按天执行——
归档时原文早已过期。此前冷归档只能存摘要，
并在 JSON 里用 `contentScope=SUMMARY_ONLY` 如实标注。

而合规审计与模型评测取数都需要**逐轮原文**，摘要不够。

### 为什么不延长 Redis TTL 代替建表

对话原文体积远大于摘要（单轮可达数 KB，含日志/堆栈粘贴）。
保留期从 2 小时拉到 90 天，等于把 Redis 当主存储用——
内存成本不可接受，且 Redis 无持久化保证时数据仍会丢。

## 三、三个设计要点

### 1. `contentScope` 据实标注，不写死

```java
boolean hasTranscript = !turns.isEmpty();
payload.put("contentScope", hasTranscript ? "FULL_TRANSCRIPT" : "SUMMARY_ONLY");
```

**存量会话**（本次改动上线前产生的）没有原文记录，取出来是空列表。
一律标 `FULL_TRANSCRIPT` 会让使用者以为「这个会话只聊了 0 轮」，
而实际是原文从未被记录过。

> **得出错误结论，比信息缺失更糟。**

### 2. 轮次序号取自原文表自身的 `MAX+1`

不用温记忆的累计轮次：两者是独立写入路径，任一条失败过就会错位。
用错位序号写入会撞唯一键，而 `ON CONFLICT DO NOTHING` 会让它**被静默跳过**。

### 3. 单字段截断到 32K 并显式标注

运维场景常粘贴整段日志。不截断会让单行无限膨胀，
而这张表的用途是审计与评测取数，前 32K 足以还原上下文。
标注是为了避免评测时把「被截断的半句」当成模型输出异常。

## 四、旁路语义（与本项目一贯取舍一致）

| 决定 | 理由 |
|------|------|
| 转写失败只记日志 | 用户已收到回答，不能因存档失败而报错 |
| **单独** try-catch 而非并入既有块 | 转写失败不该让「温记忆已更新」这件已完成的事被日志描述成失败 |
| 工具结果序列化失败仍写问答原文，仅 `tool_results` 置空 | 因次要字段的问题毁掉主要数据不划算 |
| `findBySession` 查询失败记 **ERROR** | 空列表与「该会话真无原文」无法区分，静默返回空会产出一份「看起来完整实则缺失」的归档 |

## 六、本轮的两个教训

### 教训 1：注入时 CI 红了，但红的原因不对

S2 首次注入后 CI 变红，看似验证通过。但查报错是
`bucket name must not be null`——`archiveBucket` 是 `@Value` 字段，
直接 `new` 时为 null，整组用例以**与被测逻辑无关的原因**失败。

**那不算验证通过。** 补上夹具后重验，才拿到真正的
`expected "SUMMARY_ONLY" but was "FULL_TRANSCRIPT"`。

> 判据：注入验证不能只看「CI 红了」，
> 必须确认**红的是那条声称要防住缺陷的断言**。

### 教训 2：归档逻辑此前零测试

S2 第一次注入时（夹具问题之前）CI 是**通过**的——
`contentScope` 这个字段一行测试都没有。

而它一旦标错，错误的归档文件会持续产出，
且没有任何机制会发现：**JSON 结构完全合法**。

已补 `ColdMemoryArchiveScopeTest`（5 例），
反射调 private `archiveOne` 并捕获真正上传到 MinIO 的 JSON 再断言。
