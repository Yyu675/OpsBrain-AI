## 一、本轮补齐：AppNavbar（27 例）

### 为什么选它

`AppNavbar.vue` 769 行，是最大的零测试组件之一，且它**每个页面都渲染**
——这里出问题，影响面是全站而不是某一页。

### 重点一：按角色过滤菜单的定位要先说清

「审批中心」标了 `roles: ['admin']`。

> **这不是安全边界。**
> 真边界在后端（`@SaCheckRole` + 已有的
> `GovernanceRoleGuardIntegrationTest`）——非管理员手输 URL 进去，
> 接口照样返回 403。

把它写清楚是必要的：如果把前端菜单当成安全措施，
就会有人觉得「前端藏起来了所以后端可以松一点」，那才是真正的风险。

但菜单错乱仍是真问题，**两个方向都有代价**：

| 方向 | 后果 |
|---|---|
| 该显示不显示 | 管理员找不到审批入口，高危动作卡在待审队列没人处理 |
| 不该显示却显示 | 普通用户点进去吃一脸 403，分不清是没权限还是系统坏了 |

所以正反两向都测。**只测「普通用户看不到」的话，把整项删掉也能通过**
——那时管理员同样看不到，而测试是绿的。

### 重点二：待审角标只对管理员拉取

该端点限 ADMIN。非管理员若也发请求会得到 403——
既无意义，又在控制台刷错误、掩盖真正的问题。

同时验了**拉取失败降级为 0 且不弹错误**：
角标是增值提示，为它弹红框会让用户以为系统出了大问题（同 6.51 降级策略）。

### 其余几条的实际动机

- **未启用菜单不出现**：`navigationItems` 里有 12 项 `visible:false`
  （L2/L4 规划中能力），漏过滤会让用户点进未实现的页面
- **子路由高亮父级**：在 `/tickets/TKT-001` 时「智能工单」必须仍高亮，
  否则用户以为自己不在这个模块里
- **关闭通知开关后未读数归零**：直接读 `store.unreadCount` 的话，
  关开关等于没关
- **登出必须 `await signOut` 再跳转**：signOut 含后端 logout 调用，
  不等就跳，登录页可能读到尚未清除的 token 而误判为已登录
- **卸载解绑 document click 监听**：不解绑是内存泄漏，
  且回调引用已卸载组件的闭包

## 二、方法改进：注入器加唯一性断言

上一轮出现过「注入打偏」——`formContent.value.trim()` 在文件里出现 5 次，
`replace(..., 1)` 命中的是非目标位置，导致注入没抓到时**误以为测试不严**。

本轮给注入器加了前置断言：

```python
n = s.count(pattern)
assert n == 1, f'PATTERN OCCURS {n} TIMES - ambiguous'
```

模式不唯一直接报错，不会静默改错地方。

这条改进的价值不在本轮（7/7 全抓到），而在于**消除了一类会导致
错误结论的操作风险**：注入验证的前提是「我确实把缺陷注进去了」，
这个前提此前没有被检查。

## 三、CI 排队行为的观察（供参考）

连续两轮出现「推送成功但没生成 run」。本轮确认了原因：

GitHub 在**串行处理**该分支的运行队列。查询时看到的是
`in_progress` 的是上一个 commit，我的提交排在其后。
等前一个跑完，我的会自动开始——**不需要空提交去"催"**。

上一轮我用空提交触发了新运行，事后看那是多余的
（虽然无害，但多了一个无意义的 commit）。
判据是：先看 `actions/runs` 里有没有更早的 `queued`/`in_progress`，
有就是排队，等即可。
