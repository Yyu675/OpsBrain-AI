## 一、这个缺口为什么值得优先处理

`AgentStateManager` 用 `synchronized (session)` 保证
「校验当前态 → 写入新态」的原子性。单实例下这是对的，
**但 `synchronized` 是进程内锁，多实例部署完全失效**。

后果不只是「状态丢失」这么轻。状态机里有一条 `WAITING_APPROVAL` 边，
是高风险工单的**审批闸门**：

```
两个实例同时对同一 traceId 迁移
  → 各自读到相同的 fromState
  → 各自校验通过（canTransition 都返回 true）
  → 后写覆盖先写
  → 「需人工审批」被冲成「草稿就绪」
  → 审批闸门被绕过，且没有任何报错
```

对照之下，同一套治理体系里**工具幂等已经走 Redis**（`SET NX EX`，跨实例生效）。
幂等是分布式的，状态却是单机的——这个不一致本身就是信号。

## 三、接口边界怎么划的

| 决定 | 理由 |
|------|------|
| 只暴露存取与互斥（`get`/`getOrCreate`/`save`/`inLock`） | 状态机规则（哪些边合法、耗时怎么算、审计怎么记）是**业务规则**，不该随存储实现变化，全部留在 Manager |
| 互斥用**回调式** `inLock` 而非暴露 `lock`/`unlock` | 后者把「必须成对调用」的责任推给调用方，一次早返回就漏解锁 |
| 不暴露 Redis key / TTL / Lua 脚本 | 一旦泄漏，换实现时上层照样得改，接口就白抽了 |
| **保留 `save()`**，尽管内存实现是空操作 | Redis 这类**值语义**存储必须显式回写——少了这一步，改动只留在本地副本而其它实例读到旧状态。接口上留着它，才能让这个差异在编码时就被看见 |
| 清理空闲会话按实现类型分支 | Redis 实现会用键 TTL 自然过期。不往接口上加一个只有一种实现用得到的方法 |
| `backend()` 打进启动日志 | **多实例部署却用着 memory 实现是典型配置事故**，而它在单实例测试时完全看不出来——日志是最低成本的提示 |
| Bean 用 `@ConditionalOnMissingBean` | 将来加 Redis 实现时让它以更高优先级注册即可，无需在配置类维护 if-else 实现表 |

### 一处实现细节

`transition` 里 `fromState` / `transition` / `durationMs` 三个局部变量
原先在锁外声明、锁内赋值。改成 lambda 后捕获要求 effectively final，
故引入 `record Outcome` 承载三者一并返回。

## 四、契约测试 11 例（遍历式）

守的是「换存储不会出事」。Redis 实现加进来会**自动纳入**检查——
若逐实现写，新实现接上时没人会想起补测试，
而那恰恰是契约最容易被破坏的时刻（大家关心的是「能存能取吗」，
不会有人去验「并发迁移会不会丢更新」）。

最关键的一条用「读-改-写」计数器验证互斥真能串行化：
8 线程 × 200 次，无锁时必然少算。

## 五、注入验证 3/3

| 注入项 | 检出信息 |
|--------|---------|
| M1 `inLock` 去掉互斥 | `expected: 1600 but was: 776` —— 丢更新的实证 |
| M2 锁粒度改为全局 | `TimeoutException` —— t2 会话拿不到锁而超时 |
| M3 `get` 对不存在的会话顺手创建 | `expected: null but was: SessionState@...` |

M3 值得说明：`get` 返回 null 是 `transition` 判断「会话不存在」的依据。
若顺手 create 一个，**非法迁移会变成合法**——一个早已结束的 traceId
又能重新走一遍状态机。

M2 也不只是性能问题：锁全局会让所有并发会话的状态迁移排队，
症状是「AI 响应整体变慢」，很难联想到是状态机的锁粒度。

## 六、下一步：Redis 实现要注意什么

接缝已就位，加实现时需处理三件事（写在这里避免届时重新踏坑）：

1. **状态迁移的原子性**：`inLock` 内是「读 → 判 → 写」，
   分布式锁必须覆盖整段。若用 Redisson 可重入锁，注意
   状态迁移过程中可能间接触发另一次迁移（接口约定 1 已写明）；
2. **Redis 不可用时的降级方向**：建议**降级为内存态并记 WARN**，
   而不是拒绝服务。状态机本身不是安全边界
   （真正的安全边界是审批表与 `@SaCheckRole`），
   失败方向应朝可用；但降级期间多实例一致性丧失，必须留下明确日志；
3. **`SessionState` 的序列化**：它含 `List<AgentStateTransition>` 迁移历史，
   会随会话增长。建议只序列化当前态 + 最近 N 条迁移，
   完整轨迹另走审计表——否则单个 key 会无界膨胀。
