## 第一部分：本轮修复

### 审查结论：10 处吞异常，8 处对、2 处错

`ToolExecutionRepository` 的 10 个方法**全部** `catch (Exception) 后返回兜底值`。
逐个核实后：

- **8 处是对的**：Saga 审计是旁路能力，让它把主流程带崩没有意义
  （工单已经建好了，不该因为「记录这次建单」失败而报错），且都有日志；
- **2 处是真问题**：它们连一行日志都没有。

### 缺陷 1：`findNeedingAttention` 静默返回空列表

它是**「需人工介入」看板的唯一数据源**（`SagaController#/attention`）。

查询失败时接口照常返回 `count: 0` 的**成功响应**，
运维看到「无待处理项」会认为系统健康——
而空列表与「真的没有脏数据」在界面上**完全无法区分**。
此时库里可能正躺着一批补偿失败的记录无人处理。

**修法**：补 ERROR 级日志（不是 WARN——看板失明是需要立刻知道的事）。
兜底值仍保留空列表，不改抛异常：看板是旁路，不该带崩整个页面。

### 缺陷 2：`nextStepSeq` 静默兜底返回 1

`step_seq` 决定 Saga 补偿的**逆序回滚顺序**
（`findCompensableBySagaDesc` 按 `step_seq DESC` 排序）。

兜底为 1 会让同一 Saga 内出现**重复序号**，回滚顺序退化为不确定——
后执行的步骤可能先于其依赖的前序步骤被撤销。

**修法**：兜底本身是对的（登记记录不该因取不到序号而中断），
补 WARN 日志并在 javadoc 写明后果，让它可被发现。

### 配套测试 11 例 + 注入验证 3/3

| 注入项 | 检出信息 |
|--------|---------|
| H1 看板漏查 `COMPENSATION_FAILED` | 捕获实参里找不到该状态 |
| H2 `insert` 失败返回 0 而非 null | `expected: null but was: 0L` |
| H3 `nextStepSeq` 改为抛出 | 单独注入确证（遵守注解上限 3 条规则） |

H2 那条值得说明：`insert` 失败必须返回 **null 而非 0**——
id 是后续所有状态流转的句柄，拿到假的 `0` 会让 `updateState(0, ...)`
静默更新不到任何行，表现为「Saga 步骤永远停在 PENDING」。

### 又踩一个 varargs 的坑

`findNeedingAttention` 那条用例首次 CI 报
`Expecting ArrayList: [] to contain: ["PARTIAL_SUCCESS"]`。

真因：`jdbcTemplate.query(sql, rowMapper, a, b, c)` 是 **varargs 重载**，
`ArgumentCaptor.capture()` 放在 varargs 位置时只捕获匹配那一次调用的单个槽位，
`getAllValues()` 实测拿到空列表——**断言恒假**。
改用 `thenAnswer` + `inv.getArguments()` 读展开后的完整实参。

这与上轮「断言落在调用次数而非参数值」同源：
断言要落到会被改错的那个值上，**前提是先确认自己真的拿到了那个值**。
