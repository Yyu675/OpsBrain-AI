## 一、核查范围与结论

全仓 74 个 `@Value` 默认值逐个过。**2 处真问题，其余判定可接受。**

判定方法不是「这个默认值好不好看」，而是设想一个最常见的场景：
**运维照着 README 起了服务，一个环境变量都没设**，此时系统处于什么状态。

## 二、缺陷 1：种子管理员初始密码被明文打进日志

```java
log.warn("已创建种子管理员 | username={} | 默认密码={} ...", seedUsername, seedPassword);
```

### 为什么这不是「日志难看」而是真漏洞

- 日志会被采集到 ELK / 对象存储 / 监控平台，
  **这些系统的访问面通常远宽于数据库**——一个只有看板权限的人也能搜到管理员密码；
- 日志一旦归档就**收不回来**。即便运维事后改了密码，
  历史记录仍然有效地泄露了「这套系统的初始密码是什么」，
  而多数部署根本不会改。

### 为什么没有简单地把日志删掉

删掉之后本地开发起不来会不知道密码，这会逼着下一个人再把它加回来。

折中方案：**按「是否仍在用内置默认密码」分支**

| 情形 | 日志 |
|------|------|
| 用的是内置默认密码 | WARN 提示「当前使用内置默认密码，生产必须用 `AUTH_SEED_PASSWORD` 覆盖，默认值见 README」 |
| 用了自定义密码 | INFO「密码取自 AUTH_SEED_PASSWORD」——不提内容，部署方本就知道自己设了什么 |

可发现性保住了，密码没进日志。

## 三、缺陷 2：生产 profile 未收紧种子账号

默认配置是 `seed.enabled=true` + `password=admin123`。

**生产部署若没设 `AUTH_SEED_PASSWORD`，启动即自动建出
用户名 admin / 密码 admin123 的管理员**——一个在源码里公开可查的弱口令，
且拥有全部权限。

### 修法的取舍

没有在 prod 里写死 `enabled: false`：那样全新部署会因为**没有任何用户**
而完全登录不进去，运维只能手工插库——这会让人干脆把开关改回 true，
反而更糟。

改为保留建号能力，但密码必须由环境变量提供：

```yaml
password: ${AUTH_SEED_PASSWORD:__MUST_SET_AUTH_SEED_PASSWORD__}
```

未提供时这个占位串会被 BCrypt 编码成一个**无人知晓的哈希**，
等效于「账号存在但登不进」，再由运维走改密流程。

> **失败方向朝「登不进」而不是「谁都能进」。**

## 四、判定「可接受、不改」的几处（记录理由避免重复排查）

| 配置 | 默认值 | 为什么可接受 |
|------|--------|-------------|
| `security.cors.allowed-origins` | `*` | 已有 WARN 且注释写明是本地开发权衡；`docker-compose.yml` 留了 `CORS_ALLOWED_ORIGINS` 注入口 |
| `alert.webhook.secret` | 空 | 未配时放行但**首次即告警**，且限流仍生效。若默认拒绝，装完就收不到任何告警——对运维平台不可接受 |
| `ai.health.ai-model-enabled` | `false` | 付费探测默认关，防被匿名刷接口造成成本失控 |
| `storage.attachment.allowed-extensions` | `log,txt,json` | 白名单制，默认最小集 |
| `storage.minio.presign-expiry-seconds` | `300` | 5 分钟，偏紧 |
| `schema.fail-fast` | `false`（prod 覆盖为 true） | 开发环境常带半旧库调试，生产已在 prod profile 收紧 |

这些的共同点是：**默认值已经偏安全侧，或虽宽松但有明确告警 + 注入口**。

## 五、注入验证 3/3

| 注入项 | 检出信息 |
|--------|---------|
| N1 密码退回明文进日志 | `Expecting empty but was: ["log.warn(...seedPassword)"]` |
| N2 prod 固化 `admin123` | 两条断言同时失败（含 admin123 / 缺 AUTH_SEED_PASSWORD） |

还原后 `git diff fee5874 HEAD` 为 **0 行**。

### 测试设计上的两个要点

1. **逐行检查而非整文件检查**。断言「文件不含 `seedPassword`」是错的——
   `encodePassword(seedPassword)` 是必须保留的正常用法。
   正确做法是只筛 `log.` 开头的行；
2. **加一条反向断言**防「为了让测试通过把功能删掉」：
   验证 `encodePassword(seedPassword)` 仍在。

## 六、又一次本地预跑救回的假阳性

写完测试**先在本地跑了一遍断言逻辑**，第 6 条 FAIL。

原因：注释过滤器只剔了 Java 风格（`//` `*` `/*`），
而我在生产配置的 **YAML 注释**里正好写着「默认密码是 admin123」的说明文字，
导致 `doesNotContain("admin123")` 恒假。补上 `#` 的过滤后通过。

这已是连续第三次靠本地预跑拦住假阳性（前两次：`@PreDestroy` 全限定名匹配不到、
`engine.chat` 反例字面量写在注释里）。三次成因不同，但都印证 AGENTS.md 3.9 那条：

> **扫描/断言的匹配方式本身，也需要先验证一次。**
