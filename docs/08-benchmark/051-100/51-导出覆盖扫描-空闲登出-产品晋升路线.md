## 第一部分：本轮执行的修复

### 1. 新增导出覆盖扫描（第五类扫描）

**动机**是上一轮暴露的统计口径缺陷：

```
useServerPagination.test.ts 有 46 例，
但全部打在 useServerPagination 上，
同文件导出的 useServerPaginationFrom 一例都没有。
```

而那个变体只在两个页面被用到，那两个页面当时也没测试——
分页缺陷正好落在交叉盲区里。

**「这个文件有测试」不等于「它的每个导出都被测了」。**
按文件统计会把这类缺口完全掩盖：`useServerPagination.ts`
在任何口径下都是「已覆盖」的文件。

新增 `tools/audit/scan_export_coverage.py`，粒度落到**导出符号**。
134 个值导出中报出 16 个未被任何测试引用，已接进 `run_audit.py`。

#### 设计上的两个取舍

**只扫逻辑层**（composables/utils/stores/api/utils）。不含 `.vue`
（被测形态是 mount 不是 import 符号）、不含 api/services
（测试里普遍 `vi.mock`，import 的是 mock 不是实现，统计只会产生假阴性）。

**判据宽松**——用「符号名作为完整单词出现」而非解析 import 语句。
测试里存在 `import * as` 与 `importActual` 两种写法，严格解析会漏掉。
本扫描的目的是找出**确定没人碰过**的导出：漏报可接受，
误报会让清单失去可信度。

### 2. 顺藤摸瓜删掉一处死代码

`ASSIGNEE_FALLBACK` 被报出后，全仓 grep 发现它**连生产代码也没人用**。
它记录的兜底意图（名录拿不到时至少留「待分配」）早已由
`assignees` computed 实现（无条件在末尾补 `UNASSIGNED`）。

留着的坏处不是占地方，而是下一个人会以为「兜底逻辑在这个常量里」，
改它却毫无效果。

### 3. 补 39 例，挑承重最狠的三组

| 组 | 例数 | 为什么优先 |
|---|---|---|
| authToken 三兄弟 | 14 | 认证核心：登录/会话恢复/登出/每个请求的 satoken 头 |
| 跨标签页同步 | 7 | chat store 真实依赖，自收消息会回滚正在输入的内容 |
| 空闲登出计时器 | 18 | 消费方 App.vue 无测试，控制的是自动登出 |

**authToken** 真正守的不变量是「内存与 localStorage 双写一致」：
实现为支持隐私模式做了内存优先+存储兜底，前提是 clear 时两处都清干净。
只清存储漏了内存 → 登出按钮点了人还在登录态；
只清内存漏了存储 → 刷新后又登录了。

**空闲登出**两个方向的失效都很难在开发时发现：
该登出没登出（运维离开工位，而这系统能重启 Pod、回滚发布）、
误登出正在操作的用户（写复盘时被踢，未保存内容全丢）。

### 4. 基线：逐条核对，不一刀切

剩余 9 条没有批量接受，而是逐个查了消费方及其测试状态：

- **间接覆盖 4 条** —— 扫描器已知假阳性。如 `useTicketActions`
  的全部返回值由 `TicketDetail.actions.test.ts` 的 28 例直接断言，
  扫描器只看 import 看不到这层
- **确属缺口 4 条** —— 如实记账并写明风险与优先级，
  不顺手写浅测试凑数
- **不适合单测 1 条** —— `THEME_INIT_SCRIPT` 是内联进 index.html
  的字符串，测试环境既不执行也无 DOM 可验，断言只能退化成
  「字符串包含子串」，改个变量名就红且抓不到真缺陷

## 第二部分：注入-还原验证

| 批次 | 注入 | 抓到 | 漏网及处理 |
|------|------|------|-----------|
| authToken | 5 | 5 | — |
| 跨标签页同步 | 4 | 4 | — |
| 空闲登出 | 6 | 5 | `warned` 只置位不复位——**首版漏网** |
| 扫描器自身 | 1 | 1 | 注入新导出 → 退出码 1，删除 → 0 |

### 漏网那条的原因值得记下来

原有两条用例是「已警告→操作→onActive 被调用」与
「未警告→操作→不调用」。删掉 `warned = false` 后两条都还是绿的：
前者仍会调用一次，后者初始 `warned` 本来就是 false。

**正确实现与错误实现在这两条上给出了相同答案。**

真实差异在第三个场景：不复位则 `warned` 恒为 true，
之后每一次鼠标移动都再调一次 `onActive`——
而 App.vue 里那是关闭弹窗的动作，会变成高频空调用。

### 扫描器的自我验证

补完 `useIdleTimer` 后，命中数从 10 自动降到 9，
基线里那条已失效的豁免同步删除。
基线自校验的价值在这里体现：修好了却忘了移除，
下一个人会以为那里还有坑。

## 第三部分：产品晋升路线（回答问题 2）

### 先摆事实，不谈感觉

以下都是本轮实测得到的读数，不是印象：

| 维度 | 现状 | 证据 |
|------|------|------|
| 后端规模 | 180 文件 / 873 测试 | `find` + `grep @Test` |
| 前端规模 | 148 文件 / 1550 测试 | vitest |
| **Agent 实际能做的事** | **只有 2 个工具**：检索知识库、创建工单 | `DevOpsTools.java` 仅 2 个 `@Tool` |
| **真实执行器** | **不存在** | 全仓无 kubectl / K8s client / ssh 调用 |
| 自愈能力 | 后端无任何实现 | `find -iname "*healing*"` 为空 |
| 前端占位路由 | 32 个路由中 7 个是 `FutureCapability` 占位 | router/index.ts |
| 数据库迁移 | **27 个 SQL 手工执行**，无版本表 | `sql/` 目录，无 Flyway/Liquibase |
| 自身可观测性 | **无** actuator / micrometer | pom.xml 无依赖 |
| 限流熔断 | 无 resilience4j / bucket4j | pom.xml |

### 这个事实改变了问题的性质

上一轮我问你「自动化阶段是指真执行变更，还是生成方案+人工确认」。
现在实测结果让这个问题有了更清楚的前提：

**治理骨架（策略引擎、动作白名单、风险分级、审批链、Saga 补偿）
是完整且有测试的，但它治理的对象目前只有「创建工单」这一个写操作。**

也就是说：**方向盘、刹车、安全带都装好了，但还没装发动机。**

这不是坏事——顺序是对的。绝大多数同类项目是反过来的：
先能执行，再补治理，然后在某次误操作后重写一遍。

### 三条路线，按「投入 / 风险 / 可交付性」排序

#### 路线 A：巩固为「AI 辅助运维平台」（不做自动执行）

**定位**：Agent 负责检索、诊断、生成方案、建单，人负责执行。
现有的 32 个页面里 25 个已经服务于这个定位。

**要补的**（都是工程债，不是新功能）：
1. Flyway 接管 27 个手工 SQL —— 目前换台机器部署要人肉按顺序跑
2. actuator + micrometer —— 现在这系统能监控别人，却监控不了自己
3. 前端 7 个占位页要么实现要么从导航里摘掉 —— 点进去是空页面

**风险**：低。**周期**：短。**可交付性**：这是唯一现在就能对外的形态。

#### 路线 B：半自动化（推荐的下一步）

**定位**：Agent 生成**可执行的变更计划**（不只是文字建议），
人点确认后由平台执行、记录、可回滚。

**关键在于**：这条路线**不需要新建治理体系**，
现有的策略引擎/白名单/审批/Saga 正好是为它准备的。
缺的是执行器本身。

**最小可行切口**：挑一个**只读+低危**的真实动作接进来，
比如「查询 Pod 状态」→「重启单个 Pod（限非生产命名空间）」。
走通一条完整链路：策略匹配 → 白名单校验 → 风险分级 → 审批 → 执行 →
记录 → 补偿。

**为什么从只读开始**：现有的 `ToolExecutionRecord`、
`SagaCompensationManager` 都只被「创建工单」这一个场景验证过。
先用只读动作把链路跑通，再上有副作用的。

**风险**：中，可控。**这是我建议的方向。**

#### 路线 C：全自动化（现在不建议）

**要补的东西远超想象**，而且大部分不是代码：
- 真实执行器 + 凭证管理 + 多集群路由
- 爆炸半径的**实际**计算（现在 `maxBlastRadiusCount` 是个配置数字，
  没有任何代码根据它拦截过真实操作）
- 演练模式必须能真的「演」——目前 `dryRun` 只是不执行，
  不会告诉你「如果执行会影响哪 37 个 Pod」
- 变更窗口、灰度、自动回滚判据
- 以及最难的：**出事之后的责任界定**

**关键判断**：全自动化的门槛不在技术，在于**你能不能接受
它在凌晨三点自己动了生产而没人知道**。在可观测性（路线 A 第 2 项）
补齐之前，这个问题无法回答——因为你连它做了什么都看不见。

### 我的建议：A 与 B 并行，B 只做一个切口

```
第一步（并行）
  A2 可观测性  ← 这是 B 的前置，不是可选项
  A1 Flyway    ← 部署可重复，否则 B 的每次迭代都要人肉跑 SQL

第二步
  B 的最小切口：一个只读动作走通完整治理链路

第三步（视第二步结果决定）
  低危写操作 → 非生产环境 → 生产环境
```

**不建议先做 A3（占位页）**——那是表面功夫。
7 个占位页里有 5 个属于自愈能力，等 B 有了实质内容再实现，
否则做出来的还是壳。
