# 80 · 线程池生命周期专项审查

> 承接 79 号报告列出的两个待审查切面，本轮做「定时任务并发/幂等」
> 与「异步执行器」两项，实际修复集中在后者。

## 一、先说没找到问题的部分

审查的价值一半在于**确认哪些是好的**，避免下次重复查。

### 定时任务（5 个 `@Scheduled`）—— 全部通过

| 任务 | 并发/幂等保护 |
|------|-------------|
| `FirstResponseBreachScheduler` | SQL 带 `response_breached = FALSE AND first_response_at IS NULL`，已标记的返回 0 |
| `KnowledgeRetentionScheduler` | 按 `update_time < cutoff` 判定，处理后 update_time 刷新，同文档不会重复命中 |
| `OrphanChunkCleanupScheduler` | DELETE 本身幂等，无孤儿返回 0 |
| `ColdMemoryArchiveScheduler` | `markArchived` 的 SQL 带 CAS：`WHERE id = ? AND COALESCE(archived, FALSE) = FALSE`，多实例并发时只有一个能成功，另一个记 WARN 供对账 |

`ColdMemoryArchiveScheduler` 值得单独一提：它连「对象已写入但标记未命中 →
成为孤儿对象」这种竞态都想到了，并明确判定为「数据一致性未受损，记 WARN 不算失败」。
**这一项无需改动。**

### 异步执行器的 traceId 传递 —— 逐个核对后无缺陷

项目有 `TraceContext.wrap` 机制，但多处异步提交点没用它。
逐个核实后确认都不是问题，典型如 `OperationAuditInterceptor`：
它在**提交前**就把 `traceId` 取出放进 record，异步体只做 `repository.save`。

## 二、真缺陷：3 个线程池缺优雅停机

`ManagedExecutors` 的类注释里明确写着，它要解决的三个问题之一是：

> **无优雅停机**——4 个池没有 `@PreDestroy`。重新部署时
> 队列里待写的审计、待发的通知**被静默丢弃**。

但**工具类管不住调用方**。审查发现三处要么没迁移到工厂、要么迁了却没配 `@PreDestroy`。

### 1. `OperationAuditInterceptor`（后果最重）

手写 2 线程 + 队列 500 + CallerRuns + daemon，**无优雅停机**。

应用停止时队列里未落库的审计随进程消失，且毫无痕迹。
而审计的用途恰恰是「事后追溯谁在什么时候做了什么」——
**最需要它的场景（发布、重启、故障处置）正是关闭发生的时刻**。

改用 `ManagedExecutors.forCriticalWrites`（语义与手写版完全一致）+ `@PreDestroy`。

### 2. `DingTalkNotifier`

用 `Executors.newSingleThreadExecutor` —— 内部是**无界队列**
（容量 `Integer.MAX_VALUE`）。钉钉侧持续超时时任务会无限堆积直到 OOM，
且堆积期间线程池指标一切正常，毫无征兆。

改用 `forBestEffort`：通知丢了只影响体验，不该用 CallerRuns
拖慢告警回调/定时扫描主链路。**与审计池的取舍相反，依据是「丢掉这个任务的代价」。**

### 3. `DocumentIndexer`

同样是无界队列工厂。但这里 `currentDocId` 的 CAS 已保证同时最多一个任务，
**队列实际不会堆积，无界不是真风险**——我没有把它当成 OOM 隐患来报。

真问题是缺 `@PreDestroy`：停机时正在向量化的文档被硬中断，
`index_status` 停在 `PENDING`，而**没有任何机制会自动重试**——
那篇文档就此永远检索不到，而文档列表里它看起来完全正常。

等待时间给 10 秒（其它池 3~5 秒）：单次向量化要调外部 Embedding API，
耗时本就以秒计，给太短等于没等。

## 三、契约测试：让「下次新增线程池」不会再漏

修完三处只解决了当下。真正的问题是**这类遗漏不会有任何报错**，
下一个线程池加进来时同样没人会想起。

新增 `ExecutorLifecycleContractTest`（8 例），两条守规则：

1. **持有 `ExecutorService` 字段的类必须有 `@PreDestroy`**；
2. **禁用三个无界队列工厂**（`newFixedThreadPool` / `newSingleThreadExecutor` /
   `newCachedThreadPool`），跳过注释行——因为多处文档正是在说明「为什么不用它们」。

外加 6 例验证 `ManagedExecutors` 自身行为：
`forCriticalWrites` 一个任务都不丢、`forBestEffort` 提交不阻塞调用方
（两者相反是刻意的）、线程名带业务前缀、队列确实有界、
`shutdownGracefully` 等待在途任务而非立刻中断、对 null 安全。

### 为什么用源码扫描而不是 Spring 上下文

起 `@SpringBootTest` 拿全部 Bean 再反射找线程池，看似更「真」，实则更脆：
依赖数据库/Redis 可用，且只覆盖被容器实例化的类。
而这条契约的本质是**一条编码约定**，用源码扫描表达最直接，也跑得最快。

### 豁免清单只有 2 项，且都写明理由

| 类 | 理由 |
|---|------|
| `ManagedExecutors` | 工具类自身只提供工厂方法，不持有池 |
| `DevOpsAgentServiceImpl` | 用的是虚拟线程 per-task 执行器，无队列无池化线程，关闭它没有意义 |

豁免是最容易被滥用的口子——「加进白名单」不该比「补上 `@PreDestroy`」更省事，
所以每条都要求写理由。

## 四、一个本可以变成假阳性的细节

写完测试后我**先在本地跑了一遍扫描逻辑**，结果报出
`DingTalkNotifier` 和 `DocumentIndexer` 仍缺 `@PreDestroy`。

原因是我给这两个类加的是**全限定名** `@jakarta.annotation.PreDestroy`，
而扫描按字面 `@PreDestroy` 匹配不到。已改为规范导入形式。

这一步若不做，CI 上会报出两个「假阳性」，而我很可能**误以为是产品问题**
再去改一遍产品代码。与 AGENTS.md 3.9 记的三类陷阱是同源问题：
**断言/扫描的匹配方式本身也需要先验证一次**。
