# 87 · 会话状态 Redis 实现（缺口 A 闭环）

> 82 号报告抽出了 `AgentSessionStore` 接缝但没写 Redis 实现，
> 理由是「取决于部署形态」。本轮你确认要做，补齐实现。

---

## 一、解决的问题

`InMemoryAgentSessionStore` 用 `synchronized (session)` 做互斥——**进程内锁**。

多实例部署时两个实例可同时通过同一会话的状态校验，后写覆盖先写。
状态机里的 `WAITING_APPROVAL` 是高风险工单的**审批闸门**，
被冲掉后审批就被绕过，**且没有任何报错**。

---

## 二、三个设计决定

### 1. 显式 DTO，而非直接序列化 `SessionState`

后者的 `traceId` / `sessionId` / `transitions` 是 `final`、无无参构造，
Jackson 反序列化会失败。

但更重要的理由是：**DTO 让「存了哪些字段」变成一处显式声明**。
将来给 `SessionState` 加字段时，不写进 DTO 就不会跨实例可见——
而「本地有、别的实例没有」这种不一致极难排查。

DTO 上加了 `@JsonIgnoreProperties(ignoreUnknown = true)`，
这是为**滚动发布**：新版本加了字段、旧版本实例读到时不应直接崩，
那会让整个会话不可用，而实际只是少了一个它用不上的字段。

### 2. 只持久化最近 50 条迁移轨迹

`transitions` 随会话轮次无限增长。整条存进 Redis 会让单个 key 不断膨胀，
而**每次状态迁移都要完整读写这个 value**——表现为「聊得越久 AI 响应越慢」，
很难联想到是状态存储。

完整审计轨迹本就落在 `sys_agent_tool_execution` 与操作审计表里，
Redis 这份只服务于「当前状态机怎么走」。

### 3. 锁用 `SET NX PX` + 唯一持有者标识，释放走 Lua 原子比对

不带持有者标识的话：

```
A 拿到锁 → A 的锁 TTL 到期自动释放 → B 拿到同一个 key
        → A 执行完调 DEL → 删掉的是 B 的锁 → 两个实例同时进入临界区
```

这正是加锁要防的事。删锁前比对 value 即可避免，
而「比对 + 删除」必须用 Lua 保证原子——分两步做的话，
恰好在比对通过后锁过期、别人拿到锁，同样会误删。

## 三、降级方向：朝可用

Redis 不可用时**回落本地互斥并记 WARN**，而不是拒绝服务。

理由：状态机本身不是安全边界（真正的边界是审批表与 `@SaCheckRole`），
为它牺牲整个对话链路的可用性不划算。
但降级期间多实例一致性丧失，**必须留下明确日志**——
否则这段时间的越权毫无痕迹。

## 四、顺带修正的两处

### `size()` 用了 `KEYS`

`KEYS` 会阻塞 Redis 单线程遍历整个键空间。而 `size()` 只是观测接口，
让它拖慢所有业务请求不可接受。已改用 SCAN，
与 `SemanticCacheService.clearAllCache` 同一范式
（那里的注释早就写明了这个坑）。

### `SessionState` 缺 `setCreatedAt`

构造器把 `createdAt` 置为 `now()`。反序列化时若不还原，
每次跨实例读取都相当于「刚创建」——而 `getIdleSince()`
在从未迁移过的会话上正是回落到 `createdAt`，
于是这类会话**永远不会被判定为空闲**，清理线程一个都清不掉。

表现为：「重启前内存正常，接上 Redis 后会话数只涨不跌」。

已补 setter 并在 javadoc 写明「仅供存储实现反序列化使用，业务代码不应调用」。

## 五、为什么用真实 Redis 而不是 mock

这个类的价值全在**跨进程语义**：`SET NX PX` 的原子性、Lua 的比对删除、TTL。
mock 掉 `StringRedisTemplate` 之后这些全变成「我说它返回什么它就返回什么」——
测的是我对 Redis 的想象，而不是 Redis 的行为。

15 例 `@SpringBootTest` 集成测试，用**两个独立 store 实例**模拟两个进程
（它们之间没有任何共享内存，只能靠 Redis 协调）。

## 六、注入验证：又抓到一个自己写的假测试

| 注入项 | 结果 |
|--------|------|
| R2 `createdAt` 不还原 | 命中（时间被刷新 25 毫秒） |
| R1 释放锁不比对持有者 | **首次未检出** → 加固后命中 |

### R1 为什么没被抓到

第一版用例是「在**另一个 traceId** 上放一把外来锁，验证它没被删」。

但那把锁与 `nodeA` 要删的 key 本就不同，
**不比对持有者的实现同样不会碰它**——根本没构造出竞争。

真正要复现的是**同一把锁易主**。已改为在 A 的临界区内
把锁的 value 改成别人的 token（等价于「锁已易主」，无需真等 TTL 过期），
再验证 A 释放后那把锁仍在。

重新注入 R1，CI 如期变红：

```
[A 收尾时只能删自己那把；删掉接管者的锁会让两个实例同时进临界区]
expected: "token-of-node-B" but was: null
```

> **第五种假断言形态：用例构造的场景与要防的缺陷不是同一件事。**
> 前四种是「断言写松了」，这一种是**前提就搭错了**——
> 无论断言多严格都抓不到。

## 七、如何启用

```yaml
devops:
  ai:
    session:
      store: redis              # 或 AGENT_SESSION_STORE=redis
      ttl-minutes: 60
```

**不做「检测到 Redis 就自动启用」**：项目里 Redis 还承担缓存、限流、幂等，
单实例部署同样连着 Redis，自动启用会白付每次状态迁移的网络往返。
部署形态只有部署方知道，必须显式声明。

当前生效的后端会打进启动日志（`backend=memory` / `redis`）——
「多实例却用着 memory」是一类典型配置事故，而它在单实例测试时完全看不出来。
