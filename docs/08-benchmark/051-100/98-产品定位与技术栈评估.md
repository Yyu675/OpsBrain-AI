# 一、产品定位

## 1.1 当前定位（PRD 自述 vs 代码实测）

PRD 定位为「**下一代 AI AIOps 自治运维中枢**」，用 L1–L5 自治分级做产品框架。
代码实测对照：

| 级别 | 能力 | PRD 声称 | **代码实测** |
|:---:|---|---|---|
| L1 | 辅助问答、查知识、开工单 | ✅ | ✅ **真实可用**（SSE 流式、RAG 检索、工具调用） |
| L2 | 主动感知、自动告警建单、降噪 | ⚠️ | ✅ 主链路完整，**但信号源只有 Prometheus 一种** |
| L3 | 人机协同、审批后执行 | ✅ | ✅ 闭环完整，**但治理对象目前只有「建单」** |
| L4 | 低危自动执行 | ❌ | ⚠️ **治理骨架全齐，执行器只有 K8s 一个且只读** |
| L5 | 端到端自治 | ⏳ | ❌ 未启动 |

**实测口径的准确定位是**：

> **一个 L1–L3 完整落地、L4 骨架就绪的「AI 运维协同中枢」，
> 以「工单 + 知识库 + 告警」三位一体为业务底座，以「治理与审计」为差异化。**

## 1.2 这个定位的优点

**① 治理先行的顺序是对的，而且是罕见的对。**

多数 AI 运维项目的做法是先炫能力（让 AI 直接执行命令），出事后再补管控。
本项目反过来：`sys_approval_request`（审批）、`sys_operation_audit`（审计）、
`sys_risk_policy`（风险分级）、`sys_action_allowlist`（动作白名单）、
`sys_automation_policy`（自动化策略）**五张治理表先于执行器落地**，
配套 19 个治理端点 + Saga 补偿机制。

这符合 Gartner 的判断——2027 年前 40%+ 的 agentic AI 运维项目会被取消，
主因就是**信任与管控没跟上**。先建治理，是把「能不能上生产」这个问题提前解决了。

**② 知识库是真差异化，不是凑数模块。**

`sys_knowledge_*` 六张表 + 15 个端点，做了完整的文档生命周期
（草稿→发布→废弃→归档→物理删除）、版本历史与回滚、近重复检测（simhash）、
父子分块、混合检索。这是监控巨头（Prometheus/Zabbix/Datadog）**不做也不想做**的事。

差异化逻辑成立：**告警平台能被替换，沉淀了三年故障处置经验的知识库不能。**

**③ Agent 工程化程度超出常见水平。**

三层记忆（Redis 热 / PG 温 / MinIO 冷）、上下文预算裁剪、
Saga 工具补偿、成本配额、状态机、四层防幻觉——这些不是 demo 级的堆砌，
每一项都有对应的表、调度任务与契约测试。

## 1.3 这个定位的缺点（必须直说）

**① L4 是当前定位的最大空头支票。**

`OpsExecutor` 接口 + `OpsExecutorRegistry` + `K8sOpsExecutor` 齐了，
但 `K8sOpsExecutor` 实测**只有只读诊断动作**（`queryPodStatus`）。
也就是说：**治理体系管的是一个还不存在的执行能力**。

PRD 把 L4 标为「❌ 执行器为零」是诚实的，但产品叙事里
「受控自愈」占的分量与实际能力不匹配。对企业客户讲这个故事，
第一次 POC 就会被拆穿。

**② 定位过宽，主线有失焦风险。**

PRD 提到 FinOps 商业化、SecOps、混沌工程、CI/CD。
即使 v2.2 已收敛到「FinOps 一个方向」，但当前代码里
FinOps 的实现只有 `sys_agent_call_log` 的成本统计——**是 AI 调用成本，不是云资源成本**。
这两者差着一整个产品。

**③ 多租户是纸面能力。**

27 张表里只有 3 张有 `tenant_id`（`sys_ticket_activity`、
`sys_agent_session_summary`、`sys_agent_conversation_turn`），
且没有任何行级隔离机制。**当前实质是单租户系统。**
这决定了它现在只能私有化部署，不能做 SaaS。

## 1.4 推荐定位（三个方案，附推荐理由）

### 方案 A：**「AI 运维知识中枢 + 智能工单」**（收窄，主推）

把定位从「自治运维中枢」收到「**运维知识资产平台，附带 AI 工单协同**」。

- **优点**：与现有代码 100% 匹配，不需要任何空头支票；
  知识库 + 工单 + 告警建单这条链路是**真跑得通的完整闭环**；
  差异化清晰（监控厂商不做知识运营）；私有化交付即可，无需多租户改造。
- **缺点**：想象空间小，估值故事弱；容易被归类为「工单系统 + 向量检索」。
- **推荐理由**：**现在就能拿去做 POC 且不会被拆穿**。
  企业客户买运维产品最怕「演示能跑、上线两周就发现做不到」，
  而这个定位下每一句话都有代码兜底。

### 方案 B：**「Agentic AIOps 治理平台」**（扬长，次推）

把「治理」本身作为产品——**不卖执行能力，卖「让 AI 敢在生产环境动手」的管控层**。
审批流、风险分级、动作白名单、Saga 补偿、全链路审计，
对接客户已有的自动化工具（Ansible / SaltStack / ArgoCD）而不是自己写执行器。

- **优点**：把最大短板（无执行器）变成**中立优势**——不与客户既有工具竞争；
  治理五表 + 19 端点是现成的；符合 Gartner 对「agentic AI 治理」的判断，故事新。
- **缺点**：需要建执行器适配层（对接 Ansible 等），是新工作量；
  市场教育成本高，客户可能还没意识到自己需要「AI 治理层」。
- **推荐理由**：**技术资产利用率最高**，且避开了「自己写执行器」这个又重又危险的坑。

### 方案 C：维持「L1–L5 自治中枢」（不推荐）

- **缺点**：L4/L5 的实现成本被严重低估。真做受控自愈，
  需要执行器矩阵（K8s/云厂商/中间件/数据库）、灰度与回滚验证、
  故障注入测试——这是一个团队一年以上的工作量，不是补几个类。
- **不推荐理由**：**定位与能力的差距会持续消耗信任**。
  每次演示都要解释「这块还没做」，比一开始就不说更伤。

> **综合推荐：以方案 A 交付、以方案 B 讲演进。**
> 即：当前版本对外定位「AI 运维知识中枢 + 智能工单」，
> 治理能力作为「已就绪的下一阶段底座」呈现，
> L4 明确标注为 roadmap 而非现有能力。

# 二、技术栈评估

## 2.1 后端技术栈实测清单

| 领域 | 选型 | 评价 |
|---|---|---|
| 框架 | Spring Boot 3.5.6 / Java 21 | ✅ 合理。虚拟线程对 SSE 长连接是实打实的收益 |
| AI 编排 | LangChain4j（+ open-ai starter） | ✅ Java 生态最成熟选择 |
| 向量库 | PostgreSQL + pgvector（1536 维） | ✅ **中小规模最优解**，省一个组件 |
| 模型 | 阿里云 DashScope（qwen-plus/max/embedding-v2） | ✅ 国内合规、成本可控；大小模型分流设计好 |
| 数据访问 | Spring Data JDBC + JPA **混用** | ⚠️ 见下 |
| 缓存/会话 | Redis（Sa-Token + 三层记忆热层） | ✅ |
| 鉴权 | Sa-Token 3 + jbcrypt | ✅ 国产轻量，够用 |
| 对象存储 | MinIO | ✅ S3 兼容，可平滑换云 |
| K8s | fabric8 kubernetes-client | ✅ 选型对，但只用了只读能力 |
| 指标 | Micrometer + Prometheus registry | ✅ |
| 实时推送 | WebSocket（告警）+ SSE（AI 流式） | ✅ 分工正确 |

### 后端的三个明确问题

**① JDBC 与 JPA 混用，没有统一口径。**

`pom.xml` 同时引入 `spring-boot-starter-data-jdbc` 与 `data-jpa`。
实测代码里大量手写 `JdbcTemplate` SQL（97 处 `jdbcTemplate.update`），
JPA 只在部分实体上用。**两套 ORM 心智模型并存**，
新人不知道该用哪个，且事务语义容易踩坑（JPA 一级缓存 vs JDBC 直写）。

> 建议：**统一到 JdbcTemplate/JDBC**。理由是本项目 SQL 复杂度高
> （动态查询、向量检索、批量清理），JPA 的抽象反而是负担；
> 且已有 97 处 JDBC 写法，迁移方向应该是去掉 JPA 而非反过来。

**② 没有数据库迁移工具（Flyway/Liquibase 均为 0）。**

当前靠 `sql/init.sql` 幂等脚本 + `*SchemaInitializer` 类在启动时建表。

这在**生产环境是硬伤**：
- 无版本记录，不知道某个环境的库是什么状态；
- 无回滚路径；
- 多实例同时启动可能并发建表；
- 已经出现症状——`KnowledgeTagSchemaInitializer` / `KnowledgeCategorySchemaInitializer`
  两个类在代码里建表，说明 `init.sql` 已经不是唯一真相源了。

> **这是本次评估里优先级最高的技术债。**

**③ 无 API 文档（springdoc/swagger 为 0）。**

130 个端点没有机器可读的接口描述。前后端靠 `backend-contract.json`
（后端测试导出）+ 人工维护的 TS 类型对齐——已经出过事故
（95 号：错误码前后端语义冲突）。

### 前端的两个问题

**① 两套富文本编辑器并存**（`@wangeditor/*` + `md-editor-v3` + `turndown` 转换）。
这是历史选型摇摆的残留，多打包约几百 KB，且两套编辑器的粘贴/图片/XSS 行为不一致。
AGENTS.md 技术债清单里已登记但未处理。

**② 依赖版本非常激进**（Vite 8 / TS 6 / ESLint 10 / Vue Router 5 / knip 5）。
优点是没有历史包袱；风险是**这些大版本在企业环境的生态兼容性未经充分验证**，
出问题时社区答案少。生产交付前建议锁定并做一次依赖审计。

## 2.3 建议补充的技术选型（按优先级）

### P0 — 上生产前必须补

| # | 补什么 | 解决什么问题 | 推荐方案 | 理由 |
|---|---|---|---|---|
| 1 | **数据库迁移** | 无版本、无回滚、多实例并发建表 | **Flyway** | 比 Liquibase 简单，SQL 原生，与现有 `init.sql` 迁移路径最短 |
| 2 | **API 文档** | 130 端点无契约，前后端已出过错 | **springdoc-openapi** | 注解即文档，可导出 OpenAPI 给前端生成 TS 类型，直接消除 95 号那类事故 |
| 3 | **集成测试真实依赖** | 当前 DB/Redis 靠 CI service 容器，本地不可复现 | **Testcontainers** | 让 `@SpringBootTest` 自带 PG+pgvector+Redis+MinIO，测试可信度上一个台阶 |
| 4 | **熔断限流** | 模型 API 抖动会击穿整条链路 | **Resilience4j** | 已有 `SlidingWindowRateLimiter` 自研版，但缺熔断与舱壁；LangChain4j 调用必须有熔断 |

### P1 — 规模化前应补

| # | 补什么 | 解决什么问题 | 推荐方案 | 理由 |
|---|---|---|---|---|
| 5 | **分布式追踪** | 现有 traceId 是自研的，跨服务/跨中间件断链 | Micrometer Tracing + OTLP | 已有 Micrometer，接 OpenTelemetry 增量小；AI 链路排障强依赖它 |
| 6 | **消息队列** | 告警洪峰、异步归档、工具执行都在同步链路上 | RabbitMQ 或 Kafka | 告警风暴时 webhook 同步处理会拖垮建单；执行器落地后更需要异步 |
| 7 | **多租户隔离** | 3/27 表有 `tenant_id`，无行级隔离 | PG RLS 或统一租户上下文 | 决定能否做 SaaS；不做则明确「私有化专用」 |
| 8 | **前端类型生成** | TS 类型手写镜像后端 | openapi-typescript | 与 #2 配套，一次投入长期收益 |

### P2 — 视规模决定

| # | 补什么 | 何时需要 |
|---|---|---|
| 9 | 独立向量库（Milvus/Qdrant） | pgvector 在千万级切片后性能下降时。**现在不要动** |
| 10 | 全文检索（ES/OpenSearch） | 混合检索的 BM25 侧目前靠 PG 全文索引，语料上百万后再说 |
| 11 | 前端微前端拆分 | 30 条路由 / 73K 行，**还没到需要拆的规模** |

> **明确不建议引入的**：
> - **Spring Cloud 全家桶 / 微服务拆分** —— 当前是单体，30 万行以下的单体是优势不是问题。
>   拆了之后分布式事务、服务发现、链路追踪的复杂度会淹没团队。
> - **换掉 pgvector 上专业向量库** —— 现在换等于凭空多一个组件要运维，收益为零。
> - **前端换 React** —— 无技术理由，纯迁移成本。

# 三、业务模块全景

按代码实测梳理，共 **8 大模块 / 130 端点 / 27 表 / 30 路由**。

## 3.1 AI 对话与 Agent 引擎（L1 核心）

| 项 | 实测内容 |
|---|---|
| 端点 | `/api/v1/chat`（2）、`/api/v1/agent/traces`（2）、`/api/v1/sessions`（3） |
| 前端 | `/ai-chat`、`ChatMode.vue`、`AlertStreamMode.vue`、`AgentTraceDrawer` |
| 表 | `sys_agent_call_log`、`sys_agent_session_summary`、`sys_agent_conversation_turn`、`sys_agent_tool_execution` |

**功能**：
- SSE 流式问答（事件：`start`/`token`/`tool_status`/`complete`/`error`）
- 大小模型分流（`DevOpsIntentRouter`：简单问答走 qwen-plus，复杂推理走 qwen-max）
- **三层记忆**：Redis 热层（TTL 120min）→ PG 温层（摘要+关键事实）→ MinIO 冷归档
- **上下文预算裁剪**（`ContextBudgetManager`，窗口 32K，预留 1500+800）
- **四层防幻觉**：输入守卫 → 提示词注入检测 → RAG 强制引用 → 输出校验
- 成本配额（`CostQuotaManager`）、语义缓存
- Agent 状态机（`AgentStateManager` + 可插拔 `AgentSessionStore`：内存/Redis）
- 全链路追踪（traceId 串联 AI 调用与业务操作）

**成熟度**：★★★★☆ 这是全项目最扎实的部分。

## 3.2 知识库（差异化核心）

| 项 | 实测内容 |
|---|---|
| 端点 | 文档 15 + 分类 6 + 标签 5 + 管理 3 = **29 个** |
| 前端 | `/knowledge`、`/knowledge/:id`、`/knowledge/editor/:id` |
| 表 | `sys_knowledge_doc`、`_chunk`、`_category`、`_doc_history`、`_doc_tag`、`_tag`（6 张） |

**功能**：
- 完整生命周期：草稿 → 发布 → 废弃 → 归档 → 物理删除（含保留期调度）
- 版本历史与回滚（`sys_knowledge_doc_history`，乐观锁 CAS）
- **父子分块**（`ParentChildDocumentSplitter`）——检索用子块、喂模型用父块
- **混合检索**（`HybridRetrieverService`：向量 + 关键词）
- 近重复检测（simhash）、内容清洗、指纹去重
- 分类树 + 标签体系（含合并/重命名，本轮 92 号刚修过并发缺陷）
- 孤儿切片清理、向量化失败补偿重试

**成熟度**：★★★★☆ 功能完备度超出多数同类产品。

## 3.3 工单系统（业务底座）

| 项 | 实测内容 |
|---|---|
| 端点 | 工单 37 + 复盘 6 = **43 个**（最大模块） |
| 前端 | `/tickets`、`/tickets/:id`、`/action-items` |
| 表 | `sys_devops_ticket`、`_reply`、`_activity`、`_attachment`、`_tag`、`_ai_analysis`、`_action`、`_postmortem`、`sys_postmortem_action_item`（9 张） |

**功能**：CRUD + 状态机 + SLA（首响超时扫描）+ 回复/活动流 + 附件（MinIO + 安全校验）
+ 标签 + AI 分析 + 处置动作 + **复盘与改进项看板** + 批量操作 + 筛选排序下沉 SQL。

**成熟度**：★★★★☆ 工单本身很完整，**复盘闭环是加分项**（多数工单系统没有）。

## 3.4 告警接入（L2）

| 项 | 实测内容 |
|---|---|
| 端点 | `/api/v1/alerts`（4）+ webhook（1） |
| 前端 | `/alerts`、`/alerts/:id`、`/monitoring`、`/trends` |
| 表 | `sys_alert` |

**功能**：Alertmanager webhook 接入 → 5 分钟去重窗口 → 级别归一化 → 自动建单

# 四、总体结论与优先级建议

## 4.1 一句话结论

> **这是一个 L1–L3 真正跑通、治理体系超前、知识库有差异化的中型运维系统；
> 工程质量（测试、契约、审查）显著高于同类项目；
> 但离「企业级生产可落地」还差三件硬东西：数据库迁移、API 契约、真实执行器。**

## 4.2 优先级路线（建议）

**第一梯队（上生产的门槛，1–2 周）**
1. 引入 **Flyway**，把 `init.sql` + 两个 `SchemaInitializer` 收编为版本化迁移
2. 引入 **springdoc-openapi**，130 端点产出 OpenAPI，前端据此生成 TS 类型
3. 引入 **Testcontainers**，让集成测试自带真实 PG/Redis/MinIO

**第二梯队（可信度，2–4 周）**
4. **Resilience4j** 给模型调用加熔断与舱壁
5. 明确 L4 边界：要么做 **1–2 个真实执行器**（建议先做「重启 Pod + 扩缩容」并全程走审批），
   要么把 L4 从对外叙事里摘掉
6. 决定多租户路线：**做 RLS** 或**明确私有化定位**

**第三梯队（规模化）**
7. 消息队列（告警洪峰 + 异步执行）
8. 分布式追踪接 OTLP
9. 清理两套富文本编辑器、knip 存量死代码

## 4.3 对「校招作品集 vs 企业级产品」的坦率判断

- **作为作品集**：远超标准。97 篇审查报告、注入-还原验证纪律、
  契约测试体系，这些是很多工作三五年的工程师都没建立过的习惯。
- **作为企业级产品**：**核心链路（L1–L3）可以真实交付**，
  但需补齐上面第一梯队三项，且**必须停止宣传 L4 自愈**。
  按方案 A 定位交付，是当前最稳的路。
