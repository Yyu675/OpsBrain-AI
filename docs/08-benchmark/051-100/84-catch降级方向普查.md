# 84 · `catch (Exception)` 降级方向普查

> 81 号报告 P2 的最后一项。全项目 166 处 `catch (Exception)`，
> 判据不是「有没有吞异常」，而是**吞掉之后有没有留下线索**。

---

## 一、先说清楚判据

吞异常**本身不都是错的**。审计、通知、缓存、健康检查这类旁路能力，
让它们把主流程带崩没有意义——工单已经建好了，不该因为「记录这次建单」
失败而让接口报错。

真正决定「故障能查还是查不到」的是两件事：

1. **兜底值是否安全**（失败方向朝安全侧还是危险侧）；
2. **有没有留下线索**（日志或重新抛出）。

所以本轮的分级标准是：块内有 `log.*` 或 `throw` 即视为「留下了线索」，
两者都没有才是需要逐个核实的「完全静默」。

## 三、修复的 2 处

`ToolExecutionRepository.findBySaga` / `findByTrace` 查询失败静默返回空列表。

**与上轮修的 `findNeedingAttention` 完全同型——当时漏掉了这两个。**

`findBySaga` 是 Saga 链路回放（`/saga/{sagaId}/steps`）的唯一数据源。
查询失败时接口返回「0 步」，排查者会认为**这个 Saga 根本没执行过**，
而实际可能有一批步骤正等着补偿。

兜底仍返回空列表（回放是旁路，不该带崩页面），但补上 ERROR 日志。

## 四、判定合理、不改的 22 处

共同特征是**「异常本身就是预期分支」**：

| 位置 | 为什么合理 |
|------|-----------|
| `AuthController` / `OperationAuditInterceptor` | 未登录或非请求上下文时取不到用户，回落匿名是正常路径 |
| `HotMemoryStore` | 单条历史解析失败跳过，不影响其余 |
| 各 `*Repository` 的只读查询 | 失败返回空集合，调用方本就按「查不到」处理 |
| `LlmHealthIndicator` / `VectorStoreHealthIndicator` | 健康探测失败即「不健康」，异常就是结论本身 |
| `MockStreamingChatModel` | 测试替身，非生产路径 |

强行给它们加日志只会制造噪音——每次未登录访问都打一条 WARN，
真正的问题反而被淹没。

## 五、契约测试：守增量，不动存量

新增 `SilentCatchContractTest`（4 例）。

### 设计取舍

| 决定 | 理由 |
|------|------|
| **文件白名单 + 总数封顶**，而非要求存量清零 | 22 处逐个核实过，改了反而是噪音。新增静默 catch 会让计数超标而失败，迫使作者要么补日志、要么显式登记并写明理由 |
| 按**文件**登记而非精确行号 | 行号随任何一次编辑漂移，失败信息会变成「第 137 行不该静默」——而那行早就是别的代码了 |
| 额外加 `allowlistHasNoStaleEntries` | 防止无效豁免长期挂着。留着已修好的条目，会掩盖将来在这些文件里新增的静默 catch |
| 白名单注释里写明**准入判据** | 「往这里加条目前请先问：吞掉之后，运维能从别处发现这件事吗？答案是否定的就别加白名单，去补日志。」 |

## 六、扫描器写坏了两次，这件事本身值得记

第一版扫描器报出 **166 处全部静默**——而我明知其中有些是上一轮刚加过日志的。
这个「结果好得/坏得不像真的」的信号救了这次普查。

两个 bug：

1. **未跳过注释行**。代码注释里常引用
   `catch (Exception e) { return 1; }` 来说明「原实现是怎样的」，
   扫描器把说明文字当成了真代码；
2. **从行首配平花括号**。`} catch (Exception e) {` 这一行
   `{` 与 `}` 各一个，净变化为 0，块被判为「立刻结束」，
   于是**每一处都被判成静默**。必须从 catch 行的 `{` 之后开始计数。

修好后从 166/166 变成 24/166，与人工抽查一致。

因此另加了一条 `scannerDistinguishesSilentFromLogged` 给扫描器**自身**兜底：
一个坏掉的扫描器会「永远通过」或「永远失败」，两种都等于没有这条契约。

> 这与 AGENTS.md 3.9 记的三类陷阱同源，且是更基础的一条：
> **当扫描结果是「全中」或「全不中」时，先怀疑扫描器。**
