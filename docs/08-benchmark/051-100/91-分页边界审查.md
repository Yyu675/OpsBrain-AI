## 二、缺陷：`retryFailedIndexing(limit)`

### 成因

```
POST /reindex/pending?limit=N
  → KnowledgeDocController.retryIndexing(limit)      // 裸传
  → KnowledgeDocService.retryFailedIndexing(limit)   // 裸传
  → KnowledgeDocRepository.findNeedingIndex(limit)   // LIMIT ?
```

全链路无任何上界。

### 为什么它比普通分页危险得多

**取回的每一条都会触发一次远程 embedding 调用**
（`indexIfNeeded` → `indexer.reindex`），且每条成功后还会
`semanticCache.clearAllCache()` 清空一次语义缓存。

普通列表分页 `size=100000` 的后果是「查得慢、占内存」；
这个接口的 `limit=100000` 的后果是：

1. **embedding 账单被打爆** —— 十万次远程调用；
2. **请求长时间挂起直至超时**；
3. **语义缓存被反复清空**，全站问答退化到无缓存状态。

这不是「慢一点」，是真实的成本与可用性事故。而 `POST /reindex/pending`
是个无参数校验的端点。

### 下界同样重要

`limit=0` 不会报错，它**静默返回空列表**。调用方看到「成功处理 0 条」，
会以为没有待索引文档——而真相是参数写错了。**静默失败比报错更难查。**

### 修复

```java
static final int MAX_REINDEX_BATCH = 200;

int safeLimit = Math.min(Math.max(1, limit), MAX_REINDEX_BATCH);
if (safeLimit != limit) { log.warn(...); }
```

- 上界 200 与既有入口同口径（`SagaController` / `AlertController` 都是 200），不引入新魔法数；
- 钳制放 **service 层**而非 controller：`retryFailedIndexing` 是公开方法，
  将来被定时任务复用时不会绕过保护；
- 越界记 WARN——运维得知道自己传的值没生效。

## 三、注入-还原验证

| 编号 | 注入 | 结果 |
|---|---|---|
| P1 | 去掉钳制，`safeLimit = limit` | 🔴 `Wanted findNeedingIndex(200) / Actual (100000)`、`Wanted (1) / Actual (0)` |
| P2 | 改用 `Math.abs` 纠正负数 | 🔴 **只有两条负数用例红**，上界用例照常通过 |

P2 证明 `Integer.MIN_VALUE` 那条用例不是凑数：
`Math.abs(Integer.MIN_VALUE)` 仍是 `Integer.MIN_VALUE`（溢出），
用 `abs` 而非 `max` 的实现会把它原样传进 `LIMIT`。

7 例测试的断言**全部落在「传给 `findNeedingIndex` 的那个整数值」上**，
而非「被调用过」——不钳制的实现照样会调用，只是参数不同（第 2 类假测试）。
边界用 200/201 两侧夹逼锁死位置。

## 四、把「必须钳制」固化为契约

真实缺陷的形态是「24 处都对，1 处漏了」。这类问题逐个写单测既冗长
又**挡不住新增端点**。故加 `PaginationClampContractTest`（3 例），
扫的是「有没有钳制」这件事本身。

### 三条断言的分工

| 断言 | 防的问题 |
|---|---|
| `everyPagingEndpointIsClamped` | 主扫描。含 `scanned >= 15` 下限断言，防正则与代码写法脱节时「一条都不匹配」导致主断言恒真 |
| `downstreamClampsStillExist` | 反查白名单指向的钳制代码确实还在。**只列白名单不反查，等于给「以后把下游钳制删掉」开后门** |
| `whitelistHasNoRedundantEntries` | 已内联钳制的入口不该留在白名单里，否则白名单逐渐失去「这些是特例」的信号价值 |

### 扫描器自验

Python 复刻同一逻辑实测：**15 个分页方法 = 8 内联 + 7 白名单**，
`UNCLAMPED` 与 `REDUNDANT` 均为空，白名单方法名全部对得上。
非「全中」也非「全不中」。

方法体截取**从形参右括号之后的第一个 `{` 开始配平**，而非从签名行首——
后者会被形参里的括号与注解干扰（84 号静默 catch 扫描器栽在
`} catch (Exception e) {` 净变化为 0 上）。

### 契约测试自身的注入验证

| 编号 | 注入 | 结果 |
|---|---|---|
| Q1 | `SessionMemoryController` 去内联钳制 | 🔴 主扫描报它；**且既存 WebTest 也红**（`size expected:<100> but was:<100000>`） |
| Q2 | `TicketService.getHotTags` 去下游钳制 | 🔴 反查断言精确报出「白名单过期：找不到该钳制代码」 |

Q1 顺带确认了 `SessionMemoryController` 原本就有 WebTest 在守护，
与契约测试互补：WebTest 验单个端点的实际输出，契约测试防新增端点漏钳制。

## 五、下一步建议修复思路

### 立即可做（下轮首选）：并发写幂等

90/91 两轮都在「读路径」上。写路径目前只有 saga 与 session 做过系统审查，
其余写入口的幂等性未成体系检查。**具体切入点**：

1. **重复提交防护**。工单创建、审批提交、知识文档发布这几个 `POST`
   若被前端重试或用户双击，会不会产生两条记录？
   已知 `sys_agent_conversation_turn` 用 `(session_id, turn_seq)` 唯一键 +
   `ON CONFLICT DO NOTHING` 解决了这个问题——**其余写入口有没有对应机制**
   是个明确可查的问题。
2. **CAS 更新的返回值有没有被检查**。`KnowledgeDocService.update` 把
   `rows == 0` 解读为乐观锁失败并抛异常，这是对的；
   全仓其它 `update` 调用点是否都检查了返回行数？
   不检查的话，并发覆盖会**静默丢失**一次修改。
3. **先查后写的竞态**。`ON CONFLICT` 之外，有多少地方是
   `if (!exists) insert`？这个模式在并发下必然撞唯一键或产生重复。

预期产出形态与本轮一致：能查的用扫描器普查 + 逐个追到底，
有则修、无则固化契约。

### 中期候选

- **N+1 查询普查**。`TicketController` 已用 `fillTags` 批量装填避免 N+1，
  说明团队意识到了这个问题；但这是个**逐个发现**的模式，
  值得做一次系统扫描（列表接口里有没有在循环内查库）。
- **错误码一致性**。`40001/40004/50001` 这套码在各 controller 里
  是硬编码字面量，语义是否处处一致未经校验。

### 明确不做

- **给所有分页入口统一改成注解式校验**（如 `@Min/@Max`）。
  收益是写法统一，代价是要动 15 个方法签名 + 全局异常处理要新增
  `ConstraintViolationException` 分支，且钳制语义会从「夹紧」变成「报错」——
  与当前「不静默纠正但也不让手滑变成失败请求」的产品口径冲突
  （`MetricsController` 的注释明确写了这个取舍）。**风险高于收益**。
