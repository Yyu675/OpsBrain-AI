## 二、本轮最重要的发现：第三个假测试，成因与前两个都不同

### 事情经过

注入 G2——去掉准确率计算里的除零保护：

```java
- double rate = rated > 0 ? (double) helpful / rated : 0.0;
+ double rate = (double) helpful / rated;
```

我原以为这必然被抓到，因为我专门为它写了一条用例，
断言 `helpfulRate` 等于 `0.0` 且不是 `NaN`。

**CI 通过了。**

### 根因：NaN 被下游的取整悄悄吞掉

方法末尾还有一步：

```java
"helpfulRate", Math.round(rate * 1000) / 1000.0
```

写了个最小样例实测（沙箱无 JDK 编译器，用 ECJ 编译后运行）：

```
rate=NaN isNaN=true
Math.round(rate*1000)/1000.0 = 0.0
equals 0.0 ? true
```

`Math.round(NaN)` 返回 **0**。也就是说去掉保护后，
返回值依然是 `0.0`，我那条断言分辨不出任何差别。

### 与前两个假测试的区别

这是本轮/上轮连续第三个假测试，但成因各不相同：

| # | 假测试 | 成因 |
|---|--------|------|
| 1 | SLA 截止时刻 | `toMinutes()` **截断精度**，微秒差异被抹平 |
| 2 | 批量重命名版本号 | 断言落在**调用次数**上，而缺陷在参数值里 |
| 3 | 准确率除零（本轮） | **下游的取整意外"修复"了上游的 NaN**，断言看不到中间态 |

第三种最隐蔽：前两种是「我写的断言不够细」，
这一种是**被测代码自身有一步无意的兜底**，
把我想验证的错误状态转换成了正确的输出。
光读代码很难想到，只有真的注入一次才会暴露。

### 修法：换一组能让两种实现给出不同答案的输入

不用 0/0，改用 **`rated=0` 但 `helpful=3`** 的不一致数据：

- 保护在 → 短路为 `0.0`；
- 保护不在 → `3/0 = Infinity`，`Math.round(Infinity * 1000)` 得
  `Long.MAX_VALUE`，除以 1000.0 是 `9.223372036854776E15`。

重新注入 G2，CI 如期变红：

```
[rated=0 时必须短路为 0，而不是让除法产生 Infinity/NaN]
expected: 0.0 but was: 9.223372036854776E15
```

这组输入并非臆造：`feedbackStats` 是多个聚合子查询拼出来的，
统计口径不一致或并发写入时，`rated` 与 `helpful` 确实会对不上。

## 三、两个被测类的共同特征：错了没有任何信号

### `TicketAiAnalysisService`

准确率是评估模型质量、决定要不要换模型/调提示词的依据。
它不像工单状态那样有人天天核对——**数字只要在 0~100% 之间就显得正常**。

锁住的关键行为：

| 行为 | 写错的后果 |
|------|-----------|
| 反馈布尔 → `HELPFUL`/`UNHELPFUL` | 两分支写反会让有用/没用完全对调，而准确率看起来仍是个正常百分比 |
| 置信度越界纠偏（>100 / <0） | 模型偶发给出 120，不纠偏会参与后续质量统计 |
| 置信度 `null` 保持 `null` | `null` 是「模型没给」，`0` 是「模型认为完全不可信」，混为一谈会把大量未知算成极低置信度 |
| 影响 0 行返回 `false` | 否则用户点了「有用」看到成功提示，而这条反馈从未进入统计 |
| 成本 `null` → `0` | `null` 参与求和会 NPE 或被跳过，表现为「总成本偏低」这种不报错但一直错的数 |

### `AgentMemoryManager`

这两个方法整体包在 try-catch 里、失败只打 WARN——**这是对的**
（用户已经收到回答了，不该因为记忆没存上而报错）。
代价是写错时完全无声，后果在下一轮显现为「AI 忘了刚说过的话」
或「AI 记住了错的事」，排查时几乎不会有人追到上一轮的记忆写入。

最值得测的是**「一处用总数、一处传增量」**：

- 摘要文本用**累计轮次**（DB 已有 + 1）——它要展示「聊了几轮」；
- UPSERT 传的 `turnCount` 是**本轮增量 1**——仓储侧是累加语义。

两者写反：传总数会让轮次**指数增长**（1→2→4→8），token 与成本同步虚高；
摘要用增量则永远显示「第 1 轮」。**两种都不会报错。**

注入 G1 验证时报错正是这条断言：
`[UPSERT 是累加语义，必须传本轮增量 1 而非累计 4] expected: 1 but was: 4`。

## 六、下一步建议

### 建议 1：把「注入验证」这件事本身沉淀成规则

连续三轮、三个成因各异的假测试，说明这不是偶发疏忽。
它们的共同点是：**光看测试代码判断不出真假，只有注入一次才知道**。

建议在 `AGENTS.md` 里补一条硬约束（我可以下轮执行）：

> 新增测试后必须注入-还原验证。注入项要针对**该用例声称防住的那个缺陷**，
> 而不是随便改点什么让它变红。特别注意三类会让断言失效的情况：
> ① 聚合/取整函数截断精度；② 断言落在调用次数而非参数值上；
> ③ 被测代码下游有无意的兜底（如 `Math.round(NaN)=0`）把错误状态转成了正确输出。

### 建议 2：剩余的技术债不再是「补测试」

基线确属缺口已清零，继续按扫描器清单补测试的边际收益在下降。
更值得做的是前面几轮识别出、但受阻或未展开的事：

1. **`run_audit.py` 接入 CI**（一行 `run: python3 tools/audit/run_audit.py`）
   —— 目前审计只能靠我手动跑，接入后新增命中会自动拦住；
2. **`ToolExecutionRepository` 的 12 个写方法全部 `catch(Exception) return 0`**
   —— 需要逐个判断「哪些吞异常是对的、哪些不是」。Saga 审计写失败时静默，
   与本轮 `recordCompletedTurn` 的降级是同类设计，但那里有明确理由，
   这 12 处未必都有；
3. **前端 `knip` 的 21 个未使用导出**（低优先级，风险高于收益）。
