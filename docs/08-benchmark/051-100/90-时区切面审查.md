## 二、缺陷：`AlertService.toLocalDateTime` 存 UTC

### 成因

`sys_alert.first_occurred_at` 来自 Alertmanager 下发的 RFC3339 时间，
此前统一 `atZoneSameInstant(ZoneOffset.UTC)` 转成 UTC 墙钟再存。

而**同一张表的其它时间列全是本地时间**：

- `last_occurred_at` / `create_time` / `update_time` ← `LocalDateTime.now()`
- 数据库默认值 ← `CURRENT_TIMESTAMP`
- 容器 TZ 固定 `Asia/Shanghai`（Dockerfile + docker-compose）

列类型都是无时区的 `TIMESTAMP`。同一行里一列 UTC、邻列 +08:00，
**相差 8 小时，而没有任何字段记录这个差异**。下游无从分辨，
只能一律按本地时间解释——前端 `utils/time.ts` 的 `parseDate` 正是这么做的
（注释明写「服务器固定 Asia/Shanghai，故把无时区的字符串按 +08:00 解释」）。

### 用户可见后果

1. **告警详情页「持续时长」**把 `firstOccurredAt` 与当前时间相减 →
   **刚触发的告警显示「已持续 8 小时」**；
2. **处置时间线**上「首次发生」排在「已恢复」之后，顺序倒置；
3. 告警列表与 `AlertStreamMode` 的相对时间显示「8 小时前」而非「刚刚」。

告警是 L2 实时监测的核心，时间错乱直接影响值班人判断故障新旧与优先级。

### 修复

```java
- return odt.atZoneSameInstant(ZoneOffset.UTC).toLocalDateTime();
+ return odt.atZoneSameInstant(ZoneId.systemDefault()).toLocalDateTime();
```

**为什么是 `systemDefault` 而非硬编码 `+08:00`**：目标是与同表其它列口径一致，
而那些列用的是 `LocalDateTime.now()` 和 `CURRENT_TIMESTAMP`，两者都跟随部署环境时区。
硬编码会在部署到其它时区时重新制造同一个偏差，而且**更隐蔽**——
本地跑测试正常，线上错 N 小时。

## 三、测试为什么能抓到（本轮最值得记的一条）

**GitHub Actions runner 的系统时区是 UTC。**

在 UTC 环境下，`atZoneSameInstant(ZoneOffset.UTC)` 与
`atZoneSameInstant(ZoneId.systemDefault())` 给出**完全相同的答案**。
照常写测试，正确实现与错误实现都会通过——**第 5 类假测试**
（用例构造的场景与要防的缺陷不是同一件事）的一个新实例。

破法：用例显式把 JVM 默认时区切到非 UTC 时区，让两种实现必然分叉，
`@AfterEach` 还原（JVM 默认时区是进程级全局状态，不还原会污染同 JVM
内后续所有测试的时间断言）。

`AlertTimeZoneConsistencyTest` 4 例，两个时区：

| 时区 | 用例 | 防的缺陷 |
|---|---|---|
| Asia/Shanghai | 与 `createTime` 的差值 < 300 秒 | 转 UTC（差 28800 秒） |
| Asia/Shanghai | 落在 `[before, after]` 窗口内 | 同上，换一种断言形态 |
| Asia/Shanghai | `startsAt=null` 的兜底分支 | 兜底路径口径不一致 |
| **America/New_York** | 落在 `[before, after]` 窗口内 | **硬编码 `+08:00`** |

第 4 条是刻意加的负偏移时区：硬编码 `+08:00` 的实现在 Asia/Shanghai 下
与正确实现表现一致，前三条抓不到。

另：断言单位用**秒**而非分钟。`Duration.toMinutes()` 的取整截断是
第 1 类假测试的经典来源；阈值 300 秒足够容纳执行耗时，
又远小于任何时区偏移（现存最小时区差是 15 分钟 = 900 秒）。

## 四、注入-还原验证

| 编号 | 注入 | 结果 |
|---|---|---|
| T1 | 还原为 `atZoneSameInstant(ZoneOffset.UTC)` | 🔴 `28800L to be less than 300L` —— 正是 8 小时 |
| T2 | 改成硬编码 `ZoneOffset.ofHours(8)` | 🔴 **只有** America/New_York 那条红（12 小时差），三条 Shanghai 用例照常通过 |

T2 的价值在于它**证明了第 4 条用例不是凑数**：如果拿掉它，
硬编码 `+08:00` 这个错误实现会完全溜过去。

还原后 `git diff b951dfb -- src/main src/test` 为空。

## 五、把隐式约定固化为契约

修复的结论依赖一个**跨三个文件的隐式约定**：

1. `Dockerfile` —— `/etc/localtime` → `Asia/Shanghai`（决定 JVM 的 `systemDefault()`）
2. `docker-compose.yml` —— **app 与 postgres 两个服务**都设 `TZ: Asia/Shanghai`
3. `devops-platform-frontend/src/utils/time.ts` —— `SERVER_UTC_OFFSET = '+08:00'`

三处必须表达同一事实。**任一处被单独改动，系统不报任何错**，
只是所有时间悄悄偏移——与本轮修掉的缺陷完全同型。

`DeploymentTimeZoneContractTest`（4 例）把它钉住：迁时区时改
`EXPECTED_ZONE` 一个常量，测试会告诉改动者还有哪几处要跟着改。

### 三条扫描器自查（避免「全中/全不中」）

1. **compose 的断言用「出现次数 ≥ 2」+ 逐服务块定位**，而非 `contains` 一次。
   只给 app 设而漏掉 postgres 时，`CURRENT_TIMESTAMP` 写 UTC，
   与 `LocalDateTime.now()` 在同表差 8 小时——`contains` 抓不到「漏了一个服务」。
   实测：计数 = 2，两个服务块各含一次，切分逻辑正确。
2. **防回退断言先剥 Java 注释再匹配**。本轮修复的 javadoc 里正引用了错误写法
   `atZoneSameInstant(ZoneOffset.UTC)` 来说明成因，不剥注释会被自己的说明文字
   打中而**永远失败**——静默 catch 扫描器（84 号）踩过同一个坑。
   实测：原文含该串、剥注释后不含，逻辑有效。
3. **`read()` 对文件不存在显式断言失败**，避免文件被移动后静默跳过检查。

### 契约测试自身也做了注入验证

契约测试最容易写成恒真断言，故同样注入：

| 编号 | 注入 | 结果 |
|---|---|---|
| C1 | 移除 docker-compose 里 postgres 的 `TZ` | 🔴 计数断言与 postgres 服务块断言均红 |
| C2 | 前端 `SERVER_UTC_OFFSET` 改 `+09:00` | 🔴 后端契约断言红，**前端自身测试也红** |

C2 顺带确认了前端已有 `time.ts` 测试在守护这个常量，两层防护不重复但互补。
