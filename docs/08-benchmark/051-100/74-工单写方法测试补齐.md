## 二、为什么挑这三个方法

它们的共同点是**出错时不会报错**——都在主流程旁边写数据，
写坏了主流程照样返回 200。这类缺陷靠人工测试基本发现不了。

### 1. `addReply` 的首响判定（本轮最关键）

人工回复计首响，**AI 回复不计**。

AI 分析在建单时自动触发（6.39）。若这条区分失效，
每张工单**建单即「已首响」**，MTTA 恒接近 0、超时告警永不触发。

这比没有这个指标更糟：**看板全线飘绿，而实际没有人在响应**。

除正例外还锁了两条容易漏的：

- 传 `"AI"`（大写）必须同样不计——若判断写成区分大小写的 `equals` 就会漏；
- 未知角色降级为 `agent` 后**必须计首响**——否则「未知角色」会成为绕过 SLA 的后门。

### 2. `addAction` 的 `effective=false`

PRD §2.1：排查占 40% 且严重依赖经验。
「试过重启，没用」恰恰是最有价值的知识，能避免后人重走弯路。

若哪天有人把 `effective=false` 当脏数据过滤掉，
**大部分经验就被丢弃了，而这件事不会有任何报错**。
测试锁住「无效尝试必须正常入库，并在活动流里标注『无效』」。

### 3. `replaceTags` 的先删后插

中途失败会让标签**整体丢失**，而工单主体完好——
界面上只是「标签没了」，很难联想到是替换逻辑的问题。

两条重点：

- 「提交了标签却一个都没存上」这条**数据丢失**路径必须留下 error 日志；
- 「无变化不写活动流」——编辑页保存会无条件调用本方法，多数情况标签根本没动，
  每次留痕会把活动流填满噪音，真正的处置记录被挤走。

## 三、边界用例都让正确/错误实现给出不同答案

| 用例 | 正确实现 | 错误实现 |
|------|---------|---------|
| 摘要 255 字 | 放行 | `>= 255` 会误拒 |
| 回复 5000 字 | 放行 | `>= 5000` 会误拒 |
| VOID 工单记处置 | 拒绝 | — |
| **RESOLVED 工单记处置** | **放行** | 误用 `isTerminalStatus` 会拒（事后补录是真实路径） |
| CLOSED 工单回复 | 拒绝 | — |
| **RESOLVED 工单回复** | **放行** | 一并拦掉会让追问流失到群聊，工单上下文不完整 |
| 内容校验时机 | 查库**之前** | 之后 → 明显非法的请求也要打一次库 |
| `replaceTags` 读标签次数 | **2 次** | 1 次 → 无法判断「有没有变」，上面那条留痕规则失效 |

`isImmutableStatus()` 只对 `VOID` 为真（`TicketEnums.Status.isTerminal`），
`isTerminalStatus()` 才含 RESOLVED/CLOSED。这两个方法容易混用——
类注释里就记着「此前 5 处写操作把 `isTerminalStatus` 当作操作门禁，
导致 RESOLVED 工单无法补做验证」。测试把这条区分固定下来。

所有断言依据的 API 签名（`markFirstResponse(String,String,LocalDateTime)`、
`TicketActivity.getDetail()`、`touchUpdateTime`、`TicketAction` 各 getter）
**均已核对源码**，不是照着「我以为的接口」写。

### 过程中遇到的一个障碍，以及怎么绕开

首轮把 6 个缺陷**一起**注入，CI 变红，但 **GitHub check-runs 的 annotations
最多只返回 3 条失败**。也就是说我只能看到 D1/D3/D4，
无法证明 D2/D5/D6 也被抓到——「CI 红了」不等于「每一条都被抓到」。

试过两条路想在本地实跑：

- Maven Central 直连仍是 `SSL_ERROR_SYSCALL`（curl exit 35），拿不到 mockito/junit；
- PyPI 与 npm 可达，但都没有可用的 Mockito 载体（pyspark 只带了 objenesis）。

最后用了确定可行的办法：**逐个注入，各推一次 CI**。
每次只有一条失败，注解上限就不再是问题，D2/D5/D6 由此逐一确证。

还原后 `git diff ea02766 HEAD -- src/main/java/` 为 **0 行**，产品代码逐字节复原。
