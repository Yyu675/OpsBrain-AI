## 一、建议 1：并发 50001 的完整定位

上一轮只知道「4 路并发时 `code=50001`」。本轮把它一路查到底，
过程本身比结论更值得记录——**每一步都是先拿信息再动手，没有一次靠猜**。

### 定位链条

| 步 | 手段 | 得到 |
|---|---|---|
| 1 | 从审计表反查 `agent_answer` | `系统异常: null` |
| 2 | 审计记录**异常类型**（而非只记 `getMessage()`） | `ConcurrentModificationException` |
| 3 | 审计记录**首个业务栈帧** | `@streamAgent:681`（= `TokenStream.start()`） |
| 4 | 修掉一处后行号变化 | `681 → 467`（= `engine.chat()`）——**证明修复有效** |
| 5 | 放开包名限制，取**前 4 帧** | 真凶浮出水面 |

第 5 步是关键转折。前两轮只取 `com.devops` 帧，看起来更"干净"，
但异常在第三方库内部时**只能看到调用它的那一行**——为此多花了两轮 CI。

### 真凶：LangChain4j 1.1.0 框架缺陷

```
ConcurrentModificationException
  @HashMap.computeIfAbsent:1229
  @AbstractGuardrailService.hasInputGuardrails:71
  @DefaultAiServices.invokeInputGuardrails:351
  @DefaultAiServices$1.invoke:178
```

`AbstractGuardrailService` 用**普通 HashMap** 缓存「某方法有没有配 guardrail」，
并在 `computeIfAbsent` 里计算。而 `DefaultAiServices` 的动态代理是
**所有请求共用的单例**——并发调用同一方法时多线程同时进入 `computeIfAbsent`，
JDK 9+ 的 HashMap 会做 `modCount` 校验并抛 CME。

这是教科书式的「HashMap 当并发缓存用」，只是它在框架里。
应用侧**没有扩展点**能替换那个私有字段，可选绕法都不划算
（全局锁牺牲吞吐 / 每请求新建 AI Service 开销过大且绕开会话隔离设计）。
正解是升级 langchain4j，但沙箱 Maven 镜像不可达、无法验证依赖解析。

### 顺带修掉的三处**应用侧**真实缺陷

这才是本轮最大的收获。它们各自都会在并发下抛 CME，
只是被框架那处更早触发的缺陷盖住了：

1. **`streamAgent` 的收集容器** —— `toolResults`/`citations`/`answerBuilder`
   由模型 HTTP 回调线程写、由 `onCompleteResponse` 读。
   改 `CopyOnWriteArrayList` + `StringBuffer`；
2. **`TtlChatMemoryStore.getMessages` 返回活 List** ——
   `InMemoryChatMemoryStore` 吐的是内部那个 `ArrayList` 本身。
   类注释原本写着「委托目标线程安全」，但**委托目标的 Map 安全，
   它吐出去的 List 不安全**——这层区别正是漏掉的地方。
   改为返回副本 + 会话级锁（锁表在删除与两条驱逐路径里一并清理，防新的泄漏）；
3. **`MockStreamingChatModel` 直接遍历 `chatRequest.messages()`** ——
   改 `List.copyOf` 快照。虽只在 MOCK 启用，但同样写法出现在真实模型适配层就是线上缺陷。

> **证据**：每修一处，堆栈行号就往前推进一次（681 → 467 → 框架内部）。

### 附带产出：审计可观测性

`catch (Exception e)` 原本只记 `e.getMessage()`——**NPE 这类异常 message 恒为 null**，
审计表里只留下「系统异常: null」，等于什么都没记。
现在记录**异常类型 + 前 4 帧**。这不只服务于本次排查：
线上任何被兜底 catch 吞掉的异常，此后都能从审计表直接看到出事位置，
而不必依赖受限环境下取不到的服务端日志。

## 三、建议 3：SSE 超时测试（3 例）

**必须单开顶层类**——`@TestPropertySource` 标在 `@Nested` 上不覆盖外层属性
（HealthCheck 探针开关那次已踩过），而超时用例要把 `timeout-ms` 压到 800ms，
与正常路径用例的属性直接冲突。

`emitter.onTimeout` 里三件事漏掉任何一件都**不会报错**：
漏取消心跳 → 调度器堆积永不结束的任务；
漏 `cancelStream` → 前端已断开而后端仍在**写库建单**且模型照常计费；
漏发 error 事件 → 连接静默挂断，前端分不清「超时」与「网络断了」。

用例覆盖第 3 条（客户端可观测部分），并验证超时后服务端仍健康
——若心跳或流未正确取消，后续请求会受影响。
其中一例对「MOCK 下流可能恰好在超时前跑完」做了合法性分支，不把偶发判成失败。
