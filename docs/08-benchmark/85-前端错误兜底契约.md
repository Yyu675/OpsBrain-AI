# 85 · 前端错误兜底契约（以及一条「不照搬」的判断）

> 承接 84 号报告方向 3。原计划把后端刚做完的「静默 catch」规则搬到前端，
> 实际扫描后**判定不适用**，改为守前端真正该守的东西。

---

## 一、本轮最重要的产出是一个「不做」的决定

后端刚完成 166 处 `catch (Exception)` 普查。按同一套判据扫前端，
206 处 catch 里有 113 处「块内无日志」。

**但逐个抽查后发现，这些绝大多数是正确的写法。**

原因是前端的错误处理是**分层**的，与后端根本不同：

| 前端惯用法 | 为什么块内不需要日志 |
|-----------|-------------------|
| `catch { /* store 已提示错误 */ }` | 错误已由 store / mutation 的 `onError` 统一 toast |
| `catch { loadError.value = e }` | 写进响应式状态由 UI 渲染错误态——**比日志更好**，用户直接可见 |
| `catch { /* 用户取消 */ }` | `ElMessageBox` 的 reject 就是「用户点了取消」，不是故障 |
| `try { localStorage... } catch {}` | 隐私模式下必然抛错，是预期分支 |

而且项目**已有三层全局兜底**：`app.config.errorHandler`、
`window.unhandledrejection`、`http.ts` 统一抛 `HttpError`，
并做了去重避免同一错误弹两次。

> **结论：硬套后端标准会产出几十条误报。
> 一个天天误报的规则，最终会被加白名单加到失效——那还不如不加。**

这个判断本身比多写十条测试更有价值。我在扫描过程中三次调整判据
（补 `handleServerError`、补「写入错误态」、补前端特有模式），
每次误报都在下降，但始终收敛不到「干净」——这就是判据不匹配的信号。

## 二、那前端真正该守什么

**守兜底机制本身不被拆掉。**

这套机制的特点是：拆了之后**不会有任何报错**，页面照常跑，
只是错误不再提示给用户——一次 500 变成「点了没反应」，
而开发者在控制台也看不到。这正是 CI 该拦住的那类改动。

新增 `errorBoundary.contract.test.ts`（11 例）：

| 用例 | 防的是什么 |
|------|-----------|
| `errorHandler` 存在且给用户可见提示 | 组件渲染抛错会让子树白屏，只 console 等于没提示 |
| `unhandledrejection` 存在且给提示 | async 抛错而调用方没 catch，浏览器只打 warning，用户完全无感 |
| 两条路径都去重 | 同一错误弹两次会训练用户忽略所有提示 |
| 动态导入失败被单独识别 | 发版后旧页面加载新 chunk 失败，应提示刷新而非「发生意外错误」 |
| `http.ts` 统一抛 `HttpError` 而非返回 null | 返回 null 会让错误在几层之后以「读取 undefined 属性」炸出来，堆栈指不到失败点 |
| `toFriendlyError` 存在 | 直接把后端堆栈弹给用户毫无意义且可能泄露实现 |
| abort 不当错误提示 | 用户关弹窗/切页面都会 abort，弹「操作失败」反而让人以为取消出了问题 |
| 禁裸 `alert` | 阻塞主线程、样式不可控，且绕过统一的错误去重与分级 |
| `v-html` 必须绑定已净化内容 | XSS 主入口 |

## 三、查出并修复一处真实的约定违背

`safeMarkdown.ts` 的注释写明：

> 所有 v-html 渲染 Markdown 的场景都必须走此函数，
> **禁止自行调用 marked + DOMPurify**。

而 `KnowledgeSinkDrawer.vue` 正是一个例外——它自行组合了两者。

**为什么这是问题**：净化配置（允许哪些标签/属性、给 `a[target=_blank]` 补 `rel`）
集中在一处才能保证一致。自行组合的地方一旦漏配某项，
就成了绕过全局策略的 XSS 缺口，而**它看起来「也净化了」**。

已改为调用 `safeMarkdown`（内部 `marked` 的 `breaks/gfm` 选项与原处一致，
渲染行为不变），并清理冗余导入。

### 连带更新既有契约

项目原有 `htmlSanitizePolicy.test.ts` 要求「三处净化调用点都引入共享策略」。
改造后 `KnowledgeSinkDrawer` **不再是净化调用点**，清单由三处收敛为两处。

**这是收敛而非放宽**——调用点越少，策略漂移的入口越少。
已在注释里写明，并指向新增的「单一入口」用例保证不会再出现新的自行净化。

`editorContent.ts` 保留自行 sanitize 并**登记豁免**：富文本编辑器需保留
展示端不允许的标签（表格、样式类），净化策略天然不同；
但它复用同一份 `htmlSanitizePolicy` 常量，未另起白名单。
另加一条断言守住这个前提——若它哪天改成本地字面量白名单，测试会红。

## 四、第四种「假断言」形态

注入 P1（拆掉 `unhandledrejection` 末尾「未知 rejection」分支的用户提示，
只留 `console.debug`）后，**测试照常通过**。

真因是原断言用的窗口正则：

```
/unhandledrejection[\s\S]{0,1200}notify\.error/
```

这类写法会**跨过块边界**匹配到后面别的分支——实测它命中的是
上方 `HttpError` 分支里那个 `notify.error`，而被拆掉的是末尾分支的提示。

后果：所有非 `HttpError` 的未捕获异常静默消失，
用户只看到「点了没反应」——**恰恰是这个测试文件声称要防的那件事**。

修法：新增 `blockAfter()` 按花括号配平精确提取回调体，再在块内断言；
另补一条针对末尾分支的独立断言。

### 四种形态汇总（已记入 AGENTS.md 3.9 的延伸）

| # | 形态 | 实例 |
|---|------|------|
| 1 | 聚合/取整截断精度 | `Duration.toMinutes()` 抹平微秒差异 |
| 2 | 断言落在调用次数而非参数值 | 只验 `update` 被调 2 次 |
| 3 | 下游兜底把错误状态转成正确输出 | `Math.round(NaN)` 返回 0 |
| 4 | **匹配范围过宽，命中别处同名内容** | 窗口正则跨块匹配（本轮） |
