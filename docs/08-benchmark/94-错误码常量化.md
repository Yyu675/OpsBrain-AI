# 94 · 错误码常量化：33 处裸写数字全量替换

> 日期：2026-08-28 ｜ 分支 `arena/01a031f6-opsbrain-ai` ｜ 提交 `a72c66c`

## 一、背景

`ApiResponse` 的 javadoc 从第一版起就写着「非 0 见**错误码表**」，
但**这张表从来不存在**。33 处 `ApiResponse.error(40004, ...)`
全是裸写的五位数字，散在 9 个文件里。

93 号已把数据摸清：

| 错误码 | 次数 | 语义 |
|---|---|---|
| `50001` | 10 | 服务端异常 |
| `40004` | 8 | 资源不存在 |
| `40001` | 8 | 参数不合法 |
| `40101` | 3 | 未登录/凭证失效 |
| `40103` | 2 | 权限不足 |
| `40100` | 1 | 登录失败 |
| `40010` | 1 | 端点已废弃 |

本轮做 93 号建议的**第一步**：抽常量类 + 全量替换 + 契约锁死。

## 二、裸数字的实际代价

不是「不好看」，是两件具体的事：

1. **没有唯一真相源**。新增错误分支时写 40001 还是 40004 只能靠翻别处代码猜。
   猜错了前端会走进错误的处理分支——把「参数不合法」当成「资源不存在」，
   **页面显示空状态而不是错误提示，用户完全不知道自己填错了**；
2. **改不动**。想知道 40103 用在哪几处只能全文搜数字，
   而数字会撞上端口号、超时毫秒数、测试夹具里的无关常量。

替换前先核对了语义一致性：同一个码在各处的 message 语义完全对得上
（`40004` 全是「××不存在」，`50001` 全是「××失败，请稍后重试」），
**无歧义**，可以安全地一一映射成常量。

## 三、本次不改任何语义

每个常量的值与替换前的字面量**完全一致**。

前端 `api/types.ts`、`api/auth.ts`、`api/knowledge.ts` 等处
同样硬编码了这些数字，数值不动则跨端契约不受影响。

这是有意的：语义调整（例如 40100 与 40101 的边界是否清晰）
需要拉上前端一起确认，与机械替换分开做——
**免得一次改动里混着「重命名」和「改行为」两种性质的变更**，
出问题时无从判断是哪一类引起的。

### 「不改行为」是被证明的，不是声称的

替换后逐处比对：

```
常量值与替换映射一致 ✅
逐处比对 33 个调用点，顺序与数值不一致的文件: 0
```

脚本取 `git show HEAD:文件` 的原始内容，提取每处 `error(数字`，
与替换后的 `error(ApiCode.常量` 按常量表还原成数字，
**逐一比对序列**。不是抽查，是全量。

## 四、契约测试三例

| 断言 | 防的问题 |
|---|---|
| `noLiteralErrorCodes` | 不得再用数字字面量（含 `scannedFiles > 100` 下限断言） |
| `codesAreWellFormedAndUnique` | 4xxxx/5xxxx 分区 + **互不重复** |
| `valuesMatchFrontendContract` | 常量取值与前端已硬编码的数字一致 |

### 第 2 条为什么单列

**重复码是最危险的**：两个语义共用一个数字，前端无从区分。
而人工 review 很难发现——两个常量可能隔着几十行，
数字又长得像（40101 / 40103）。

### 第 3 条看似「重复写了一遍常量」，其实不是

它防的是一类真实误改：有人觉得「40100 和 40101 太像了，改成 40102 更清楚」——
**后端测试全绿**，而前端 `auth.ts` 里判断 40100 的分支再也不会命中，
登录失败退化成通用错误提示。改数值必须前后端一起改，这条断言是那道闸。

## 五、扫描器三向自验

沿用 92/93 号的做法，这次加了第三个方向：

| 方向 | 结果 |
|---|---|
| 正向 | 197 文件，裸数字 **0 处** |
| 反向 | 改回 1 处裸数字 → 立刻命中并指名道姓 |
| **注释干扰** | `ApiCode` 与测试类的 javadoc 都引用了旧写法说明成因 → 剥注释后命中 **0 处** |

第三个方向是必要的：不剥注释会被**自己的说明文字**打中而永远失败
（84 号静默 catch 扫描器踩过这个坑）。

## 六、注入-还原验证

| 编号 | 注入 | 结果 |
|---|---|---|
| U1 | `FORBIDDEN` 改成 40101（与 `UNAUTHORIZED` 撞车） | 🔴 第 2 条精确报出「码 40101 被 UNAUTHORIZED 与 FORBIDDEN 同时使用」；第 3 条报 `expected: 40103 but was: 40101` |
| U2 | `TicketController` 一处改回裸数字 | 🔴 第 1 条报出 `controller/TicketController.java L129 → ApiResponse.error(40004, ...)` |

**U2 顺带验证了 93 号那条教训的落实**：报出的 L129 点开确实就是那一行。
93 号栽在「剥注释导致行号错位、报出的位置指到空行」上，
本轮的 `stripCommentsKeepLines` 用等量换行占位，行号准确。

还原后 `git diff a72c66c` 为空。

## 七、下一步建议修复思路

### 立即可做（下轮首选）：错误码语义的第二步 —— 前端消费面核对

93 号建议的第二步，现在有了后端的常量表作为基准，可以做了。

**已知事实**：前端在 `api/types.ts`、`api/auth.ts`、`api/knowledge.ts`、
`api/alerts.ts`、`api/queries/*.ts`、`api/services/ticket.service.ts`
等处**同样硬编码**了 40001 / 40004 / 40100 / 50001。

**具体要回答的问题**：

1. 后端 7 种码，前端识别了几种？扫下来前端只出现 4 种
   （40001 / 40004 / 40100 / 50001）——那么 **40010（端点已废弃）、
   40101（登录失效）、40103（权限不足）前端是怎么处理的**？
   若都落进「未知错误」的通用分支，40103 就会显示成
   「系统繁忙请稍后重试」，而用户重试一百次也没用——它需要的是找管理员授权。
2. 前端是否也该抽一份常量（`api/errorCodes.ts`），
   并加一条 vitest 契约锁住与后端一致。

**风险评估**：这一步会**改前端行为**（新增分支处理），
不再是纯机械替换，需要逐个确认交互文案。建议先只做「扫描 + 出结论」，
把「哪些码前端没处理、各自应该怎么处理」列清楚，再决定改哪些。

### 中期候选

1. **日志脱敏普查** —— 本轮顺手扫了，**先给结论**：
   574 条日志语句，3 处出现敏感字段名，**逐个核对全部安全**：
   - `DevOpsAgentServiceImpl:277` —— 变量名 `budgetedHistory` 撞了 `credential` 之外的词，误报；
   - `WebhookGuard:90` —— 只提示「未配置 secret」，不输出值；
   - `DingTalkNotifier:110` —— 输出的是「加签=是/否」，不是 secret 本身。

   **判定：本项无需单独立轮**。但值得把这个扫描规则固化成契约测试
   （成本低、防的是 83 号那类「种子密码明文进日志」重演），
   可与下轮的前端错误码工作合并做。
2. **SSE 流式接口的错误语义**。本轮的 `ApiCode` 只覆盖非流式接口
   （`ApiResponse` 的 javadoc 明写「所有非 SSE 接口」）。
   SSE 出错时前端收到什么、能否区分「模型超时」与「鉴权失效」，
   尚未审查过。

### 明确不做

- **把 `ApiCode` 改成 enum**。看起来更「面向对象」，但会破坏
  `ApiResponse.error(int, String)` 的签名兼容性，
  且前端契约是**数字**，enum 还要额外取 `.getCode()`——
  多一层转换，没有实质收益。`public static final int` 已经够用。
