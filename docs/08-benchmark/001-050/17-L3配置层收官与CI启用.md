## 二、关键设计取舍

### 1. 策略只引用 action_key，不内联动作定义

策略说「匹配上了就执行 `k8s.pod.restart`」，至于该动作能否执行、
是否需要审批、爆炸半径多大，全部由 v26 两张表回答。

若在策略里再存一份动作参数约束，就会出现
「策略说能跑、白名单说不能跑」的自相矛盾状态，而运维无法判断该信哪个。

### 2. dry_run 是一等公民，新建默认开启

自动化最危险的时刻是**「刚配好、还没人知道它会匹配到什么」**。
演练模式下策略照常匹配、照常记录「我本来会做什么」，但不执行。

它在三个层面被特殊对待：

- **独立端点** `POST /policies/{id}/dry-run`，不混在通用更新里；
- **独立审计标识** `governance.policy.dry-run`——事故复盘时要能直接按它过滤，
  而不是在一堆 `policy.update` 里翻 diff；
- **关闭时用 `log.error`**，因为这是策略开始真实操作生产系统的时刻。

关掉演练要二次确认，且确认框里列出该策略会做什么；**切回演练不确认**——
回到更安全的状态不该有摩擦。

### 3. 匹配条件是「与」关系，且不能全空

四个条件（级别/模块/服务/告警名）必须全部命中。

用「或」会让**加条件反而变宽**——这是配置类系统里最容易出的反直觉错误：
用户本意是收窄，结果覆盖面扩大了。

同时**不允许所有条件为空**（`*` 也算空）。全空等于「对所有告警执行该动作」，
影响面是全站范围的，几乎必然是配错了。

### 4. 通配只支持 `*`，不支持完整正则

正则的表达力在这里是负担：运维写错一个正则可能让策略匹配到意料之外的服务，
而 `order-*` 所见即所得，出错空间小得多。

实现上对通配符之外的部分做了正则转义——否则 `order.svc` 里的 `.`
会被当成「任意字符」，误命中 `orderXsvc`。这条有专门的测试守着。

### 5. 列表顺序 = 引擎求值顺序

列表按 `priority` 升序排，与 `idx_automation_policy_eval` 一致。

若列表按创建时间排而引擎按 priority 排，用户就无法回答
**「为什么是这条策略生效」**——而这是排查自动化行为的第一个问题。

预演结果里还区分了「求值了但没匹配」与「根本没被求值」
（前序策略已命中且设了「命中即停」）——两者的排查方向完全不同。

### 6. 冷却期防自动化风暴

没有它，一个反复 firing 的告警会让策略每次都触发重启，形成
「重启 → 还没起来 → 又告警 → 又重启」的死循环，比不自动化更糟。

### 7. 策略允许物理删除（动作白名单不允许）

差异的理由：策略不是审计记录的关联键，执行历史里记的是 `action_key`
与具体目标，删掉一条匹配规则不会让历史变孤儿。
而策略往往是试出来的，不给删会让列表堆满废弃规则，干扰对求值顺序的判断。

## 三、本轮修复的一致性问题

### 🟠 「已启用但不生效」的僵尸策略

**成因**：策略引用的动作可能在配好之后被停用。
此时策略自身显示「已启用」，但引擎永远不会执行它。

**为什么危险**：界面说启用了、实际不会跑，而**界面上没有任何迹象**。
运维以为自愈能力在线，实际那条链路是断的——
这比「明确没配」更糟，因为它给了虚假的安全感。

**修复**（三处协同）：

1. 后端列表接口装填 `effective` 与 `ineffectiveReason`；
2. 前端列表对这类行显示红色「不生效」标签，hover 出原因；
3. **启用策略与关闭演练时都重新校验**——堵死
   「停用 → 动作被停 → 重新启用」这条产出僵尸策略的路径。

第 3 点与 v26 白名单的 `toggleAction` 复查是同一类防护：
安全配置里「先退出再进入」是最常见的绕过方式。

governance 相关文件。详细步骤见 `ci/如何启用CI.md`，摘要：

```bash
git pull && mkdir -p .github/workflows
git mv ci/github-actions-ci.yml .github/workflows/ci.yml
git commit -m "ci: 启用工作流" && git push
```

**预期首次运行后端是红的**，这是正常的。把失败日志给我即可。

我在本轮额外验证了 CI 工作流本身的两个潜在问题，均已确认无碍：
- `AI_MODE` / `SCHEMA_FAIL_FAST` 在 `application.yml` 里都有对应占位符，能正确绑定；
- 工作流先跑 `init.sql` 再跑全部迁移，而**全部 21 个 SQL 文件的 INSERT 都可重复执行**
  （`ON CONFLICT DO NOTHING` 或 `WHERE NOT EXISTS`），不会因内容重叠而中断。
