### 2. Controller 测试（任务 1，进行中：2/18）

补 `AutomationGovernanceControllerWebTest`（24 例）。选它先做是因为
它端点最多（19 个），且配置的是「AI 能不能自动动生产系统」的边界。

覆盖四类契约：

- **参数绑定** —— 重点是 `enabled=false` 这类「有效的假值」不能被当成 null。
  丢掉的话，用户勾「只看已停用」却看到全部条目，且完全看不出哪里错了。
- **异常映射** —— 40001/40004/40009 三条。它们由 `GlobalExceptionHandler`
  跨切面接管，编译期完全看不出对错。
- **版本号必填** —— 乐观锁不被悄悄关掉的最后一道防线。
- **`@Valid` 生效** —— 用 `never()` 断言校验失败时 Service 根本没被调用。

另用 `ArgumentCaptor` 钉死两个默认值：新建策略 `dryRun` 必须缺省 true、
`enabled` 必须缺省 false。缺省成 false 会让「忘了传这个字段」
变成「直接上线真实执行」。

**顺带修了一个编译错误**：`Map.of` 最多 10 组键值对，风险策略请求体有 11 个字段。
这类错误只在编译期暴露，正是后端此前从未编译过才会积累的类型。

### 3. 阶段 B 第一步：Prometheus 集成（任务 3，B1+B2 完成）

| 组件 | 说明 |
|---|---|
| `PrometheusClient` | instant / range / health 三类查询 |
| `PromQuery` | 领域模型，把上游 JSON 收敛成项目自己的结构 |
| `MetricsCatalog` | 7 条内置指标，对外只暴露 ID |
| `MetricsController` | 5 个端点（catalog / instant / range / overview / datasource） |
| `MetricsUnavailableException` + `BizError.METRICS_UNAVAILABLE` | 50020 / 503 / Retry.NEVER |

**核心取舍：代理查询，不自建时序存储。**
自建 TSDB 是数月工程量，而 Prometheus 已是事实标准、用户本来就有；
再存一份会出现「两套数据对不上，以哪个为准」的无解问题。
代价是「Prometheus 挂了本页没数据」——但这是正确的失败模式。

**只暴露指标 ID，不接受任意 PromQL**：否则一条高基数聚合就能拖垮
整个监控体系，且前端各页各写查询语句、指标改名要改十几处。

几个真会出问题的细节（均已写成测试）：
- 超时必须短（5s）——一条写错的 PromQL 跑几十秒会占满 Web 线程池，
  **监控页把主站拖挂是运维系统最难堪的失败**
- NaN/Inf 转 null——JSON 没有 NaN 字面量，且 NaN 参与运算会静默污染整条链
- HTTP 200 但 `status != success` 也算失败——否则会在解析时空指针，
  报错位置离真实原因十万八千里
- range 查询按「最多 1500 点」反推最小步长——否则长时间窗会产出几十万个点

**契约同步被前端测试当场抓住**：新增 50020 后，
`backendContract.test.ts` 立刻报「前端映射了后端不存在的业务码」。
这正是那套契约机制存在的意义。
