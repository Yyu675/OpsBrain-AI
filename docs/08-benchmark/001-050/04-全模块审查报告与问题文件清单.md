## 一、本次已修复（2 项真实缺陷）

### 🔴 P0-1：工单域完全没有事务

**取证**

```
知识库域 @Transactional：22 处
工单域   @Transactional：0 处   ← 而它注入了 6 个 Repository
```

`TicketService` 注入 6 个 Repository、约 15 个写方法，**一个事务都没有**。最严重的是 `deleteTicket`：

```java
ticketRepository.deleteById(ticketId);       // 表 1
replyRepository.deleteByTicketId(ticketId);  // 表 2
activityRepository.deleteByTicketId(...);    // 表 3
tagRepository.deleteByTicketId(...);         // 表 4
actionRepository.deleteByTicketId(...);      // 表 5
postmortemRepository.deleteByTicketId(...);  // 表 6
```

**任何一步失败，前面已删的不会回滚**，留下指向已删工单的孤儿回复、标签、复盘记录。而且没有任何报错——用户看到「删除成功」，数据库里躺着一堆孤儿行。

`createTicket`（工单+标签+活动流）、`addReply`（回复+工单+活动流+首响）同理。

**已修**：14 个多表写方法统一加 `@Transactional(rollbackFor = Exception.class)`。

两个核查点：
- **自调用代理陷阱**：`recordActivity` / `markFirstResponse` 被同类方法调用。已确认它们**未单独标注** `@Transactional`，因此继承调用方事务，不触发 Spring AOP 自调用失效。
- **对象存储边界**：`TicketAttachmentService.delete` 同时写数据库和删 MinIO 对象。这里**不能简单套事务**——MinIO 无法回滚。已在注释里写明顺序设计：先删库后删对象，删库失败则回滚、对象仍在（只多占存储）；反序则会留下「记录在但文件没了」的死链。

### 🔴 P1-1：工单状态机缺失，可越权流转

**取证**：`updateStatus` 只校验「目标值是不是合法枚举」，不校验「能不能从当前状态走过去」。

```java
if (!TicketEnums.Status.isValid(status)) { ... }   // 只有这个
```

后果：
- **CLOSED → PENDING**：已归档工单重回待办池，SLA 计时错乱
- **VOID → PENDING**：作废工单被复活，「这张单到底存不存在」不可判定

对照之下，`AgentState` 有完整的 `canTransition` 状态机——**同一个项目里两套标准**。

**已修**：
- `TicketEnums.Status` 新增 `canTransition` / `nextStates` / `isTerminal`
- VOID 为不可逆终态；同态幂等放行（重试不报错）
- 前端同步新增 `statusOptionsFor`，**非法选项直接置灰并给出原因**——防呆优于事后报错
- **契约测试直接解析后端 Java 源码**交叉校验，防止两侧分叉（已注入分叉验证测试确实会失败）

规则自洽性已用等价实现验证：无孤立态、仅 VOID 无出边、正常闭环畅通、误接单可退回、复发可重开。

## 四、可行性优化建议（按 ROI 排序）

### 4.1 ★★★★★ 消除 78 处 Controller 样板（约 0.5 天）

**现状**：项目已有 `GlobalExceptionHandler`，但 Controller 里仍写了 **78 处** `catch(Exception)`，典型形态：

```java
try {
    DevOpsTicket updated = ticketService.updateStatus(id, req.status());
    return ApiResponse.success(updated);
} catch (IllegalStateException e) {
    return ApiResponse.error(40004, e.getMessage());
} catch (IllegalArgumentException e) {
    return ApiResponse.error(40001, e.getMessage());
} catch (Exception e) {
    log.error(...);
    return ApiResponse.error(50001, "变更状态失败: " + e.getMessage());
}
```

**问题**：① 同样的 10 行重复 78 遍；② 各处错误码映射不一致（同是 `IllegalStateException`，有的映 40004 有的映 40001）；③ **`e.getMessage()` 直接下发给用户**，可能泄漏内部实现细节。

**建议**：把映射收敛到 `GlobalExceptionHandler`，配合已建的 `BizError` 枚举：

```java
@ExceptionHandler(IllegalArgumentException.class)
public ApiResponse<Void> handleIllegalArgument(IllegalArgumentException e) {
    return ApiResponse.error(BizError.INVALID_PARAM.code(), e.getMessage());
}
@ExceptionHandler(IllegalStateException.class)
public ApiResponse<Void> handleIllegalState(IllegalStateException e) {
    return ApiResponse.error(BizError.CONFLICT.code(), e.getMessage());
}
```

Controller 收缩为 3 行。**收益**：删除约 700 行样板、错误码映射单一真相、便于后续统一脱敏。

---

### 4.2 ★★★★☆ 引入 Bean Validation（约 1 天）

**现状**：`spring-boot-starter-validation` 在 pom 里，但 `@Valid` **0 处使用**，`@NotBlank`/`@Size` **0 处**。校验全靠 Service 手写——仅 `TicketService` 就 20 处 `throw new IllegalArgumentException`。

**问题**：校验规则埋在业务逻辑里，无法从 API 文档看出字段约束；同一字段在不同入口的校验可能不一致。

**建议**（对 DTO 而非实体加注解）：

```java
public record CreateTicketRequest(
    @NotBlank(message = "工单标题不能为空")
    @Size(max = 120, message = "标题不超过 120 字")
    String title,

    @NotNull @Pattern(regexp = "P0|P1|P2|P3", message = "优先级必须是 P0-P3")
    String priority,

    @NotBlank @Size(max = 5000) String description
) {}
```

Controller 加 `@Valid`，配合 `MethodArgumentNotValidException` 的统一 handler，**字段级错误可直接映射回前端表单字段**（这也是 4.4 的前置）。

Service 层的手写校验**保留**——它是领域不变量的最后防线，DTO 校验只挡格式问题。

---

### 4.3 ★★★☆☆ 统一消息出口（约 0.5 天）

**现状**：121 处裸 `ElMessage.success/error`，绕过 `utils/notify.ts` 已实现的 **1 秒冷却去重**。

**后果**：批量操作（如批量删除 10 条）会连弹 10 个提示条刷屏。

**建议**：全局替换为 `notify.success/error`，并加 lint 规则防回潮：

```js
'no-restricted-imports': [{
  paths: [{ name: 'element-plus', importNames: ['ElMessage'],
            message: '请用 @/utils/notify（含冷却去重）' }]
}]
```

---

### 4.4 ★★★☆☆ 表单分组（约 1 天）

**唯一明显欠缺的 UX 项**。`TicketFormDialog.vue` 1073 行，字段平铺无分组。

**建议**按业务语义分三组，用 `el-divider` 或折叠面板：

```
① 基本信息   标题 · 优先级 · 所属服务 · 模块
② 问题详情   描述 · 堆栈 · 附件
③ 处理安排   负责人 · 标签 · 期望完成时间   ← 可折叠，新建时默认收起
```

**同时建议**：把校验规则从 SFC 内联抽到 `features/ticket/lib/ticket-form.schema.ts`，与 4.2 的后端 DTO 约束对齐（上限 120 字这类数字两边要一致）。
