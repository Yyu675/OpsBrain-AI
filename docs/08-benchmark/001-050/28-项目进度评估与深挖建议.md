## 二、本轮查出的 2 个缺陷

### 缺陷 1：Spring 自调用导致事务完全失效

`acknowledgeTicket` 自身没有 `@Transactional`，却直接：

```java
this.transferTicket(...)   // 标了 @Transactional
this.updateStatus(...)     // 标了 @Transactional
```

**Spring 的事务由 AOP 代理织入，自调用不经过代理**，那两个注解在这条路径上形同虚设。

修复前这里是**三次独立的自动提交写入**。转派成功但状态变更失败时，
工单停在「负责人已改、状态仍是待处理、活动流只留了转派记录」的半截状态，
而调用方收到异常，会以为整个操作都没发生。

> 为确认不是孤例，写脚本扫了全项目「非事务方法自调用 `@Transactional` 方法」，
> 结果只有这一处（2 个调用点），范围可控。

### 缺陷 2：一个方法承担了两种互斥语义

`isTerminalStatus()` 返回 `RESOLVED / CLOSED / VOID`，被用在两类地方：

| 用途 | 处数 | 是否正确 |
|---|---|---|
| SLA / 首响计时停止 | 3 | ✅ 正确 |
| **写操作门禁**「工单已终结，无法 XXX」 | 5 | ❌ **错误** |

第 2 类把 RESOLVED 也挡在门外，导致这些真实流程根本走不通：

- 先标已解决、**事后补做验证**（当时忙着救火，事后补录）
- 验证没过，**退回 FIXING** 继续修
- 问题重现，**在原单上重新接手**（新建单会丢掉根因、验证、时间线全部上下文）

**代码自己就暴露了矛盾**：`submitVerification` 的门禁拒绝所有 RESOLVED，
而它下面紧接着有一句

```java
if (!RESOLVED.equals(existing.getStatus())) { updateStatus(ticketId, RESOLVED); }
```

这个判断**永远为真**——是死代码。作者显然预期 RESOLVED 能走到这里。

更值得注意的是：项目里本来就有正确的定义
（`TicketEnums.Status.isTerminal()` 只认 VOID），**两套定义并存，用错的那套没人发现**。

修复：拆成 `isTerminalStatus()`（计时终态，Javadoc 明确写「不要用作操作门禁」）
与 `isImmutableStatus()`（仅 VOID，委托给已有定义，避免第三套）。

## 三、回答「是否需要再全面核查」

**需要，但不该靠人工通读——本会话已经验证了更有效的方式。**

### 有效的做法：写脚本做模式扫描

本会话查出的缺陷有一个共同规律：**编译期无信号、运行期无报错、只在特定路径才暴露**。
人工通读几乎不可能发现，但它们都有可被脚本识别的固定模式。

本轮跑了 4 类扫描，结果如下：

| 扫描项 | 结果 |
|---|---|
| `@Transactional` 标在 private/protected 上 | ✅ 0 处 |
| 非事务方法自调用 `@Transactional` 方法 | ⚠️ **1 处（已修）** |
| 配置项定义了但无代码读取 | ✅ 0/69（P1-7 那类已清干净） |
| 空 catch / 吞异常无日志 | ✅ 6 处，均有解释性注释，属有意为之 |

**建议把这几个扫描固化成 CI 的一个 job**，成本很低但能持续拦住同类回归。

### 已识别但尚未覆盖的风险面（量化）

脚本统计了「Service 层 public 写方法 vs 测试覆盖」：

| Service | 未覆盖写方法 | 风险 |
|---|---|---|
| `TicketService` | **本轮从 13 降到 2** | 已基本收口 |
| `ToolRuntimeManager` | 8/11 | 🔴 **高**——工具执行治理，含幂等键、重试、审批判定 |
| `AgentStateManager` | 5/6 | 🟠 中——会话状态机 |
| `ApprovalService` | 3/5 | 🔴 **高**——`approve` / `expireOverdue` 是授权动作 |

| `KnowledgeDocService` | 3/18 | 🟢 低 |
| `DevOpsAgentServiceImpl` | 3/3 | 🟠 中——SSE 流式，需异步测试方案 |

## 四、后续建议（按性价比排序）

### 建议 1：把模式扫描固化进 CI（成本最低，收益持续）

把本轮那 4 个 Python 扫描脚本收进 `tools/audit/`，
在 CI 加一个非阻断 job。它们能持续拦住：
自调用事务失效、注解位置错误、配置项无人读取。

> 之所以有效，是因为这几类缺陷**一旦引入就长期潜伏**——
> P1-7 那个付费探针开关失效存在了很久，直到写测试时才被发现。

### 建议 2：优先补 `ToolRuntimeManager` 与 `ApprovalService`

这两个是「AI 能不能动生产系统」链路上的核心：

- `ToolRuntimeManager.executeTool` —— 幂等键、重试次数、超时、审批判定全在这里
- `ApprovalService.approve` —— 授权动作本身；`expireOverdue` 决定超时审批怎么处理

它们的错误后果与本会话修的付费探针同级：**不会报错，但安全边界已经变了**。

### 建议 3：给 SSE 设计异步测试方案（独立工作）

`DevOpsChatController`（386 行）+ `DevOpsAgentServiceImpl` 的 3 个写方法
都卡在同一个技术问题上：`MockMvc` 对异步流支持有限。

需要 `MockMvc.asyncDispatch` + `SseEmitter` 事件收集，或改用 `WebTestClient` 消费流。
**不建议硬塞进常规批次**——那只会得到几条断言「HTTP 200」的假测试。

### 建议 4：前端大文件拆分（可延后）

`TicketList.vue` 2679 行、`KnowledgeEditor.vue` 2013 行仍未拆。
但按第 22 轮的经验，**拆分前必须先补测试**——
上次拆 `TicketDetail` 时，正是 74 例测试抓出了我自己引入的破坏
（删模板时多删了一个闭合标签，`vue-tsc` 只报一串误导性的「变量未使用」）。

`KnowledgeEditor` / `KnowledgeDetail` / `KnowledgeBase` 三个大文件目前零测试，
建议先补测试再考虑拆分。
