> 本轮范围：`AgentStateManager` / `AgentState` / `TicketAttachmentService`
> 新增测试 **66 例**（后端 723 → **789**，测试文件 58 → **60**）

---

## 一、为什么挑这两个类

两者的共同点是：**它们出错时不抛异常，只是结果不对**。

| | `AgentStateManager` | `TicketAttachmentService` |
|---|---|---|
| 调用方 | `DevOpsAgentServiceImpl` 里 13 处 `transition(...)` | `TicketController` 上传/下载/删除/级联清理 |
| 失败表现 | 返回 `null`，**13 处调用方无一检查返回值** | 库与对象存储不一致，界面照常显示 |
| 事后可见性 | 会话轨迹缺一段，分不清「没走到」还是「被吞了」 | 下载 404 / 「已删除」的文件其实还在 |

状态迁移被判非法时静默返回 `null`，业务继续往下跑——这意味着状态机里任何一条边写错，
**都不会有任何一行错误日志指向它**。

## 二、查出并修复的缺陷

### 缺陷 1 🔴 补偿与人工升级的出边是死代码，会话永远归不了档

`AgentState.isTerminal()` 把 `COMPENSATING`、`MANUAL_ESCALATED` 一并算作终态，
而 `canTransition` 开头就是：

```java
if (from.isTerminal()) return false;   // 终态不可再迁移
```

于是 switch 里精心写好的这两行**永远执行不到**：

```java
case COMPENSATING     -> to == CLOSED || to == MANUAL_ESCALATED;
case MANUAL_ESCALATED -> to == CLOSED;
```

**成因**：把「不再活跃」和「不许再改」混成了一个判断。
语义上这两个状态本就是**进行时**——「补偿**中**」「已转人工**处理**」，
不是流程的句号；真正的句号是它们之后的 `CLOSED`。

**用户可见后果**：Saga 补偿跑完、人工接管处理完之后，会话永久停在
「补偿中」「人工升级」。运维在会话轨迹里看到一批分不清死活的僵尸会话，
无法区分「真的还在补偿」和「补偿早就结束了但状态没推进」；
后台还会持续刷出「非法状态迁移」告警。

**修复**：`isTerminal()` 只保留 `SUCCESS / FAILED / CLOSED`；
另拆 `isSettled()` 供看板「从进行中摘出去」的统计口径使用。
这与上一轮 `DevOpsTicket.isTerminalStatus()` / `isImmutableStatus()` 是同一类问题、同一种拆法。

### 缺陷 2 🔴 空闲清理对新会话完全失效——一条线性增长的内存泄漏

```java
sessionStates.values().removeIf(s -> {
    if (s.getLastTransitionTime() == null) return false;   // ← 直接放行
    ...
});
```

而 `getOrCreateSession` 新建的会话，`lastTransitionTime` 恰好就是 `null`。

**用户可见后果**：任何在首次迁移之前就中断的会话——请求刚进来就被安全门卫拒绝、
预算超限、客户端断连、或后续迁移全被判非法而未落地——都会**永久驻留内存**。
清理线程每 5 分钟兢兢业业跑一次，一个都清不掉，日志里还写着
「清理空闲会话 removed=0」，看上去一切正常。
最终表现为服务运行数日后堆占用只涨不跌、Full GC 频繁、响应变慢，直至 OOM。

**修复**：新增 `SessionState.getIdleSince()`，空闲基准优先取最后迁移时间，
从未迁移过则**回落到创建时间**。

### 缺陷 3 🔴 `transition` 的「校验-写入」不是原子的

迁移的调用方分布在至少两类线程上：处理请求的 `sessionExecutor` 线程，
以及模型的 SSE 回调线程（`onToolExecuted` / `onCompleteResponse` / `onError` 里都在迁移状态）。
二者对同一 `traceId` 并发迁移是**常态而非例外**。

无锁时的三种具体后果：

1. 两个线程同时读到 `fromState`，各自校验通过，后写的覆盖先写的——
   状态机凭空跨过一条不存在的边，**「需人工审批」的会话可能被冲成「草稿就绪」，直接绕过审批闸门**；
2. `transitions` 是普通 `ArrayList`，并发 `add` 会丢记录，扩容期撞车甚至让审计轨迹出现 `null` 空洞；
3. `durationMs` 基于 `lastTransitionTime` 计算，交错读写会算出负数或离谱大值，各阶段耗时统计随之失真。

**修复**：把「读当前态 → 校验 → 写新态 → 追加轨迹」整段收进 `synchronized (session)`。
锁粒度取**单个会话对象**而非整个管理器——不同 `traceId` 本就互不影响，
锁在 `sessionStates` 上会让所有并发会话的状态迁移互相排队。

### 缺陷 4 🟠 审计轨迹只进不出

类注释白纸黑字写着职责之一是「提供状态查询、**回放数据导出**」，
但此前**没有任何导出方法**：迁移记录锁在 `private static class SessionState` 里，
而 `getSession` 虽是 public 方法却返回私有类型，**包外连接住返回值的变量都声明不出来**。

**用户可见后果**：每次迁移辛苦攒下的审计轨迹只进不出，等会话被清理就彻底消失。
出问题时运维拿不到任何可回放的执行链路，只能翻散落的日志文本。

**修复**：`SessionState` 改为 public；新增 `exportTransitions(traceId)`（返回**不可变副本**）、
`getCurrentState(traceId)`、`sessionCount()`。

副本而非原 List 是必须的：内部用普通 `ArrayList`，直接交给外部遍历时，
若模型回调线程正好在 `addTransition`，调用方会撞上 `ConcurrentModificationException`——
一次「只是看看审计轨迹」的读操作反而把请求打挂。

### 缺陷 5 🔴 `delete()` 在事务中间就删对象，回滚后成死链

原顺序：`deleteById → removeObject → recordActivity`。

方法注释洋洋洒洒论证了「先删库、后删对象」的正确性，**顺序确实是对的，但时机不对**：
最后一步 `recordActivity` 写活动流表若抛异常，
`@Transactional(rollbackFor = Exception.class)` 会把 `deleteById` **回滚**——
元数据完好如初回到库里，可 MinIO 里的对象**已经删掉且无法随数据库回滚恢复**。

**用户可见后果**：用户刷新后附件仍在列表上，点下载得到 404。
这正是那段注释里明确说要避免的「记录还在但文件已没」的死链。

**修复**：新增 `removeObjectAfterCommit(bucket, key)`，
通过 `TransactionSynchronizationManager` 把对象删除挂到 `afterCommit`。
事务中任一步失败都不会碰对象存储；无事务上下文时退化为立即删除（行为可预期，不静默跳过）。

### 缺陷 6 🟠 删除对象用的是当前配置的 bucket，而非记录里存的 bucket

元数据表专门存了 `bucket` 列，`presignDownloadUrl` 也确实用 `meta.getBucket()`，
**唯独删除路径写死 `@Value` 注入的当前配置**。

**用户可见后果**：一旦迁移存储、分环境改桶名，或历史数据本就写在旧桶里，
删除就会打到新桶里那个不存在的 key 上，旧桶里的真实文件**永远删不掉**。
附件从列表消失、文件却仍留在对象存储中——
若是按合规要求删除敏感文件，用户得到的是「已删除」的假象，实际数据仍可被访问。

**修复**：`silentRemoveObject(objectBucket, objectKey)` 用记录里的 bucket，
为空（早于该列存在的历史数据）时才回落到当前配置。

### 缺陷 7 🟠 活动流留痕失败，让一次成功的上传报错

`upload()` 末尾的 `recordActivity` 是裸调用，抛异常时整个方法失败、Controller 返回错误。
但此刻文件**已经躺在 MinIO、元数据也已经落库**。

**用户可见后果**：用户看到「上传失败」，刷新页面附件却好端端在列表里；
于是他重传一次，被 SHA-256 查重逻辑拦下报「该文件已上传过」——
陷入**「说失败又说重复」的死结**，只能找运维。

**修复**：活动流是留痕，不是上传成功的必要条件。主链路（对象 + 元数据）
已经一致的前提下，降级为 `log.warn`。

## 四、测试有效性验证

按既定纪律，**改完必须验证测试真能抓到缺陷**。本轮针对缺陷 1 做了注入-还原：

把 `isTerminal()` 改回含 `COMPENSATING`/`MANUAL_ESCALATED` 的旧实现，
用同一组断言跑（`AgentState` 是零依赖枚举，可脱离 Maven 独立编译执行）：

```
【1】COMPENSATING / MANUAL_ESCALATED 出边可达
  ❌ COMPENSATING→CLOSED
  ❌ COMPENSATING→MANUAL_ESCALATED
  ❌ MANUAL_ESCALATED→CLOSED
【3】isSettled 与 isTerminal 语义分离
  ❌ COMPENSATING 不应是终态
  ❌ MANUAL_ESCALATED 不应是终态
```

精确命中 5 项，还原后全绿。**测试确实在测东西，不是摆设。**

> 值得注意：「每状态皆可达终态」这一项在缺陷版本下**仍然通过**——
> 因为那两个状态被*定义*成了终态。这说明单靠可达性检查抓不到缺陷 1，
> 必须有针对具体边的显式断言。结构性用例与具体断言互为补充，缺一不可。

## 六、下一轮建议

1. **`DevOpsAgentServiceImpl` 的 13 处 `transition` 全部不检查返回值。**
   本轮把状态机本身钉死了，但「迁移失败被静默吞掉」这个结构性问题仍在。
   建议至少在关键闸门（`WAITING_APPROVAL`、`FAILED`）处校验返回值并告警。
2. **`AgentStateManager` 的 `exportTransitions` 目前无生产调用方。**
   与上一轮 `getBizError` 的情况同构——有能力但没接线。
   建议接到会话轨迹查询接口上，让运维真能回放。
3. **`TicketList.vue`（2679 行）/ `KnowledgeDetail.vue`（1730 行）仍零测试**，
   是前端最大的存量风险，建议先补测试再拆分。
4. **仍需用户操作**：`tools/audit/run_audit.py` 接入 CI（我无 `.github/workflows/` 写权限）：
   ```yaml
         - name: 代码模式扫描
           run: python3 tools/audit/run_audit.py
   ```
