## 缺陷一：切 Tab 时上一个 Tab 的筛选仍在生效（我引入的）

**归类**：数据准确性 · 隐形过滤

使用日志页两个 Tab 的筛选维度完全不同，却共用同一批 ref。
在 AI 调用页筛了 `model=qwen-max` 后切到操作审计：

| 环节 | 实际行为 |
|---|---|
| `modelName` ref | 仍是 `'qwen-max'` |
| `load()` 请求 | 把它拼进了参数 |
| 操作审计筛选栏 | **根本没有「模型」这个控件** |
| `hasFilters` | 不把它算进去 → **「清除筛选」按钮不显示** |

用户看到一份被悄悄过滤过的列表，界面上**没有任何筛选生效的迹象**，
而且无从清除。这类"隐形筛选"比报错更难排查——数据少了，但没人知道为什么。

**修复**：切 Tab 时清掉上一个 Tab 专属的筛选。

**时间范围刻意保留**：查「今天」的 AI 调用后再看「今天」的操作审计，
是合理预期，不该被一起清掉。这是我做的产品判断，不是遗漏。

## 缺陷二：越界页码产出「显示 199961-50 共 50 条」（影响三个页面）

**归类**：展示准确性 · 共享组件缺陷

`?page=` 来自分享的链接或手工编辑，而"第几页有效"只有拿到后端
`totalPages` 才知道。实测 `?page=9999`（total=50、每页 20）：

```
pageStart = 199961     ← (9999-1) * 20 + 1
pageEnd   = 50         ← Math.min(9999*20, 50)
文案      = 「显示 199961-50 共 50 条」   ← start 远大于 end
```

且页码按钮全部失效（当前页不在 1..3 的窗口内），用户被困在空白页。
`useServerPagination` 是共享的，**TicketList / AlertList / AuditLogs 都受影响**。

### 我先写错了一版，这里值得记录

第一反应是在 `setMeta` 里夹取页码——看起来最自然。结果**直接挂掉两条既有用例**：

```
× 总数为 0 时不退页 —— 这是「筛选无结果」而非「删空了当前页」
× 连续删空多页时每次退一页，不会退到 0 页
```

去看那些用例，发现有一条明确的既有契约：

> `setMeta` 不改动当前页 —— **翻页与元信息更新是两件事**

**测试是对的，我的改法是错的**，已撤销。这正是那些用例存在的意义——
它们挡住了一个看似合理、实则破坏既有语义的改动。

### 最终分两层修

| 层 | 位置 | 做什么 | 为什么在这 |
|---|---|---|---|
| 展示层 | `useServerPagination` | `pageStart` 加 `Math.min` 兜底 | 纯展示修正，不碰契约。保证文案永远读得通 |
| 业务层 | `AuditLogs` | 确认越界且当前页无数据 → 夹回末页重拉 | 契约在 composable 那边，页码修正是调用方的责任 |

## 缺陷三：登出后 Query 缓存残留（安全）

**归类**：越权读取 · 与此前「对话历史残留」同类

TanStack Query 的 `gcTime` 是 5 分钟，期间工单列表、告警、审批队列、
审计日志全部原样留在内存，而**登出流程从不清理它**。

下一个用户在同一标签页登录后若命中相同 queryKey，
**会先看到上一个人的数据**——这是 stale-while-revalidate 的默认行为：
先渲染缓存，再后台刷新。

对只读用户尤其严重：他本无权看到的工单标题、审批摘要、审计里的 AI 问答，
会在后台刷新完成前的那一瞬间完整呈现。

探针实测确认（登出后仍可读出）：

```
登录期间缓存条数 = 1
缓存内容 = {"items":[{"id":"TKT-1","title":"支付链路熔断阈值调整"}]}
--- 登出后（无清理）---
缓存条数 = 1
仍可读到 = {"items":[{"id":"TKT-1","title":"支付链路熔断阈值调整"}]}
```

**这是我此前的疏漏**：修「对话历史残留」时只想到了 localStorage 那一层，
没意识到内存缓存是同一类载体。

**修复**：在已有的 `useSessionCleanup` 里加 `queryClient.clear()`。

**用 clear 而非 invalidateQueries**：后者只标记过期、数据仍在缓存中，
挡不住"先渲染旧数据"这一步。这里要的是**移除**，不是"下次重拉"。
已写用例专门钉住这个区别。

## 本轮教训

**1. 新写的代码要优先自查。**
3 个缺陷里 2 个是我自己上一轮引入或漏掉的。新代码没经过时间检验，
缺陷密度最高，"刚写完还热乎"不等于"没问题"。

**2. 测试挂了先怀疑自己的改动，不要先改测试。**
`setMeta` 夹取那次，两条用例失败的第一反应可以是"这测试过时了"。
但去读用例注释，发现它记录着明确的设计契约——**测试是对的，我错了**。
这类既有用例的价值恰恰在于挡住看似合理的破坏性改动。

**3. 同一类缺陷要横向扫一遍所有载体。**
修「对话历史残留」时我只处理了 localStorage，没想到 Query 内存缓存
是同一个问题的另一种载体。以后遇到"登出未清理"这类问题，
应该系统地列出所有数据载体（localStorage / sessionStorage / 内存 store /
Query 缓存 / 组件状态）逐一确认，而不是只修眼前看到的那个。
