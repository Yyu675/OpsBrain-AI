## 后端缺陷（本轮首次深入后端）

### 🔴 X-Forwarded-For 无条件信任 → 限流被绕过 + 审计 IP 可伪造

后端有两处各自读 XFF 并**取第一段**，且无条件信任：

| 位置 | 用途 | 后果 |
|---|---|---|
| `WebhookGuard` | 限流主体 | **限流被彻底绕过** |
| `OperationAuditInterceptor` | 审计来源 IP | **审计证据可伪造** |

**限流绕过的严重性**：每次请求换一个伪造 XFF，限流键就换一个，
ZSET 计数永远到不了阈值。而 `/api/v1/alerts/webhook` **免鉴权、
直接写库、可触发自动建单**——限流是它唯一的防线。

原代码注释写着「不构成鉴权绕过（鉴权靠密钥）」。这句话本身没错，
但它低估了后果：密钥泄露或内部误用时，限流本该是第二道闸门，
而当时那道闸门形同虚设。

**审计污染的严重性**：攻击者可把来源 IP 写成任意值，
事后追溯会指向无辜的内网地址。审计表恰恰是最不能被伪造的地方——
它存在的意义就是事后能查。

#### 修复的两个关键判断

**① 只在 remoteAddr 属于受信任代理时才采信 XFF**
`getRemoteAddr()` 是 TCP 层对端地址，无法伪造，用它当判据。
信任列表走 `devops.security.trusted-proxies`，**默认为空**——
未部署代理时直接可用且安全；部署了再显式配置，
比「默认信任、忘了收紧」安全得多。

**② 取最后一段而非第一段**
XFF 格式是 `客户端, 代理1, 代理2...`，左侧由客户端伪造、右侧由每一跳
代理追加。常见写法取第一段，拿到的恰好是攻击者可写的部分。

顺带统一了 `DevOpsChatController` 的限流主体（原本直接用 `getRemoteAddr()`，
安全但在代理后会让全站共用一份额度）。

## 前端缺陷：SSE 断流卡死（第 3、4 处）

`fetchEventSource` 在服务端关流时**正常 resolve**——不抛错、不进 catch、
不触发 onError。只在 complete/error 里复位「生成中」状态的写法必然漏掉这条路径。

### 全部 5 个调用点的核对结果

| 调用点 | 状态 | 卡死后果 |
|---|---|---|
| ChatMode | 上轮已修 | 输入框禁用、停止按钮点了没反应 |
| useTicketAnalysis.runAnalysis | 本轮修 | 「重新分析」点不动 |
| useTicketAnalysis.generateReply | 本轮修 | 同上 |
| **KnowledgeSinkDrawer.generateDraft** | **本轮发现** | **「发布并入库」永远禁用** |
| TicketFormDialog.aiSuggest | 免疫 | 在 `finally` 里复位 |

**KnowledgeSinkDrawer 后果最重**：用户既发布不了、也重新生成不了，
只能关掉抽屉重开——而重开会 `generateDraft()` 重新生成，
之前 AI 已经写好的内容**全部丢失**。

三处还有共同的第二个问题：`onBeforeUnmount` 只 abort 不收尾。
abort 走 catch 分支，而组件已卸载、那段 catch 未必执行完。

### 加 lint 规则终结该缺陷类

```js
selector: "CallExpression[callee.name='chatStream']
           > ObjectExpression:not(:has(Property[key.name='onClose']))"
```

这个缺陷出现三次，每次都是新增调用点时照着旧写法抄。
靠 review 记住不现实。

规则一上就报出 `TicketFormDialog`——它虽然免疫，但**没有用 disable 敷衍**，
而是补了 onClose 用来区分「模型没给出可用 JSON」与「压根没收到完整响应」，
两者用户的下一步不同（改描述重试 vs 直接重试）。

## 本轮教训

**同一缺陷出现第二次，就该停下来找模式，而不是继续逐个修。**

SSE 断流这个问题，前两次我都是"遇到→修好→继续"。第三次出现时才意识到
应该横向扫全部调用点——结果一次找出剩余两处，其中一处后果比前两处都重。

更进一步：**能用工具挡住的，就不要靠人记住**。加了 lint 规则之后，
第 6 个 chatStream 调用点在写的时候就会被拦下，而不是等到线上卡死才发现。

这条同样适用于本轮的后端缺陷——`X-Forwarded-For` 在两处被独立写错，
根因也是"每个人各写一遍"。修法是收敛到 `ClientIpResolver` 单一入口，
而不是把两处分别改对。
