## 一、建议 3：`AgentTraceController` 鉴权定级修正

### 上一轮我判断失误

上一轮我把这个接口描述为「只读且不含敏感内容」，只建议「确认是否加」。
本轮核查了轨迹里 `triggerDetail` 到底拼进了什么：

| 拼接来源 | 泄露内容 |
|---|---|
| `"HIGH 优先级工单待审批: " + draft.title()` | **工单标题原文**，常直接写着内部系统名与故障细节 |
| `"系统异常: " + e.getMessage()` | **原始异常消息**，可能带出内网地址、SQL 片段、依赖服务名 |
| `"安全拦截: " + e.getMessage()` | **安全规则命中原因**——等于把提示词注入防线的判定逻辑告诉攻击者 |
| `"Saga 补偿失败，需人工清理: " + result.failed()` | 脏数据位置 |

这与 `AuditLogController`（已限 ADMIN）是**同一量级的高敏数据**，只是载体从数据库换成了内存。

> **「只读」说的是不改数据，不等于可以随便看。定级应当看数据内容，而不是操作类型。**

已加 `@SaCheckRole("ADMIN")`，并把这个判断失误连同判据一起写进类注释，避免后来人沿用「反正是 GET」的直觉。

### 配套：测试边界声明

切片测试排除了 `WebConfig`，因此 `@SaCheckRole` 在 `AgentTraceControllerWebTest` 里**不会执行**。
沿用 `AuditLogControllerWebTest` 的做法，在类注释显式声明「本类的绿灯不构成对权限的任何保证」——
避免将来有人看到这组绿灯就以为权限有回归保护。

## 二、建议 1：轨迹 UI 组件

新增 `src/components/ai/AgentTraceDrawer.vue`（时间轴 + 慢段高亮）+ 14 例测试。

### 核心设计：两种「空」不能长成一个样

这是组件里唯一真正需要动脑的地方：

| 情况 | `transitions` | 含义 | 该怎么办 |
|---|---|---|---|
| `found=false` | `[]` | 会话已被清理 / traceId 有误 | 去「AI 调用日志」查落库记录 |
| `found=true` 且零迁移 | `[]` | **流程真的卡在最开始** | 这是真实故障，就地排查 |

两者数据形态完全相同、含义完全相反。若组件只判 `transitions.length` 就渲染统一的
「暂无数据」，**运维会把一次真实卡死当成「记录过期了」放过去**。
组件为此分了两套文案、两种图标，测试逐条钉住，并额外加了一条
「两种文案确实不同」防止将来被合并。

其余三条：
- 接口报错必须显示 + 可重试。吞成空轨迹会让人以为「流程没跑」，而实际是「没查到」——排查方向相反；
- 「最慢一段」只在两段以上时提示。单段轨迹里最慢的就是它自己，标出来没有信息量反而像报警；
- `traceId` 为空 / 抽屉未打开时不发请求。

## 三、建议 2：存量大页面补测试

`TicketList.vue`（2679 行）与 `KnowledgeDetail.vue`（1730 行）零测试，是前端最大存量风险。

### 为什么是「先补测试，再拆分」

没有测试兜底的重构，等于把现有缺陷原样搬进新文件，还额外引入搬运错误。
本轮只补测试，不动结构。

### 3.1 `TicketList` 筛选 chip 增删对称性（8 例）

`activeFilterChips` 负责**造出** chip（每个带 `kind`），`removeFilterChip` 用 switch 按 `kind` **消掉**它。
两处各写各的——加了新筛选项却忘了加 `case`，那个 chip 就变成**点了没反应的死按钮**：
用户看得见它挂在那儿，点 × 怎么也删不掉，**且不会有任何报错，控制台干干净净**。

测试从源码抽出两个集合做双向比对（多余的 `case` 也查，那是死代码）。

**为什么用源码解析而非 mount**：这个页面要挂起来得 stub 掉 store、router、
element-plus 表格与十几个子组件，大部分断言会耗在「有没有 stub 全」上。
而本不变式的两端**都是静态字面量**，直接比对反而更直接、更不易碎。
此手法在本项目已有先例（业务码词表契约、净化白名单一致性）。

另外守住三条易漏项：移除 chip 后页码归 1、移除关键词时 `cancel()` 掉 300ms 防抖
（否则在途回调会把 `appliedQuery` 又写回去，造成「chip 没了筛选还在」的幽灵状态）、
`clearFilters` 要连标签数组一起清。

### 3.2 全项目 `v-html` 净化契约（6 例）

`KnowledgeDetail` 的核心风险是 `v-html`。但**逐个组件测守不住这条线——风险不在已有的那几处，而在下一处**：
明天有人加一个 `v-html="item.desc"`，所有既有测试照样全绿。

所以改为扫描全部 `.vue`，强制每个 `v-html` 绑定表达式都来自已知净化通道
（`safeMarkdown()` / `DOMPurify.sanitize(..., sanitizeConfig())` / 组件内 `renderMarkdown` / `safe*` 前缀 ref）。

排查中确认了一处**看起来可疑但实际安全**的写法：`AnalysisCard.vue` 有 3 处 `v-html`
却没有任何净化导入——它通过 **prop 接收** `renderMarkdown`，净化责任在提供方
`useTicketAnalysis`（`const renderMarkdown = (text) => safeMarkdown(text)`）。
这个隐式契约已被单独一条断言显式化：**谁提供 `renderMarkdown`，谁负责净化**。

这与「三套净化白名单已统一到 `htmlSanitizePolicy`」配套：那次统一了**净化规则**，这次守住**是否净化**。
