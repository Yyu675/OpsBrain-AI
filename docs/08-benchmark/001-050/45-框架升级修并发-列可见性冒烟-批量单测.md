### 为什么选 1.2.0 而非最新的 1.19.x

这是**包含修复的最小跨度**。langchain4j 1.x 期间 API 仍在演进，
而本项目重度依赖 `TokenStream` / `AiServices` / `ChatMemoryProvider`，
跨十几个小版本的收益远不及回归风险。修完这个具体缺陷即止。

另注意到一个风险点：`langchain4j-spring-boot-starter` 与
`open-ai-spring-boot-starter` **不在主仓库、版本独立演进**。
所幸本项目五个 artifact 全部由 BOM 托管，只需改一处 property。
沙箱内 Maven 不可达，依赖解析由 CI 验证——这是本次改动最主要的风险。

### 结果

**CI 全绿**，`concurrentStreamsDoNotInterleave` **一行未改**就从红转绿。
集成测试里的 `@Disabled` 至此**归零**。

用例注释也从「暂缓说明」改写成了「它查出了什么」的历史记录：

> 并发用例的价值不在跑通，而在于它能逼出顺序执行永远碰不到的问题，
> **包括依赖库里的**。

## 二、建议 2：补上列可见性的渲染断言（+5 例）

上一轮建议里明确写了「拆列表视图前先确认冒烟测试覆盖表头列显隐」。
核查发现：冒烟测试**声明了** `columnVisible`/`toggleColumn`，
却从未断言「隐藏一列后 DOM 真的少一列」——正是那个缺口。

### 过程中发现 stub 配置本身有问题

初版断言拿到的列数是 **0**。排查发现 `'el-table': true` 是全量 stub，
**会把默认插槽整段吞掉**，而列定义全在插槽里。

修正时又踩到第二层：让 `el-table-column` 也渲染插槽会抛
`Cannot read properties of undefined (reading 'id')`——
列内容是**作用域插槽**，依赖 el-table 真实传入的 `row`。

最终方案：`el-table` 渲染插槽（让列进入 DOM），
`el-table-column` **不**渲染插槽（只要列壳子，不要单元格内容）。

> 值得记的是：**我加的那条 `expect(before).toBeGreaterThan(5)` 守卫立刻发现了这个问题**。
> 没有它，`0 - 0 === 0` 会让「隐藏一列后少一列」这类断言**永远为真**——
> 又一个「两种实现给出同一答案」的假绿，与上一轮 `useDocOutline` 边界用例同型。

### 注入验证

删掉 `service` 列的 `v-if`（模拟拆分时漏搬）→ **精确失败 2 例**。
**现在可以安全拆列表视图了。**

## 三、建议 3：`useTicketBulkActions` 直接单测（+22 例）

此前只由 `TicketList.bulk.test.ts` **通过页面**覆盖，复用到别处就没有保护。
`BulkActionStore` 已是为可测性抽出的窄接口，用普通对象当替身即可，无需 Pinia。

覆盖三类不变式：**状态机可达性**（不发注定失败的请求）、
**部分成功如实上报**（勾 3 成 1 却报「已完成」会让两张工单无人认领）、
**操作后必须 fetchList**（version 乐观锁，不刷新会误报编辑冲突）。

注入「可达性绕过状态机」→ **精确失败 3 例**。

### 一个测试写法上的坑

`bulkDelete()` 返回 `void`，真正的删除挂在 `ElMessageBox.confirm` 的 `.then()` 里——
`await b.bulkDelete()` 只是 `await undefined`，等不到那条链。
需用 `flushPromises` 排空微任务队列。
