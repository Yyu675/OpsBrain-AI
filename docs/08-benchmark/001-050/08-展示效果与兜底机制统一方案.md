# 08 · 展示效果与兜底机制统一方案

> 范围：列表页四态展示、加载骨架、空态、异常处理、异步动作防重入
> 基线：`4479f45` → 产出 `1a2d05f`、`849ba78`
> 测试：627 → **652**（新增 25 例）
> 日期：2026-08-24

---

## 零、方法与结论

本轮不做"看起来更好看"的调整，只做两件事：

1. **把五个列表页各写一份的状态机收敛成一个组件**——顺带暴露并修掉
   分散实现必然产生的漂移缺陷
2. **补齐真正缺失的兜底**——防重入、降级提示、暗色适配

核心判断：**重复实现本身不是问题，重复实现导致的"写对了四处、写漏一处"才是**。
本轮 6 个缺陷全部属于这一类，没有一个是靠"再读一遍代码"能发现的——
必须先统一，漏写的那处才会浮出来。

## 一、修复的缺陷（6 项，全部可复现）

### 🟠 1. ActionItemBoard 改筛选时内容闪断

```vue
<!-- 五个列表页里，只有这一处漏了 length 判断 -->
<div v-if="loading" class="board-state">   <!-- 其余四页都是 loading && xxx.length === 0 -->
```

每次改筛选，已有列表整个消失换成加载态，加载完再出现。用户看到的是**闪断**，
而不是"在原位刷新"。列表越长，页面高度塌陷再撑开的跳动越明显。

### 🟠 2. ApprovalCenter / KnowledgeBase 刷新失败会清空列表

错误分支同样漏 length 判断。切 tab 或翻页失败时，用户手上的数据被整个换成错误页。

**值守场景下这是不可接受的**：网络抖一下就让待审批列表变空白，
而那些数据虽然旧但仍然有用。改为保留内容 + 顶部可重试的提示条。

### 🟠 3. TicketList / AlertList 翻页与筛选完全没有加载反馈

`listLoading` 此前**只出现在首屏骨架的条件里**。有数据之后再请求，界面纹丝不动——
慢接口下用户以为点击没生效，于是反复点。

### 🟡 4. 暗色主题下列表加载闪白

四份骨架实现里，TicketList 与 KnowledgeBase **硬编码 `#f0f0f0` / `#e0e0e0`**
（AlertList / ApprovalCenter 用的是令牌）。暗色主题下这是刺眼的亮白色块。

讽刺的是：`index.html` 里专门写了一段同步脚本防止主题切换闪白，
却在每次列表加载时又闪一次。

### 🟠 5. TicketList 事件订阅被并行请求的失败带崩

```ts
try {
  await Promise.all([fetchList(), loadStats(), loadHotTags(), loadTeamMembers()])
  ticketEvents.on('ticket-created', handleTicketCreated)   // ← 在 try 内、且在 await 之后
} catch (e) { console.error(...) }
```

四个请求里**任意一个**失败（例如统计接口 500），就跳到 catch，订阅永远不注册。
此后用户新建的工单不会插进列表——表现为「创建成功的提示弹了、列表里却没有」，
用户以为工单丢了，实际只是列表没刷新。

同时 `Promise.all` 改 `allSettled`：四个请求互相独立，统计接口挂了不该让
工单列表也一起没有（`all` 在首个 reject 时短路，其余三个结果全被丢弃）。

### 🟠 6. 三个写活动流的动作可重复提交

TicketDetail 的「升级上报」「提升优先级」「标记处理中」只有 try/catch，
**没有进行中标记**（同页的 `doAcknowledge` 有，是写漏的那几个）。

慢接口下双击「升级上报」会提交两次，工单活动流里出现两条一模一样的升级记录。
**工单时间线是事后复盘与追责的依据**，脏数据的代价不是"不好看"——
复盘时无法判断到底升级了一次还是两次。

## 二、新增的三个基础件

### `DataStateBoundary` —— 列表四态的唯一真相

状态优先级（这是契约，不是实现细节）：

| 优先级 | 条件 | 渲染 |
|---|---|---|
| 1 | 有数据 | **内容**（加载中叠加进度条，失败叠加提示条） |
| 2 | 无数据 + 加载中 | 骨架 |
| 3 | 无数据 + 有错误 | 错误态（可重试） |
| 4 | 无数据 + 无错误 | 空态（区分「还没有数据」/「筛选没命中」） |

**「有数据优先」是刻意的**：翻页时把内容换成骨架会让页面高度塌陷再撑开，
滚动位置跟着跳。保留旧内容 + 顶部细进度条是列表类产品的通行做法
（GitHub、Linear 皆如此）。

两个额外状态也在这里收口：
- **就地刷新**：有数据 + 加载中 → 顶部 2px indeterminate 进度条
- **陈旧数据**：有数据 + 刷新失败 → 保留内容 + 可重试的警告条

### `SkeletonRows` —— 骨架的唯一实现

全部走设计令牌，暗色自动适配；补 `role="status"` + `aria-busy`
（原四处骨架都是纯视觉 `div`，读屏用户只会听到一片沉默，
无从判断是在加载还是加载完了没数据）。

`prefers-reduced-motion` 下不是简单把动画压到 0.01ms——那会让渐变停在
随机一帧、看着像渲染坏了。改为显式给静态底色。

### `useAsyncAction` —— 异步动作的防重入

TicketDetail 里已经有 **15 个** `const xxx = ref(false)`。继续这个模式的代价是：
每加一个动作就多一个 ref + 多一处 finally，而**忘写 finally 会让按钮永久禁用**，
比不加防护更糟。

```ts
const escalateAction = useAsyncAction(
  async (id, reason) => { await escalateTicket(id, reason); await loadActivities(id) },
  { action: '升级上报', successMessage: '已提交升级，已记入活动流' }
)
```

四个刻意的设计：

| 设计 | 原因 |
|---|---|
| 重入返回 `undefined` 而非排队 | 运维操作没有"攒着一起做"的语义，第二次点击应被忽略 |
| 用户取消不算失败 | ElMessageBox 取消抛 `'cancel'`，弹「操作失败」会让人以为自己点错了 |
| 不吞异常也不外抛，返回 `T \| undefined` | 调用方判返回值即可，不必再套一层 try/catch——那正是样板代码的来源 |
| 保留 `autoHandleError: false` | 需要自定义错误处理的场景有逃生口 |

## 三、退掉的重复实现

| 项 | 处理 |
|---|---|
| `EmptyState` 组件 | **删除**。与 `AppEmpty` 并存导致同一产品的"没有数据"长着两副面孔（圆角/内边距/图标底色/按钮样式都不同）。统一到 `AppEmpty`——它有 search/network/permission/notfound 语义分型，能区分「还没有数据」与「筛选没命中」，这两句话对应的用户下一步动作完全不同 |
| 4 份 shimmer 关键帧 + 骨架 CSS | 收敛到 `SkeletonRows`，各页删除对应样式 |
| 5 份四分支 v-if 链 | 收敛到 `DataStateBoundary` |
| CSV 导出的裸 `notify.error` | 改走 `handleServerError`。原写法丢掉业务码映射：配额超限（40005）与后端 500 显示同一句「请稍后重试」，而前者等一会儿确实能好、后者等多久都没用 |

## 四、核查通过、确认无需改动的部分

避免后续重复排查：

| 项 | 结论 |
|---|---|
| 焦点陷阱 | 4 个自定义弹窗全部有 `useFocusTrap`；其余 10 处用 `el-dialog`（原生支持） |
| 二次确认 | 24 处 `ElMessageBox.confirm`，删除/状态流转/登出/废弃文档全覆盖；删除类还配了 `showUndoToast` 撤销窗口（比确认框更好——确认框打断心流，撤销不打断） |
| AI 对话异常恢复 | 中断/失败/重新生成三条路径完整，`sourceQuery` 保证重生成用的是原始提问 |
| `AlertDetail` 处置动作 | 已有 `acting` 计算属性统一防重入，两个 mutation 都受控 |
| 错误边界 | `AppErrorBoundary`（路由级，含错误摘要一键复制）+ `PanelErrorBoundary`（面板级，图表挂了不拖垮整页） |
| `prefers-reduced-motion` | `theme.css` 已全局处理 |
| 剩余 10 处 `console.error` | 全部与 `loadError` 或 store 级 notify 配对，属正当日志 |
