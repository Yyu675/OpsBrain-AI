**特别值得肯定**：`safeMarkdown` 是全局唯一入口，`ALLOWED_TAGS`/`ALLOWED_ATTR` 白名单收敛，异常时降级为**纯文本转义**而非放行原文。这个设计比多数项目严谨。

> 一个观察：`ALLOWED_ATTR` 含 `href`/`src`，理论上是注入面，但 DOMPurify 默认就会剥离危险协议，且项目有对应测试。**不建议改动**——收得更紧会误伤正常的文档链接与图片。

## 二、性能：首屏体积 -75%（已修）

### 问题

构建产物里有个 **2.9 MB 的 `vendor` 块**，且它出现在 `index.html` 的预加载列表里——意味着**每个访问者首屏都要下载**。

排查后定位到 `manualChunks` 末尾的兜底规则：

```js
return 'vendor'   // ← 把所有剩余依赖强行合成一个块
```

只要这块里有**任意一个**依赖被入口用到，整块都会被预加载。而它包含了只有 `/knowledge/editor` 一个路由才用得到的富文本编辑器（wangEditor + md-editor-v3，约 800 KB）。

**路由本身是 lazy 的，但分块把它拽回了首屏。**

### 排查过程中的反复（值得记录）

我第一反应是「给编辑器单独命名一个块」：

```js
if (id.includes('@wangeditor') || ...) return 'vendor-editor'
```

结果**更糟**——命名块自身也被提升进首屏预加载，体积反而涨到 1712 KB。

真正的解法是**反过来：移除兜底块**，`return undefined` 交回 Rollup 按真实引用关系自动分割。同时把 `KnowledgeRichEditor` 的静态 `import` 改为 `defineAsyncComponent`（静态依赖会被提升，让 lazy 路由失效）。

| | 修复前 | 修复后 |
| :-- | --: | --: |
| 首屏 JS 合计 | 2169 KB | **545 KB** |
| 首屏块数 | 10 | 8 |
| 编辑器是否在首屏 | ❌ 是 | ✅ 否（801 KB 独立懒加载） |

> 教训：`manualChunks` 的兜底 `return 'vendor'` 是个常见反模式。它看起来是「把第三方库集中管理」，实际是**把无关依赖焊死在一起**，让打包器失去按需分割的能力。

## 三、准确度：两个「看起来正常但结果错误」的缺陷（已修）

### 3.1 跨时区时间解析错误 —— 最严重的一个

后端用 Java `LocalDateTime` 序列化，形如 `2026-08-24T10:30:00`，**不带时区后缀**。而 `new Date('2026-08-24T10:30:00')` 按 ES2015+ 规范以**浏览器本地时区**解析。

服务器固定 `Asia/Shanghai`，用户浏览器一旦不在东八区，时间戳就是错的。实测复现：

```
服务器 Asia/Shanghai，用户 America/New_York
一张 1 小时前创建的工单 → 前端算出「11 小时后」
偏差：12 小时
```

**危险之处在于绝对时间显示完全正常**（10:30 就是 10:30），只有相对时间、告警时长、SLA 倒计时在错。用户不会察觉，直到照着错误的时间做决策。

**修复**：`parseDate` 对无时区后缀的 ISO 形式补 `+08:00`（与 `docker-compose` 的 `TZ`、Dockerfile 一致），已带时区的输入不改写。同时修正三处绕过 `parseDate` 的调用：

- `AlertDetail` 告警时长（与 `Date.now()` 混算，最典型的受害场景）
- `ActionItemBoard` 到期日（跨时区差一天）
- `Dashboard` 趋势图 X 轴（时间点整体平移）

现全项目已无 `new Date(后端时间)` 的写法。

> 已核实：**SLA 剩余分钟由后端计算**，不受此问题影响——修复范围是准确的，没有波及正确的逻辑。
>
> 关键验证：在 `TZ=America/New_York` 下重跑测试仍全绿，证明修复不依赖运行环境时区。

### 3.2 Markdown 渲染缓存键碰撞

缓存键形如 `doc-42-{内容长度}`。**长度相同但内容不同会撞 key**，返回上一次的 HTML。

```
运维文档：「主从延迟 30 秒」→ 改成「90 秒」
长度不变 → 用户看到的仍是「30 秒」
```

在运维手册里这种数字是要照着执行的，属于会导致误操作的缺陷。已用可运行脚本复现确认。

**修复**：`safeMarkdown` 内部附加 FNV-1a 内容指纹（2 万样本零碰撞），调用方给的 key 只用于分组。

**同时修正了一个锁住缺陷的测试**：

```ts
// 原用例——把 bug 当契约锁死了
it('显式 cacheKey 相同时复用结果', () => {
  const first = safeMarkdown('内容 A', 'msg-1:5')
  const second = safeMarkdown('内容 B（不同内容，同 key）', 'msg-1:5')
  expect(second).toBe(first)   // ← 断言「返回旧内容」是对的
})
```

这正是 `AGENTS.md` 警示的「测试锁定实现细节而非正确行为」。**如果不看这个测试只看代码，很容易以为缓存逻辑是有意为之。**

`useUrlFilters` 已建好并接入 `AlertList`。`TicketList`（只读不写）与 `KnowledgeBase`（自写一套）仍是各自实现，行为不一致。

### 5.2 ★★★☆☆ 补一条 lint 规则禁止直接 `new Date(后端字段)`（约 1 小时）

本次修了 3 处绕过 `parseDate` 的调用，但**没有机制防止再次引入**。建议：

```js
'no-restricted-syntax': [{
  selector: "NewExpression[callee.name='Date'][arguments.length>0]",
  message: '解析后端时间请用 @/utils/time 的 parseDate（后端 LocalDateTime 无时区后缀）'
}]
```

先设 `warn`，确认无误报后转 `error`。**这类"修完就会复发"的问题，加护栏比修本身更重要。**

### 5.3 ★★★☆☆ 首屏再优化：ECharts 按需引入（约 0.5 天）

`vendor-echarts` 仍有 570 KB（gzip 192 KB）。当前是整包引入，改为 `echarts/core` + 按需注册用到的图表类型与渲染器，通常能省 60%+。

### 5.4 ★★☆☆☆ knip 存量清理（约 1 天）

24 个未用导出 + 55 个未用类型。CI 已设 `continue-on-error`，清零后可转为阻断。

## 六、总体评价

**安全与可靠度是这个前端的强项**——XSS 防护、错误兜底、竞态处理都做得比多数项目扎实，`safeMarkdown` 的设计尤其规范。

**短板集中在「静默错误」**：本次修的两个准确度缺陷（时区、缓存键）有共同特征——**界面看起来完全正常，只有计算结果是错的**。这类问题不会报错、不会崩溃，也不会被类型系统发现，只能靠针对性核查。

性能问题（首屏 2.9 MB）则是典型的「配置反模式」：`manualChunks` 的兜底块看似是优化，实则让打包器失去了按需分割能力。

三项修复共新增 8 个回归测试，全部锁死的是**用户可见行为**（"改了文档要看到新内容"、"1 小时前不能显示成 11 小时后"），而非实现细节。
