## 三、核查发现的两个真实缺陷（已修）

两个缺陷成因是**同一个**：`constants/bizCode.ts` 那张 22 条业务码词表
**没有任何生产代码在查它**。`grep getBizError` 调用方，结果为零。

它有 `bizCode.contract.test.ts` 守着与后端 `BizError` 枚举一一对应，
测试一直是绿的——因为那个测试只校验「表和后端一致」，
**从不校验「表被用上了」**。

### 缺陷 1：18 个业务码的文案与处置建议从未生效

`toFriendlyError` 自己硬编码了 40001/40004/40009/40021 四个分支，
其余 18 个码统统落到通用兜底。

最典型的是 **50020（监控数据源不可用）**：

| | 修复前 | 修复后 |
|---|---|---|
| 用户看到 | 「服务暂时不可用，可能正在重启或过载，**请稍后重试**」 | 「监控数据源不可用，**请在「接入管理」中检查 Prometheus 连接**」 |

这个码的 retry 语义是 `NEVER`——Prometheus 没起时反复刷新永远不会好。
词表里本来就写着正确的 hint，只是没人读它。

顺带查出一处**后端语义与前端文案的错配**：
后端 40004 = `STATE_CONFLICT`（当前状态不允许该操作，如对已作废工单改状态），
资源不存在另有 40400 = `NOT_FOUND`。而前端硬编码把 40004 显示成
「数据不存在」——会让用户去刷新列表找一条其实还在的记录。改查词表后自动纠正。

### 缺陷 2：retry 语义被绕过，不该重试的错误静默重试 3 次

重试判断发生在**读 body 之前**，只看 HTTP 状态。
于是业务码携带的 retry 语义完全失效。

503 在 `RETRYABLE_STATUS` 白名单里，所以 Prometheus 没起时
**每次打开监控页都会静默发 3 次请求、退避等待约 3 秒**，最后仍然失败。
用户白等，后端白扛。40009（`CLIENT`，要不要覆盖他人修改得由用户决定）
同理会被自动重试。

**这里有个坑值得记下**：改完第一处后写回归测试，实测 50020 仍发 3 次。
原因是 `httpRequest` 里有**两条**重试路径——`!res.ok` 分支抛出的
`HttpError` 会落到下面的 `catch` 再判一次，而那处只看
`retryOn.includes(e.status)`。两条路径判据不一致，只修一处不生效。
**是新写的回归测试把它抓出来的。**

## 四、补齐 L2 最大的测试缺口：AlertService

逐个类清点时发现 `AlertService` 是**告警链路上唯一的写入方**
（514 行、5 个配置开关、3 条分支路径），却**一行测试都没有**。

它的错误全是「静默」的，不会有人报障：

- **去重键算错** → 同一故障反复建单刷屏；或者反过来，
  两个不同故障被判成同一个，**第二个故障永远不会有人知道**
- **聚合窗口失效** → 一次节点宕机引发十几条告警各建一张工单
- **级别映射塌缩** → P0 生产宕机与 P3 磁盘告警建出同优先级工单
- **建单失败阻塞入库** → 告警本体丢失

补了 22 例，覆盖入口防护 / 去重 / 恢复 / 级别映射 / 建单与聚合五组不变式。

### 连续两轮都是「桩失真」而非产品缺陷

CI 先后报了 4 例、2 例失败，**两次判定方向都是测试写错**：

1. `createTicket` 的 assignee 实参是 `null`，我桩成 `anyString()`——
   Mockito 的 `anyString()` **不匹配 null**，桩没生效返回 null，
   后面「回填工单号 + 通知」整段被静默跳过。
   > 如果顺手把产品代码的 `null` 改成空串来「修复」测试，
   > 就会把「未指派」变成「指派给一个空名字的人」，
   > 而工单列表的负责人筛选恰恰靠 null 判断未指派。

2. `never()).updateTicketId(...)` 把两个场景混为一谈：
   「聚合到组工单」和「回填自己新建的单号」都会调它，
   后者本来就该发生。改为断言**回填的是哪个单号**。

## 五、真实缺口：从未做过前后端联调测试

这是核查中最该正视的一点。

### 当前的测试金字塔缺了最上面一层

```
E2E / 联调        0        ← 完全空白
契约测试        129 例     ← Controller 层（本会话补的）
单元测试        469 + 1074 ← 后端 + 前端
```

后端 `@SpringBootTest` 只有 3 个，且都不是全链路。
**没有任何测试验证过「Alertmanager 推一条告警 → 后端建单 → 前端列表看得到」。**

### 为什么现在做不了

沙箱环境实测：

```
docker : command not found
java   : command not found
Maven  : 全部镜像不可达
```

后端起不来，所以无法做真实联调。这不是借口——
**它意味着 L2 那条最关键的链路，至今只在单元层面验证过。**

### 建议的补法（按性价比排序）

1. **Testcontainers 集成测试**（推荐）
   在 CI 里起 PostgreSQL + Redis，用 `@SpringBootTest` 打真实的
   `POST /api/v1/alerts/webhook`，断言告警入库 + 工单生成 + 去重生效。
   这条链路的价值最高，且不依赖前端。

2. **前端 MSW 契约桩**
   用 `backend-contract.json`（项目里已经有）生成 MSW handler，
   让前端测试打的是与后端契约一致的桩，而不是各写各的 mock。

3. **一份可执行的手工联调清单**
   在有 Docker 的环境下按步骤走一遍，把结果记进文档。
   成本最低，且能立刻发现配置类问题（如 CORS、context-path）。
