## 建议 1 ✅ 模式扫描做成可 CI 化的门禁

把之前几个一次性脚本收敛成统一入口 `tools/audit/run_audit.py`，
零依赖（只用标准库，不需要 JDK/Maven）。

### 关键设计：基线机制

扫描输出是**线索不是判决**。「空 catch」在本项目有 6 处，逐个看过都属有意为之。

若不区分「已审阅接受」与「新引入」，这个检查会从第一天起就是红的，
而**长期红着的检查等于没有检查**。所以 `baseline.json` 记已接受条目，
只对新增报错。当前基线为空——四类扫描全部无命中，可以直接设为阻断门禁。

指纹刻意不含行号：加几行代码不该让基线全部失效。

### 做出来才发现的两个坑

**1. 必须剥离注释再扫描**

首版直接扫源码，误报 2 处——命中的是上一轮修复时写在 Javadoc 里的注解名
（专门解释「`@ConditionalOnProperty` 标在 `@GetMapping` 上不生效」）。

也就是说：**修复缺陷时写下的说明，反而触发了对该缺陷的告警**。
越是把教训写清楚的地方误报越多。

**2. 注解匹配必须用正则而非字面量**

做回归验证时（把已修的两个缺陷人为注入回去，确认扫描能报红），
发现注入全限定名形式的 `@org.springframework...ConditionalOnProperty` **直接漏报**。

> 漏报比误报危险得多：它让人误以为这一类问题已经不存在。

这次回归验证本身也写进了 README——改扫描逻辑后要验证它真能抓到缺陷，
而不只是「什么都查不出」。

## 建议 2 ✅ 补 ToolRuntimeManager + ApprovalService

### `ToolRuntimeManager`（17 例）

AI 调用任何工具的唯一入口，一个方法串了五道治理：
幂等 → 熔断 → 超时 → 重试 → 失败登记。
这些逻辑**正常路径下完全看不出来**，只在下游抖动时才生效——
而那正是没人盯着的时候。

三条最要紧的：

- **参数错误绝不重试**。断言 `maxRetries=3` 的工具只执行 1 次——
  重试一个参数写错的调用毫无意义，若工具有副作用就是把错误动作做三遍
- **异常必须循环解包到根因**。只解一层的话 `fromException` 只看到包装层、
  判 UNKNOWN 不可重试，**结果是超时和连接失败这些本该重试的异常永远不重试**。
  用例造三层包装的 `SocketTimeoutException`，断言真的重试了 3 次
- **幂等命中必须短路**。命中后工具体一次都不能执行，否则就是重复建单

### 顺带修的：类注释宣称的职责与实现不符

类注释把「审批拦截」列为本类职责，但 grep 确认
`ToolMeta.requiresApproval()` 在执行流程里**从不被读取**。
审批实际由编排层结合风险策略在写前动态判断。

问题在于注释会误导：有人看到「审批拦截」是本类职责，
就会以为给工具加 `@ToolMeta(requiresApproval = true)` 能拦住高危操作，
而那个字段在这条路径上没有任何效果。

### `ApprovalService`（21 例）

「AI 能不能动生产系统」的状态机。最关键的是 **CAS 防重复批准**：
两个管理员同时点批准时只能有一个生效，靠影响行数判断。
若 `rows==0` 时静默返回成功，两人的批准都会「成功」，
编排层就会重放执行两次——**重启两次 Pod、扩容两次**。

其余：`payload` 是批准后能否执行的前提（不传则用户点了「同意」系统什么都做不了）、
`timeoutHours` 配 0 时兜底 1 小时（否则每张单一提交就过期，审批被静默关掉）、
`recordExecution` 未命中不抛异常（副作用已产生，回滚状态只会让记录与现实不符）。

## 建议 3 ✅ SSE 端点：只测能测死的，明说不测什么

之前几轮一直留着这个 Controller，理由是「`MockMvc` 对异步流支持有限」。
**那个判断依然成立**，所以本类明确不测正常对话路径，并在类注释写清了原因。

但有一类路径可以测死：**同步拒绝**。空查询与触发限流两条不进入 Agent 链路，
直接 `sendErrorEvent` + `complete()`，`MockMvc` 能拿到完整响应体。

而这两条恰恰最该守：

- **限流** —— 本端点是全项目最贵的：一次请求 = 一次真实 LLM 调用。
  限流失效时一段循环脚本就能同时打爆额度、连接池与 Tomcat 异步容量
- **拒绝必须走 SSE error 事件而非 HTTP 状态码** —— 响应此刻已是
  `text/event-stream`，前端走 SSE 解析器，改用 429 它只会看到「连接异常」。
  用例特意断言 HTTP 层仍是 200 而 error 事件里是 42901
- **空查询校验在限流之前** —— 顺序反了的话，用户手滑发一串空请求
  就会把自己的额度耗尽

**Controller 契约测试 17/18 → 18/18 收官。**

## 建议 4 ✅ 前端：拆分前先测死核心逻辑

建议 4 原本是「大文件拆分前先补测试」。但直接给 `KnowledgeEditor.vue`（2013 行）
写组件测试性价比不高——先把它依赖的核心逻辑测死，拆分时这些才是真正的安全网。

`draftStorage`（22 例）+ `useDirtyGuard`（13 例）合起来是
「用户写的东西会不会丢」的完整保障，此前**两者都是零测试**。

几条值得记的：

- **缺 `savedAt` 时不做过期判断** —— 老版本写入的数据没这个字段，
  判「过期」丢弃会让升级发版时所有人的在编草稿凭空消失
- **`baseVersion=0` 与 `null` 必须可区分** —— null=新文档，0=基于 v0，
  用 falsy 判断会混为一谈，而编辑器靠它判断版本冲突
- **三选一的 Esc 分支** —— `distinguishCancelAndClose` 关掉后，
  取消与关闭都 reject 且无从区分，**用户按 Esc 想继续编辑，系统却把草稿丢了**

### 又一个测试搭台的坑

第一版用 `mount(Editor)` 直接挂组件，8 个用例全部
「跳转成功、确认框从未弹出」——**看起来像产品没做拦截**。

实际是 `onBeforeRouteLeave` 注册在「渲染它的那条路由记录」上，
脱离路由树挂载守卫根本不会注册。改用 `<RouterView>` 后全过。
已把原因写进 helper 注释，避免后来者照抄错误写法。
