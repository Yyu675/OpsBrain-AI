## 一、本轮发现并修复的真实缺陷（4 项）

### 🔴 P0-1 登出后 AI 对话历史残留 → 知识库内容越权读取

**归类**：安全（越权读取）｜**已修复** `df1584f`

对话历史全量持久化在 localStorage 的 `chat-sessions`，**没有按用户隔离**。
登出只清了 token 与身份缓存，对话原样留在磁盘。

危害不止隐私尴尬——`metadata.citations` 存的是 AI 从知识库检索出的**原文片段**，
随会话一起持久化。而知识库有可见性分级（PUBLIC / 内部，v24 迁移 + `KnowledgeScope`）：

```
管理员在共享值守机上问「支付链路熔断阈值怎么调」
  → AI 引用内部 runbook 原文，写进 citations
  → 管理员登出，token 清了、对话没清
  → 下一班只读用户登录，打开 AI 助手
  → 直接读到那段内部文档
```

**这绕过了后端刚落地的权限域隔离**。共享值守机、跨班交接同一终端在运维场景里
非常普遍，不是极端假设。

**修复要点**：
- chat store 新增 `clearAll()`：清空会话桶 + **显式** `clearPersisted`
  （不能依赖 watch 写空对象——persist 是 400ms 防抖，登出后页面立刻跳转，
  防抖回调来不及跑，磁盘旧数据就留下了）
- 新增 `useSessionCleanup` 挂 App 根组件，监听 `isAuthenticated` 的 true → false。
  **不逐个改登出入口**是刻意的：登出有 4 条路径（菜单 / 闲置超时 /
  闲置警告选退出 / http 层 401 后 resetToGuest），逐个加必漏一条，
  漏的往往是最难复现的 401 自动登出。
- `wasAuthed === true` 判断不能省：启动时 watch 会因初始化触发一次
  （undefined → false），漏判会**每次刷新都抹掉对话**——修复本身极易引入的回归。

**刻意不清**：通知 readIds/dismissedIds（操作记忆，不含内容，清了历史告警全变未读）、
列宽/主题（属设备非账号）、编辑器草稿（在 sessionStorage，清了等于删用户没保存的文字）。

### 🟠 P1-1 请求超时被误报为「无法连接服务器」

**归类**：可靠度（误导排查方向）｜**已修复** `3319c07`

```ts
// 修复前
setTimeout(() => controller.abort(new Error('timeout')), timeout)
```

fetch 会**以 abort reason 原样 reject**，而普通 `Error` 的 `name` 是 `'Error'`，
`isAbortError` 只认 `'AbortError'`/`'TimeoutError'`，判不出来 → 落到 NETWORK 分支。

用户看到：**「无法连接服务器，请确认后端服务已启动（默认端口 8088）」**
真相是：服务连上了，只是 15 秒没返回（慢查询 / 连接池打满 / 大结果集）

这两种故障的排查方向完全相反——一个查进程是否存活，一个查慢 SQL。
**提示给错会把排查的人直接带向错误方向**，而这恰恰发生在系统已经出问题的时刻。

**顺带修的两处**：
- 非超时的 abort 不再重试。原逻辑对所有 AbortError 都重试，组件卸载 /
  用户点「停止生成」后仍继续打后端，无视取消意图。
- 超时文案改由实际 `timeout` 派生，不再写死「15 秒」（各调用方可传自定义值）。

新增 `http.request.test.ts` 7 例。**已实测**：回退成 `new Error('timeout')`，2 例立即失败。

### 🟠 P1-2 时区解析残留点（工单回复/活动流）

**归类**：准确度｜**已修复** `3319c07`

上一轮修了 `parseDate` 与 3 处绕过点，但 `ticket.service.ts` 的 `toTimeLabel`
仍在 `new Date(iso)`——工单**回复与活动流**的时间戳全走这里。

后端 `LocalDateTime` 不带时区，按浏览器时区解析整体偏 12 小时（服务器
Asia/Shanghai vs 用户 America/New_York）。表现为「今天上午的回复」被标成
昨天的 `MM-DD`，同一工单里回复顺序看着错乱。

**这类缺陷绝对时间显示完全正常，肉眼几乎不可能发现**，必须靠工具层拦住：

```js
// eslint.config.ts —— 新增
'no-restricted-syntax': ['error', {
  selector: 'NewExpression[callee.name="Date"][arguments.length>0]',
  message: '请改用 @/utils/time 的 parseDate()...'
}]
```

无参 `new Date()` 不受限（无时区歧义），`time.ts` 与测试文件为合法例外。

### 🟡 P2-1 本地偏好写入失败被静默吞掉 + readIds 无界增长

**归类**：可靠度（静默数据丢失）｜**已修复** `3319c07`

两个问题互为因果，放在一起说：

**(a) `persist.ts` 的 `safeSet` 是空 catch**。配额撑满或隐私模式下，
用户调好的列宽、切换的主题、标记的已读会「看似保存成功、刷新后复原」，
**既没提示也没有控制台线索**，只会被当成「这功能坏了」。

**(b) `notifications` store 的 `readIds` 无界增长**。`dismissedIds` 有 200 上限，
`readIds` 却是纯 push——而「已读」比「已忽略」高频得多（点一次「全部已读」
灌入 20 条）。值守人员长期用同一浏览器，这个数组只增不减地写 localStorage，
**最终就会撞上 (a) 的静默失效**。

修复：
- persist 暴露 `onPersistWriteFailure` 事件（不在 utils 层直接弹提示——
  会造成 `utils → element-plus` 反向依赖），main.ts 接上 notify，
  **仅配额超限时提示**（隐私模式是用户自主选择，逐次弹窗是骚扰）
- readIds 加 500 上限，截断**收口到 `_persist` 一处**——避免再出现
  「dismiss 记得限长、markRead 忘了」这种分散处理的代价

## 二、同批完成的体验改进

### TicketList 筛选状态统一到 `useUrlFilters`

本页此前只**读** URL（供 Dashboard 带参跳转），**不写回**。用户在页面上调好的
「P0 + 未分配 + 近 24h」既不能刷新保留、也不能复制链接给同事——
而「把这个筛选结果甩到群里」正是值守交接的高频动作。

统一后与 KnowledgeBase 行为一致（读时校验 / 写时清理 / 默认值不入 URL）。
三个配套决策：

| 决策 | 原因 |
|---|---|
| `sortState` 对象 ref 拆成 `sortBy` + `sortAsc` | URL 同步按「一 ref ↔ 一参数」建模；对象需把两字段揉进一个参数，既难读又让手写 `?sortBy=priority` 失效。对外仍以 computed 聚合，调用方读取方式不变 |
| `tagFilters` 自定义 serialize | 数组走默认 `String()` 会让空数组序列化成 `""`，且与 `defaultValue []` 引用不等，导致空数组也被写进 URL |
| keyword 回填搜索框 | 只同步 `appliedQuery` 会让输入框空着，用户看到「列表明明筛过、搜索框却没内容」，想清筛选都无从下手 |

## 四、评估后**不采纳**的改动建议

保留判断依据，避免后续反复讨论：

**1. 不给 `notify` 加全局 loading 遮罩**
项目已有 `app.loadingCount` + `AppSkeleton` + 按钮级 `:loading`，
三层加载反馈已足够。再加全局遮罩会让「点一下按钮全屏变灰」，
在需要同时看多处状态的运维大屏上是倒退。

**2. 不把 `TicketDetail.vue`（2655 行）在本轮拆分**
拆巨型 SFC 是对的，但**它现在没有测试**。无测试的大规模重构，
引入回归的概率高于收益。正确顺序是：先补组件测试 → 再拆。
本轮优先修了真实缺陷，拆分留到第五节的路线里。

**3. 不给所有异步操作再加确认弹窗**
逐一核查后确认：删除工单、批量操作、状态流转、登出、废弃文档
**都已有二次确认**，且删除类还配了 `showUndoToast` 撤销窗口
（比确认弹窗体验更好——确认框打断心流，撤销不打断）。再加是过度设计。

**4. 不把 `readIds` 改成按用户隔离**
它是「本机处理过哪些告警」的设备级记忆，跨账号复用是**期望行为**：
同一台值守机上，前一班已确认过的告警，后一班不该再看到红点。
