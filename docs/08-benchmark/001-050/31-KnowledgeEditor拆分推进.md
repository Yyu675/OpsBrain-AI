## 一、本轮抽出的四组

| 组 | 函数 | 错了会怎样 |
|---|---|---|
| 目录标题增改删 | `appendHeading` / `renameHeadingIn` / `removeHeadingIn` | **直接改坏用户正文** |
| 块模板 | `HTML_BLOCKS` / `MARKDOWN_BLOCKS` / `appendMarkdownBlock` | 切换编辑模式时内容变形 |
| 标签规整 | `normalizeTagList` / `hasTag` / `MAX_TAGS` | 标签云出现重复项、筛选只命中其一 |
| 分类路径 | `buildCategoryPath` / `findCategoryIdByName` | **整个标签页死循环卡死** |

### 目录标题操作：两条路径，一个索引用错就改到别人身上

这三个函数在 HTML 与 Markdown 上做同一件事，但定位方式完全不同
（`elementIndex` vs `lineIndex`）。用错一条的表现是
「我改了 A，B 却变了」——不报错，用户只会觉得系统有鬼。

钉住的几条：

- **索引越界时原样返回**——宁可什么都不做，也不能改错一个标题
- **删除只删标题行，标题下正文保留**（连正文一起删会让用户点一下丢掉整段，且无撤销）
- Markdown 改名保留原级别（三级不能被降成二级）
- 追加标题时补空段落，否则光标无处可去、没法接着往下写
- **删除后剩余标题索引会重排**：拿旧 TOC 连着删两次会删错目标

> 抽出来的另一个理由：原先这三个函数各自包着 `ElMessageBox` 的 try/catch，
> 交互与内容变换缠在一起，**根本没法单测**。现在交互留组件、变换在 utils。

### 分类路径：防环不是防御性编程，是防页面卡死

`buildCategoryPath` 的关键不是拼字符串，是那个 `seen` 集合。

分类的 `parentId` 由用户配置，数据异常时可能出现 A→B→A 的环。
没有防护的话 `while` 会死循环——表现**不是报错、不是空白，
是整个浏览器标签页直接无响应**。

后端 `ensureNoCycle` 拦得住新建的环，但历史数据与并发写入可能绕过，
前端这层兜底不能省。测试覆盖了双节点互指与自引用两种环。

## 二、补了组件冒烟测试，并验证它真的有用

### 为什么纯函数全绿还不够

65 例纯函数测试全绿，但**纯函数全绿 ≠ 页面还能打开**。

第 22 轮拆 TicketDetail 时吃过这个亏：删模板时多删了一个闭合标签，
`vue-tsc` 只报一串「变量未使用」这类**误导性症状**，
差点顺手删掉那些变量（那才会真正毁掉页面）。
最后是组件测试报 `Element is missing end tag` 才定位到病因。

### 验证方式：人为注入一次拆分事故

写完 6 例冒烟测试后，我删掉一个 `</header>` 重跑：

```
SyntaxError: Element is missing end tag.
Test Files  1 failed
```

随后还原，`git diff` 确认零改动。

> 不做这一步的话，**一组永远绿的测试和没有测试是一回事**。
> 这与上一轮给 audit 扫描器做回归验证是同一个道理。

冒烟测试另外钉住了一条容易漏的：**卸载时必须清掉自动暂存定时器**——
不清的话用户离开后它还在往 sessionStorage 写，
而那时 `formData` 已是被销毁组件的残留引用，每开一次编辑器泄漏一个 interval。

## 三、一个刻意没做的决定：`handleSave` 不抽

`handleSave` 有 100+ 行，看着像下一个目标。但它与 `store` / `router` /
`saving` 等组件状态深度耦合。强行抽出会让一次保存的**校验、请求、状态同步
散落三处**，可读性反而更差。

这与第 22 轮对 TicketDetail B2/B3 表单的判断是同一条：

> **耦合紧的编排逻辑留在组件里是对的。
> 真正该抽的是那些「纯粹但错了会静默损坏数据」的部分。**

按行数拆到底会得到一堆互相调用的碎片，那是另一种难以维护。
