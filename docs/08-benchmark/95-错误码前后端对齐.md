## 三、缺陷 1：`ApiCode.NOT_FOUND = 40004` —— 错得最狠的一处

`BizError` 里：

| 码 | 语义 | HTTP |
|---|---|---|
| `40004` | **STATE_CONFLICT** 当前状态不允许该操作 | 409 |
| `40400` | **NOT_FOUND** 资源未找到 | 404 |

两者语义完全不同：一个说「对象在，但现在不能这么操作」，
一个说「对象根本不存在」。

### 用户可见后果

8 处「工单/文档/历史版本/分析不存在」返回 40004：

- 前端 `bizCode.ts` 查表得到「**当前状态不允许该操作** · 请刷新查看最新状态」；
- 而 `utils/http.ts` 又硬编码 40004 → 「**数据不存在**」。

**同一个码在前端两处渲染成互相矛盾的文案。**

反过来更糟：真正的状态冲突（如「已作废的工单不能改回待处理」）
会被渲染成「工单不存在」的空页面，**用户以为数据丢了**。

### 修复

`ApiCode.NOT_FOUND` 改为 40400，新增 `ApiCode.STATE_CONFLICT = 40004`。
8 处调用点语义都是「不存在」，常量名不变、值修正，调用点无需改动。

## 四、缺陷 2：三个孤儿码

前后端码表都没有，用户只能看到通用兜底文案：

| 码 | 场景 | 用户实际看到 |
|---|---|---|
| `40100` | 登录密码输错 | 通用兜底，而非「用户名或密码错误」 |
| `40102` | 审批单已被他人处理 | 通用兜底，而非「刷新看最新决策」 |
| `40005` | SSE 主链路配额超限 | 「操作失败」，而非「配额已用完」 |

三者都补进 `BizError` 并配齐前端文案。

`LOGIN_FAILED` 与 `NOT_LOGIN` **必须分列**：前者用户还在登录页，
应原地提示；后者是会话过期，需跳转登录页。
合并会让密码输错时执行一次无意义的跳转，且清空用户已填的用户名。

## 五、缺陷 3（本轮 CI 报出的）：替换脚本只认一种传码形式

94 号的替换只匹配 `ApiResponse.error(数字,`。而业务码还会以别的形式流动：

```java
int code = msg.contains("不存在") ? 40004 : 40102;      // 三元
sendErrorEvent(emitter, traceId, 40001, "输入不能为空");  // SSE 事件
throw new SecurityGuardException(40001, "...");         // 异常构造
case 40001 -> "输入不合法，请检查后重新提问";              // switch 分支
```

`ApprovalController` 三元里的 40004 就这么活下来了。
上一提交把常量值改成 40400 后它没跟着变，CI 才报出
`expected:<40400> but was:<40004>`——**反向的不一致**。

### 扫描器扩展（本轮主要产出）

契约测试的正则从「`ApiResponse.error` 的第一个参数」扩为
**任意裸露的 4xxxx/5xxxx 五位数字**，白名单只放行
`BizError` 与 `ApiCode` 两个定义处。

自验：命中 **19 处，逐条点开全是真实的业务码裸写，无一误伤**——
端口号、超时毫秒数没被误判，因为正则要求前后不是 `\w` 或 `.`。

全部具名化后，`ApiCode` 补齐 11 个别名覆盖 `BizError` 里的全部码。

## 六、新增契约断言：`everyApiCodeExistsInBizError`

**这是 94 号缺失的那道闸**。

既有的 `bizCode.contract.test.ts` 只校验 `BizError` ↔ 前端 `BIZ_ERRORS`，
**管不到我新建的 `ApiCode`**——所以 94 号 CI 全绿。

新断言要求 `ApiCode` 每个取值都能在 `BizError` 里找到，
杜绝再造第二套码表。

## 八、本轮踩的另外两个坑

### 坑 1：WebTest 断言不能盲目全改

CI 报 40004 不一致后，全仓有 12 处 `value(40004)` 断言。
但**只有一半该改**：

- `status().isOk()` → controller 内 catch 显式返回，是「资源不存在」，改 40400；
- `status().isConflict()` → 异常冒泡到 `GlobalExceptionHandler`，
  由 `BizError.STATE_CONFLICT` 转码，40004 本就正确，**保持不动**。

改动脚本带双重断言（目标行含 `value(40004)` **且**上下文含 `isOk()`），
任一不满足即中止。

保持不动的 6 处里，`TicketControllerWebTest:204` 测的
「已作废的工单不能改回待处理」恰恰是 STATE_CONFLICT 的教科书场景——
它和「工单不存在」此前共用同一个码，**前端无从区分**。

### 坑 2：ECJ 缺 jar 时抓不到「方法未定义」

我在断言里调用 `lineTextAt` 却没写实现，CI 报 `cannot find symbol`。

这正是 AGENTS 3.9 记的能力边界：缺 junit/assertj 等 jar 时，
「方法未定义」与「jar 缺失」都报成 `cannot be resolved`，
而我的过滤器恰好把这整类滤掉了。

**补的手段**（本地可执行，不依赖编译）：正则交叉核对
「本文件内定义的方法」与「无接收者的本地调用」。
这个手段对「调用了本文件没有的私有方法」有效，弥补 ECJ 在缺 jar 场景的盲区。

### 顺带修一条被自己影响的测试

`http.test.ts` 的「未列举的业务码」用 40005 当样本，
40005 被补进词表后该用例失效。改用 40999——
**测「词表里没有的码」这个分支，就该用一个不会被补进词表的号段**，
拿真实码当样本是把用例的前提交给了别处的变更。

## 十、下一步建议修复思路

### 立即可做（下轮首选）：SSE 流式接口的错误语义

本轮把 `sendErrorEvent` 的裸码具名化了，但**只改了写法，没审语义**。
`ApiResponse` 的 javadoc 明写它只覆盖「非 SSE 接口」，
而 SSE 是本产品的主链路（AI 问答全走它）。

**要回答的问题**：

1. SSE 出错时前端收到的事件结构是什么？与 `ApiResponse` 是同一套码吗？
   （已知 `sendErrorEvent` 用的是同一批业务码，但事件外壳不同）
2. 前端能否区分「模型超时」（50210，可重试）与「鉴权失效」（40101，需跳登录）？
   `BizError` 里 50210/50211/50212 三个模型相关码都有 `Retry` 语义，
   SSE 侧有没有用上？
3. 流已经开始输出后才出错，前端是保留已输出内容还是整体丢弃？

这一步偏「审查 + 出结论」，改动面视发现而定。

### 中期候选

1. **日志脱敏契约固化**。94 号已扫完并给出结论（574 条日志、3 处含敏感字段名、
   全部安全），只差把扫描规则写成契约测试。成本低，防的是 83 号那类重演。
2. **前端 `utils/http.ts` 的分支与 `BIZ_ERRORS` 表重复**。
   `http.ts` 里对 40001/40004/40009/40021 有硬编码分支，
   而 `bizCode.ts` 已有完整文案表——两套文案并存，本轮就撞见过它们互相矛盾。
   建议让 `http.ts` 统一走 `getBizError()` 查表，但需逐条核对文案差异
   （有些分支的措辞是刻意区分的），**不是纯机械替换**。

### 明确不做

- **把 `ApiCode` 与 `BizError` 合并成一个类**。看似消除重复，
  但两者定位不同：`BizError` 是带 HTTP 映射与重试语义的富枚举，
  `ApiCode` 是给 `ApiResponse.error(int, ...)` 这个 int 签名用的取值别名。
  合并要么改 `ApiResponse` 签名（触及全部 33 处调用），
  要么在每个调用点写 `.code()`——两种都是为了「看起来干净」付出实际代价。
  现在有契约测试保证两者不脱节，够了。
