# 57 · PRD 架构评估与文档拆分细化规划

> **回答三个问题**：
> ① 此项目的 PRD 是什么状态？② 市场调研后架构是否需要进一步优化？③ PRD 各章节是否需要拆分细化？
> **结论先行**：PRD 现状健康但有「三重身份」隐患；架构**不需要推翻**，只需 5 处定向优化；
> 章节**需要拆分**为三层文档体系，但应按迭代节奏拆，不能一次拆完。

## 一、当前 PRD 的体检结论（问题 ①）

### 1.1 结构盘点（`docs/PRD.md` v2.0，454 行）

16 章 + 2 附录：产品概述（L1-L5 框架）→ 目标与成功指标 → 用户与场景 → 功能总览 → L1/L2/L3/L4/L5 分章 → 安全边界 → 看板 → 商业化 → NFR → 发布路线 → 验收标准 → 风险未决 → 附录 A（模块状态速查）→ 附录 B（历史调研决策）。

### 1.2 三个优点（应该保留的）

| 优点 | 说明 |
|------|------|
| L1-L5 自治分级是强框架 | 信任逐级挣得，自主权与可靠性挂钩——这是产品最清晰的叙事主线 |
| 契约完备 | 幻觉防护四层、审批状态机、去重三层语义、安全五机制，每一条都可验收 |
| 代码状态标注防过时 | 「状态标记会过时，代码引用不会」——已实测修正过一次七处过时 |

### 1.3 三个问题（需要处理的）

| # | 问题 | 具体表现 |
|---|------|---------|
| 1 | **三重身份混装** | 一份文档同时是「目标态蓝图」（v2.0 愿景层）+「模块需求规格」（M1-M12 层）+「实现状态核对表」（附录 A）。导致详略不均：L1-L3 有代码状态但缺字段级/状态机级需求；L4 只有场景骨架；看板章节很薄 |
| 2 | **易变状态污染不变契约** | PRD 本应是「冻结的需求契约」，现在内嵌「持续变化的实现状态」列，会反复过时（已经过时过一次） |
| 3 | **与既有文档职责重叠** | 技术实现已有 `05-development-design/01-04`（架构/模块/API/数据库），决策记录已有 `CLAUDE.md`，架构蓝图已有 `02-architecture-design/`——PRD 与它们边界不清，改一处要同步多处 |

## 二、市场调研后：架构是否要优化？（问题 ②）

### 2.1 判断：主线不动，定向优化

市场调研结论（78 亿市场、闭环企业不足 15%、60% 企业停在 L1、竞品强监控弱知识）**验证了差异化主线**——「知识库 + 工单 + 受控执行」三位一体、不盲目追监控接入。因此：

> ✅ **架构不需要推翻重来。** 但有以下 5 处定向优化，不做会在后续迭代返工。

### 2.2 五处定向优化（按优先级）

| # | 优化点 | 为什么现在做 | 现状依据 | 落点 |
|:---:|-------|------------|---------|------|
| 1 | **事件网关双向化预留** | L4 执行器落地后必然要「回写处置结果到源系统」，现在不预留接口，P4 做完要返工 | 当前网关单向（只接收 Webhook） | 架构设计文档（02-architecture-design） |
| 2 | **信号源适配器 SPI** | 第二个信号源（日志平台）接入前必须有统一抽象，否则每个源写一套处理逻辑 | 仅 Prometheus 一种来源 | PRD-L2 + 技术架构设计 |
| 3 | **执行层三件套设计定稿** | 这是 P4 的**设计前置**，不能在代码里拍板：执行器抽象、凭证层、爆炸半径真实计算 | `maxBlastRadiusCount` 只是配置数字，**没有任何代码根据它拦截过真实操作** | PRD-L4（见 §三） |
| 4 | **自身可观测性设计** | 系统能监控别人却监控不了自己；「自动化是否安全」无法回答 | pom.xml 无 actuator/micrometer | 技术架构设计（P2 工程） |
| 5 | **指标评测集架构** | §2.2 八个指标（MTTR↓50%、收敛比 10:1、采纳率 80%、拒答率 95%…）目前**无评测集支撑**，只是目标数字 | 无 eval 数据集、无降噪回放集 | PRD-看板与指标体系 |

> 这 5 点的共性：**都是「先设计后编码」的决策点**，不是功能缺口。它们应该产出于 PRD/架构文档，而不是等代码里遇到再补。

## 三、PRD 是否要拆分细化？（问题 ③）

### 3.1 判断：要拆，拆成三层文档体系

**判断依据**：
1. 454 行承载愿景 + 需求 + 状态三重职责，任何一层改动都牵动其他层——单文档已达维护拐点；
2. 读者不同：产品评审看蓝图、开发排期看模块 PRD、验收看功能规格，混在一份里各读各的互相干扰；
3. 项目阶段需求：**L4 开工前必须把 L4 PRD 写细**——白名单场景、执行器抽象是设计决策，不能在代码里临时拍板。

### 3.2 目标结构（三层 + 状态追踪独立）

```
L0 产品蓝图层（薄 · 已有 · 维持）
   docs/02-architecture-design/OpsBrain_AI_L1至L5全自动智能自愈与商业化拓展蓝图.md

L1 产品主 PRD（中 · 瘦身）
   docs/PRD.md
   → 只保留：愿景/定位/L1-L5 框架/模块清单与优先级/指标目标/发布路线/风险
   → 删除：内嵌实现状态列（改为一行链接）、模块级细节

L2 模块级 PRD（厚 · 本次规划 6 份）
   PRD-L1-智能问答.md          四层幻觉防护细则 / 工具白名单 / 评测验收
   PRD-L2-实时监测与主动触达.md  信号源适配器 SPI / 去重三层语义 / 触达矩阵 / 通知渠道
   PRD-L3-智能诊断与人机协同.md  审批状态机 / payload 契约 / 权限矩阵 / 回滚预案
   PRD-L4-受控自愈.md          白名单场景界定 / 执行器抽象 / 补偿与审计细则 ← P4 设计前置
   PRD-安全边界与审计.md        五机制细则 / 角色权限矩阵 / 审计模型
   PRD-看板与指标体系.md        指标口径定义 / 埋点清单 / 评测集设计

L3 技术实现层（已有 · 不动）
   docs/05-development-design/01-技术架构设计 / 02-功能模块设计 / 03-API接口设计 / 04-数据库设计
   + CLAUDE.md（技术决策记录）

实现状态追踪（独立 · 已有）
   docs/08-benchmark/54（基线读数）+ 56（v2.0 对齐取证）→ PRD 只留链接
```

### 3.3 拆分节奏：跟着迭代走，不一次拆完

| 时机 | 拆分动作 | 理由 |
|------|---------|------|
| **现在可拆（低成本）** | PRD 瘦身 + 状态列迁出 + **L1/L3 模块 PRD 落地** | 内容已齐备，纯搬运组装；L4/L2 缺拍板内容，现在拆会返工 |
| **P4 开工前必拆** | **PRD-L4-受控自愈** | 写这份文档 = P4 的设计前置（执行器抽象依赖目标系统选型） |
| **接第二个信号源前必拆** | PRD-L2 的信号源章节细化 | 适配器 SPI 设计必须在第二源之前定稿 |
| **做评测集时拆** | PRD-看板与指标体系 | 指标口径先于埋点实现 |
| **不建议现在拆** | L5 远景、商业化拓展 | 蓝图层已够，无开发计划支撑的详细 PRD 是空转 |

### 3.4 每份模块 PRD 的固定模板（保证拆分后质量一致）

```
① 模块目标与边界（做什么/明确不做什么）
② 用户场景与角色
③ 功能需求 FR 表（编号 / 优先级 / 需求描述 / 验收标准）
④ 状态机或数据契约（如有）
⑤ 权限矩阵（角色 × 操作）
⑥ 埋点与指标（对应 §2.2 哪个指标）
⑦ 验收清单（用户视角，可勾选）
⑧ 关联技术设计文档链接
```

## 五、一句话总结

**架构**：不需要推翻，市场调研验证了主线；但 5 处「先设计后编码」的决策点（网关双向、源适配器、执行层三件套、可观测性、评测集）必须前置到文档。
**PRD**：需要拆成「蓝图（已有）→ 主 PRD（瘦身）→ 模块 PRD（6 份）→ 技术实现（已有）」四层，状态追踪独立成档；按迭代节奏拆——**现在拆 L1/L3，P4 前拆 L4，其余跟着立项走**。
