## 一、本轮做了什么

### 落地范围

| 项 | 之前 | 现在 |
|---|---|---|
| `/automation/risk-levels` | `ComingSoonPanel` 占位 | **风险等级配置**（4 级策略，可编辑） |
| `/automation/action-allowlist` | `ComingSoonPanel` 占位 | **动作白名单**（CRUD + 启停 + 模拟校验） |
| 后端治理接口 | 无 | 10 个端点，限 ADMIN |
| 数据表 | 无 | `sys_risk_policy` + `sys_action_allowlist` |

### 为什么先做这两个，而不是「自动化策略」

L3 三个页面里，**自动化策略**（告警 → 动作的编排规则）依赖前两者：
它要引用「有哪些动作可用」和「每级风险怎么管」。先做被依赖方，
下一轮做策略编排时就有真实的下拉数据可选，而不是又一批硬编码选项。

### 为什么这不是空壳

`docs/08-benchmark/15` 里我反对做 L4 页面的理由是「引擎不存在，页面只能展示空列表」。
L3 配置类不同——**配置本身就是交付物**：

- 运维团队现在就能把「哪些动作允许自动执行、什么风险等级需要几人审批」定下来；
- 这些配置在引擎落地前是**决策记录**，落地后直接被消费，不需要返工；
- 页面有真实数据（v26 种下 4 条策略 + 9 条动作），不是空表。

## 二、关键设计取舍

### 1. 风险等级「不可增删，只可改」

`sys_risk_policy` 的主键就是 `ToolRiskLevel` 的枚举名，只提供 UPDATE。

理由：等级由 Java 枚举定义，引擎只会产出这四个值之一。
若允许用户新建第五级，它**永远不会被任何动作命中**——
页面上看着有、实际是死配置，比没有更糟（用户会以为自己设过了）。

可改的是「每级怎么管」，不是「有哪几级」。

### 2. 白名单是**允许清单**，不是禁止清单

**表里没有记录 = 不允许自动执行**，而不是「不受限制」。

默认拒绝是安全配置的唯一正确默认值：漏配一条动作的后果应当是
「这个动作没自动跑」，而不是「它不受任何约束地跑了」。
页面文案专门强调了这点——否则用户会把它当黑名单用，方向正好相反。

### 3. 核心不变式：**只能自己收紧，不能自己放宽**

所有跨表校验都朝同一个方向。条目可以比策略更严，绝不能更松：

| 绕过方式 | 拦截点 |
|---|---|
| 把高危动作的 `requiresApproval` 设成 false | `validateAction` 规则 1 |
| 条目环境写 prod、策略只开了 dev | `validateAction` 规则 2 |
| 条目爆炸半径 100、策略上限 1 | `validateAction` 规则 3 |
| **停用 → 策略收紧 → 重新启用** | `toggleAction` 启用时复查 |

最后一条是这类系统最常见的绕过路径：条目是在旧策略下配好的，
之后策略被收紧了。若启用时不复查，走一遍「停用再启用」就能带着
旧配置重新生效。

有了这个不变式，「调整策略」才有可预期的语义——把某一级收紧，
该级下所有动作立刻同步收紧，不需要逐条去找漏网的例外。

### 4. 解析失败一律倒向最严格

```java
// ApprovalMode.parseOrStrictest —— 无法识别时返回 DUAL 而非 NONE
// EscalateTarget.parseOrDefault —— 无法识别时返回 TICKET 而非 NONE
```

若哪天有人图省事把回退值改成 NONE，编译能过、功能"正常"，
但一次数据脏值就会让高危动作变成免审批直接执行。
`GovernanceEnumTest` 专门守这条，改坏了测试会红。

同理，`evaluate` 在**读不到策略时拒绝而非放行**——读不到约束等于没有约束，
此时执行是在完全无防护的状态下操作生产系统。

### 5. 爆炸半径用「百分比 + 绝对值」双上限

- 只配百分比：1000 实例的集群 5% = 50 个，一次挂 50 个不可接受；
- 只配绝对值：小集群配 1 个合理，大集群 1 个又太保守失去意义。

取较小值兼顾两端。另外算出 0 时**兜底为 1**——
算出 0 会让自愈永远不执行却不报任何错，
这种「配置生效了但什么也没发生」最难排查。

### 6. 生效值由后端合并，前端不复算

「这条动作到底要不要审批」= `requiresApproval ?? policy.approvalMode.requiresHuman()`。

这个合并逻辑放在服务端并随列表下发（`effectiveRequiresApproval`）。
让前端各自去算，必然与引擎的实际判断漂移——而**界面显示「不需审批」
但引擎实际拦下来，用户会认为系统坏了**。

本项目已经因为「前后端各写一份」踩过工单状态机 8 处不一致，不重复这个错误。

### 7. 二次确认只对「放宽」触发

`RiskLevels.vue` 的 `loosenings()` 逐项识别五种放宽方式（降审批门槛、
开自动执行、提高两种爆炸半径、新增环境），只有命中才弹确认框。

收紧不弹是刻意的：**若对收紧也弹确认，用户会对确认框脱敏，
真正危险的那一次也一路点过去**。

同理，动作白名单里启用高危动作要确认，**停用不确认**——
故障当下用户要能一秒关掉某个动作，弹框只会拖慢止血。

## 三、本轮发现并修复的存量问题

### 🔴 P1：`init.sql` 漏同步 v25 的 `sys_operation_audit`

**成因**：v25 迁移脚本已提交，但当时没按 `AGENTS.md` 3.5 的约定
同步更新 `init.sql`。

**用户可见后果**：按 `init.sql` 建库的**全新环境缺这张表**。
而审计写入失败是被 catch 的——业务照常跑，只是**悄悄没有审计记录**。
到需要回答「谁在什么时候改了这张工单」时才发现没数据，那时已经晚了。
在 L3/L4 阶段这是合规问题而不只是缺陷。

**修复**：`init.sql` 补回 `sys_operation_audit` 全部列与 5 个索引，
并与 v26 两张新表一起用「列定义 + 种子数据逐字节对比」自检通过。

**防复发**：`AGENTS.md` 3.5 加了这条的具名记录与自检方法，
不再只写「必须同步」这种没人会照做的泛化要求。

### 🟠 P2：`AuditActionRegistry` 无法匹配枚举名路径段

**成因**：`normalize()` 只把「纯数字 / UUID / 业务编号」判定为可变段。
新增的 `PUT /api/v1/governance/risk-policies/{level}` 里，
`{level}` 是 `HIGH_RISK_EXECUTION` 这样的枚举名，会被原样保留，
配 `/risk-policies/*` **永远匹配不上**。

**若不发现的后果**：这几条路由的审计会全部落到 `generic` 兜底标识。
留痕不会丢（设计上已保证），但「谁在故障前 10 分钟打开了自动执行」
这个查询会失效——而这恰恰是这几个端点最需要审计的理由。

**修复**：逐个登记四级路径，而不是放宽 `normalize()` 的可变段判定。
后者会误伤其他路由（任何非数字路径段都变 `*`，映射表将大面积错配）。

## 五、仍然存在的问题（未解决）

### 🔴 头号阻塞：CI 仍未启用，后端 200 个 Java 文件从未编译

本轮新增的 10 个后端文件同样**未经过任何编译**。沙箱内无 JDK、
Maven 全部镜像不可达（已试 8 个源），CI 是唯一验证途径。

我实测过推送 `.github/workflows/ci.yml`，被服务端拒绝：
```
refusing to allow a GitHub App to create or update workflow
`.github/workflows/ci.yml` without `workflows` permission
```

**需要你本地跑一次（30 秒）**：
```bash
git pull && mkdir -p .github/workflows
git mv ci/github-actions-ci.yml .github/workflows/ci.yml
git commit -m "ci: 启用工作流" && git push
```

在此之前，所有后端代码都处于「有理由相信正确、但未验证」的状态。

而引擎不存在。做出来只能展示空列表——比 `ComingSoonPanel` 更糟：
占位页诚实地说「能力建设中」，空列表页会让用户以为「功能有了但没数据」，
反复去查为什么没数据。
