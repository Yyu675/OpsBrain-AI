## 一、建议 1：删除 `TOOLS_PLANNING`

### 它不只是「多一个没用的枚举值」

上一轮发现 `TOOLS_PLANNING` 全项目零引用。表面看是无害的冗余，但它造成了实际损害：

迁移表要求工具执行**必须**经它中转：

```java
case EVIDENCE_READY -> to == TOOLS_PLANNING || to == DRAFT_READY || to == FAILED;
case TOOLS_PLANNING -> to == TOOLS_RUNNING  || to == DRAFT_READY || to == FAILED;
```

而编排层只能从 `EVIDENCE_READY` 直接跳到 `TOOLS_RUNNING`——
**一个永远不会亮的中间站，把真实存在的那条路给堵死了**。
所有带工具调用的会话，整个工具执行段的两次迁移全部被判非法并静默丢弃。

### 为什么它「永远不可能」被触发

LangChain4j 1.1.0 只提供 `onToolExecuted` 这一个「执行**后**」回调。
框架层根本不存在「模型开始规划工具」这个可观测时点。
不是「暂时没接」，而是**没有可接的东西**。

### 处理

- 删除枚举值（15 → 14）；
- 迁移表移除相关两行；
- 在类注释里完整记录删除理由，并写明**加回来的前提**：
  框架先提供对应回调，且**同时**有生产代码触发它。
  只加枚举值不加触发点，等于再造一次同样的堵路。

## 二、建议 2：`EXECUTING` / `OBSERVING` 定性为预留状态

这两个同样零触发，但**保留**。上一轮我建议加注释区分，本轮落实并给出了判据。

### 死代码与预留接口的界线

| | `TOOLS_PLANNING` | `EXECUTING` / `OBSERVING` |
|---|---|---|
| 现在有没有被触发 | 否 | 否 |
| **有没有可能被触发** | **否**（框架回调不存在） | **是**（能力未落地） |
| 蓝图定义 | 无 | L3 半自动自愈，有明确落地路径 |
| 结论 | 删除 | 保留 |

**判据是「它有没有可能被触发」，而不是「它现在有没有被触发」。**
只看后者会把预留接口误删，只看「反正没用到」则会把堵路的死状态留下。

### 蓝图依据

查证 `docs/02-architecture-design/OpsBrain_AI_L1至L5全自动智能自愈与商业化拓展蓝图.md`：

> **⚠️ P2 / P3（中低危局部异常）** → **L3~L4 自治（半自动自愈+观察）**
> 2. 自动调用非破坏性自愈指令（如 `kubectl rollout restart deployment/order-svc`）；
> 3. 修复后自动启动 5 分钟健康指标心跳监控，确认心跳恢复正常则自动结单，异常则升级 P1 人工介入。

`EXECUTING` 对应第 2 步、`OBSERVING` 对应第 3 步。二者已在注释里写明对应关系与接入条件。

这与前端 `FutureCapability.vue` 占位（8 条自愈路由）是同一套约定的两端。

## 三、建议 3：前端接入轨迹接口

新增 `src/api/agentTrace.ts`（+ 19 例测试）。

### 与既有 `fetchTraceDetail` 的分工

前端 `auditLogs.ts` 早有「按 traceId 下钻」，但那是**另一条线**：

| | `auditLogs.fetchTraceDetail` | `agentTrace.fetchAgentTrace`（新） |
|---|---|---|
| 数据源 | 落库的审计记录 | 内存里的状态机轨迹 |
| 保留期 | 长期 | 30 分钟空闲即清理 |
| 回答的问题 | 花了多少钱、说了什么 | **走到哪一步、为什么没走完** |

排障时后者更直接。二者互补，不重复。

### 三个判空语义写进了测试

1. **`found` 字段不能省**。`found=false`（会话已清理）与 `found=true` 且零迁移
   （流程真卡在最开始）都是空列表，含义却相反。
   只看 `transitions.length` 会把**真实故障**显示成「已过期」；
2. **`durationMs` 的 0 是有效读数**（首段迁移耗时本就是 0）。
   用 `if (!ms)` 判空会把「瞬间完成」显示成「-」，看起来像没采到数据；
3. **`slowestTransition` 空数组返回 `null`** 而非零值对象，
   否则调用方会以为存在一段耗时 0 的迁移。

另附 `agentStateColor`：归类依据是「运维看到它该不该紧张」而非状态机拓扑位置。
`MANUAL_ESCALATED` 与 `FAILED` 同为 danger——**有脏数据残留比单纯失败更需要被看见**。
未知状态回落 primary 而非报错，后端新增状态时前端不该白屏。

- `noPermanentlyUnreachableState` —— 遍历枚举，确认 `TOOLS_PLANNING` 不复活。
