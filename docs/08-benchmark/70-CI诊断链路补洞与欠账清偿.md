## 一、欠账清偿：那 12 例为什么挂

### 上一轮的处境

`TicketVoidDeleteTest` 进 CI 后后端失败，但**失败原因完全取不到**：

- annotations 只有一句 `Process completed with exit code 1`
- 完整日志与 surefire artifact 都走 Azure blob，本沙箱防火墙不可达
- 本地无 Maven（`repo1.maven.org` SSL_ERROR_SYSCALL）无法复现

只能先 `@Disabled` 隔离恢复绿灯。

### 本轮的选择：先修「看不见」，而不是继续猜

反复读代码猜原因既低效又危险——上一轮已经因此产出过一个
**基于错误前提的"修复"**（误以为增强 for 的循环变量不是 effectively final，
写最小样例实测后证伪并撤销）。

真正的瓶颈不是代码难懂，是**诊断链路有个洞**：

`mvnw` 里已有的失败重放逻辑覆盖「测试失败」场景（读 surefire XML），
但**编译失败时根本不产生 surefire 报告**，那条通道整个空转。
而 Maven 的 `[ERROR]` 概览往往只是「Compilation failure」这类标题，
真正的 `路径:[行,列] 错误描述` 在其后的缩进行里、不带 `[ERROR]` 前缀，
被上游 grep 过滤掉了。

**这就是「知道挂了、不知道为什么」的根因。**

于是给 `mvnw` 加了编译诊断通道：检测到「无 surefire XML」时，
直接从日志捞 javac 诊断行升级为 `::error::` 注解。

> 注：`.github/workflows/` 我无写权限（实测被拒），
> 但 `mvnw` 是仓库内普通文件，诊断能力加在这里同样生效，
> 且整段只在 `_mvnw_rc != 0` 时执行，对本地构建无影响。

### 结果：真因浮出，且推翻了我的假设

同一提交里我把测试类重新启用。**CI 直接绿了。**

回溯 `git diff 上次失败提交 HEAD`，代码侧唯一差异是一行：

```java
- verify(ticketRepository, never()).findById(anyString());
+ verify(ticketRepository, never()).findById(any());
```

也就是说：

- **失败原因不是编译错误** —— 我此前从「无 surefire 报告」
  推出「编译失败」，方向就是错的
- 真因是 **Mockito 的 `anyString()` 不匹配 null 实参**。
  该用例遍历 `{null, "", "   "}`，`never()` 校验遇到 null 时
  与 `any()` 行为不同，把「未发生的调用」判定搞乱
- 而这一行，我在上一轮是当作**顺手的断言改进**提交的，
  并如实写了「与本次 CI 失败是否同源尚待确认」——现在确认了：就是它

### 已据实改写代码注释

原注释写的是「用 anyString() 会漏掉『传 null 时误查库』的情况」，
描述的是**错误的失败模式**。已改写为真实经过，并记下两层教训：

1. 涉及 null 实参的 verify，一律用 `any()` 而非 `anyString()`
2. **「CI 挂了但取不到详情」时，不要急着推断失败类型** ——
   正确做法是先把诊断链路补上，让 CI 自己说话

## 二、这一轮真正的产出是诊断能力

12 例测试本身是上一轮写的。本轮的增量价值在于：

| 项 | 说明 |
|---|---|
| `mvnw` 编译诊断通道 | 补上「编译失败无报告」这个盲区，以后同类问题一次就能看到原因 |
| 一个被证伪的推断 | 「无 surefire 报告 = 编译失败」不成立 |
| 一处真实断言缺陷 | `anyString()` 对 null 的行为 |

本会话此前也出现过同类模式：另一个会话连续三次「修编译错误」，
实际根因是 Spring 上下文起不来。**共同点都是在诊断信息不足时
凭推测行动。** 补工具比补猜测有效。
