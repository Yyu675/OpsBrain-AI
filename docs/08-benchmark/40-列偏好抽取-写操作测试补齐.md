## 一、建议 1：抽出 `useTicketColumns`

与上一轮的 `useTicketFilters` 同理——列宽/列可见性共享
「默认值 + 用户覆盖 + 版本失效」三段式规则，是天然的内聚单元。
`TicketList.vue` 因此再少 157 行内联逻辑。

### 核心：坏数据不能让页面变成用户自己修不好的状态

列偏好存在 `localStorage`，那是**用户可改、且跨版本残留**的存储：

| 脏数据 | 后果 |
|---|---|
| 列宽 = 0 / 负数 | 那一列直接消失。**而列宽调节入口就在该列表头上**——用户没有任何办法把它调回来 |
| 列宽 = `'200'`（字符串） | 传给 el-table 后样式算出 NaN，整行错位 |
| 列名是上个版本的 | 表里多出渲染不出来的幽灵键 |

因此回填走**白名单 + 类型 + 范围**三重校验，任何不合法项**静默丢弃并回落默认**。
宁可让用户的自定义丢一次，也不能让页面变成一个他自己修不好的坏状态。

版本号（`COL_*_VERSION`）的作用是：列集合增删后旧键位对不上，
递增版本让整份旧数据失效，避免「新列没宽度、旧列错位」的混合状态——
那比直接回落默认更难排查。

## 二、建议 2：批量转派的「部分成功如实上报」（6 例）

store 层的 `bulkAssign` 已有测试，但**那只保证返回的数字对**。
这里守的是视图层：那个数字有没有如实传达给用户。

> 部分失败是这类操作最常见也最危险的结局——用户勾了 3 张、成功 1 张，
> 若一律弹「已分配」，他会以为全办完了，**剩下两张就此无人认领**，
> 而且不会有任何地方再提醒他。

同时覆盖了三条易漏项：操作后清空选中并关闭下拉（否则用户会对着已处理的
选区再点一次）、未选中时不打后端、转派后重新拉取（不刷新会让 `version`
过期，后续编辑误报「数据已被他人修改」）。

## 三、建议 3：`KnowledgeDetail` 写操作（18 例）

1730 行里绝大部分是只读渲染与目录/滚动联动。真正「错了会出事」的是五个写操作：
**发布、回滚版本、废弃、恢复、彻底删除（不可逆）**。

它们共享同一形状，每一环的失败模式都**不会报错**：

```
二次确认 → 置 loading → 调 store → 成功提示 → 刷新/跳转 → finally 复位
   ↓           ↓                        ↓                      ↓
取消却继续  失败后永久   失败却弹成功提示        未复位 → 按钮
执行：点了  转圈，只能   用户以为发布了，实际   永久 loading
取消照样删  刷新页面     AI 检索里没有这篇
```

物理删除额外守住**理由必填 + 裁剪**：合规场景下「谁、为什么删的」是审计的
核心证据，空理由等于没有举证依据，这类不可逆操作宁可不做。
另验证失败时**不跳转**——跳走了用户就看不到失败原因，会以为删成功了。

## 五、写测试时踩的两个坑（已记入注释）

这两个都属于「**测试红了但错在测试**」，且都会以误导性的方式表现：

### 1. `persist` 的 `__store__:` 键前缀

种子数据不带前缀就写不进去，`loadPersisted` 读到 null。
后果是「校验是否生效」的用例**因为压根没读到数据而假通过**——
初版 4 例红恰恰帮我发现了这点；若断言方向反了，它会静静地绿着。

### 2. 整模块 `vi.mock('@/api/knowledge')` 抹掉纯展示函数

该模块同时导出请求函数和 `statusLabel`/`indexStatusLabel`。
整模块 mock 会把后者一并抹掉，模板 `statusLabel(doc.status)` 直接抛错，
表现为「**所有有文档的用例全挂**」，而错误栈指向渲染层——
很容易误判成组件缺陷。已改用 `importActual` 只替换请求函数。

> 这与之前记录的「`mount(Editor)` 整模块 mock 抹掉 `SERVICE_OPTIONS`」是同一类问题。

另有一处：`purgeDoc` 里的 `router.push` 未被 `await`，
`isReady()` 在路由已就绪时立即 resolve，等不到这次跳转，
需用 `flushPromises` 排空微任务队列。
