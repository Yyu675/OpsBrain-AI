## 三、D1 执行器选型可行性（关键决策）

### 3.1 三方案对比（含沙箱实测约束）

| 方案 | 可演示性 | 凭证复杂度 | 爆炸半径可控性 | 成本 | 可行性评估 |
|------|:---:|:---:|:---:|:---:|-----------|
| **K8s（fabric8）+ 本地 kind** | 高（真实 `kubectl` 语义，面试可现场演示） | 中（ServiceAccount + RBAC，凭证天然隔离） | 高（namespace 隔离 + 只读动作） | 免费 | **推荐**——但沙箱无 docker/kind，开发与 CI 需用 mock，真实演示在本机 |
| 云厂商 API（阿里云/华为云） | 中高（真实云资源） | **高**（AK/SK 轮转 + KMS，凭证管理是独立工程） | 中 | 有真实成本 | 暂缓——凭证安全是硬门槛，且沙箱无云账号 |
| 内部脚本平台 | 低（无真实运维对象） | 低 | 低 | 免费 | 不推荐——演示力弱，且「平台」本身也要造 |
| **纯 Mock 执行器 + 契约测试** | 中（可演示治理链路，但动作是假的） | 无 | 高 | 免费 | **兜底方案**——保证 CI 与面试演示不依赖外部环境 |

### 3.2 推荐：K8s（fabric8）+ 双轨验证

```
轨道 A（开发/CI，沙箱内完成）
  新增 fabric8 kubernetes-client 依赖（0.5 天）
  → 定义执行器抽象接口 OpsExecutor（queryPodStatus 第一个实现）
  → CI 中用 FakeK8sClient（fabric8 官方 mock）走通治理全链路
    （策略匹配 → 白名单 → 风险分级 → 执行 → 记录 → 审计）
  → 单测 + 集成测试全部在沙箱可跑，不依赖真实集群

轨道 B（演示，你本机完成）
  本机安装 kind（单节点 K8s）+ 起一个 demo 命名空间
  → 同一套 OpsExecutor 连真实集群
  → 演示剧本 v2：真实告警 → AI 诊断 → 只读查询 Pod 状态 → 审计留痕

若本机也不便装 kind → 轨道 A 的 mock 直接作为演示载体（接口契约不变，后续可无缝换真）
```

**为什么这个方案可行**：
1. **接口先行**：执行器抽象（`OpsExecutor` + `ToolExecutionRecord`）不依赖具体目标系统，选型错误只影响一个实现类；
2. **mock 保底**：fabric8 官方 `FakeK8sClient` 让 CI 测试完全不依赖 Docker/kind（本沙箱已实测无 docker，此为硬约束）；
3. **凭证零泄露**：真实凭证只存在于你本机 kind 的 kubeconfig，不进仓库——符合 §十一 凭据隔离契约。

### 3.3 若选云 API 的代价（不推荐理由）

AK/SK 轮转 + KMS 集成约 1-2 周额外工作量，且演示需要真实云资源（产生费用）；对「作品集 + 求职演示」场景 ROI 低。
