## 一、工单模块（发现 4 类缺陷）

### 🔴 1. 状态机写好了，但 UI 根本没调用它

`canTransitionStatus` / `statusOptionsFor` 实现完整、契约测试全绿，
**却没有任何 UI 组件 import 它**。TicketDetail 用手写枚举，
TicketList 批量下拉直接铺全量 5 项。

穷举比对得出 8 处不一致，三类真缺陷：

| 场景 | UI | 状态机 | 后果 |
|---|---|---|---|
| `resolved → processing` | **禁用** | 允许 | 验证不通过无法打回 |
| `closed → processing` | **禁用** | 允许 | **故障复发无法重开** |
| `pending/processing → closed` | **可点** | 禁止 | 点了被后端拒，报错莫名其妙 |

**「重开」被完全阻断是最严重的**。故障复发、验证打回是运维核心场景，
用户唯一出路是新建工单 → 同一故障的历史被拆成两张单 → MTTR 统计失真、
复盘看不到完整时间线。这是数据质量问题，不是体验问题。

**修复**：
- 三个流转按钮改为 `:disabled="!canTransitionStatus(...)"`，并补 `:title` 说明原因
- 按钮文案随状态变：对 resolved/closed 显示「**重新打开**」
- 重开加二次确认（会让已计完的 MTTR 重新走、影响考核数据），
  但普通「开始处理」不加——高频动作加确认只会烦人
- 批量选项按选中项**实际状态**算可达性，全不可达则置灰，
  部分可达标「N/M」，执行时只对可达的发请求

### 🔴 2. 乐观更新写入 UTC，时间倒流 8 小时

```ts
t.updatedAt = new Date().toISOString().slice(0, 16).replace('T', ' ')
```

`toISOString()` 是 **UTC**，而该字段约定是「服务器本地时间（+08:00）不带后缀」，
`parseDate` 按 +08:00 读。**写 UTC、读 +08:00，恒定差 8 小时。**

实测：北京时间 10:30 编辑工单 → 列表「更新时间」立刻显示「**8 小时前**」。
只在乐观更新那一瞬可见（后端响应回来就校准），但编辑是高频操作。

**修复**：新增 `nowAsBackendTime()`（用 `Intl.DateTimeFormat` 按 Asia/Shanghai 取时），
并扩展 lint 规则禁 `toISOString()`。**规则一上又抓到 2 处**：
- CSV 文件名用 UTC 日期 → 北京时间 0:00-8:00 导出会命名成前一天（真缺陷，已修）
- 错误摘要用 UTC（**不是缺陷**）→ 要与服务端日志比对，抽成带 disable 注释的
  `utcTimestamp()` 并说明理由。规则是为了防错，不是消灭所有 `toISOString`

## 二、告警模块（1 类安全缺陷）

### 🔴 登出后在途 WS 消息仍写入通知列表

`stop()` 只调 `ws.close()` 而**不解绑 `onmessage`**。close 是异步的——
已在网络上的那一帧仍会抵达并触发回调，把**上一个用户**的告警
（含标题等业务内容）推进通知 store。共享值守机上，下一个登录的人
会在通知中心看到不属于自己的告警。

与 `useSessionCleanup` 是同一类问题：**登出必须切断所有数据入口**，
而不只是清掉已有数据。

**修复**：stop 时先解绑四个回调再 close。

**一处自我修正**：我起初判断还存在「登出后无限重连」，写了两条用例。
回退验证时发现**这两条在缺陷代码下也通过**——因为 `scheduleReconnect`
本来就有 `disposed` 判断，该缺陷不存在。已替换为真正能证伪的用例
（回退解绑后必然失败，实测确认），并在提交信息里标注这是误判修正。
`onclose` 判 disposed 与 `start()` 先 stop 保留为加固，不虚报为缺陷修复。

## 三、知识库模块（1 类体验缺陷）

### 🟠 版本冲突后用户被困住

`KnowledgeEditor` 遇 40009 只弹一句「请刷新查看最新内容后重新提交」，
但用户的实际处境是：

- 页面上**没有任何刷新入口**，只能按 F5
- 按 F5 会把刚写的内容全丢掉（编辑器里是未落库的）
- 草稿虽在 sessionStorage，但 `baseVersion` 已过期，恢复时又触发
  一次「草稿版本冲突」弹窗

既不敢刷新、也提交不上去。对比同项目 tickets store 处理同一业务码时
会自动重新拉取，这里明显不完整。

**修复**：冲突时**先把当前内容存进草稿**，再给两条明确出路——
「载入最新版本」（自动 loadDoc，可对照草稿合并）或「留在本页继续编辑」。

## 四、构建配置（1 类可用性缺陷）

### 🔴 Vite 代理前缀吞掉 `/ai-chat` 路由

```ts
proxy: { '/ai': { target: 'http://localhost:8088' } }   // 字符串 key 是前缀匹配
```

`/ai-chat` 命中该规则被转发到后端 → 502/404。

AI 对话页挂在**全站悬浮按钮**上，是高频入口。从其它页面点 FAB 因为是 SPA
内部导航所以正常，**但直接输地址或 F5 刷新就白屏**。这类"点进去能用、
刷新就坏"的问题在开发期极易漏掉。

**修复**：key 改为正则 `'^/ai(/.*)?$'`。验证（后端未启动，502 恰好证明确实转发了）：

| 路径 | 修复前 | 修复后 |
|---|---|---|
| `/ai-chat` | 502 | **200** |
| `/ai/api/v1/health` | 502 | 502（正确代理） |
| 其余 8 个前端路由 | 200 | 200 |

## 附：本轮教训

**1. 有实现 ≠ 被使用。**
工单状态机是本项目质量最高的代码之一——注释详尽、契约测试完备、
前后端表格对齐。但它**没有被任何 UI 调用**。以后审查要多问一句
「这个模块谁在用」，而不只是「这个模块对不对」。

**2. 静态审查有盲区，必须跑起来。**
Vite 代理吞路由这个缺陷，读配置文件看不出（字符串 key 是前缀匹配
这件事不写在代码里）。逐路由 curl 花了 30 秒就暴露了。

**3. 时间相关的测试极易写成 flaky。**
我第一版写 `expect(relativeTime(nowAsBackendTime())).toBe('刚刚')`，
实测**三次跑挂两次**——函数截断到分钟，产出时刻最多比"现在"早 59 秒，
而「刚刚」阈值是 30 秒。已改为断言「不出现小时级漂移」，连跑 5 次稳定。

**4. 验证自己的判断，不要想当然。**
「登出后无限重连」是我的误判。写完用例后回退代码验证，发现用例在缺陷版本下
也通过，才发现 `scheduleReconnect` 早有防护。**每个"修复"都应该用回退验证
证明用例确实能抓到它**——这次靠这个方法避免了一次虚报。
