# 79 · 事务内「不可回滚副作用」专项审查

> 基线缺口已清零后，转为**主动找缺陷**。本轮选定一个高价值切面：
> 事务方法内部是否存在**回滚也撤不回来**的副作用。

---

## 一、为什么选这个切面

这类缺陷有个共同特征：**两边各自都对，只有合起来看才是错的**。

- 通知发送成功——没问题；
- 事务回滚——也没问题；
- 但合起来就是「群里通报工单已升级，库里查无此事」。

没有任何一处会报错，日志里两条记录都显示成功，
事后也无从复现。靠人工 review 或跑测试都很难发现，
**必须针对性地扫**。

---

## 二、审查方法

写脚本遍历全部 `@Transactional` 方法，按花括号配平取出方法体，
再检查体内是否出现不可回滚的外部调用：

```
通知发送 / WebSocket 推送 / 对象存储 / Redis 删除 / 外部 HTTP / 缓存清理
```

命中 **5 处**，逐个核实后：**1 处真缺陷，4 处判定可接受**。

---

## 三、真缺陷：升级通知在事务提交前发出

### 位置

`TicketService#escalateTicket` —— 带
`@Transactional(rollbackFor = Exception.class)`，
而 `Notifier.send` 是**立即异步投递**，不等事务结束。

```java
// 原实现：事务内直接发
notifier.send(NotifyMessage.urgent(title, md));
return ticketRepository.findById(ticketId);   // ← 这行或提交阶段失败就回滚
```

### 用户可见后果

事务整体回滚 → **库里查无此次升级，钉钉群里却已经 @所有人
通报「工单升级 P0」**。

被 @ 到的人赶来处理，打开工单发现状态根本没变。
而这种不一致没有任何报错，事后无从复现。

### 修法

抽出 `sendAfterCommit`：

- **有事务** → 注册 `afterCommit` 回调，只在库侧板上钉钉后才发；
- **无事务上下文** → 退化为立即发送，**而不是静默丢弃**。
  后者会让通知在某些调用路径上「无声消失」——比发早了更难查：
  发早了至少还能看到内容对不上，静默丢失完全没有痕迹。

沿用项目内已有范式：`TicketAttachmentService` 删对象存储是同一类问题，
其注释里已记录过同样的教训（「元数据回滚了，MinIO 里的文件已经删掉且无法恢复」）。

> 通用原则：**不可撤销的副作用必须排在事务之后。**

### 配套测试 9 例 + 注入验证 2/2

| 注入项 | 检出信息 |
|--------|---------|
| J1 退回事务内直接发送 | `notifier.send(<any>); Never wanted here ... But invoked here` |
| J2 升级通知降级为普通 | `[升级是「需要更多人关注」的强信号...] Expecting value to be true but was false` |

关键测试技巧：单元测试**不经过 Spring 事务代理**，
`TransactionSynchronizationManager` 处于未激活状态，
`sendAfterCommit` 会走「无事务 → 立即发送」的兜底分支——
那样用例测的就不是要验证的行为了。
必须用 `initSynchronization()` 手工模拟事务上下文。

## 四、判定「不是缺陷」的 4 处（附理由）

审查的价值一半在于找出问题，另一半在于**明确哪些不用改**，
避免后人反复纠结。

### 1-2. `KnowledgeDocService.deprecate` / `purge` 调 `indexer.removeVectors`

**不是缺陷**：向量写在同一个 PostgreSQL 库、同一个事务里，
回滚时会一起撤销。它看起来像「外部调用」，实际是本地写。

### 3-4. `KnowledgeDocService.deprecate` / `purge` 调 `semanticCache.clearAllCache`

**判定可接受**，理由是**失败方向是安全的**：

| 情形 | 后果 |
|------|------|
| 事务回滚了、缓存已清 | 缓存被多清一次，下次查询重新计算 —— 只损失一点性能 |
| 事务提交了、缓存没清 | ❌ 用户拿到基于已废弃文档的旧答案 —— 这才是危险方向 |

也就是说「早清」是安全侧，「漏清」才是危险侧。
当前实现偏向安全侧，符合 `SemanticCacheService` 类注释里写的一致性边界：

> 知识库更新后必须调 `clearAllCache()`，
> 否则旧答案会在 TTL 内继续命中——用户拿到的是基于旧文档的回答，
> 而这种「答案陈旧」比「无答案」更难排查。

若改成 `afterCommit`，反而引入了「提交成功但回调没跑」的漏清窗口。
**不改。**

---

## 五、这次审查沉淀下来的判据

遇到「事务内的外部副作用」时，不要一律改成 `afterCommit`，
先问两个问题：

1. **它真的不可回滚吗？** —— 写同库同事务的操作（如上面的向量删除）
   看着像外部调用，其实会一起回滚；
2. **失败方向哪边更安全？** —— 若「早做了」的后果轻于「漏做了」
   （如缓存清理），维持现状比改动更好。

只有**不可回滚 + 早做的后果更重**时，才值得移到 `afterCommit`。
升级通知正是这一类：发早了会误导人赶来处理，而漏发只是少一条提醒。

## 六、下一步

### 可继续的审查切面（同类方法，尚未做）

1. **`@Async` 方法内的 ThreadLocal 依赖** —— 异步线程拿不到
   `TraceContext` / Sa-Token 登录态，项目里已有多处踩坑记录
   （`KnowledgeScope` 类注释、`ToolRuntimeManager` 的 traceId），
   值得系统扫一遍还有没有漏网的；
2. **定时任务的并发与幂等** —— `@Scheduled` 方法在多实例部署下会重复执行，
   查是否都有分布式锁或幂等保护。
