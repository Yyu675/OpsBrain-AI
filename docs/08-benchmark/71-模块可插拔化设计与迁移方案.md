# 71 · 模块可插拔化设计与迁移方案

> 本轮一次代码提交，**CI 全绿**。
> 目标：让任何模块可插拔——技术栈一致时能整包迁移代码，
> 技术栈不一致时能迁移开发思路。

---

## 一、先量化现状，不凭感觉设计

### 结论一：模块划分其实是干净的

`domain` 下 9 个模块，跨域依赖只有 4 条：

| 模块 | 依赖 | 规模 |
|---|---|---|
| `approval` / `auth` / `biz` / `memory` / `notify` | **零跨域依赖** | — |
| `alert` | → biz, notify | 7 文件 / 1530 行 |
| `tools` | → biz, rag | 13 文件 / 1426 行 |
| `governance` | → tools | 9 文件 / 2500 行 |
| `rag` | → auth | 21 文件 / 3802 行 |

**5 个模块本来就零耦合。** 依赖方向也没有环。
所以问题不在「模块划错了」。

### 结论二：真正的障碍是「只有 1 个接口」

```
整个 domain 层的 interface 数量：1
  └─ tools/executor/OpsExecutor.java   ← 上一轮做执行器适配器时建的
```

跨模块依赖**全部是具体类直接注入**。这才是「换个实现要改一堆不相干的类」
的根因——不是结构问题，是**缺少接缝**。

> 这个判断改变了方案：不需要大动结构，
> 只需要在既有边界上**补接口**。成本比重构低一个数量级。

## 二、本轮做出第二个样板：Notifier

### 为什么选 notify

它最能说明问题，且风险最低：

- `DingTalkNotifier` 这个**具体厂商类**被注入 4 处业务类
- 换 Slack/Teams 要改 4 个与通知无关的文件
- 而 `NotifyMessage` 已经是渠道中性模型，`send()` 是天然接缝

### 做了什么

抽出 `Notifier`（`channel` / `send` / `available`），
4 处调用点改依赖接口。**业务逻辑一行未动。**

换渠道从此 = 新增一个实现类 + 改一行配置。

### 三条实现约定（写进接口注释）

1. **永不抛异常** —— 通知是旁路。工单已建好却因钉钉限流让建单接口报错，
   是本末倒置
2. **异步发送** —— 调用方常是告警回调线程或定时扫描线程，
   同步发送会让一次 8 秒超时拖住整批告警
3. **未配置时降级为日志而非静默** —— 开发期要能看见「本该发什么」

**这三条才是技术栈不一致时唯一值得迁移的东西**——用任何语言重写都适用。

## 三、可插拔的三层定义（本项目采用）

不是所有「可插拔」都是同一件事。混为一谈会导致过度设计：

| 层级 | 含义 | 适用 | 成本 |
|---|---|---|---|
| **L1 接缝** | 抽接口，实现可替换 | 有多种实现可能的能力（通知/执行器/存储） | 低 |
| **L2 包边界** | 独立 Maven module，编译期隔离 | 确定要被别的项目复用 | 中 |
| **L3 运行时插件** | SPI / 动态加载 | 第三方开发者要扩展 | 高 |

**本项目现阶段只需要 L1。** L2 在有第二个项目真的要复用时再做；
L3 在有外部开发者生态时再考虑——现在做是浪费。

判据很简单：**「这个能力有没有第二种实现的现实可能」**。
有就抽接口，没有就别抽。

## 四、按此判据排出的接缝清单

| 优先级 | 能力 | 现状 | 第二种实现的现实可能 |
|---|---|---|---|
| ✅ 已完成 | 运维执行 | `OpsExecutor` | 云厂商 API / 脚本平台（已预留） |
| ✅ 本轮完成 | 通知 | `Notifier` | Slack / Teams / 企业微信 |
| **P1** | 向量检索 | `HybridRetrieverService` 具体类 | pgvector → Milvus / Qdrant / ES |
| **P1** | LLM 调用 | 已有 langchain4j 抽象，但 `AiModelConfig` 绑死 OpenAI 协议 | 换 Claude / 本地 vLLM |
| **P2** | 对象存储 | MinIO 具体类 | S3 / OSS / 本地磁盘 |
| **P2** | 告警来源 | `AlertService.processWebhook` 绑 Alertmanager 格式 | Zabbix / 云监控 |
| — | 工单存储 | JDBC | 不建议抽——换数据库是伪需求 |

**最后一行是刻意的**：抽一个「工单存储接口」听起来很美，
但本项目不会换掉 PostgreSQL，抽了只是多一层无人使用的间接。
**可插拔不是越多越好。**

## 五、迁移到其它项目：两条路径

### 路径 A：技术栈一致（Spring Boot / Java）

可**整包带走**的模块，按「带走成本」排序：

| 模块 | 带走什么 | 需改什么 |
|---|---|---|
| `notify` | `Notifier` + `NotifyMessage` + 实现类 | 无（零领域依赖） |
| `tools/executor` | 接口 + 命令/结果模型 + 注册表 | 无 |
| `memory` | 三层记忆 | 无 |
| `auth` | Sa-Token 封装 | 用户表结构 |
| `rag` | 检索链路 | 需先解开 → auth 的依赖 |
| `governance` | 策略引擎 + 白名单 | 需先解开 → tools 的依赖 |

**前两个现在就能复制粘贴**——这是本轮工作的直接产出。

### 路径 B：技术栈不一致（迁移思路而非代码）

此时值得带走的是**约定**，不是实现。本项目沉淀下来的、
与语言无关的设计决策：

1. **旁路能力永不影响主流程**（Notifier 三条约定）
2. **统一命令/结果模型**（`OpsCommand` / `OpsExecutionResult`）——
   让治理链路不感知目标系统
3. **幂等与「零行影响」必须区分**（Saga 补偿）——
   两者都是「没改动数据」，但一个是成功、一个是失败
4. **未配置 ≠ 不可用**（`available()`）——健康检查要能区分
5. **三态契约**：loading / error / notFound 必须分开，
   不能用「数据为空」兼表
6. **写操作后的缓存失效用声明式**（queryKey 失效）而非手工刷新

这六条是本项目**踩坑后固化的结论**，每一条背后都有真实事故。
换语言、换框架都成立。

## 六、可行性与风险

### 低风险（建议做）

- **P1 向量检索抽接口**：`HybridRetrieverService` 已有清晰的
  `retrieve` 入口，抽接口不动实现。收益是 pgvector 换 Milvus 时
  RAG 上层不用改
- **P1 LLM 接缝**：langchain4j 本身已是抽象层，
  只需把 `AiModelConfig` 里的 OpenAI 协议细节收敛到一处

### 中风险（想清楚再做）

- **P2 告警来源**：抽 `AlertSource` 接口意味着要定义一个
  「厂商中性的告警模型」。Alertmanager / Zabbix / 云监控的字段差异不小，
  中性模型设计不好会变成最小公倍数，反而丢信息

### 不建议做

- 为「所有模块」统一抽接口。没有第二种实现可能的地方抽接口，
  只是增加一层无人使用的间接，还会让新人多读一跳
- 现在拆 Maven multi-module。当前是单体部署，拆了徒增构建复杂度，
  等真有第二个项目要复用时再拆，那时需求也更清楚

## 七、下一步建议

1. **P1 向量检索接缝**（`Retriever` 接口）—— 复用本轮的模式：
   抽接口 + 契约测试守约定 + 现有实现类改为 implements
2. **P1 LLM 配置收敛** —— 把 OpenAI 协议细节从 `AiModelConfig` 收进一处
3. 每做一个接缝，**同步补一个契约测试**——本轮的
   `NotifierContractTest` 是模板：用遍历而非逐实现写，
   新实现自动纳入检查

**仍需你操作**（workflows 权限限制）：
Flyway 接管、`run_audit.py` 接入 CI。
