## 二、缺陷成因与用户可见后果

**成因**：「写了删除能力却没人调用」——这是最容易被漏掉的一类缺口。
代码读起来是完备的（有表、有仓储、有 delete 方法、有批量参数），
静态审查很难发现「这个方法从未被调用」，除非专门做一次全仓调用点普查。

**用户可见后果**：`sys_agent_conversation_turn` 存的是**逐轮对话原文**。
运维场景里用户常整段粘贴日志与堆栈，单轮可达数十 KB（仓储层按 32K 字符截断），
而摘要只有百字级。这张表的增长速度比库里其它任何表快一到两个数量级。
不清理会在数月内让它成为库里最大的表，拖慢备份与全表维护操作，
最终以磁盘告警的形式暴露——而那时数据已经堆到不好处理了。

## 三、四个设计决策

### 1. 清理边界取 `max(配置保留期, 归档保留期 + 7 天安全余量)`

这是本轮**最要紧的一条**，也是最容易漏掉的。

冷归档任务（`ColdMemoryArchiveScheduler`，每日 04:23）按
`devops.ai.memory.archive-after-days`（默认 90 天）挑选候选会话，
**归档时才把原文从本表读出、写进归档 JSON**。

若原文清理得比归档更早会怎样？原文在会话被归档之前就消失，
`turnRepository.findBySession` 返回空列表，`hasTranscript=false`，
归档文件退回 `SUMMARY_ONLY`——**88 号刚补的缺口被静默地重新打开**，
而且**没有任何报错**，JSON 结构完全合法，只有事后有人翻归档文件
才会发现「原文怎么又没了」。

所以本任务不直接用配置值，而是取
`max(retentionDays, max(archiveAfterDays, 0) + SAFETY_MARGIN_DAYS)`，
被抬升时记 WARN 让运维看得见。

> 判据：**配置错误的代价应当是「多留一些数据」，
> 而不是「不可逆地删掉尚未归档的审计原文」。**

7 天余量的依据：归档任务每天只跑一轮且单轮上限 200 条，
会话刚满保留期时可能排在积压队尾，要等几轮才被归档。
7 天 × 200 条 = 1400 条的消化窗口。

### 2. 分批循环删到未满批为止，而非只删一批

单批上限（500）防长事务锁表，这没问题。但**只删一批会让积压永远追不上**：
若某天产生了 10 万条超期原文，每天删 500 条要 200 天。

故一次执行内循环删除，终止条件是「本批删除数 < 批上限」（说明已删完）
或达到 `max-batches-per-run`（默认 20，即 10000 条/轮）。
达到上限时如实 WARN 报告积压，不静默截断（6.24 no silent caps）。

顺带一个细节：仓储层异常时返回 0，同样会走到「未满批」退出循环——
这是期望行为，数据库出问题时不该继续空转打满日志。

### 3. 非法配置拒绝执行而非兜底

`retention-days = 0` 会让 SQL 命中 `create_time < CURRENT_DATE - 0`，
即**除今天以外的全部数据**，等于清空整张审计表，且不可逆。
这只可能是配置写错，不可能是真实意图。

这里特意**没有**做「兜底为下界 97 天照常跑」——那样看起来更"健壮"，
但会让运维以为自己的配置生效了。明确拒绝 + ERROR 日志才是对的。
`batch-size ≤ 0`（`LIMIT 0` 会死循环空删）与 `max-batches-per-run ≤ 0` 同理。

### 4. cron 04:47，排在冷归档 04:23 之后

**先归档、再清理**。反过来会让当天刚满保留期的会话在归档前丢原文。
同时错开 :00/:30 与其它定时任务（孤儿切片 03:17、知识保留期 03:30/04:00）。

另：总开关默认 **`true`**，与冷归档（默认 `false`）相反。
归档默认关是因为它写对象存储、需要外部依赖就绪；
而清理只依赖数据库，且不清理的后果会持续恶化。
关闭它应当是一次有意识的「我接受表继续增长」的决定。

三项注入全部**红在其声称要防的那条断言上**，非「红了就算过」。

### 一个被测试用例本身抓住的陷阱

`negativeArchiveWindowDoesNotShrinkFloor` 最初写成 `retentionDays=10`，
自查时发现：不夹 0 的实现算 `-100+7=-93`，`max(10,-93)=10`；
夹 0 的实现算 `0+7=7`，`max(10,7)=10`——**两种实现给同一答案，用例形同虚设**
（第 5 类假测试：用例构造的场景与要防的缺陷不是同一件事）。
改成 `retentionDays=3`（小于安全余量 7）后两者才分叉：3 vs 7。
CI 实测确认该用例在 S1 注入下报 `expected 7 but was 3`。

## 五、配置清单

```yaml
devops.ai.memory.turn-retention:
  enabled: true                # 默认开启
  retention-days: 180          # 明显长于 archive-after-days(90)
  batch-size: 500              # 单批上限，防长事务
  max-batches-per-run: 20      # 10000 条/轮
  cron: "0 47 4 * * *"         # 排在冷归档 04:23 之后
```

## 六、结论与下一步

B-2（冷归档原文补全）至此**完整闭环**：表 → 写入 → 归档读取 → 保留期清理，
生命周期四段齐全，没有留下「写得进去删不掉」的单向增长表。

下一轮按切面继续自主审查，候选：
1. **时区处理**——`LocalDateTime.now()` 全仓多处，容器 TZ 与业务 TZ 是否一致、
   跨时区租户的「今天」如何界定；
2. **分页边界**——`page/size` 的上界、`offset` 溢出、总数与列表不一致；
3. **并发写幂等**——除已覆盖的 saga/session 外的写路径。

沿用一贯口径：**有则修、无则固化**（写契约测试锁住当前正确的实现方式），
「不做」的判断同样写明理由存档。
