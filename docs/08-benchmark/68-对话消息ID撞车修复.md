# 68 · 对话消息 ID 撞车修复

> 本轮一次代码提交，**CI 全绿**。前端 1716 例（+25）、后端 918 例。

## 一、本轮最有价值的产出：写测试时撞出一个真缺陷

本轮目标是补 `ChatMode.vue`（821 行，最大零测试组件）的非流式部分。
写完后「重新生成」那条用例**偶发失败**——单独连跑 3 次挂 1 次。

**没有当成 flaky 跳过，而是查了根因。** 结果是产品缺陷。

### 缺陷：`Date.now()` 只有毫秒精度

```ts
id: `user-${Date.now()}`
id: `assistant-${Date.now()}`
```

两种场景会在**同一毫秒内**连续建两条消息：

1. 「重新生成」：`removeMessage(旧回答)` 紧接着 `startAssistantMessage(新)`
2. 发送时 `pushUserMessage` 之后立刻 `startAssistantMessage`

### 后果不是显示乱，是操作打在错的消息上

| 位置 | 行为 | 撞车后 |
|---|---|---|
| `removeMessage(id)` | `findIndex` 取第一个匹配 | 删掉的可能是另一条 |
| `streamingMessage` | 按 id `find` | token 追加到旧消息上 |

**用户可见形态**：点「重新生成」，结果**另一条回答消失了**；
或者新回答的内容被写进了上一条里。

这类缺陷在生产上极难复现——它依赖两次操作落在同一毫秒，
而本地手点几乎不可能触发。**是自动化测试的高频调用把它逼出来的。**

### 修复

```ts
let msgSeq = 0
const nextMsgId = (role: 'user' | 'assistant') =>
  `${role}-${Date.now()}-${++msgSeq}`
```

保留时间前缀便于排序与排查。修复后 ChatMode 连跑 6 次全绿。

## 二、为什么测试范围只切非流式部分

`ChatMode.vue` 的核心是 SSE 流式问答，而流式测试成本高
（要模拟事件序列、时序、中断）。

但**缺陷更多集中在"周边"而非核心流程**：发送前校验、
停止/重新生成的守卫、清空互斥、卸载收尾。

本轮正好印证了这个判断——撞出来的缺陷不在流式协议里，
而在「重新生成」这个周边动作上。

其中最重要的一条是**卸载后 `isStreaming` 必须复位**：
该状态存在 store（跨组件共享），只 abort 不收尾的话，
切走再回来输入框永久禁用，用户只能刷新。

## 三、两处测试脚手架的坑

### 1. chatStream 桩不能返回「永不 resolve 的 Promise」

`sendMessage` 内部 `await runStream(...)`，永不结束会让
`await vm.sendMessage()` 一直挂起。第一版 **11 个用例集体 5 秒超时**，
失败信息只有一句 `Test timed out`，与被测逻辑毫无关系。

**正确做法**：立即 resolve 但**不触发任何回调**。
这样调用结束了，而 `isStreaming` 仍为 true（没有 complete/error 收尾）——
正好模拟出「流式进行中」这个待测状态，且不阻塞测试。

### 2. 测 stopGeneration / 卸载中断必须用可控 deferred

`runStream` 的 `finally` 会把 `abortController` 置回 null。
若 chatStream 立即 resolve，等到调用 `stopGeneration` 时 controller 已没了，
守卫第一行就 return——**测的根本不是停止逻辑**。

改为挂起 + 不 await（`void` 起飞），测完再 `release()` 收尾。

## 四、注入-还原验证

| 对象 | 注入 | 抓到 |
|---|---|---|
| ChatMode | 8 | 8 |
| chat store（ID 生成） | 1 | 1 |

store 那条注入是「ID 退回纯 `Date.now()`」——即还原缺陷本身，
立刻失败，证明新增用例确实守住了这个不变量。

注入器沿用上一轮加的唯一性断言（`count == 1`），模式不唯一直接报错。
