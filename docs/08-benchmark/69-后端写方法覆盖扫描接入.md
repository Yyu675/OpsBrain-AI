## 一、主线：一个「写了但没在跑」的扫描器

`tools/audit/scan_service_write_coverage.py` 早已存在，
但**从未接入 `run_audit.py`**——写了、没人跑、等于不存在。

### 首次真实运行：36 个命中，约 40% 是误报

逐个核实后发现的噪音类型：

| 误报 | 真实身份 |
|---|---|
| `ToolRuntimeManager` 的 riskLevel / timeoutMs / idempotent 等 6 个 | **匿名内部类**里实现的 `@ToolMeta` 注解属性 |
| `KnowledgeDocService.IndexOutcome` | `public record` 声明 |

**误报率高的后果是清单失去可信度**：没人愿意逐条核对 36 项，
于是整个扫描被忽略。所以重写的重点不是找出更多，而是**少骗人**。

### 重写：36 → 17，抽样核实全部为真

四条过滤规则均由上述真实误报反推：

1. 跳过 record / enum / interface 声明
2. **按花括号配平剔除嵌套类型与匿名内部类**（治第一类误报）
3. 扩充只读前缀白名单 + 识别 `*Stats` / `*Snapshot` 等只读后缀
4. 跳过 `@Override` —— 实现外部契约，不该记在本类头上

已接入 `run_audit.py` 成为**第六类扫描**。
注入一个新写方法验证：退出码 1，删掉回 0。

- **生命周期钩子 3 条**（`@PreDestroy`）—— 容器调用，非业务路径
- **确属缺口 10 条** —— 写明风险与优先级，`compensateStep` 列为下一轮首选

## 三、过程中的两次自我纠正

### 其一：一个基于错误前提的「修复」，已撤销

我一度判断失败原因是「增强 for 的循环变量不是 effectively final，
被 lambda 捕获导致编译失败」，并据此改了代码。

随后写了个最小 Java 样例用 ECJ 实测——**证明这个前提是错的**：
增强 for 的循环变量每轮迭代都是 effectively final，能正常编译。

已撤销该改动。

> **记下来的理由**：基于错误前提的「修复」比不修更糟。
> 它会让人以为问题已经解决，而真实原因仍在原地。
> 本会话此前也出现过同类情况——另一个会话连续三次「修编译错误」，
> 实际根因是 Spring 上下文起不来。

### 其二：一处真实的断言失效，已修正

```java
verify(ticketRepository, never()).findById(anyString());
```

Mockito 的 `anyString()` **不匹配 null**，而该用例恰好传 null。
这条断言看着在、实际没守住「传 null 时误查库」这种情况。已改为 `any()`。

与本次 CI 失败是否同源尚待确认——不臆断。
