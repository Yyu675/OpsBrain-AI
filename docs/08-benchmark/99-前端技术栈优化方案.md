## 二、问题定性

### 问题 1：两套富文本编辑器并存

| 编辑器 | 唯一消费方 | 体积 |
|---|---|---|
| `@wangeditor/editor` + `-for-vue` | `components/knowledge/KnowledgeRichEditor.vue` | 782 KB |
| `md-editor-v3` + `turndown` | `views/KnowledgeEditor.vue` | ~300 KB + 依赖 |

**好消息**：**各自只有 1 个消费方**，隔离度非常高——这决定了合并的改动面比想象中小得多。

**代价**：
- 打包多出约 700 KB～1 MB；
- 两套编辑器的**粘贴行为、图片处理、XSS 过滤口径不一致**——
  知识库同一份文档用两个入口编辑，结果可能不同；
- `turndown`（HTML→Markdown 转换）的存在说明两套之间还要做格式互转，
  **这是纯粹因为选型没收敛而产生的额外复杂度**。

### 问题 2：语法高亮语言包全量打包

148 个碎片 / 630 KB，其中绝大多数是运维场景永远用不到的语言。

### 问题 3（次要）：依赖版本激进

Vite 8 / TS 6 / ESLint 10 / Vue Router 5 / knip 5 都是大版本。
实测 **knip 在本项目上直接崩溃**（`oxc-parser` 段错误），
这就是激进版本的代价——工具链本身不稳。

---

## 三、三个可行方案

### 方案 A：统一到 md-editor-v3，移除 wangEditor（**推荐**）

**做什么**：
- 删除 `KnowledgeRichEditor.vue`（wangEditor 的唯一消费方），
  其功能由 `KnowledgeEditor.vue` 的 md-editor-v3 承接；
- 移除 `@wangeditor/editor`、`@wangeditor/editor-for-vue` 依赖；
- 视情况保留 `turndown`（若仍需导入历史 HTML 文档）。

**优点**
1. **省下最大的那块**：782 KB 的首屏外产物直接消失；
2. **Markdown 是运维知识库的天然格式**——工程师写手册本来就用 Markdown，
   Git 友好、diff 可读、可被 RAG 直接切片（本项目的
   `ParentChildDocumentSplitter` 处理 Markdown 结构比处理 HTML 干净得多）；
3. 消除双入口不一致：粘贴、图片、XSS 过滤只剩一套口径；
4. `md-editor-v3` 自带预览与代码高亮，与知识库详情页的渲染链路
   （`marked` + `DOMPurify` + `safeMarkdown`）**同源**，行为一致；
5. **改动面小**：只有 1 个组件消费 wangEditor。

**缺点**
1. 失去所见即所得的富文本体验——**不习惯 Markdown 的非技术用户会有门槛**；
2. 若存量知识文档中有 HTML 格式内容，需一次性转换（`turndown` 可做，但要验数据）；
3. 复杂表格在 Markdown 里编辑体验不如富文本。

**推荐理由**：本产品的用户是 **SRE 与运维工程师**，不是市场或行政人员——
他们本来就写 Markdown。而且知识库内容最终要喂给 RAG，
**Markdown 的结构化程度直接影响切片质量与检索准确率**。
这不只是省 782 KB 的事，是让格式与产品定位对齐。

---

### 方案 B：统一到 wangEditor，移除 md-editor-v3

**做什么**：反过来，`KnowledgeEditor.vue` 改用 wangEditor。

**优点**
1. 所见即所得，非技术用户友好；
2. 复杂表格、图文混排体验好。

**缺点**
1. **体积反向恶化**——留下的是 782 KB 那个，删掉的是小的；
2. HTML 存储对 RAG 不利：切片前要剥标签，`ParentChildDocumentSplitter`
   依赖的标题层级在 HTML 里更难可靠解析；
3. XSS 面更大：富文本 HTML 入库，渲染时对 `DOMPurify` 的依赖更重；
4. 与详情页现有的 Markdown 渲染链路不同源，需要额外适配。

**推荐理由**：**不推荐**。除非明确知道有大量非技术用户要编辑知识库。

---

### 方案 C：维持双套，只做语言包裁剪

**做什么**：不动编辑器，只配置代码高亮语言白名单
（`bash`/`yaml`/`json`/`sql`/`java`/`python`/`go`/`js`/`ts`/`dockerfile`）。

**优点**
1. 改动最小、风险最低，1～2 小时可完成；
2. 立刻省下约 550 KB（148 个碎片留 10 个左右）。

**缺点**
1. **没解决根本问题**——双入口不一致、`turndown` 互转的复杂度都还在；
2. 782 KB 的 wangEditor 仍在；
3. 技术债继续挂着，下次有人改知识库编辑还是要面对两套。

**推荐理由**：**作为方案 A 的第一步是合理的**，作为终点不合理。

---

## 四、推荐路径

> **A + C 组合，分两步走**：
>
> **第 1 步（低风险，先做）**：语言包裁剪 —— 省 ~550 KB，1～2 小时，不碰业务逻辑。
> **第 2 步（需验数据）**：统一到 md-editor-v3 —— 省 782 KB，
> 但**动手前必须先确认存量知识文档里有没有 HTML 格式内容**，有则先做转换验证。

**分两步的理由**：第 1 步的收益/风险比极高且完全独立；
第 2 步涉及数据格式，必须先摸清存量再动，不能一起做。

### 需要你决策的点

1. **编辑器方向**：选 A（Markdown 统一）还是 B（富文本统一）还是 C（只裁剪）？
2. **知识库用户画像**：编辑知识库的人**是否全是技术人员**？
   这直接决定 A 与 B 的取舍。
3. 第 1 步（语言包裁剪）是否可以**立即开做**？它与编辑器方向无关，
   选哪个方案都要做。

## 五、其余前端选型的评估结论（无需改动）

| 选型 | 结论 | 理由 |
|---|---|---|
| Vue 3.5 + TS + Vite | ✅ 保持 | 无替换理由 |
| Pinia 3 | ✅ 保持 | |
| **TanStack Vue Query** | ✅ **保持，是亮点** | 服务端状态与客户端状态分离，缓存/重试/失效统一，比手写 loading/error 强一个量级 |
| Element Plus | ✅ 保持 | 中后台标配，381 KB 可接受 |
| ECharts 6 | ✅ 保持 | 已按需引入，557 KB 是 core 本身的下限 |
| `@microsoft/fetch-event-source` | ✅ 保持 | 比原生 `EventSource` 强（支持 POST/自定义头/重连控制），SSE 主链路刚需 |
| marked + DOMPurify | ✅ 保持 | 已有 `safeMarkdown` 统一入口，85 号加固过 |
| Vitest + @vue/test-utils | ✅ 保持 | 1,756 例，是本项目最强的资产之一 |
| **knip** | ⚠️ 需修 | **当前在本项目上崩溃**（`oxc-parser` 段错误），死代码扫描实际处于停摆状态 |

### 建议补充（前端侧，依赖后端 P0-2）

| 补什么 | 解决什么 | 前置条件 |
|---|---|---|
| **openapi-typescript** | TS 类型手写镜像后端，已出过 95 号那类事故 | 需先做 P0-2（springdoc-openapi） |
| **构建体积预算**（`vite build --report` + CI 阈值） | 防体积回弹 | 无，可随第 1 步一起做 |
