# 99 · 前端技术栈优化方案（v2，已重新决策）

> 日期：2026-08-28 ｜ 基线 `0f79e91`
> **v2 修订说明**：v1 基于「用户全是技术人员」的假设推荐「删除 wangEditor」。
> 该假设经代码与 PRD 核查**不成立**，且核查中发现 v1 对现有实现的理解有误——
> 双编辑器不是「两个独立入口」，而是**同一页面里已实现的双模式切换**。
> 本版推翻 v1 的编辑器结论，重新给方案。

---

## 一、v1 错在哪（先说清楚）

| v1 的判断 | 实际情况 | 证据 |
|---|---|---|
| 「两套编辑器各有 1 个消费方，是选型摇摆的残留」 | ❌ **是同一页面的双模式切换**，`editorMode: 'visual' \| 'markdown'` | `KnowledgeEditor.vue:127` |
| 「`turndown` 是因选型没收敛而多出的复杂度」 | ❌ **是双模式切换的必要组件**，负责 visual→markdown 转换 | `KnowledgeEditor.vue:276` |
| 「用户全是技术人员，Markdown 无门槛」 | ❌ PRD 明确列了**业务方/报障人**与**合规审计员**两类非技术角色 | `docs/PRD.md:81` 目标用户表 |

**教训**：v1 只 `grep` 了「谁 import 了这两个包」，看到各 1 处就断定是两个独立入口，
**没有读 `KnowledgeEditor.vue` 的实现**。这与 93/95 号记过的同型错误一致——
**用 grep 得出结构性结论前，必须打开文件确认**。

## 二、核查到的三条事实

### 事实 1：双模式已经实现，且实现得不差

```ts
const editorMode = ref<'visual' | 'markdown'>('visual')

const switchEditorMode = async (mode) => {
  formData.value.content = mode === 'visual'
    ? await toVisualContent(formData.value.content)   // md → html
    : turndown.turndown(formData.value.content)        // html → md
  editorMode.value = mode
}
```

- 富文本（wangEditor）与 Markdown（md-editor-v3）**同页切换**；
- 两个方向的转换都有；
- `insertBlock` 按当前模式分别插入 HTML 块或 Markdown 块——**细节考虑到了**。

**这恰好就是「非技术人员也要写」场景所需要的方案**，而它已经存在了。

### 事实 2：非技术角色确实在目标用户里

PRD `§三 目标用户与场景` 的 7 类角色中：

| 角色 | 技术属性 |
|---|---|
| 值班 SRE / 一线运维 / 平台管理员 / 运维负责人 | ✅ 技术 |
| 技术管理者 | ⚠️ 偏管理 |
| **业务方/报障人**（PRD 标注「新增」） | ❌ 非技术 |
| **合规审计员**（PRD 标注「新增」） | ❌ 非技术 |

用户已确认：**非技术人员也要写**（如业务方写业务侧排查说明、审计员写合规条款）。

### 事实 3：存储格式不一致 —— 这是个真缺陷

```ts
// handleSave 第 614 行
content: formData.value.content,   // 用户停在哪个模式就存哪个格式
```

而数据库注释写的是：

```sql
content TEXT NOT NULL,   -- Markdown 原文
```

**用户在 visual 模式保存 → 库里存的是 HTML，但 schema 声称是 Markdown。**

后果链条：
1. **RAG 切片质量下降** —— `ParentChildDocumentSplitter` 按 Markdown 标题层级切分，
   拿到 HTML 时层级识别不可靠，切片边界错乱 → **检索准确率下降**；
2. **详情页渲染** —— `KnowledgeDetail` 走 `safeMarkdown`（marked + DOMPurify），
   HTML 内容经 Markdown 渲染器处理，结果依赖 marked 对裸 HTML 的宽容度，**不可控**；
3. **`content_hash` 去重失效** —— 同一篇文档用两种模式保存，
   哈希不同，近重复检测认不出它们是同一篇。

> 这个缺陷比「打包大 700KB」严重得多，但 v1 完全没看到——因为 v1 没读实现。

## 三、重新给方案

### 方案 A′：保留双模式，修正存储格式统一为 Markdown（**推荐**）

**做什么**：
1. **保留** wangEditor + md-editor-v3 双模式（它服务的是真实的用户分层）；
2. **保存时统一转 Markdown 落库** —— `handleSave` 里若当前是 visual 模式，
   先 `turndown` 再提交；
3. 加测试锁住「无论从哪个模式保存，落库的都是 Markdown」；
4. 语言包裁剪（与编辑器方向无关，独立收益）。

**优点**
1. **修掉真缺陷**（存储格式不一致 → RAG 切片、渲染、去重三处受影响）；
2. **保住非技术用户的可用性** —— 这是用户明确的需求；
3. 存储层单一格式，schema 注释与实际一致；
4. RAG 切片质量恢复到设计预期；
5. 改动面小：核心是 `handleSave` 一处 + 测试。

**缺点**
1. 打包体积不变（仍有 782 KB 的 wangEditor）——**但这是为真实用户需求付的钱，不是浪费**；
2. HTML→Markdown 转换有信息损失（复杂表格、嵌套样式），
   需要在保存时给用户提示，或在切换模式时就提示（现在切换已经会转，但没提示）。

**推荐理由**：**它同时解决了「用户分层」和「数据一致性」两个真问题**，
而删掉一套编辑器只解决体积、还会伤到一类用户。

---

### 方案 B′：双模式 + 按角色默认模式

在 A′ 基础上，**按登录角色决定默认编辑模式**：技术角色默认 Markdown，
非技术角色默认 visual。

**优点**：各得其所，技术人员不必先点一下切换。
**缺点**：需要前端拿到角色并做映射，且**依赖角色体系可信**——
而当前知识库写操作根本没有角色校验（见下），先决条件不成立。

**推荐理由**：**A′ 之后的增强项**，不是现在做的事。

---

### 方案 C′：仍然删掉 wangEditor（**不推荐**）

**不推荐理由**：用户已明确非技术人员要写。删掉等于让业务方和审计员
去学 Markdown 语法——**为了省 782 KB 让一类用户不会用，这个交换不划算**。

## 四、顺带发现的安全缺陷（用户已确认要修）

> **⚠️ 2026-08-31 修正**：本节初稿说「7 个写端点全部无角色校验」**不准确**。
> 复核发现 `purge`（物理删除）**已有** `@SaCheckRole("ADMIN")`，
> 是用行内全限定名写的（`@cn.dev33.satoken.annotation.SaCheckRole`），
> 我第一次用 `grep -c "SaCheckRole"` 统计时数到了、但看漏了它属于哪个端点。
> 准确表述是：**7 个写端点中 6 个无角色校验，最危险的物理删除已限管理员**。
>
> 另一处修正：角色值实际是 **`ADMIN` / `OPS`**（见 `User.java` 与
> `SaTokenPermissionProvider`），不是我此前写的 `admin/operator/viewer`。
> 系统里**没有 `viewer` 角色**——这改变了修复方案的形态（见下）。
>
> 且缺口不止 `KnowledgeDocController`：
> | 控制器 | 写端点 | 有角色注解 |
> |---|---:|---:|
> | `KnowledgeDocController` | 7 | 1（仅 purge） |
> | `KnowledgeCategoryController` | 4 | 0 |
> | `KnowledgeTagController` | 4 | 0 |
> | `KnowledgeManageController` | 1 | 0 |
> **合计 16 个写端点，15 个无角色校验。**

`KnowledgeDocController` 的 **7 个写端点**：

```
POST   /api/v1/knowledge/docs              新建
PUT    /api/v1/knowledge/docs/{id}         编辑
POST   /api/v1/knowledge/docs/{id}/publish 发布
POST   /api/v1/knowledge/docs/{id}/deprecate 废弃
POST   /api/v1/knowledge/docs/{id}/restore 恢复
DELETE /api/v1/knowledge/docs/{id}/purge   物理删除
POST   /api/v1/knowledge/docs/reindex/pending 重建索引
```

**一个角色注解都没有。** 对比全仓其它模块：

| 控制器 | 限权 |
|---|---|
| `ApprovalController` | `@SaCheckRole("ADMIN")` 类级 |
| `AuditLogController` | `@SaCheckRole("ADMIN")` 类级 |
| `AutomationGovernanceController` | `@SaCheckRole("ADMIN")` 类级 |
| `SagaController` | `@SaCheckRole("ADMIN")` 类级 |
| `AgentTraceController` | `@SaCheckRole("ADMIN")` 类级 |
| **`KnowledgeDocController`** | **无** |

前端路由 meta 也只有 `title: '编辑文章'`，无权限声明。

### 为什么这是严重问题

**知识库是 AI 回答的事实来源。** 任何登录用户（包括 `viewer` 角色）
都能改知识库，意味着**任何人都能污染 AI 的输出**——
改一篇「生产数据库重启流程」，之后所有问到这个问题的 SRE 都会拿到被篡改的答案。

而且 `purge` 是**物理删除**，不是软删。

**用户已确认这是缺陷，应加角色限制（admin/operator 可写，viewer 只读）。**

## 五、修订后的推进顺序

| # | 任务 | 风险 | 收益 |
|---|---|---|---|
| **1** | 语法高亮语言包裁剪 | 零业务风险 | 省 ~550 KB |
