## 一、补上最大单点风险的测试

上一轮盘点结论：`KnowledgeDocService` 风险最高——702 行、9 个 `@Transactional`
写方法，此前**没有任何直接单测**，只有实体默认值测试与 Controller 契约间接沾边。

它管着知识库的**发布、废弃、版本回滚、物理删除**。出错的后果不是报错，而是两类静默事故：

- **数据丢了**：物理删除少清一张表就留孤儿，多清一张就抹掉不该删的历史；
- **AI 检索不到**：发布了没建向量、或废弃了没删向量——文档在列表里看着好好的，
  问 AI 它却说不知道；反过来，已废弃内容仍被检索出来当决策依据。

### 覆盖的四组不变式（24 例）

| 方法 | 例数 | 关键不变式 |
|---|---|---|
| `deprecate` | 5 | **先归档再改状态**（反了会把废弃后的状态存进历史，回滚时滚到一个废弃版本）；必须删向量；必须清语义缓存 |
| `purge` | 5 | 合规理由必填**且校验先于查库**（不合法就不该有任何 IO）；四类关联数据全清；**先删向量再删主表**（反序则主表已没，再没有 docId 能定位那些向量） |
| `restore` | 7 | 内容被其他**活跃**文档占用时给可操作提示而非 500；占用者是自己或已废弃时放行；**回滚必须显式设 PUBLISHED**（否则废弃文档回滚后仍是 DEPRECATED，用户以为成功实则 AI 检索不到） |
| `update` 门禁 | 7 | 乐观锁 CAS；已废弃文档禁改正文但**允许改元信息**（否则再也无法归置分类）；只改元信息时**跳过清洗**（旧内容当初已通过，重新校验会让清洗规则一收紧老文档连改分类都做不到） |

### 靠核对源码避免的三处签名错误

沙箱无法跑 Maven，每个错误都要耗一轮 CI，所以动手前逐个核对：

- `docRepo.update` 是**双参** `(doc, expectedVersion)`；
- 候选查询叫 `findSimhashCandidates(category, excludeId, limit)`，不是我以为的 `findNearDuplicateCandidates`；
- `KnowledgeDocTagRepository` 在 `domain.rag`，而 `KnowledgeTagRepository` 在
  `infrastructure.persistence.repo`——**两个名字相近的类分属不同包**。

## 二、两个真实的测试缺陷（都不在产品代码里）

### 缺陷 A：`docRepo.update` 忘了打桩

它返回受影响行数，未打桩时 Mockito 默认返回 **0**，
而 service 把「0 行」解读为 CAS 失败并抛 `OptimisticLockException`——
所有走到 `update` 的用例都以一个**与被测行为完全无关**的异常告终。

> 这类「返回原始类型的方法忘打桩」很隐蔽：Mockito 不报错，
> 只是静默返回 `0/false/null`，然后在离桩点很远的地方炸掉。

### 缺陷 B：`String.valueOf` 的重载陷阱

```java
// 错误写法
when(fingerprint.sha256(anyString())).thenAnswer(i ->
    "hash-" + String.valueOf(i.getArgument(0)).hashCode());
```

`getArgument` 返回泛型 `T`，编译器据此挑中 `String.valueOf(char[])` 这个重载，
运行时抛 `ClassCastException: String cannot be cast to [C`。

难查之处在于：**异常在 lambda 内抛出，堆栈指向 `setUp` 而非用例本身**——
8 个用例报的都是同一个看不懂的错误。改为先 `String content = i.getArgument(0)` 即可。

## 三、CI 诊断链路：四个静默失败的环节

这个两行就能修的 bug，为了「看到它」花了 **6 轮 CI**。原因是诊断链路上串着四处各自静默失败的环节，每一处都不报错：

| # | 环节 | 症状 |
|---|---|---|
| 1 | Maven `[ERROR]` 摘要块**无条件**占满 10 条注解配额 | 真正的异常一条都发不出 |
| 2 | 报告文件名与 `Tests run` 行也在抢配额 | 同上 |
| 3 | **重放逻辑读 `.txt`，而失败详情只在 `.xml` 里** | 找到了文件却提取不出任何详情 |
| 4 | 我用**手工造的假 `.txt`** 做本地验证 | 前两次「验证通过」都是假的 |

第 3 条是决定性的，靠往 CI 打探针拿到真实读数才发现：

```
[诊断1] rc=1 dir=yes txt=64      → 重放块执行了、报告也在
[诊断2] 匹配失败的报告数=0        → 但 64 个 txt 无一含 FAILURE!/ERROR!
[诊断3] xml数=64 含失败的xml=1    → 失败详情只在 .xml 的 <error> 节点
```

surefire 的 `.txt` 是**通过用例**的摘要，失败信息写进 `.xml`。

### 最值得记的教训

> **仿真数据是照着「我以为的样子」造的，自然验证不出「我以为错了」。**

前两次本地验证都用我手工塞了 `<<< ERROR!` 的假 txt，结构与真实产物不同，
所以逻辑「当然通过」。真正戳破它的是**探针 + 真实读数**，而不是更仔细地推理。

修复后用**贴近真实结构的 surefire XML**（含 `<error message= type=` 与转义堆栈）
重新验证，输出 2 条注解，正是异常类型与消息。
