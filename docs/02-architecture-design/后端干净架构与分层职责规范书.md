# 🏛️ 企业内部知识库智能运维助手 —— 后端干净架构与分层职责规范书

> **架构目标**：结合 Spring Boot 3.x 与 LangChain4j 生态，针对复杂 AI Agent 工程落地建立遵循 **单一职责原则 (SRP)**、**依赖倒置原则 (DIP)** 与 **领域驱动设计 (DDD/Clean Architecture)** 的分层规范。  
> **核心承诺**：彻底告别将大模型调用、Prompt 拼接、向量检索与数据库查询揉在这个单体 Controller 里的“上帝类 (God Class)”，确保你的后端项目在源码层次、模块清晰度与解耦能力上达到阿里/字节大厂技术专家的审核标准。

## 三、 六大层次的单一职责铁律 (SRP) 与严酷边界清单

为了保持你这套系统终身的高解耦与高可维护性，请死死牢记并遵守以下各层次的 **“做与不做 (MUST vs MUST NOT)” 铁律**：

### 1️⃣ `controller` 层（接口接入层）
* ✅ **只做的事**：负责解析 HTTP Request Header、参数判空、提取当前的 `traceId/userId`、包装 `new SseEmitter(60000L)`，并统一处理连接异常 (`onTimeout/onError`)。
* 🚫 **严禁做的事**：**严禁在 Controller 里出现任何拼接 Prompt 的字符串！严禁在 Controller 里直接调用 `chatLanguageModel.generate()`！严禁直接写 SQL 或调用 `redisTemplate`！**

### 2️⃣ `application` 层（AI Agent 核心编排与调度层）
* ✅ **只做的事**：它是唯一的**大总管**。接收来自 Controller 的提问 -> 优先调用 `RedisSemanticCacheService.tryHitCache()` 试图走捷径 -> 如果未命中，调用 `DevOpsIntentRouter` 决定用哪个模型 -> 调起 `DevOpsAgentEngine` 启动 ReAct 循环 -> 问答完结后，通过线程池异步调起 `AgentCallLogService.recordLog()`。
* 🚫 **严禁做的事**：**编排层严禁自己去编写具体切片算法！严禁直接写工单入库 SQL！** 它只需委托给下层的 `rag` / `tools` / `biz` / `cache` 服务去干活。

### 3️⃣ `domain.rag` 层（RAG 知识检索层）
* ✅ **只做的事**：专注处理“文本切成什么样的段落”、“如何把段落生成 1536 维向量化数值”、“如何在 `PgVector` 中把 `Score < 0.73` 的垃圾段落过滤掉并把完整父段落去重返回”。
* 🚫 **严禁做的事**：**RAG 层仅仅负责向外部输出优质的、带着 `[页码与标题]` 元数据的参考文本段落，绝不干涉最终大模型如何跟用户聊天说话！**

### 4️⃣ `domain.tools` 层（安全白名单工具层）
* ✅ **只做的事**：负责大模型“长了手脚”能干的具体动作。这里所有有 `@Tool` 注解的方法必须是**纯粹的原子化能力封装**。当大模型传入 `title`, `priority`, `description` 参数时，先用 `ToolParameterValidator` 做强校验（如 `priority` 必须在枚举范围内），不通过直接抛出 Java 异常供大模型反思，通过则调用 `TicketService.save()`。
* 🚫 **严禁做的事**：**工具层内部绝不能再发起一轮新的 Agent 大总管对话循环（防止死循环爆炸）！**

### 5️⃣ `infrastructure.llm` 层（大模型底层驱动层）
* ✅ **只做的事**：负责跟外部第三方大模型厂商（DeepSeek / 阿里云百炼 / OpenAI）打交道。管理 API 密钥注入、超时配置 (`timeout = Duration.ofSeconds(30)`)、温度系数 (`temperature = 0.1`) 以及将 LangChain4j 的 `OpenAiChatModel / StreamingChatModel` 包装成标准 `@Bean` 放入 Spring 容器。
* 🚫 **严禁做的事**：**如果明天你想把 DeepSeek API 替换成私有云部署的 Qwen 或者 Azure OpenAI，全工程的所有业务代码必须一字不改！你只需要改这一层里 `AiModelConfig` 里的 Bean 构造代码！** 这就是完美的“依赖倒置与底层抽象隔离”。

## 五、 面试官高频深挖：这套架构设计为你带来的“三大核心防御底气”

如果在秋招或春招实习面试中，技术面试官问道：**“为什么你不写在一起，要花这大费周章搞出六个分层架构？这会不会过度设计？”**  
你可以直接向面试官甩出这三句满分硬核答复，瞬间镇住场面：

1. **第一句 —— 面对底层大模型快速迭代与切换时的“零成本解耦”**：  
   > “面试官您好，这绝对不是过度设计。在当下大模型大爆发时代，底层基础模型更新换代极快（如从 Qwen-Max 到 DeepSeek-V3 再到 R1）。如果将大模型 API 调用揉在业务代码层，换一次模型全工程都要重构调试。  
   > 通过把所有的模型连接、嵌入模型统一隔离在 **`infrastructure.llm` 基础设施抽象层**，上层业务逻辑层和编排层仅仅依赖于 `ChatModel` 标准抽象接口。这意味着如果哪天公司想要把外网 DeepSeek API 全部切换为内网私有部署的 Ollama 70B，我的所有核心 RAG、意图路由、工具验证层代码**一字不用改，只需修改一行底层抽象 Bean 的连接工厂**，将整体适配成本从几天降低到了 5 分钟！”

2. **第二句 —— 面对 ReAct 复杂安全攻防与参数校验时的“沙盒式隔离”**：  
   > “在企业智能运维这一高危操作领域，绝对不能允许大模型直接跨界操作数据库或宿主机。  
   > 将工具层 **`domain.tools`** 独立并赋予单一职责，我能在这个边界上精准建立防御闭环。任何大模型生成的工单参数，在触碰真实 `TicketService` 之前，都必须在 `Tool` 层先经历严格的 `Schema JSON 强校验拦截与清洗`。如果模型发疯捏造了越界的优先级，工具层立刻抛出 Java 业务异常反馈给编排层让模型反思重试，把 AI 的不确定性彻底囚禁在了下层工具的‘安全沙盒’里，确保写数据库业务逻辑层 (`domain.biz`) 永远只接收 100% 正确且结构化的数据！”

3. **第三句 —— 面对前后端联调、接口调试与多并发测试时的“极速独立可测性 (Unit Testability)”**：  
   > “采用严格的单一职责架构，彻底解决了单人或小组并行研发时‘上游依赖卡死下游’的痛点。  
   > 比如我的 `DevOpsChatController` 接入层不依赖具体实现，只依赖 `Application` 层接口。在开发头 3 天，我能直接在这一层注入 `MockAiService` 返回模拟 SSE 数据流，保证前端全栈流式打字机界面 100% 全速推进；与此同时，负责 `RAG` 层或 `IntentRouter` 的测试能够完全独立不依赖 Web 容器直接用 JUnit 发起 `pgvector` 精度自动化压测。**架构的职责分明，本质上就是对开发工期和维护风险的最强保险！**”
