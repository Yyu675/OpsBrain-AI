## 二、P0 问题（必须修复，影响核心价值主张）

### P0-1 多轮记忆只记录、从未注入模型

**问题**：6.7 三层记忆的核心承诺「多轮失忆修复」整体落空。`handleStreamChat` 加载 `memCtx`（热记忆 history + 温记忆 keyFactsText）后**仅**用于 `budgetManager.allocate()` 预算裁剪，结果被丢弃；`streamAgent` 只调 `engine.chat(query)` 传用户提问，引擎构建无任何 ChatMemory。

**证据**：
- `DevOpsAgentServiceImpl.java:159-164` — history 构建后只在 167 行传给预算
- `DevOpsAgentServiceImpl.java:287` — `TokenStream tokenStream = engine.chat(query)`（单参）
- `DevOpsAgentEngine.java:60` — `TokenStream chat(@UserMessage String userMessage)`
- grep 全项目 `ChatMemory|MessageWindowChatMemory|@MemoryId` 零命中

**触发场景**：同一 `sessionId` 连续追问第二句时，模型看不到第一轮内容。「帮我查 OOMKilled 原因」→「那这台机器怎么排查？」→ 模型不知道「这台机器」指什么。

**修复设计（决策点）**

| 决策点 | 方案 | 说明 |
| :--- | :--- | :--- |
| 记忆注入载体 | **方案A：`AiServices` 装配 `MessageWindowChatMemory` + `@MemoryId`（推荐）** vs 方案B：把 history 拼进 `@UserMessage` 文本 | A 是 LangChain4j 标准做法，`MessageWindowChatMemory.builder().id(sessionId).maxMessages(20)` 按会话隔离，随 TokenStream 流式自然生效；B 需自行转义拼接、无法与预算裁剪解耦。选 A |
| 与预算裁剪的关系 | **先裁剪后注入**：预算裁剪出的 `includedHistory` 才进 ChatMemory | 预算上限是硬约束（P99<2s），内存窗上限（20 条）是软约束，二者都要保留，裁剪在 Service 层完成 |
| keyFacts 锚点 | 以一条 `SystemMessage`/`AiMessage` 前缀注入（温记忆事实） | 关键事实是长期锚点，不随窗口滑出；注入为独立 system 消息，防止与用户轮次混排 |
| 会话 ID 映射 | `@MemoryId` 绑定 `sessionId`（非 traceId） | traceId 每请求唯一，绑定它等于无记忆；`@MemoryId` 支持 `AiServices.chatBuilder().memory(...)` 后由框架按 id 取窗口 |

**改动文件**（设计）：`DevOpsAgentEngine`（+`@MemoryId` 参数）、`AgentEngineConfig`（装配 `MessageWindowChatMemory`）、`DevOpsAgentServiceImpl.handleStreamChat/streamAgent`（把 `budgetCheck.includedHistory()` 注入引擎，keyFacts 拼入 system 消息）。

**验证**：同一 sessionId 连续两问，第二问模型能引用第一问内容；不同 sessionId 相互隔离；预算裁剪生效时超长历史仍被截断。

## 三、P1 问题（11 个，影响正确性或性能目标）

### P1-1 流式回调线程状态迁移在 REAL 模式静默失效

**问题**：`streamAgent` 的 `onToolExecuted/onCompleteResponse/onError` 调 3 参 `transition()`，内部依赖 `TraceContext`（ThreadLocal）。模型 HTTP 回调线程取不到 traceId → `transition` 返回 null 仅 WARN。MOCK 模式同步同线程迁移正常，开发期发现不了。附带缺陷：双工具场景 `TOOLS_COMPLETED→TOOLS_RUNNING` 是非法迁移。

**触发场景**：REAL 模式下状态机审计轨迹停在 `EVIDENCE_READY`，`TOOLS_RUNNING→TOOLS_COMPLETED→DRAFT_READY→SUCCESS/FAILED` 全部丢失；6.6「状态机可审计可回放」契约失效。

**修复设计**：回调 lambda 闭包已持有 traceId → 改 4 参 `transition(traceId, ...)` 显式传参（与 6.6 修复 traceId 回填同思路）；多工具迁移路径在 `AgentState` 补 `TOOLS_COMPLETED→TOOLS_RUNNING` 合法边；`AgentStateManager.transition` 内部对 TraceContext 为空时改用显式参数兜底。

### P1-2 失败工具调用被记为 SUCCESS

**问题**：L3 自愈把错误文本回传模型，`onToolExecuted` 拿到的是错误文本 → parse null → 无条件 SUCCESS 登记；`InvocationTargetException` 只解一层 → `fromException` 判 UNKNOWN 不可重试，ConnectException 等本应重试的异常永不触发 maxRetries。

**修复设计**：① 按「是否有草稿（TicketDraft）」区分成功/失败——工具返回的文本能 parse 出草稿才算 SUCCESS，否则登记 FAILED；② `InvocationTargetException` 循环解包至根因再分类（对齐 6.8「根因必须解包」契约）。

### P1-3 固定 4 线程池串行化全部会话并与记账共用

**问题**：`asyncExecutor = newFixedThreadPool(4)`，每个会话 `done.join()` 阻塞整个流式周期（数十秒），`recordLogAsync` 也走同一池。4 个长会话即占满池，与「100+ 并发 / P99<2s」目标直接冲突。

**修复设计**：拆池——会话执行用可扩缩池（`Executors.newCachedThreadPool` 或 JDK21 虚拟线程），审计记账独立小池；`done.join()` 阻塞改为回调驱动（`CompletableFuture` 组合链），避免线程占满期间被无用占用。

### P1-4 配额「单用户日限额」维度静默失效

**问题**：`CostQuotaManager.preCheck/recordUsage` 均以 `traceId` 作 userId，而 traceId 每次请求唯一 → userQuotas 永不跨请求累积，「用户日 Token/成本配额耗尽」两个拒绝分支永远走不到。单请求上限与系统日熔断仍生效，但用户维度形同虚设。

**修复设计**：引入真实用户标识（登录态/会话标识，当前可先用 sessionId 兜底）作为配额 key，traceId 仅作请求级 key。与 P1-3 关联：无真实鉴权前（P2-前端假管理员），配额 key 用 sessionId 是过渡方案，需在文档标注「待真实登录后替换」。

### P1-5 cost_rmb 恒为 0，成本链路断裂（两端报告重叠）

**问题**：`actualCost` 算出后仅传给 `quotaManager.recordUsage`，`sendCompleteEvent` 硬编码传 `0.0`，所有 `recordLogAsync` 调用点 cost 恒传 `0.0`。前端 `AIChatDrawer` 仅在 `costRmb` 为真时显示 → 成本永不展示；`sys_agent_call_log.cost_rmb` 恒 0 → 看板「7 日降本对比」「平均成本」全部失真。

**修复设计**：把 `:365-366` 算出的 `actualCost` 传入 `sendCompleteEvent` 与 `recordLogAsync`（CHAT 与 FAILED_STREAM 路径都传真实估算成本）。需核对 MOCK 模式成本估算逻辑，确保非 0 且有语义。

### P1-6 DashboardServiceImpl 返回演示数据 + 吞异常回假数据

**问题**：`totalQueries < 5` 返回编造的 250 查询/89 命中/42 工单/qwen 分布；任何 SQL 异常 catch 吞掉后也返回同一份假数据（HTTP 200）——DB 宕机时看板显示「健康且数字饱满」。演示模型名 `qwen-turbo` 在真实路由不存在。与 6.13「假数据以真实数据呈现」同缺陷定性。

**修复设计**：移除演示数据兜底。数据不足时返回真实 0 值与 `isEmpty` 标记，前端据此显示空态；异常向上抛（经全局异常处理返回错误码），禁止吞异常回假数据。删除 `:59-61` 失效注释（注释描述的反模式正是代码仍在执行的）。

### P1-7 健康检查端点无认证，可被匿名刷成本

**问题**：`GET /api/v1/health/ai-model` 直接 `turboModel.chat("ping")` + `reasonerModel.chat("ping")` + `embeddingModel.embed("test")`，无任何鉴权/限流。REAL 模式每次请求触发 2 次付费 LLM + 1 次 embedding，可被匿名刷成本/DoS。

**修复设计**：加认证（限定 admin/内部网段）+ 限流；或 REAL 模式默认禁用仅保留 `/ping`。同时补 `health/db`（`SELECT 1`）与 `health/redis`（ping）真实探测——现 javadoc 声称的 pgvector 检查实际不存在，`/ping` 恒 UP。

### P1-8 Dashboard 前后端字段契约不一致

**问题**：前端 `DashboardOverview` 期望 `cacheHitRate/avgCostRmb/modelDistribution:[{name,value}]`；后端 `DashboardOverviewDTO` 返回 `modelDistribution:[{model,count,percentage}]`、`costSavingsChart`，且从不返回 `cacheHitRate/avgCostRmb`。逐字段比对无一对齐。

**修复设计**：以 Schema-First 双端统一。建议后端补 `cacheHitRate`/`avgCostRmb`（看板价值主张字段，成本链 P1-5 修复后才有真实值），前端 `modelDistribution` 类型对齐后端 `{model,count,percentage}`，前端类型补 `costSavingsChart`。

### P1-9 遗留摄入路径写 doc_id=NULL 孤儿切片

**问题**：`/api/v1/knowledge/ingest` 仍是活入口，`buildChunkEntities` 不写 `doc_id`。这类切片逃脱 6.21 生命周期治理：`deprecate/purge` 只按 doc_id 删向量，孤儿切片永远残留且 status='ACTIVE' 持续被检索命中。与文档 CRUD 并行写同一张表，绕过去重/版本/生命周期。

### P1-10 init.sql 与 v9 迁移去重索引漂移（✅ 经核实已解决，无代码改动）

**核实结论（2026-08-12 批次 3 调查）**：
