## 一、调研结论（先纠正过期前提）

### 1.1 PRD 覆盖度表已过期

`PRD.md` §三 的覆盖度评估写于 6.32 之前，与当前代码不符。逐项核实后的真实状态：

| 阶段 | PRD 说法 | 代码实际现状 | 结论 |
| :--- | :--- | :--- | :---: |
| 1 监控告警 | ❌ 无，L2 规划中 | ✅ 6.34/6.35 已落地：Alertmanager Webhook → SHA-256 去重 → 持久化 → 自动建单 → WebSocket 实时推送 | **PRD 过期** |
| 2 发现建单 | ✅ 双入口 | ✅ 三入口（AI 对话 / 手动表单 / 告警自动） | 一致 |
| 3 首响派单 | ⚠️ 无 SLA 超时升级 | ⚠️ 有派单（`assignee` + 名录后端化 6.36），**无首响概念** | 一致 |
| 4 现场处置 | ⚠️ 无止损/修复引导 | ⚠️ 有回复/状态/AI 分析，**无处置动作留痕** | 一致 |
| 5 根因分析 | ❌ 无 RCA | ⚠️ AI 分析已结构化持久化（6.40 策略 B：reasons/commands/confidence/citations + 多版本 + 反馈），**但缺"确认根因"** | **PRD 偏保守** |
| 6 修复验证 | ❌ 无验证步骤 | ❌ 确认无任何字段 | 一致 |
| 7 复盘归档 | ✅ 已打通 | ⚠️ `KnowledgeSinkDrawer` 可转知识库，**无复盘结构化字段** | **PRD 偏乐观** |

**含义**：PRD 规划的"第二阶段 L1.8 告警接入"实质已完成大半。真正缺口比 PRD 描述的更窄：**首响、处置留痕、根因确认、修复验证、复盘结构**五项。

### 1.2 阻塞性前置缺陷：优先级只有 3 档

PRD §2.3 要求四档首响 SLA（P0 15min / P1 30min / P2 4h / P3 24h），但代码：

```
后端 TicketEnums.Priority.ALL = { HIGH, MEDIUM, LOW }            ← 3 档
前端 TicketPriority = urgent | high | medium | low                ← 4 档
mapFrontendPriorityToBackend: urgent → HIGH, high → HIGH          ← 塌缩
mapBackendPriorityToFrontend: HIGH → urgent                       ← 回读恒为 urgent
```

**这是一个正在生效的数据缺陷**：用户选「高」，保存后回读变「紧急」——`high` 档事实上不存在。库中 3 张工单全为 `HIGH` 即此现象。

**不修则分级首响 SLA 无法实现**，故列为闭环的前置任务（P0-0）。

### 1.3 告警侧已有首响模型，工单侧缺失且未接出

`Alert` 实体已有 `ACKNOWLEDGED` 状态 + `acknowledged_at` 字段（语义即首响确认），但：
- `AlertWebhookController` 只有 1 个 `@PostMapping`（webhook 接收），**确认能力已定义但无端点可调**
- 工单侧完全没有首响概念

**设计原则**：工单首响与告警确认应共用同一语义，不各造一套。

## 二、用户已拍板的三项架构决策

| # | 决策点 | 用户选择 | 落地含义 |
| :---: | :--- | :--- | :--- |
| D1 | 优先级分档 | **后端改四档 P0/P1/P2/P3** | 对齐 PRD §2.3 与告警侧 P0~P4；存量迁移 HIGH→P1 / MEDIUM→P2 / LOW→P3；消除塌缩 |
| D2 | 处置阶段建模 | **主状态不变 + 新增「处置阶段」字段** | 不动已验证的 5 态状态机（不破坏 6.9~6.16 的乐观锁/活动流/统计口径），另加 `handling_stage`；前端两级展示 |
| D3 | 修复验证强制度 | **必填，但允许带理由跳过** | 转 RESOLVED 须填验证信息，或显式「跳过验证」+ 强制理由（同 6.21 `purge` 的 `complianceReason` 做法）；MTTR 只统计已验证工单 |

**D1 影响面实测**：`priority` 字面量分布在 9 个 Java 文件、38 处；库中仅 3 行数据（全 HIGH），迁移成本极低——**现在改是最佳时机**。

## 三、数据模型设计

### 3.1 优先级四档（D1）

```java
// TicketEnums.Priority 改造
public static final String P0 = "P0";   // 紧急：生产宕机 / 核心业务不可用
public static final String P1 = "P1";   // 高：影响业务但有临时方案
public static final String P2 = "P2";   // 中：需处理但不紧急
public static final String P3 = "P3";   // 低：优化建议
public static final Set<String> ALL = Set.of(P0, P1, P2, P3);
```

**SLA 时限表**（单一来源，后端定义）：

| 优先级 | 首响时限 | 解决时限 | 对应 PRD |
| :---: | :---: | :---: | :--- |
| P0 | 15 分钟 | 4 小时 | ✅ §2.3 |
| P1 | 30 分钟 | 8 小时 | ✅ §2.3 |
| P2 | 4 小时 | 24 小时 | ✅ §2.3 |
| P3 | 24 小时 | 72 小时 | ✅ §2.3 |

**前端映射**：`urgent↔P0 / high↔P1 / medium↔P2 / low↔P3`，一一对应无塌缩。

**兼容与迁移**：
- 迁移 SQL：`UPDATE ... SET priority='P1' WHERE priority='HIGH'` 等（幂等，带 `WHERE priority IN ('HIGH','MEDIUM','LOW')` 守卫）
- `normalizePriority()` 保留对旧值的容错映射（旧客户端/AI 工具传 `HIGH` 仍可用，日志 WARN）
- `ToolParameterValidator` 提示词改为 `[P0, P1, P2, P3]`，同时接受旧值
- 排序权重 `CASE priority WHEN 'P0' THEN 1 ... END`（6.37 已建立此模式）

### 3.2 工单主表扩展（migration_v16）

```sql
ALTER TABLE sys_devops_ticket
  -- 阶段 3 首响
  ADD COLUMN IF NOT EXISTS first_response_at    TIMESTAMP,      -- 首次响应时刻（NULL=未首响）
  ADD COLUMN IF NOT EXISTS first_responder      VARCHAR(64),    -- 首响人
  ADD COLUMN IF NOT EXISTS response_deadline    TIMESTAMP,      -- 首响截止（建单时按优先级派生）
  ADD COLUMN IF NOT EXISTS resolve_deadline     TIMESTAMP,      -- 解决截止（建单时派生）
  ADD COLUMN IF NOT EXISTS response_breached    BOOLEAN DEFAULT FALSE,  -- 首响是否超时
  ADD COLUMN IF NOT EXISTS escalated_at         TIMESTAMP,      -- 升级时刻
  ADD COLUMN IF NOT EXISTS escalate_reason      VARCHAR(255),
  -- 阶段 4 处置阶段（D2）
  ADD COLUMN IF NOT EXISTS handling_stage       VARCHAR(24),    -- TRIAGE/MITIGATED/FIXING/VERIFYING
  ADD COLUMN IF NOT EXISTS mitigated_at         TIMESTAMP,      -- 止损完成时刻（业务恢复）
  -- 阶段 5 根因
  ADD COLUMN IF NOT EXISTS root_cause           TEXT,           -- 人工确认的根因（≠AI 建议）
  ADD COLUMN IF NOT EXISTS root_cause_category  VARCHAR(32),    -- 根因分类（见 3.5）
  ADD COLUMN IF NOT EXISTS root_cause_by        VARCHAR(64),
  ADD COLUMN IF NOT EXISTS root_cause_at        TIMESTAMP,
  -- 阶段 6 修复验证（D3）
  ADD COLUMN IF NOT EXISTS verified_at          TIMESTAMP,      -- 验证通过时刻（MTTR 终点）
  ADD COLUMN IF NOT EXISTS verifier             VARCHAR(64),
  ADD COLUMN IF NOT EXISTS verify_method        VARCHAR(32),    -- MONITOR/LOG/BUSINESS/MANUAL
  ADD COLUMN IF NOT EXISTS verify_conclusion    TEXT,
  ADD COLUMN IF NOT EXISTS verify_skipped       BOOLEAN DEFAULT FALSE,
  ADD COLUMN IF NOT EXISTS verify_skip_reason   VARCHAR(255);   -- 跳过时强制填写
```

**为何 deadline 存字段而非每次计算**：
- SLA 时限表可能随策略调整，若每次按当前表计算，历史工单的截止时间会被"追溯改写"——考核数据必须冻结在建单时刻的口径
- 便于 SQL 直接查「即将超时」清单（`WHERE response_deadline < NOW() + INTERVAL '5 min' AND first_response_at IS NULL`），无需应用层遍历

### 3.3 处置动作记录表（阶段 4 留痕）

```sql
CREATE TABLE IF NOT EXISTS sys_ticket_action (
    id           BIGSERIAL PRIMARY KEY,
    ticket_id    VARCHAR(64)  NOT NULL,
    action_type  VARCHAR(24)  NOT NULL,  -- MITIGATE止损/INVESTIGATE排查/FIX修复/ROLLBACK回滚/VERIFY验证
    summary      VARCHAR(255) NOT NULL,  -- 做了什么（一句话）
    detail       TEXT,                   -- 命令/配置/日志片段
    operator     VARCHAR(64)  NOT NULL,
    effective    BOOLEAN,                -- 是否有效（NULL=未判定）——失败尝试同样有价值
    started_at   TIMESTAMP,
    finished_at  TIMESTAMP,
    create_time  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_ticket_action_ticket ON sys_ticket_action (ticket_id, create_time);
```

**关键设计：`effective` 允许为假**。PRD §2.1 阶段 4 指出排查定位占 40% 耗时且严重依赖经验——**失败的尝试恰恰是最有价值的经验**（"我试过重启，没用"避免后人重走弯路）。只记成功动作等于丢弃 60% 的知识。

### 3.4 复盘归档表（阶段 7）

```sql
CREATE TABLE IF NOT EXISTS sys_ticket_postmortem (
    id              BIGSERIAL PRIMARY KEY,
    ticket_id       VARCHAR(64) NOT NULL,
    timeline        TEXT,                -- 时间线（可由 action + reply 自动生成草稿）
    impact_scope    VARCHAR(255),        -- 影响范围
    impact_duration INT,                 -- 影响时长（分钟）
    lessons         TEXT,                -- 经验教训
    doc_id          BIGINT,              -- 已转知识库文档 ID（来源回链）
    author          VARCHAR(64),
    create_time     TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time     TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 改进项独立成表：一次复盘可有多条改进，各有责任人与截止日，需独立跟踪
CREATE TABLE IF NOT EXISTS sys_postmortem_action_item (
    id             BIGSERIAL PRIMARY KEY,
    postmortem_id  BIGINT       NOT NULL,
    ticket_id      VARCHAR(64)  NOT NULL,   -- 冗余便于按工单直查
    content        VARCHAR(500) NOT NULL,
    owner          VARCHAR(64),
    due_date       DATE,
    status         VARCHAR(16) NOT NULL DEFAULT 'OPEN',  -- OPEN/DOING/DONE/DROPPED
    create_time    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

**为何改进项独立成表**：PRD §2.1 阶段 7 指出"这一步最容易被忽视……相同的故障在不同团队反复发生"。改进项若只是复盘文档里的一段文字，就无法查询「所有逾期未完成的改进项」——**不可查询 = 不会被跟踪 = 等于没写**。

### 3.5 根因分类词表

供聚合分析「哪类根因最多」，指导系统性改进：

`CONFIG`配置错误 / `CAPACITY`容量不足 / `CODE`代码缺陷 / `DEPENDENCY`依赖故障 / `NETWORK`网络问题 / `DATA`数据异常 / `HUMAN`人为操作 / `EXTERNAL`外部服务 / `UNKNOWN`未定位

## 四、状态机与阶段流转

### 4.1 双层模型（D2）

```
主状态（status，5 态不变）        处置阶段（handling_stage，仅 PROCESSING 期间有效）
─────────────────────────        ──────────────────────────────────────────
PENDING    待处理                 （空）
   ↓ 首响（记 first_response_at）
PROCESSING 处理中        ──→      TRIAGE     排查中
                         ──→      MITIGATED  已止损（业务已恢复，根因待查）
                         ──→      FIXING     修复中
                         ──→      VERIFYING  验证中
   ↓ 验证通过 / 带理由跳过
RESOLVED   已解决                 （空，verified_at 已写）
   ↓
CLOSED     已关闭（复盘归档后）
VOID       已作废（Saga 补偿）
```

**阶段流转规则**：
- `handling_stage` 仅在 `status=PROCESSING` 时有意义；转出 PROCESSING 时清空
- 阶段可**跳跃与回退**（排查中直接止损、修复后验证失败退回 FIXING）——真实运维不是线性的，强制线性会让用户绕过系统
- `MITIGATED` 是关键里程碑：**业务已恢复但根因未定位**。这是 SRE 实践中最常见的中间态，也是 MTTR 与 MTTD 分离统计的依据

### 4.2 首响判定（阶段 3）

**触发首响的动作**（任一即可，取最早时刻）：
1. 状态 `PENDING → PROCESSING`
2. 首次添加回复（`role != 'ai'`——AI 自动分析不算人工首响）
3. 首次记录处置动作
4. 显式点击「确认接单」

**为何 AI 回复不算首响**：AI 分析在建单时自动触发（6.39），若计入则每张工单建单即"已首响"，首响 SLA 形同虚设——这与 6.24 P1-4「配额 key 用 traceId 导致永不累积」是同一类"指标被自动行为稀释"的错误。

### 4.3 MTTR 口径（D3）

```
MTTA (Acknowledge) = first_response_at - create_time     首响耗时
MTTM (Mitigate)    = mitigated_at      - create_time     止损耗时（业务恢复）
MTTR (Resolve)     = verified_at       - create_time     解决耗时（验证通过）
```

**MTTR 只统计 `verify_skipped = false` 的工单**。跳过验证的工单不计入 MTTR，另列「跳过验证率」指标——否则"点一下已解决"就能刷低 MTTR，考核数据失真。这遵循 6.41 已确立的契约：**KPI 统计口径必须与标签语义一致**。

## 五、接口设计

```
# 阶段 3 首响/派单
POST   /api/v1/tickets/{id}/acknowledge      确认接单（记首响）
POST   /api/v1/tickets/{id}/escalate         升级（记 escalated_at + 理由）
GET    /api/v1/tickets/sla/at-risk           即将超时清单（首响/解决分别列）

# 阶段 4 现场处置
POST   /api/v1/tickets/{id}/actions          记录处置动作
GET    /api/v1/tickets/{id}/actions          动作列表
PATCH  /api/v1/tickets/{id}/stage            切换处置阶段
POST   /api/v1/tickets/{id}/mitigate         标记已止损（记 mitigated_at）

# 阶段 5 根因
PUT    /api/v1/tickets/{id}/root-cause       确认根因（含分类）
GET    /api/v1/tickets/root-cause/stats      根因分类聚合（改进决策依据）

# 阶段 6 修复验证
POST   /api/v1/tickets/{id}/verify           提交验证（通过则转 RESOLVED）
POST   /api/v1/tickets/{id}/verify/skip      跳过验证（强制 reason）

# 阶段 7 复盘归档
GET    /api/v1/tickets/{id}/postmortem       复盘详情
PUT    /api/v1/tickets/{id}/postmortem       保存复盘
POST   /api/v1/tickets/{id}/postmortem/draft AI 生成复盘草稿（基于 action+reply+AI分析）
GET    /api/v1/postmortem/action-items       改进项清单（支持 status/owner/逾期筛选）
PATCH  /api/v1/postmortem/action-items/{id}  更新改进项状态

# 闭环度量
GET    /api/v1/tickets/metrics/closure       MTTA/MTTM/MTTR + 各阶段完成率 + 跳过验证率
```

**契约遵循**：
- 所有写操作走 `TicketService` 单点（6.10 Single Writer），带乐观锁 `version`（6.11）
- 每个阶段动作自动记活动流（6.12），前端只读不写
- 工单物理删除级联清理 action/postmortem/action_item（6.9 契约）

## 八、需持续遵守的既有契约

本设计已对齐以下已立契约，实施时不得违反：

- **6.6 审计铁律**：任何终止路径落 `sys_agent_call_log`
- **6.9 部分成功如实上报**：批量操作返回成功数
- **6.10 Single Writer**：工具产草稿，编排层单点落库
- **6.11 乐观锁**：写操作回传 `version`，冲突 40009 不静默吞
- **6.12 活动流后端单点写**：前端只读
- **6.13 前端不得凭其他字段派生展示数据**
- **6.15 派生字段在后端算**：SLA/MTTR 等不在前端重复实现
- **6.20 配置项必须有代码读取**
- **6.41 KPI 口径必须与标签语义一致**：MTTR 排除跳过验证的工单
- **6.42 未落地能力诚实占位**：不造假数据
