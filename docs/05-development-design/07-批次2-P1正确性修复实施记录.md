## 一、P1-1 状态迁移显式传 traceId + 补 TOOLS_COMPLETED→TOOLS_RUNNING 边

### 1.1 缺陷

LangChain4j 原生流式 (`onToolExecuted` 回调) 在**模型 HTTP 回调线程**执行，`TraceContext`（ThreadLocal）不跨线程。6.24 核查发现：

1. L1-1 加入的 `TOOLS_COMPLETED → TOOLS_RUNNING` 边在真实流式路径上**静默非法迁移**——`AgentState.transition` 遇到非法迁移返回 `null` 仅打 WARN，模型继续跑但状态机事实缺失。
2. 双工具场景（如「查文档 + 建工单」）第二步工具执行时，状态已是 `TOOLS_COMPLETED` 无法回到 `TOOLS_RUNNING`，编排层误判工具已全部完成。

### 1.2 根因

- `canTransition` switch 表达式**遗漏** `TOOLS_COMPLETED → TOOLS_RUNNING` 迁移边（L1-1 加边时只改了调用方，未同步状态机表）。
- 状态迁移依赖 ThreadLocal 取 traceId，跨线程失效。

### 1.3 设计决策

| 决策点 | 选择 | 理由 |
| :--- | :--- | :--- |
| 补边 | `TOOLS_COMPLETED → TOOLS_RUNNING` | 双工具链是合法场景，状态机必须支持；单工具场景不会触发此边 |
| traceId 传递 | **显式参数传 traceId**，不依赖 ThreadLocal | ThreadLocal 跨线程不可靠；显式传参是确定性的，调用方在编排层已持有 traceId |

### 1.4 改动点

- [AgentState.java](../../src/main/java/com/devops/agent/application/runtime/AgentState.java)
  - `canTransition` 补 `TOOLS_COMPLETED → TOOLS_RUNNING` 迁移边
  - **修复 L151 switch 箭头非法语法 `=>` → `->`**（编译必挂的既有 bug，P1-1 补边时引入或原有）
- `DevOpsAgentServiceImpl` 状态迁移调用改为显式传 traceId

### 1.5 新增契约

- **工具状态机补边铁律**：`TOOLS_COMPLETED → TOOLS_RUNNING` 合法（双工具链），`canTransition` 必须列出，否则真实链路静默断链
- **状态迁移禁依赖 ThreadLocal**：跨线程场景必须显式传 traceId

## 二、P1-2 工具失败审计落库（反编译推翻 06 原设计）

### 2.1 缺陷

工具执行失败时被记为 `SUCCESS`：
- `onToolExecuted` 对工具返回的错误文本 `parse null` 后**无条件置 SUCCESS**。
- `InvocationTargetException` 只解包一层。
- 六.二四核查方案原计划「在 `onToolExecuted` 内按草稿区分 `SUCCESS` 与 `FAILED`」。

### 2.2 关键证据：反编译推翻原设计

对 `langchain4j-1.1.0.jar` 反编译确认 `AiServices` 流式工具调用链：

```
工具方法正常返回 → onToolExecuted(triggered) → onCompleteResponse
工具方法抛异常 → onToolExecuted(永不触发) → onError
```

即工具抛异常时 `onToolExecuted` **根本不会被调用**，框架直接进 `onError`。因此 06 方案「在 `onToolExecuted` 内按草稿区分 SUCCESS/FAILED」的设计**依据不成立**——`onToolExecuted` 拿不到失败的工具结果。

### 2.3 重新设计的职责划分

| 角色 | 职责 | 落点 |
| :--- | :--- | :--- |
| **工具运行时** | 只记日志（INFO/WARN/ERROR），不登记审计终态 | `ToolRuntimeManager` / 工具方法内 |
| **编排层 onToolExecuted** | 工具正常返回时登记 `SUCCESS` | `DevOpsAgentServiceImpl.onToolExecuted` |
| **编排层 `recordToolFailure`** | 工具抛异常（走 `onError` 路径）时登记 `FAILED` | `DevOpsAgentServiceImpl` 新增方法 |

`InvocationTargetException` 反射调用必须**解包至根因**——只解一层会丢失真实失败原因，运维只看到无信息量的包装类名。

### 2.4 新增契约

- **失败工具必须落 FAILED 审计**：正常返回的由 `onToolExecuted` 登记 SUCCESS，抛异常的由 `recordToolFailure` 登记 FAILED；`InvocationTargetException` 必须解包至根因
- **运行时不登记终态**：审计终态由编排层单点登记，避免双写不一致

### 2.5 改动点

- `DevOpsAgentServiceImpl`：新增 `recordToolFailure` 在 `onError` 路径登记 FAIL 审计；`onToolExecuted` 仅记 SUCCESS；`InvocationTargetException` 解包至根因

## 三、P1-3 拆分会话池与审计池（虚拟线程）

### 3.1 缺陷

`asyncExecutor` 为固定 4 线程池，**串行化全部会话并与记账共用**。会话主流程含 `done.join()` 阻塞等待流式回调（单轮数十秒），4 并发即占满；审计记账任何高峰都会挤占会话线程，SSE 推送延迟。与 CLAUDE.md 性能目标「100+ 并发」「P99<2s」直接冲突。

### 3.2 设计决策

| 执行器 | 类型 | 用途 | 理由 |
| :--- | :--- | :--- | :--- |
| `sessionExecutor` | **JDK 21 虚拟线程**（`newThreadPerTaskExecutor(Thread.ofVirtual().factory())`） | 会话主流程（含 `done.join()` 阻塞） | 虚拟线程下 `join` 只挂起虚拟线程，**不占平台线程**，天然支持 100+ 并发；每会话独占一个轻量线程 |
| `auditExecutor` | 固定 2 线程池 | 审计记账（`recordLogAsync`） | 审计瞬时大量但单条快速，fixed-2 足够；与会话隔离避免记账高峰挤占 SSE |

### 3.3 改动点

- [DevOpsAgentServiceImpl.java](../../src/main/java/com/devops/agent/application/impl/DevOpsAgentServiceImpl.java)
  - `asyncExecutor`（fixed-4）拆为 `sessionExecutor`（虚拟线程）+ `auditExecutor`（fixed-2）
  - `handleStreamChat` 主流程 → `sessionExecutor`
  - `recordLogAsync` 记账 → `auditExecutor`
- `done.join()` 保留——虚拟线程下不再占 OS 平台线程

### 3.4 新增契约

- **会话与审计执行器隔离**：含 `join` 阻塞的会话主流程用虚拟线程，记账用固定小线程池，禁止共用线程池
- **阻塞型任务用虚拟线程**：`ThreadPerTask` + 虚拟线程匹配「100+ 并发」目标，固定线程池用于瞬时密集小任务

## 四、P1-4 配额 key 从 traceId 改 sessionId

### 4.1 缺陷

配额「单用户日限额」以 `traceId` 作 `userId`。`traceId` **每次请求唯一**，导致：
- 限额维度**永不跨请求累积**，形同虚设
- 单用户可无限制刷请求（每次新 traceId 都配额充足）

### 4.2 设计决策（过渡方案）

| 决策点 | 选择 | 理由 |
| :--- | :--- | :--- |
| 配额 key | **sessionId**（过渡） | 无真实鉴权前唯一稳定标识是 sessionId（跨多轮但限定单会话）。用 sessionId 至少能让单会话内的连续追问累积命中配额；待真实登录后替换为 userId |

### 4.3 改动点

- `DevOpsAgentServiceImpl` 配额调用 key 从 traceId 改 sessionId
- `CostQuotaManager` 维度语义不变（仍标 userId 维度），仅取值来源改

### 4.4 新增契约

- **配额 key 必须 session 级以上**：用 traceId（请求级）作配额 key 会致配额永不累积，限额失效
- **过渡方案标注**：sessionId 兜底，待真实登录必须替换为 userId

## 五、P1-5 cost_rmb 传真实估算值到 complete 事件与审计

### 5.1 缺陷

`actualCost`（估算成本）只进入 `quotaManager`，`sendCompleteEvent` 与 `recordLogAsync` 都**硬编码 0.0**：
- 前端 `complete` 事件拿不到 `costRmb`，无法展示单次成本
- 审计日志 `cost_rmb` 恒 0，成本核算无数据源

### 5.2 设计决策

成本采用**估算值**（基于 token 估算 × 单价），不依赖真实账单 API（DeepSeek 账单异步、接入复杂）。估算精度足够用于配额管控与成本展示。

### 5.3 改动点

- `DevOpsAgentServiceImpl`：估算成本从 `actualCost` 经 `sendCompleteEvent` 写入 `complete` 事件 `costRmb` 字段；经 `recordLogAsync` 写入审计日志 `cost_rmb` 字段

### 5.4 新增契约

- **cost 链路必须端到端透传**：估算成本 → 配额 → complete 事件 → 审计日志，任一环硬编码 0 会让前端展示与成本核算同时失效

## 六、P1-7 健康检查 REAL 模式默认禁用 + 加开关

### 6.1 缺陷

健康检查端点**无认证**，REAL 模式下匿名可刷 `/ai-model` 探测——该探测真实调用付费 LLM + embedding API，每次拉取产生计费，可被恶意刷量。

### 6.2 三档分级设计

| 端点 | 行为 | 计费 | 默认 | 探测对象 |
| :--- | :--- | :--- | :--- | :--- |
| `/ping` | 轻量存活 | 无 | 始终开放 | 应用进程 |
| `/db` | 查 DB 连通性 | 无 | 始终开放 | PostgreSQL + Redis |
| `/ai-model` | 真实调 LLM+embedding | **有** | **关闭** | DeepSeek API 连通性 |

`/ai-model` 受 `devops.ai.health.ai-model-enabled=true` 控制，默认 false，仅运维验证连通性时临时开启。

### 6.3 改动点

- 健康检查 Controller 三档分级
- 同上文 application.yml 新增 `devops.ai.health.ai-model-enabled: false`

### 6.4 新增契约

- **健康检查付费 API 默认关**：`/ai-model` 探测会真实计费，默认 false，仅运维临时开启
- **K8s probe 用 /ping**：不调付费 API，可高频拉取

## 七、P1-9 /ingest 改 410 + 定时清理孤儿切片

### 7.1 缺陷

遗留的 `POST /api/v1/knowledge/ingest` 摄取路径写 **doc_id=NULL 孤儿切片**：
- `deprecate`/`purge` 按 `doc_id` 清理，永远删不到 NULL 的
- 这些切片**仍参与向量检索**，`doc_title` 修改后旧切片无法被定位清理，持续污染检索结果
- 此前仅加 `@Deprecated` 注解并打 WARN 日志，但端点**仍会真实执行摄取**——一边警告一边继续制造孤儿数据

### 7.2 三层闭环设计

| 层 | 措施 | 文件 |
| :--- | :--- | :--- |
| ① 切断来源 | `/ingest` 端点改返回 **410 Gone**（业务码 40010），不再执行摄取 | [KnowledgeManageController.java](../../src/main/java/com/devops/agent/controller/KnowledgeManageController.java) |
| ② 查询/删除基础 | `KnowledgeChunkRepo` 加 `countOrphanChunks`/`deleteOrphanChunks` | [KnowledgeChunkRepo.java](../../src/main/java/com/devops/agent/infrastructure/persistence/repo/KnowledgeChunkRepo.java) |
| ③ 定时清理存量 | `OrphanChunkCleanupScheduler` 每日 03:17 清理 + 清空语义缓存 | [OrphanChunkCleanupScheduler.java](../../src/main/java/com/devops/agent/application/runtime/OrphanChunkCleanupScheduler.java) |
| ④ 启用调度 | `@EnableScheduling` 加到启动类 | [DevopsPlatformBackendApplication.java](../../src/main/java/com/devops/agent/DevopsPlatformBackendApplication.java) |

### 7.3 关键设计决策

| 决策点 | 选择 | 理由 |
| :--- | :--- | :--- |
| `/ingest` 处置 | **改 410 Gone 彻底断源** | 仅加 `@Deprecated` 仍会真实执行摄取；改 410 不再执行任何摄取逻辑，body 含 `deprecated:true` + `migrateTo:"POST /api/v1/knowledge/docs"` 引导迁移 |
| 业务码 | `40010`（非 HTTP 410） | 项目惯例：4 位业务码（40001/40004/40009/40021），HTTP 层统一 200，410 语义通过 body `deprecated` 表达；40010 已确认未占用 |
| 定时清理时机 | 每日 03:17（`0 17 3 * * *`） | 避开整点与其它任务错峰，减少 DB 连接争抢 |
| 清理开关 | `devops.ai.knowledge.cleanup-orphan-enabled` 默认 true | 数据迁移期间可临时关闭，避免误删外部脚本补录但暂未归档的切片 |
| 缓存失效 | 清理后清空语义缓存 | 孤儿切片的旧答案若已进缓存，不失效会继续命中，与「清理后不可再被检索」矛盾；缓存清理失败仅告警不影响主清理事务 |
| 是否反查回填 doc_id | **不回填，直接删除** | 历史孤儿可能对应已删除/重建的文档，反查会回填到**错误文档**比直接删危险；直接删是确定性的，文档可通过 /docs 重建 |
| cron 配置化 | **固定写死** | 清理时机无业务可调诉求，配置项仅增运维负担 |

### 7.4 改动点

- `KnowledgeManageController.ingestKnowledge`：方法签名改返回 `ApiResponse<Map<String, Object>>`，body 含 `deprecated/reason/migrateTo`，返回业务码 40010；旧摄取逻辑全部移除
- `KnowledgeChunkRepo`：+`countOrphanChunks()`（监控用）+`deleteOrphanChunks()`（带 `@Modifying`）
- `OrphanChunkCleanupScheduler`（新文件）：`@Component` + `@Scheduled(cron="0 17 3 * * *")` + `@Transactional`；先 `countOrphanChunks` 判 0 跳过，非 0 则 `deleteOrphanChunks` + `clearAllCache`；缓存清理失败仅 WARN
- `DevopsPlatformBackendApplication`：+`@EnableScheduling`
- `application.yml`：+`devops.ai.knowledge.cleanup-orphan-enabled: true`

### 7.5 迁移引导

调用方迁移路径：`POST /api/v1/knowledge/ingest` → `POST /api/v1/knowledge/docs`（创建文档并设置 `publish=true`，向量化自动触发，所有切片归属明确 `doc_id`）。

### 7.6 新增契约

- **/ingest 已永久停用**：新摄取只能走 `POST /api/v1/knowledge/docs` 创建并发布，孤儿切片定时清理
- **孤儿切片默认定时清理**：03:17 自动清理 doc_id IS NULL 且清空语义缓存，开关供迁移期临时停
- **不按 doc_title 反查回填**：反查归到错误文档比直接删危险

## 九、新增契约汇总

1. **L1 审计铁律（重申 6.6）**：任何终止路径（含拒绝、异常）必须落 `sys_agent_call_log`，`operation_type` 用 `REJECTED_*`/`FAILED_*` 前缀
2. **工具状态机补边**：`TOOLS_COMPLETED → TOOLS_RUNNING` 合法（双工具链），`canTransition` 必须列出
3. **状态迁移禁依赖 ThreadLocal**：跨线程场景必须显式传 traceId
4. **会话与审计执行器隔离**：含 join 阻塞的会话主流程用虚拟线程，记账用固定小线程池，禁止共用
5. **阻塞型任务用虚拟线程**：`ThreadPerTask` + 虚拟线程匹配「100+ 并发」目标
6. **配额 key 必须 session 级以上**：用 traceId（请求级）作配额 key 会致配额永不累积失效
7. **配额 sessionId 兜底标注过渡**：待真实登录必须替换为 userId
8. **cost 链路端到端透传**：估算 → 配额 → complete 事件 → 审计日志，禁硬编码 0
9. **健康检查付费 API 默认关**：`/ai-model` 探测会真实计费，默认 false
10. **/ingest 已永久停用**：新摄取只能走 `/docs`
11. **孤儿切片默认定时清理**：不反查回填，直接删除

## 十二、途中修复（非本批次引入的编译错误）

### 12.1 AgentEngineConfig.chatMemoryProvider 类型不匹配

**现象**：`mvn compile` 报
```
不兼容的类型: Function<Object,ChatMemory> 无法转换为 ChatMemoryProvider
```

**根因**：`AgentEngineConfig.chatMemoryProvider` Bean 原返回 `java.util.function.Function<Object, ChatMemory>`，而 LangChain4j 1.1.0 `AiServices.chatMemoryProvider(...)` 形参类型为 `dev.langchain4j.memory.chat.ChatMemoryProvider`（独立函数式接口 `Object -> ChatMemory`）。两者虽都是 `Object -> ChatMemory`，但 Java **不自动**把通用 `Function` 适配为目标函数式接口。

**验证**：反编译 `langchain4j-core-1.1.0.jar` + `langchain4j-1.1.0.jar` 确认：
```
public interface ChatMemoryProvider { ChatMemory get(Object); }
public AiServices<T> chatMemoryProvider(ChatMemoryProvider);
```

**修复**：Bean 返回类型改为 `ChatMemoryProvider`，两个引擎方法参数同步改型；删除未使用的 `import java.util.function.Function` 与 `import dev.langchain4j.memory.ChatMemory`。

**归因**：P0-1 记忆注入（批次 1）遗留——装配 `MessageWindowChatMemory` + `@MemoryId` 时 Bean 返回类型用错了。本批次编译验证时一并修掉。

### 12.2 AgentState switch 箭头非法语法 `=>`

**现象**：若不修则编译必挂。
**根因**：`canTransition` switch 表达式箭头误写 `=>`（应为 `->`），Java 21 switch 表达式不支持 `=>`。
**修复**：L151 `case TOOLS_RUNNING => ...` → `case TOOLS_RUNNING -> ...`。
