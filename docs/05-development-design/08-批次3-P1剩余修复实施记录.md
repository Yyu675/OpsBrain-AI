## 一、P1-10 init.sql 与 v9 迁移去重索引漂移 — 经核实已解决，无代码改动

### 1.1 06 方案的原始陈述

06-模块核查设计修复方案对 P1-10 的原始描述（现已修正）：

> 「init.sql:289 仍建全表唯一索引 `uk_doc_hash`，v9 迁移已改部分唯一 `uk_doc_hash_active`，二者漂移，全新部署会重新引入『回滚撞唯一索引→500』。需全面核查 init.sql 与 v2~v10 全部迁移漂移。」

含三条具体陈述：
1. init.sql:289 仍是**全表唯一索引**
2. v9 迁移改用的是名为 `uk_doc_hash_active` 的部分唯一索引
3. 全新部署会重新引入「回滚撞唯一索引→500」缺陷

### 1.2 逐条核实（2026-08-12 批次 3）

**核实方法**：逐行读取 `init.sql`、grep 全仓索引名、列举 `sql/` 目录全部文件。

| # | 06 陈述 | 代码现状 | 结论 |
| :---: | :--- | :--- | :---: |
| 1 | init.sql:289 仍是全表唯一索引 | `init.sql:289-292` **已是部分唯一索引**：`CREATE UNIQUE INDEX IF NOT EXISTS uk_doc_hash ON sys_knowledge_doc (content_hash) WHERE status IN ('DRAFT', 'PUBLISHED');` | ❌ 不实 |
| 2 | v9 改用 `uk_doc_hash_active` | 全仓 grep `uk_doc_hash_active` **零命中**；索引名仍是 `uk_doc_hash`（加 `WHERE` 谓词实现部分唯一） | ❌ 不实 |
| 3 | 全新部署会重新引入回滚撞索引→500 | 部分唯一索引天然排除 DEPRECATED/ARCHIVED 历史版本，回滚恢复 PUBLISHED 不会撞已退出约束的同 hash 记录 | ❌ 不成立 |

附：`sql/` 目录列举结果——**无任何 `migration_v*.sql` 迁移文件**（仅 `init.sql` 与 `mock_data.sql`）。init.sql 是幂等 `IF NOT EXISTS` 全量脚本，是全新部署**唯一真相源**，无独立迁移文件可与之漂移。「全面核查 init.sql 与 v2~v10 全部迁移漂移」一项亦不成立——无迁移文件可核查。

### 1.3 根因推断（为何 06 方案描述失实）

6.21 实施文档生命周期治理时，实施记录（CLAUDE.md 6.21）描述「新增 `sql/migration_v8_knowledge_doc.sql` 与 `sql/migration_v9_doc_dedup_constraint.sql`」——这是**当时实施过程中间产物**：v9 先以独立迁移文件形式把全表唯一改为部分唯一（`uk_doc_hash_active` 是当时考虑过的命名），随后实施者把 v9 的语义直接合并进 `init.sql`（索引名沿用 `uk_doc_hash`，加 `WHERE` 谓词），独立迁移文件随之删除（项目最终以 init.sql 单一幂等脚本为 schema 唯一真相源，不留独立迁移文件）。

06 核查 agent 撰写方案时大概率读到了 6.21 实施记录中「v8/v9 迁移文件」的**中间产物描述**，未对照 `sql/` 目录现状与 init.sql 实际内容，直接把「v9 改了部分唯一 `uk_doc_hash_active`，但 init.sql 仍是全表唯一 `uk_doc_hash`」当作现存漂移写入方案——而实际 init.sql 当时已是部分唯一，两边从未漂移。

### 1.4 决策：不改动代码，仅修正 06 方案失实描述

| 决策点 | 选择 | 理由 |
| :--- | :--- | :--- |
| 是否改 init.sql | **不改** | init.sql 已是正确的部分唯一索引，改代码反而引入错误 |
| 是否补建独立迁移文件 | **不补** | 项目以 init.sql 单一幂等全量脚本为 schema 唯一真相源，不维护独立迁移文件；补建会与既有约定冲突 |
| 06 方案 P1-10 段落 | **修正为「经核实已解决」+ 附核实结论** | 避免后续基于失实描述再次返工，同时留档核实过程与代码现状证据 |

- [06-模块核查设计修复方案.md](06-模块核查设计修复方案.md) P1-10 段落（第 118-127 行）：标题改为「（✅ 经核实已解决，无代码改动）」，body 替换为核实结论（三条陈述逐条对照代码现状 + 判定前提不成立 + 说明处理方式）

## 二、P1-11 前端退出登录不生效 — 修复落地

### 2.1 缺陷

`AppNavbar.doLogout`（[AppNavbar.vue](../../devops-platform-frontend/src/components/common/AppNavbar.vue) 第 108-125 行）原实现：

```ts
const doLogout = async () => {
  showUserMenu.value = false
  try {
    await ElMessageBox.confirm('确定要退出登录吗？', '退出登录', {...})
    ElMessage.success('已退出登录')
    router.push('/')              // ← 仅跳首页
  } catch {
    // cancel
  }
}
```

问题：成功路径**只 toast + 跳首页，不调 `app.signOut()`** → `isAuthenticated` 永久 true。用户点「退出登录」后：
- UI 仍表现为已登录（头像仍显示、菜单仍有「退出登录」入口）
- 与 `App.vue` 的空闲超时路径不一致（那条路径调 `app.signOut()` 会真正置 false）
- 属「假交互」——与 6.13「假数据以真实数据呈现」同缺陷定性，UI 暗示已登出但状态未变

### 2.2 根因

`signOut()` action 已存在于 [stores/app.ts](../../devops-platform-frontend/src/stores/app.ts) 第 123-133 行：

```ts
signOut() {
  this.isAuthenticated = false
  this.currentUser = {
    name: '访客', email: '', avatar: '访',
    role: 'guest', title: '', permissions: []
  }
}
```

但 `AppNavbar` 第 14 行已注入 `const app = useAppStore()`，`doLogout` 却没调用 `app.signOut()`——纯粹的调用遗漏，不是缺 action。

### 2.3 决策：直接实施（纯技术小修）

| 决策点 | 选择 | 理由 |
| :--- | :--- | :--- |
| 修复范围 | **doLogout 成功路径补 `app.signOut()` 一行** | `signOut()` action 已存在、`app` 已注入，仅缺一处调用，属纯技术小修，按 CLAUDE.md「常见技术决策可自主实施」直接实施 |
| 是否清理硬编码假管理员 | **不清理，仅加 TODO 标注** | L1 阶段无真实鉴权，`DEFAULT_USER`/`isAuthenticated:true`/`permissions:['*']` 是 MVP 演示所需。清理会破坏 MVP 演示模式（访客身份无法操作工单/知识库）。按 06 方案 P2 要求标注 `TODO(P2-鉴权)` 待真实鉴权接入时统一替换 |
| TODO 内容 | 说明硬编码原因 + 保留决策 + 真实鉴权落地三步替换清单 | 避免被误认为既定设计，同时给出明确的未来替换路径 |

### 2.4 改动点

- [AppNavbar.vue](../../devops-platform-frontend/src/components/common/AppNavbar.vue) `doLogout` 成功路径（第 116-121 行）：

  ```ts
  ElMessage.success('已退出登录')
  // P1-11：必须调用 app.signOut() 清除登录态。
  // 此前仅 toast + 跳首页，isAuthenticated 永久 true，用户「退出」后仍是已登录状态。
  // signOut() 已存在于 stores/app.ts:118，将 isAuthenticated 置 false、currentUser 切换为访客。
  app.signOut()
  router.push('/')
  ```

- [stores/app.ts](../../devops-platform-frontend/src/stores/app.ts) `DEFAULT_USER` 前（第 29-33 行）加 `TODO(P2-鉴权)` 注释块：

  ```ts
  // TODO(P2-鉴权): 此处为硬编码假管理员，待真实登录鉴权接入后替换。
  // isAuthenticated: true（下方 state）同理——L1 阶段无认证，MVP 演示用默认管理员身份。
  // 06-模块核查设计修复方案 P1 已修 AppNavbar.doLogout 调用 signOut()，
  // 此处保留硬编码默认值；真实鉴权落地时需：① 改 isAuthenticated 初值为 false；
  // ② DEFAULT_USER 改为 guest 占位；③ 由登录回调写入真实 user。
  const DEFAULT_USER: CurrentUser = { ... }
  ```

### 2.5 新增契约

- **退出登录必须清登录态**：`doLogout`/任何「退出」入口都必须调 `app.signOut()` 或等价 action，禁止仅 toast + 跳页面而不清 `isAuthenticated`——否则用户「退出」后 UI 仍表现为已登录，属假交互
- **硬编码假管理员须 TODO 标注**：L1 阶段无真实鉴权，`DEFAULT_USER`/`isAuthenticated:true`/`permissions:['*']` 是 MVP 妥协，必须在源码显式标注 `TODO(P2-鉴权)` 与替换步骤，避免被误认为既定设计

### 2.6 已知限制

1. `signOut()` 仅置内存态，**刷新页面后 `isAuthenticated` 会被 `loadProfile()` 恢复为 `DEFAULT_USER`**（`isAuthenticated: true` 初值）——根因是 L1 阶段无真实鉴权，`isAuthenticated` 初值硬编码 true。这是 MVP 演示模式的既定行为，待 P2-鉴权落地时一并解决，不视为本批次遗漏
2. 06 方案中 P2-10「路由守卫死代码」（`router/index.ts` 无路由设 `requiresAuth`，`stores/app.ts:65` `isAuthenticated:true` 硬编码）与 P1-11 同源——均待真实鉴权接入后统一处理，本批次仅在源码标注 TODO 不删除守卫（保留扩展点）
