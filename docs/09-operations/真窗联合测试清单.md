## 第一部分：把系统跑起来（T2~T3)

### T2. 一键启动整个系统

> **批 72 预验证注记**：dev 开发栈路径已有 `scripts/SOP_一键启动.sh`（compose→后端→前端四步探活断言，幂等可重入），本机全绿（批 70/72 实测：7 容器健康/后端 22s/health UP/登录 code=0/Vite 代理 200）。**下面 docker compose 生产形态的引导仍由你亲手跑**——两条路径互补：脚本管开发自测，compose 全容器形态管「可上线」验收。

- **要准备什么**:Docker 开着；在项目根目录。
- **敲什么命令**:
```bash
cp .env.example .env        # 没有 .env 才执行；有就跳过
docker compose up -d --build
docker compose ps
curl http://localhost:8080/ai/actuator/health
```
（第一次构建要 15~25 分钟，是在 Docker 里下载依赖，正常。)
- **什么样算通过**:`docker compose ps` 里 app/postgres/redis/minio 四个容器状态都是
  healthy;health 接口返回 `{"status":"UP"}`；
  浏览器打开 `http://localhost:8080/ai/` 能看到登录页。
- **发什么给我**：终端里 `docker compose ps` 的截图或文字 + health 返回内容。

### T3. 备份一次再恢复一次（证明数据真的能救回来）

> **批 72 预验证注记**：`scripts/backup-restore-drill.sh` 已在本机 dev 栈完整演练通过（六表对账全绿，记录见 [backup-restore-演练记录.md](backup-restore-演练记录.md)）。**下面生产 compose 形态（backup.sh/restore.sh）仍由你亲手跑一遍**——两条脚本形态不同（dev 直连容器 vs 生产 compose exec），生产形态首跑才算验收。

- **要准备什么**:T2 通过；系统里已有一些数据（新建过几张工单即可）。
- **敲什么命令**:
```bash
bash scripts/backup.sh
ls -lh opsbrain-*.dump
bash scripts/restore.sh opsbrain-<刚才生成的文件名>.dump
docker compose exec postgres psql -U opsbrain -d opsbrain -c \
  "SELECT COUNT(*) FROM sys_devops_ticket;"
```
- **什么样算通过**：恢复之后，工单数量和备份前一致。
- **发什么给我**:backup 生成的文件名和大小 + 恢复后的工单数量。

## 第二部分：性能两件（T4~T6)

### T4. 新加的索引有没有用（V11 前后对比）

- **要准备什么**:T2 通过，系统跑了几天有了真实数据更准；刚建完也能跑，看到趋势就行。
- **敲什么命令**:
```bash
docker compose cp scripts/lab/explain_v11_audit.sql postgres:/tmp/
docker compose exec postgres psql -U opsbrain -d opsbrain \
  -f /tmp/explain_v11_audit.sql > explain-$(date +%F).txt
```
(脚本全程在事务里跑，最后自动回滚，**不会真的动你的索引和数据**，放心运行。)
- **什么样算通过**：输出的 B 段（索引在）比 C 段（模拟没索引）快，差距明显（比如 2 倍以上）。
- **发什么给我**:explain-*.txt 整个文件的内容。

### T5. 工单搜索要不要加一个高级索引（pg_trgm)

- **要准备什么**:T4 跑完（它的输出 D 段就是这个探测）。
- **什么样算通过**：看 D1（没装特殊索引）和 D2（装了）的查询时间对比。
  **这个不由脚本判定，由你拍板**：差距大就加，差距小就不加。无论哪种都是正确结论。
- **发什么给我**:T4 同一文件即可，加一句「加/不加」。

### T6. 告警风暴压测（一秒钟 100 条告警打进来，系统会不会垮）

> **批 72 预验证注记**：`scripts/loadtest-alert-storm.sh` 已在本机实测 100/s×10s：P95=22ms（判据 500ms）、零 5xx、零连接失败、触限流闸的 429+Retry-After 属 WebhookGuard 防风暴设计生效（A6 在案）、574 条入库零丢失、风暴聚合抑制实证（同 service+module 全部关联既有组单不重复建单）。**下面 lab/alert_loadgen.sh 路径（调大限流的满放行口径）仍由你亲手跑**——两个口径互补：一个验证闸边界，一个验证无闸吞吐。

- **要准备什么**:T2 通过；把 `.env` 里的 webhook token 复制下来（后面要用）;
  因为系统默认有防攻击限流（每分钟 300 条），压测前临时调大：
  在 docker compose 的 app 环境变量加 `DEVOPS_ALERT_WEBHOOK_RATELIMIT: "7000"` 后重启 app
  (`docker compose up -d app`)。
- **敲什么命令**:
```bash
cd 项目根目录
BASE=http://localhost:8080/ai TOKEN=<粘贴你的token> RPS=100 DURATION=120 \
  bash scripts/lab/alert_loadgen.sh
docker compose exec postgres psql -U opsbrain -d opsbrain -c \
 "SELECT count(*) FROM sys_devops_ticket WHERE title LIKE '%LabHighCpuLoad%';
  SELECT service, occurrence_count FROM sys_alert WHERE alert_name='LabHighCpuLoad' ORDER BY id;"
```
- **什么样算通过**:
  1. 返回成功的比例 ≥ 99%;
  2. 同一条告警重复打几千次，只生成一张工单（重复次数计数 occurrence_count 会涨，这是设计好的「降噪」);
  3. 脚本故意混入的不同服务的告警，各自有各自工单（不会被合并）。
- **发什么给我**：脚本最后打印的汇总几行 + 上面 SQL 的输出。

### T7. 不带密码打接口会不会被正确拦住

- **要准备什么**:T2 通过。
- **敲什么命令**:
```bash
TOKEN=x BASE=http://localhost:8080/ai RPS=300 DURATION=10 MODE=reject \
  bash scripts/lab/alert_loadgen.sh
curl -i -X POST http://localhost:8080/ai/api/v1/alerts/webhook \
  -H "Content-Type: application/json" -H "X-Webhook-Token: 错误的token" -d '{}'
```
- **什么样算通过**：没带对密码的请求返回 401；打得太快时返回 429 并带 Retry-After 头。
  （不是 403,也不是 200——401/429 才是对的。)
- **发什么给我**：两次命令的输出（状态码即可）。

## 第三部分：自愈（AI 动手)链的真机演练（T8~T10)

这三项是验证「AI 提议的动作，必须人来批准才执行」这条核心安全线。
**因为动作在执行时会改真东西，正式允许名单默认是关的，演练时要临时打开，练完马上关掉。**

### T8. 全链路走一遍(Mock 假动作)

- **要准备什么**：临时打开演练动作：
```bash
docker compose exec postgres psql -U opsbrain -d opsbrain -c \
 "UPDATE sys_action_allowlist SET enabled=true WHERE action_key='mock.disk.cleanup';"
```
- **敲什么命令**：从界面或接口对 `mock.disk.cleanup` 发起一次自愈执行
  （入口：前端「自愈中心」建一条执行，actionKey 填 `mock.disk.cleanup`)。
- **什么样算通过**：这条执行的详情页里，步骤时间线依次出现
  审批判断(GATE)→演练(DRY_RUN)→执行(EXECUTE)→执行完成，最终状态 EXECUTED。
- **发什么给我**：执行 ID + 时间线截图。
- **练完务必关掉**:
```bash
docker compose exec postgres psql -U opsbrain -d opsbrain -c \
 "UPDATE sys_action_allowlist SET enabled=false WHERE action_key='mock.disk.cleanup';"
```

### T9. 真实 K8s 干跑（只预演，不真重启）

- **要准备什么**：有一个能连的 K8s 集群（minikube、kind、云上的都可以）,
  并配好 kubectl（`kubectl get pods` 能出结果）。
- **敲什么命令**：对动作 `k8s.pod.restart` 发起一次「预演」（参数里填你实验室命名空间
  的一个 pod)；再故意把命名空间填成 `kube-system` 试一次。
- **什么样算通过**：第一次：系统列出「将会做的事」，但 pod 没有被真重启；
  第二次：被拒绝并说明不在允许的命名空间里。
- **发什么给我**：两次调用的返回内容各一段。

### T10. 批准了才动手，驳回了坚决不动手

- **要准备什么**:T8 里那个开关临时：`mock.pod.restart` 置 enabled=true。
- **敲什么命令**:
  1. 对 `mock.pod.restart` 发起一次执行 → 此时状态应是「等人批准」(WAITING_APPROVAL);
  2. 到审批中心点「批准」→ 执行链继续走完；
  3. 再发起一次同样的 → 这次点「驳回」。
- **什么样算通过**：批准的那次执行完了，时间线里有 APPROVED_EXECUTE；
  驳回的那次没有执行，留了一条「被驳回」的记录。
- **发什么给我**：两条执行 ID + 两段时间线截图。练完把开关关回（同 T8 的方法）。
