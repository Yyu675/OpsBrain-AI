> 成文：2026-10-15（灰度 Day10）｜ 视角：**流通性**——"一条业务从哪进、经过谁、以什么状态落地、交给谁继续"

## 0. 三十秒读法

```
入口层 ──▶ 主链层 ──▶ 处理层 ──▶ 沉淀层 ──▶ 治理层
告警/变更    工单       处置/诊断/自愈/审批    知识/复盘/效能    权限/审计/合规
   ▲            │              │                   │
   └── 15 个后台定时器在这些流上"推"（观察窗补单、SLA、看门狗、保留策略…）
```

三条判据贯穿全图（缺一条，链就没闭上）：
1. **进得来、单建得出**；2. **诊断有证据、结论不撒谎**；3. **恢复有闭环、经验有沉淀**。

## 2. 场景逐条（13 条）

每条固定七栏：**触发 / 主链与承载 / 状态流转 / 产物 / 交接点 / 断链表现 / 验证状态**。

### S1 告警接入与降噪
| 栏 | 内容 |
| --- | --- |
| 触发 | `Zabbix → POST /api/v1/alerts/webhook/zabbix`；`Alertmanager → POST /api/v1/alerts/webhook/{system}`；两者共用 `WebhookGuard`（令牌/HMAC/限流） |
| 主链 | `AlertSourceAdapter`（按 `sourceName()` 选源：Zabbix 顺序探测）→ `AlertService.ingest`：指纹去重（`alertname\|service\|labels`，**排除事件级字段**）→ 观察窗（P2/P3，10min）→ 风暴抑制（60s 滑窗）→ 建单 → 升级检测 |
| 状态流转 | `FIRING → ACKNOWLEDGED → RESOLVED`；重复告警走 `SUPPRESSED`（5min 窗）；恢复事件按**指纹**匹配原告警 |
| 产物 | `sys_alert` 行 + `raw_labels/raw_annotations`（V11）+ 事件流（WebSocket/SSE 推送） |
| 交接点 | → S3（建单）、→ S5（诊断提交）、→ S7（通知） |
| 断链表现 | ①同故障重复建单 ②两个故障被判同一个（第二个永远没人知道）③**恢复了但告警一直挂着**（事件级字段混进指纹，F1，本轮已修） |
| 验证状态 | ✅ 实弹：`closed_loop_drill.py` 场景 A/B/C 共 40 跳通过（`.local-verify/evidence/closed-loop-run4.json`）；Zabbix 真样本 27 例单测 |

### S2 变更事件接入

### S3 工单生命周期（主链）
| 栏 | 内容 |
| --- | --- |
| 触发 | 自动建单（S1）或人工建单（工单页） |
| 主链 | `TicketController`（38 个端点，本仓最大面）→ `sys_devops_ticket` + `sys_ticket_activity`（活动流）+ `sys_ticket_action`（处置留痕）+ `sys_ticket_reply`/`sys_ticket_attachment`/`sys_ticket_tag` |
| 状态流转 | `PENDING → PROCESSING → RESOLVED → CLOSED`；异常出口 `VOID`（作废）；`PROCESSING → PENDING`（**误接单可退回**）；`RESOLVED → PROCESSING`（验证不通过重开） |
| 产物 | 工单 + 活动流 + 关联告警/诊断回溯（`source_ticket_id`/`alert_id` 双向可查） |
| 交接点 | → S4（处置）、→ S5（诊断回填）、→ S8（知识引用）、→ S9（复盘）、→ S7（状态通知） |

| 验证状态 | ✅ 实弹：演练走完处置五连 + `resolvedAt` 穿透；SLA 首响计时由 `FirstResponseBreachScheduler` 驱动 |

### S5 自动诊断（Agent 核心）
| 栏 | 内容 |
| --- | --- |
| 触发 | 建单成功后由 `AlertService` 供应提交钩子触发；或人工在诊断页重跑 |
| 主链 | `DiagnosisOrchestrator`（异步池 4/8/100）→ 四路证据并行采集（日志 Loki / 指标 Prometheus / 变更 / 知识 RAG）→ `EvidenceAggregator` 充分度判定（SUFFICIENT/WEAK…）→ `HypothesisGenerator`（规则+LLM 双轨）→ 报告回填 |
| 状态流转 | 会话：提交 → 执行 → 完成/失败（失败也留痕，不静默）；证据：每路独立状态（SUCCESS/NO_DATA/FAILED），**缺数据源必须看得出来缺** |
| 产物 | `sys_diagnosis_session` + `sys_diagnosis_evidence` + `sys_diagnosis_hypothesis`（V4/V5）+ 诊断卡（S7） |
| 交接点 | → S3（回填工单 AI 分析区）、→ S8（知识引用与 boost 回流）、→ S9（复盘素材） |
| 断链表现 | 会话不落库 / 证据面静默跳过 / **证据不足却装成有结论** |
| 验证状态 | ✅ 实弹：演练中诊断 `COMPLETED/WEAK`，四路证据 changes/knowledge/logs/metrics 各自状态如实；另有"有数据源"正路（metrics NO_DATA→SUCCESS、假设 0→1 条）；⬜ 语义质量归 REAL 模式 |

### S6 自愈执行与审批（L4）
| 栏 | 内容 |
| --- | --- |
| 触发 | 策略命中（`HealingAutoTrigger`，`sys_automation_policy` 消费者）或人工发起 |
| 主链 | 风险门控（`AutomationGovernanceService`）→ 白名单 → 执行器（K8s fabric8）→ 逐步验证（`HealingVerificationScheduler`）→ 失败撤销 → 高风险走审批（`ApprovalOrchestrator`） |
| 状态流转 | 台账：`PENDING_APPROVAL → SUCCEEDED/FAILED/REJECTED`；撤销：`UNDONE/UNDO_FAILED`；验证：`PASS/FAIL/UNKNOWN/SKIPPED`（"验证不了"与"失败"是两种事实）；审批单：`PENDING → APPROVED → EXECUTED/EXECUTE_FAILED`，另有 `REJECTED/EXPIRED`（`ApprovalExpireScheduler`） |
| 产物 | `sys_healing_execution`（V7）+ `sys_automation_policy` + `sys_risk_policy` + 步骤时间线（V10 `steps_json`） |
| 交接点 | → S3（升级工单）、→ S12（审计）、→ S4（人工接管） |
| 断链表现 | 执行了但没留痕 / 审批后不重放（卡在"执行中"）/ 验证不给结论却显示成功 |
| 验证状态 | 🔵 机制：dryRun 留痕、幂等闸、撤销三态均有单测；⬜ **真集群未接**，不作为已交付能力宣传（口径见 ROADMAP L4） |

### S7 通知与送达
| 栏 | 内容 |
| --- | --- |
| 触发 | 建单 / 恢复 / 升级 / 诊断完成 |
| 主链 | `AlertNotifyTemplate`（**单源模板**，四类卡）→ `CompositeNotifier` 多渠道分发（钉钉/企微，DB 渠道权威 + 加签）→ 回执记账（`notify_delivery_total`） |
| 状态流转 | 受理（`successes`）→ 送达（`delivered`，回执 `errcode=0`）；失败/降级各自计数；自监控：`NotifySilentWatchdogScheduler`（全静默 5min 报警）+ 规则 `OpsBrainNotifyDeliveryFail` |

| 断链表现 | 群里没消息 / 送达率无从计算 / 恢复卡诱导误关工单 / **合法回执被判"拒收"**（F4，本轮已修） |
| 验证状态 | ✅ 实弹（假接收端）：配置→测试通知 2ms 已送达→真 P0 事件触发卡+恢复卡→`delivered=2/2`（`evidence/notify-delivery-live.txt`）；⬜ 真钉钉待用户侧配 webhook |

### S8 知识库与 RAG 飞轮
| 栏 | 内容 |
| --- | --- |
| 触发 | 运营导入（文档/附件/批量）、复盘沉淀（S9）、API 写入 |
| 主链 | 上传解析（Tika）→ 清洗 → SimHash 去重 → 父子切片（多库参数可配）→ 发布触发向量化（`INDEXED/SKIPPED/UNCHANGED` 三态，未变不烧额度）→ 混合检索（向量阈值 0.73 + 关键词）→ 引用回链 → 反馈加权（`sys_knowledge_boost`） |
| 状态流转 | 文档：`DRAFT → PUBLISHED`（+`ARCHIVED`）；切片：`sys_knowledge_chunk`；版本历史：`sys_knowledge_doc_history`；引用：落在 `sys_agent_call_log.citations`（`【来源：…】` 抽取）+ 反馈加权 `sys_knowledge_boost` |
| 产物 | `sys_knowledge_base/doc/chunk/category/tag` + 引用记录 |
| 交接点 | ← S5（诊断检索）、← S9（复盘草稿）、→ S5（boost 回流影响排序） |
| 断链表现 | 切片没落库 / 检索恒空 / 引用对不上出处 / 演练自己污染知识库（首版把列表返回键当成 `records`，每次演练新建一篇手册） |
| 验证状态 | ✅ 机制实弹：切片 5 片落库（SQL 直查）+ 引用反馈闭环 + 幂等重跑；⚠️ 语义命中受 MOCK 桩向量限制（余弦 0.03 ≪ 0.73），归 REAL 模式（`--require-rag-hit`） |

## 3. 状态机汇总（对账用）

| 实体 | 状态 | 触发者 | 守卫/留痕 |
| --- | --- | --- | --- |
| 告警 `sys_alert` | `FIRING / ACKNOWLEDGED / SUPPRESSED / RESOLVED` | webhook / 人工 ACK / 恢复事件 | 指纹匹配恢复；ACK 记人 |
| 工单 `sys_devops_ticket` | `PENDING / PROCESSING / RESOLVED / CLOSED / VOID` | 建单 / 接单 / 处置 / 关闭 | 五处置守卫 + 活动流 + SLA 计时 |
| 工单活动 | 追加式 | 各处置动作 | `sys_ticket_activity`（V15 detail 转 text） |
| 审批 `sys_approval_request` | `PENDING / APPROVED / REJECTED / EXPIRED / EXECUTED / EXECUTE_FAILED` | 人批 / 超时 / 执行回写 | `ApprovalExpireScheduler`；"批了≠执行了"分开记 |
| 自愈台账 `sys_healing_execution` | `PENDING_APPROVAL / SUCCEEDED / FAILED / REJECTED / UNDONE / UNDO_FAILED` | 策略/人工/撤销 | 幂等闸 + 步骤时间线 + 撤销凭据 |
| 自愈验证 | `PASS / FAIL / UNKNOWN / SKIPPED` | 验证器 | 未验证的 SUCCEEDED 不能长得像已验证 |
| 诊断会话 | 提交 → 执行 → 完成/失败（**失败也留痕**） | 建单钩子/人工 | 四路证据各自状态 |
| 知识文档 | `DRAFT → PUBLISHED`（+`ARCHIVED`） | 编辑/发布 | 发布触发向量化；未变不重索引 |
| 向量化 | `INDEXED / SKIPPED / UNCHANGED`（+失败态） | 发布/定时 | 失败不静默（落 INDEX_FAILED） |
| 会话 `AgentState` | `NEW → CONTEXT_PREPARED → … → DRAFT_READY` | 用户消息 | 迁移留痕 |
| 工具执行 | `PENDING / RUNNING / SUCCESS / FAILED` | Agent | `sys_agent_tool_execution` |
