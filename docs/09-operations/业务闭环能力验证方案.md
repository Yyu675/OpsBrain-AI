## 1. 六条核心业务链路（谁触发、怎么流转、留下什么）

### 1.1 告警链（L2 · 入口）

```
Zabbix / Alertmanager
   │  POST /api/v1/alerts/webhook/{zabbix|alertmanager|system}
   ▼
WebhookGuard（token / HMAC / 限流 300·min⁻¹）
   ▼
AlertSourceNormalizer（按 supports 选适配器；ZabbixSourceAdapter / AlertmanagerSourceAdapter）
   ▼
AlertService.processSignals
   ├─ 风暴记账（60s 滑窗 firing 计数，迟滞带进出）
   └─ 逐条信号
        ├─ resolved → resolve() CAS 原子更新（重试/多副本只有一个胜者）
        │      ├─ WebSocket 广播恢复
        │      ├─ 恢复卡（仅 P0/P1）
        │      └─ 关单联动（hint 提示 / auto 自动关 / off）
        └─ firing  → insertOrIncrement（ON CONFLICT 原子去重，不丢计次）
               ├─ 重复 → broadcastUpdate + 升级检测（escalated 卡）
               ├─ 新告警 → 风暴抑制？→ 聚合进摘要事件
               └─ proceedNewAlert
                     ├─ 观察窗（P2/P3，窗口 10min）→ 窗口内自愈不建单
                     ├─ 建单（TicketService，Single Writer 契约）
                     ├─ 触发卡（AlertNotifyTemplate.firing）
                     └─ 自动诊断（DiagnosisOrchestrator.submit，异步）
产物：`sys_alert` 行（含 dedup_key / labels / annotations）、工单、通知卡、诊断会话
```

**七处"不许猜"**（详见 `docs/09-decisions/多信号源接入-Zabbix适配器-2026-10-14.md` §十）：
时间按部署时区解释缺省标注"估算"、指纹用 `trigger_id@host` 不含 event_id、级别认不出原样透传、
字典键不进 labels（labels 参与去重键）、适配器不注入 `system`、负载不认识回 400（配置错要响）、
`endsAt` 只在恢复事件上填。

### 1.2 诊断链（L2 · Agent 核心）

```
诊断会话（sys_diagnosis_session，按 traceId）
   ├─ 四路证据并行采集
   │    ├─ LogsEvidenceCollector      （Loki LogQL）
   │    ├─ MetricsEvidenceCollector   （Prometheus 查询目录 + 异常检测）
   │    ├─ ChangesEvidenceCollector   （变更相关性打分）
   │    └─ KnowledgeEvidenceCollector （RAG：向量+关键词混合检索，citation 回链）
   ├─ 充分度判定（SUFFICIENT / WEAK / …）：证据不足就**如实说不足**，并给出置信度上限
   ├─ 假设生成（RuleBased 确定性 + LlmHypothesisGenerator），证据无物可说时不硬编
   └─ 通知：诊断卡 / 诊断不足卡（AlertNotifyTemplate.diagnosis）
产物：`sys_diagnosis_evidence` × N、`sys_diagnosis_hypothesis` × N、诊断回放接口 `/api/v1/diagnosis/{traceId}`
```

### 1.3 自愈链（L4 · 治理优先）

```
告警 → HealingAutoTrigger（策略匹配）→ HealingGate（风险 / 白名单 / 自动化策略 三表裁决）
        ├─ 驳回 → 留痕
        └─ 通过 → ActionExecutor（K8s restart/scale，fabric8）
                    → ActionVerifier（就绪验证）→ 成功记账（九态）
                    → 失败 → undo 回滚（undoSuccessRate 实测 1.0）
                    → 高风险 → 审批链（WAITING_APPROVAL，人工批准才动手）
产物：`sys_healing_execution` 台账、`/api/v1/healing/stats` 聚合
```

### 1.4 工单闭环链（L1.5 / B0~B5）

```
PENDING → 接单(PROCESSING) → 处置动作(INVESTIGATE/MITIGATE/FIX/ROLLBACK/VERIFY)
        → 缓解 → 根因确认(9 类分类) → 修复验证(RESOLVED) → 关闭
旁路：SLA 首响计时、活动流时间线、附件、标签、作废(VOID)、删除(仅 ADMIN)
```

### 1.5 知识链（RAG 飞轮）

```
导入（表单 / batch-import / 二进制 upload-Tika）→ 清洗 → 去重(SimHash) → 分片(ParentChild)
   → 发布 = 向量化写入 `sys_knowledge_chunk`（含 kb_id 冗余、visibility、effective/expired 有效期）
   → 检索：向量(HNSW, 阈值 0.73) + 关键词混合 → citation 回链
   → 回流：引用反馈(feedback/citations) → `sys_knowledge_boost`（地板/天花板 [0.2,5.0]）
   → 复盘保存 → `PostmortemDraftOrchestrator` 自动沉淀 DRAFT 草稿（四道守卫，AI 不替人决策）
```

### 1.6 通知链（IM 送达）

```
AlertNotifyTemplate（单源：触发/恢复/升级/诊断四类卡，八段式，1500 字砍尾留回链）
   → CompositeNotifier（多渠道分发，可插拔）
   → NotifyChannelService（钉钉/企微：DB 配置优先，yml 回落；密钥 enc:v1: 加密存储；热改）
   → NotifySilentWatchdogScheduler（送达回执自监控，/api/v1/alerts/notify-health）
```

## 2. 链路交接与"最容易断"的地方

| 交接口 | 上游 → 下游 | 断了的典型表现 | 本方案的检查手段 |
| - | - | - | - |
| 接入 | Zabbix → AlertService | 告警根本进不来 | 场景 A 注入 + 字段映射断言 |
| 建单 | AlertService → TicketService | 告警有、工单没有 | 双向溯源断言（by-trace/dedup_key） |
| 诊断触发 | AlertService → DiagnosisOrchestrator | 会话不落库（级别/服务名/开关任一不满足） | 轮询会话 + 四路证据断言 |
| RAG 取数 | 检索 → 诊断证据 | 知识证据恒 NO_DATA | 切片落库断言 + 向量探针（§4.3） |
| 处置 | 人 → 状态机 | 状态跳变被拒（400/409） | 五连流程断言 |
| 恢复 | Zabbix OK → 告警/工单 | "恢复了但告警还挂着" | resolvedAt 穿透断言 + 关单策略断言 |
| 沉淀 | 复盘 → 知识草稿 | 草稿不生成（异步编排失败只打 WARN） | 草稿轮询断言 |
| 送达 | 通知 → IM | 配置错/渠道停用（静默不报） | notify-health 自监控 + 真渠道演练（§6） |

## 3. 怎么模拟测试业务闭环：三层验证法

| 层 | 做什么 | 资产 | 频率 |
| - | - | - | - |
| **L1 单元 / 契约** | 类内逻辑、契约守卫、静默 catch、写守卫覆盖 | 后端 `mvn verify` 2011 例 + 前端 vitest 1844 例 + 四闸 | 每次改动 |
| **L2 跨模块 HTTP 实弹** | 一条真告警跑完六条链，逐跳断言 | `tools/verify/closed_loop_drill.py`（41 跳）、`scripts/e2e-business-flow.sh`、Playwright E2E 58 例 | 每批 / 每次上线前 |
| **L3 真环境联合测试** | 真 Zabbix、真钉钉、真 K8s、真 Prometheus | `docs/09-operations/真窗联合测试清单.md` T2~T15 | 灰度期 |

**L2 的三个场景（本方案的核心设计）**——因为它们对应的系统行为**本就不同**：

| 场景 | 输入 | 期望行为 | 验证的设计意图 |
| - | - | - | - |
| A 高危（P1） | severity=High，54s 后 OK | 立即建单 → 诊断 → 处置 → 恢复卡 → 复盘沉淀 | 主链路 + 时间穿透 + 飞轮 |
| B 抖动（P2） | severity=Average，窗口内自愈 | **不建单**（观察窗降噪），只留统计 | 降噪策略真的生效 |
| C 历史回放 | 事件时刻 26h 前 | 受理但既不进观察窗也不被补单扫到（**现状即发现 F2**） | 非预期时序下的行为可解释 |

### 3.1 一次跑法（本机/CI 均可）

```bash
# 前置：后端在跑（AI_MODE=MOCK 或 REAL 均可）
python3 tools/verify/closed_loop_drill.py \
  --base http://localhost:8088/ai --account admin:admin123 \
  --psql /path/to/psql --pgurl postgresql://user@host:5432/db \
```

退出码：0=硬闸全过；1=有硬闸失败（哪一跳断会点名）；2=环境问题（如登录失败）。

空结果的数据源只能验证「证据不足」分支。要验证「取到数据 → 生成假设 → 诊断充足」：

```bash

python3 tools/seed/prom-stub.py --port 29090 --rich      # 默认仍是空结果（CI 依赖空态断言）
```

## 4. 实跑记录（2026-10-15，本机 · AI_MODE=MOCK · 真 PG）

### 4.1 结果：41 跳，39 PASS / 1 SKIPPED / 1 软失败，硬闸全过

- 场景 A：入库（id=34，P1，source=zabbix，system 回落 default，service=infra，起始时刻取事件墙钟）
  → 建单 `TKT-20261014-0012`（含 by-trace 反查闭合）→ 诊断会话 `COMPLETED`（四路证据齐）
  → 处置五连（PENDING→PROCESSING→…→RESOLVED，动作留痕）→ 恢复事件穿透（resolvedAt=事件时刻）
  → 复盘保存 → 知识草稿 1 篇自动沉淀
- 场景 B：P2 抖动 54s 自愈 → **未建单**（降噪生效），观察窗统计可读（enabled=true, window=10m, levels=[P2,P3]）
- 场景 C：历史事件受理且时序自洽，无单（见 §5 F2）
- 自监控：`/alerts/notify-health` 可读（attempts=11, delivered=0, configured=false —— 因**未配置真渠道**）

证据：`.local-verify/evidence/closed-loop-run3.log`、`closed-loop-rich.log`、`closed-loop-rich.json`

### 4.2 权限实弹（DoD#7 第二列）

`tools/verify/rbac_walkthrough.py`：**42/42 格**与源码执法点一致（ADMIN / OPS / VIEWER × 14 个探针面），
含"ADMIN 可删单、OPS 403；VIEWER 写面 403、读面 200"等边界。证据 `.local-verify/evidence/rbac-walkthrough.json`。
首跑抓到两处**探针自身**的问题并已修：① 409 被误判为"未放行"（实为资源级拒绝、权限已过）；
② 知识文档列表返回键是 `content` 而非 `records`，导致演练每次新建文档（幂等失效）。

### 4.3 RAG 机制探针（回答"知识库到底有没有被用上"）

MOCK 模式下知识证据恒 `NO_DATA`。**是链路坏了还是阈值语义？** 实测定论：

| 检查 | 结果 |
| - | - |
| 切片与向量是否真的落库 | 手册 5 片，`embedding IS NOT NULL` 全绿 |
| 复刻 `MockEmbeddingModel` 算法自证 | 与库内向量余弦 = **1.000000**（复刻正确，结论可用） |
| 采集器真实查询串的相似度 | 最高 **0.0303** ≪ 熔断线 **0.73** → 必然 NO_DATA |
| 去掉阈值跑同一条检索 SQL | 立刻返回 3 条命中（含本手册）→ **检索链路本身通** |

结论：**MOCK 桩向量不承载语义**，RAG 的"命中质量"必须在 REAL 模式判定；链路的正确性已由本节证成。

## 5. 三条发现（待决策，不是"顺手改了"）

### F1｜`event_severity` 进了去重键 → 级别变更会让恢复配不上原告警

- 事实：Zabbix 适配器把 `event_severity` 写进 labels（`ZabbixSourceAdapter` 第 270 行附近），
  而 `AlertService.computeDedupKey()` 只用 `alertname/service/severity` 三个键做排除，**没有排除 `event_severity`**。
  演练中我用"PROBLEM=Average / OK=High"复现：OK 事件找不到活跃告警 → 告警永远挂在 FIRING（场景 B 首跑即此现象）。
- 现实概率：Zabbix 的 severity 是**触发器属性**，正常运行中 PROBLEM/OK 同级别 → 概率低；
  但"运维中途调整触发器级别"是真实操作，一旦发生就是**恢复丢失**。
- 建议（二选一，我推荐 A）：
  - **A**：把 `event_severity` 加入 `computeDedupKey` 的排除集（与 `severity` 同待遇），labels 里仍保留供展示/统计。
    影响面：仅影响 Zabbix 源新告警的键计算，存量告警键不变（不会造成重复建单）。
  - B：维持现状但在《告警接入命名规范》里写明"触发器级别变更会导致恢复不匹配"。

### F2｜历史事件回放（>24h）既不进观察窗、也不被补单扫描捞起 → P2 告警永久无单

- 事实：`isObservationPending = 级别∈{P2,P3} ∧ first_occurred_at 距今 < 窗口(10min)`；
  补单扫描 `AlertObservationScheduler` 只回溯 `OBSERVATION_LOOKBACK_HOURS = 24`。
  演练用真实截图的时刻（26 小时前）→ 两个条件都不满足 → 告警 FIRING、**永远没有工单**。
- 现实概率：实时推送不受影响；**补推/回放**（Zabbix 侧网络恢复后重投、迁移历史、演练回放）会踩。
- 建议：给"回放"一个明确的产品语义——要么 `first_occurred_at` 超窗时**按到达时刻重新计时**（P2 立即建单或进观察窗），
  要么在告警详情页**显式标注"历史事件，未建单"**（当前是静默无单，值班人会以为系统漏单）。

### F3｜送达面在本地是"配置为空"，口径要落到真渠道

- 事实：`notify-health` 显示 `attempts=11 / delivered=0 / configured=false`——**没配渠道**，
  所以 attempts 是"尝试渲染"而不是"尝试投递"。`delivered` 只有在配置真渠道后才有意义。
- 影响：灰度 DoD 里的"送达率真数"目前**无数据可算**，不是 0%。
- 建议：灰度 Day1 动作 4（真钉钉测试通知）落地后再回填台账，避免"0 送达率"被误读成故障。
